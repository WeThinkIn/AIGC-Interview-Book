<h2 id="p5-1-1">面试问题：动态图、图执行与编译执行有什么区别？PyTorch 中应如何选择 eager、torch.compile 与模型导出？</h2>

**难度评分：⭐⭐⭐（3/5）| 考察频率：⭐⭐⭐⭐⭐（5/5）**

**一句话结论：**动态图（eager）是在 Python 执行到算子时立即计算；图执行是先捕获一段计算再运行；编译执行则是在捕获的基础上进一步做算子融合、内存规划和硬件特化。三者不是互斥的框架标签，现代 PyTorch 通常采用 eager 开发、`torch.compile` 加速，按需导出到 ONNX/TensorRT 部署。

### 概念与区别

| 维度 | eager / 动态执行 | 图执行或编译执行 |
|---|---|---|
| 执行时机 | Python 运行到一个算子就立即执行 | 先追踪、捕获或导出计算，再由图运行时/编译器执行 |
| 控制流 | 任意 Python `if/for` 都能运行，数据相关分支最自然 | 可捕获的控制流可编译；不支持的 Python 逻辑会产生 graph break、回退或重编译 |
| 输入形状 | 天然适合可变长度和动态分支 | 不是只能固定形状，但动态形状可能增加 guard、重编译和优化成本 |
| 调试 | 可用普通 Python 调试器检查中间 Tensor | 需结合编译日志、图解释和 profiler，定位问题的成本更高 |
| 性能 | 算子逐个调度，可能有 Python 调度和 kernel launch 开销 | 有机会做融合、消除中间读写、规划内存并调用硬件专用内核 |
| 启动与部署 | 无编译冷启动，直接作为 Python 程序运行 | 首次编译有开销；导出的图/引擎更易接入 C++ 或专用推理服务 |

“静态图”在面试中常被用作图执行的简称，但严格说还应区分：

1. **Tracing（追踪）**只记录一次样例输入走过的算子，数据相关控制流可能被错误固化。
2. **Symbolic/AOT capture（符号捕获/提前导出）**尝试保留更多图结构和输入约束。
3. **Compilation（编译）**将捕获到的图交给 Inductor、XLA 或 TensorRT 等后端生成优化后的代码/引擎。

### PyTorch 中的选择

- **eager**：研究、快速迭代、复杂 Python 逻辑和自定义算子优先使用。先用它建立正确性基线。
- **`torch.compile`**：模型结构相对稳定、希望提升训练或推理吞吐时使用。它是“捕获可编译区域 + 后端编译”的混合方案，不承诺把整个 Python 程序变成一张完整静态图。
- **`torch.export`/ONNX/TensorRT**：需要跨语言、跨进程或在固定硬件上部署时使用。导出是部署边界，必须验证算子覆盖、动态维度和数值一致性。

```python
model = MyModel().cuda()
model = torch.compile(model, mode="max-autotune")  # 先正确性，再用真实负载压测
```

`torch.compile` 遇到不支持的代码可能 graph break；输入形状或控制流变化可能触发重新编译。工程上应观察编译耗时、稳态吞吐、显存、P50/P99 延迟和回退次数，而不能只看一次运行时间。推理服务还要把预热（warm-up）和编译缓存纳入发布流程。

### 常见误区

- PyTorch 并非“只有动态图”，PyTorch 2.x 已具备图捕获和编译能力；TensorFlow 2 也并非“只有静态图”。
- ONNX 是模型交换格式，不是动态图或静态图本身；ONNX Runtime、TensorRT 才是执行模型的运行时。
- 图执行不必然更快。小模型、动态输入或 graph break 较多时，编译开销可能抵消优化收益，必须基准测试。

<h2 id="p5-1-2">面试问题：PyTorch Tensor 的核心特性有哪些？它与 NumPy 数组的本质差异和互转注意事项是什么？</h2>

**难度评分：⭐⭐⭐（3/5）| 考察频率：⭐⭐⭐⭐⭐（5/5）**

**一句话结论：**Tensor 是带有形状、步长、数据类型、设备、存储布局和自动求导信息的多维数组抽象；NumPy `ndarray` 主要面向 CPU 数值计算。二者可以互操作，但设备、数据类型、梯度和是否共享内存必须明确。

### Tensor 的核心特性

1. **形状与布局**：`shape` 描述各维大小，`stride` 描述步进；`view`/`reshape`、转置和切片可能生成共享存储的 view，而不是复制。
2. **设备**：通过 `.device` 标识 CPU、CUDA 或其他后端，可用 `.to(device)` 移动；同一算子通常要求参与运算的 Tensor 在兼容设备上。
3. **数据类型**：支持 `float32`、`float16`、`bfloat16`、`float64`、整数和布尔等，混合精度时要留意累加精度和算子支持。
4. **自动微分**：`requires_grad=True` 的 Tensor 在梯度模式下参与运算时，会被 Autograd 记录。
5. **广播与向量化**：遵循 NumPy 风格广播规则，提供线性代数、索引、散射、稀疏/量化相关操作。
6. **存储与别名**：多个 Tensor 可能共享同一底层 storage；原地操作会影响所有别名，并可能破坏反向传播所需的中间值。
7. **生态集成**：可直接作为 `nn.Module`、优化器、AMP、DDP/FSDP 等组件的数据载体，但分布式通信能力来自这些组件，不是 Tensor 单独提供的。

### 与 NumPy 的关键差异

| 对比项 | PyTorch Tensor | NumPy `ndarray` |
|---|---|---|
| 计算设备 | CPU、CUDA 及已支持的加速器 | 主要是 CPU |
| 自动求导 | 原生 Autograd、可构建计算图 | 不提供 PyTorch 式反向图 |
| 模型训练 | 与 `nn.Module`、优化器、AMP、分布式训练整合 | 需要自行实现训练基础设施 |
| 异步性 | CUDA 算子通常异步执行，需同步后再精确计时 | CPU 运算通常同步 |
| 内存共享 | 可与 NumPy 零拷贝互转，但有条件 | 受 CPU 内存和 dtype 限制 |

### 互转与常见坑

```python
a = np.asarray([1, 2, 3], dtype=np.float32)
t_shared = torch.from_numpy(a)       # CPU Tensor，与 a 共享内存
t_copy = torch.tensor(a)             # 通常复制数据

# GPU 或 requires_grad Tensor 转 NumPy 的安全写法
arr = t.detach().cpu().numpy()
```

- `torch.from_numpy(a)` 和 `a` 之间通常共享存储；修改一方会影响另一方。数组需是 CPU、支持的 dtype 和合适的内存布局。
- `tensor.numpy()` 通常要求 Tensor 在 CPU、未追踪梯度且不包含不兼容的 conjugate/negative bit；不满足时使用 `detach().cpu().numpy()`，必要时再 `.copy()` 隔离内存。
- `torch.as_tensor` 会尽量复用内存，`torch.tensor` 更明确地创建副本。读取只读 NumPy 数组后不要通过共享 Tensor 原地修改。
- Tensor 和 NumPy 的 dtype 不一定相同（例如 Python 整数常推断为 `int64`）；送入模型前显式 `.to(dtype=..., device=...)`。
- `view` 需要兼容 stride；不确定是否连续时使用 `.reshape()`，或先 `.contiguous()`，并意识到这可能产生复制。

<h2 id="p5-1-3">面试问题：PyTorch 的数据加载链路是什么？Dataset、DataLoader、Sampler 与 collate_fn 如何分工？</h2>

**难度评分：⭐⭐⭐（3/5）| 考察频率：⭐⭐⭐⭐⭐（5/5）**

**一句话结论：**Dataset 负责“如何得到一个样本”，Sampler 负责“取哪些索引及其顺序”，DataLoader 负责“按批次、多进程/预取地调度”，`collate_fn` 负责“如何把样本拼成一个 batch”。

### 两类 Dataset

- **Map-style Dataset**：实现 `__getitem__(index)` 和 `__len__()`，适合可按索引随机访问的文件、图片和表格。DataLoader 可配合 `shuffle` 或自定义 `Sampler`。
- **IterableDataset**：实现 `__iter__()`，适合日志流、远程流式数据、超大文件和长度未知的数据。多 worker 时必须用 `torch.utils.data.get_worker_info()` 或分片逻辑，让每个 worker 读取不同区间，否则会重复样本。

### DataLoader 的一次迭代

```text
Sampler 产生索引 → worker 调用 Dataset 读取/预处理 → collate_fn 拼 batch
→ （可选）pin memory → 训练进程拷贝到 GPU → 模型前向
```

常用参数及含义：

- `batch_size`：单进程看到的 micro-batch 大小；分布式训练时全局 batch 还要乘以进程数及梯度累积步数。
- `shuffle`：Map-style Dataset 每个 epoch 重新打乱索引；不能与 `sampler`/`batch_sampler` 同时指定。IterableDataset 通常由其迭代器自己决定顺序。
- `num_workers`：读取 worker 数量，不是越大越快。受 CPU、磁盘/网络带宽、预处理成本和进程通信开销共同限制。
- `collate_fn`：默认函数可拼接等形状 Tensor；变长序列通常要在这里 padding、返回长度或使用 bucket sampler。
- `pin_memory=True`：将 CPU Tensor 放入锁页内存；它不等于放到 GPU，通常配合 `.to(device, non_blocking=True)` 使用。
- `persistent_workers=True`：跨 epoch 保留 worker，减少反复创建进程的成本；仅在 `num_workers>0` 时有意义。
- `prefetch_factor`、`drop_last`：分别控制 worker 预取批次数、是否丢弃最后的不完整 batch。

### 分布式和可复现性

```python
sampler = DistributedSampler(dataset, shuffle=True)
loader = DataLoader(dataset, batch_size=32, sampler=sampler,
                    num_workers=4, pin_memory=True,
                    persistent_workers=True)

for epoch in range(num_epochs):
    sampler.set_epoch(epoch)  # 让各 epoch 的打乱顺序真正变化
    for x, y in loader:
        x = x.to("cuda", non_blocking=True)
```

在 Windows 或使用 `spawn` 启动 worker 时，把训练入口放进 `if __name__ == "__main__":`；通过 `generator`、`worker_init_fn` 和统一随机种子控制 Python/NumPy/PyTorch 的随机性。若数据增强含随机状态，还要确保每个 worker 的种子不同。

### 工程排查顺序

1. 先用 `num_workers=0` 验证 Dataset、标签和 `collate_fn` 的正确性。
2. 再逐步增加 worker，观察 GPU 利用率、数据等待时间、CPU/内存和文件句柄。
3. 训练集通常 `shuffle=True`；验证/测试集固定顺序。分布式场景优先 `DistributedSampler`，不要再额外设置 `shuffle`。
4. 数据增强、归一化和 tokenizer 放在 Dataset/预处理管道；昂贵且可缓存的步骤尽量离线完成。

<h2 id="p5-1-4">面试问题：Autograd 如何构建动态计算图并完成反向传播？requires_grad、detach、no_grad 有什么区别？</h2>

**难度评分：⭐⭐⭐⭐（4/5）| 考察频率：⭐⭐⭐⭐⭐（5/5）**

**一句话结论：**在梯度模式下，PyTorch 为 Tensor 运算记录由“反向函数（Function）—依赖 Tensor”组成的动态 DAG；`backward()` 从输出沿 DAG 应用链式法则，把梯度累加到叶子 Tensor。每次前向都会建立一张新的图，默认反向完成后释放。

### 图是怎样建立的

```python
x = torch.tensor(2.0, requires_grad=True)  # 叶子 Tensor
y = x ** 2
z = 3 * y + 1                              # 标量输出
z.backward()
print(x.grad)  # 12 = dz/dx
```

- 叶子 Tensor 通常由用户直接创建（模型参数是最典型的例子），其 `grad_fn` 为 `None`，梯度默认累加到 `.grad`。
- 非叶子结果带有 `grad_fn`，它指向记录该结果的反向 Function；Function 保存反向所需的输入、输出或中间量。
- 从概念上说，Tensor 是图中的数据边/值，Function 是执行节点；实际实现会用 next-functions 等结构保存依赖关系。

### 反向传播步骤

1. 对标量 `loss`，隐式把 `d(loss)/d(loss)` 初始化为 1；非标量输出必须显式传入同形状的 `gradient`。
2. Autograd 从输出的 `grad_fn` 反向遍历 Function，按链式法则把上游梯度乘以局部导数。
3. 到达叶子 Tensor 时，将梯度**累加**到 `.grad`；因此每个优化 step 前要 `optimizer.zero_grad(set_to_none=True)` 或清零。
4. 默认释放本次图及其保存的中间值；需要重复反向才使用 `retain_graph=True`，需要高阶导数才使用 `create_graph=True`。

### `requires_grad`、`detach`、`no_grad` 与 `inference_mode`

- `requires_grad=True/False` 是 Tensor 的属性，决定它是否作为梯度追踪的起点；冻结 backbone 时常将参数设为 `False`。
- `x.detach()` 返回与 `x` 共享存储、但从当前计算图断开的 Tensor；常用于记录指标、生成伪标签或把特征交给不需要反传的模块。若还要避免共享存储的原地修改，使用 `x.detach().clone()`。
- `torch.no_grad()` 是上下文管理器，作用于上下文内的运算，禁止记录计算图，但不改变 `model.train()/eval()` 状态。
- `torch.inference_mode()` 比 `no_grad()` 更激进，会使用 inference tensor 元数据，通常推理更省开销；这些 Tensor 不能再安全地用于需要梯度的后续计算，训练/验证混合代码应谨慎选择。

### 工程注意事项

- 不要用 `.data` 绕过 Autograd；这可能静默破坏图和梯度。需要更新参数时用 `with torch.no_grad(): param.copy_(...)`。
- 对需要保存梯度的非叶子 Tensor，调用 `.retain_grad()`；否则其 `.grad` 默认仍为 `None`。
- 原地操作（如 `x.add_()`）若覆盖了反向所需的值会触发错误或造成难以发现的数值问题。
- 梯度累积、梯度裁剪、AMP 的 `GradScaler` 都应放在正确的顺序中：反向后（必要时 unscale 后）裁剪，再 `optimizer.step()`。

<h2 id="p5-1-5">面试问题：model.train()、model.eval()、torch.no_grad() 和 torch.inference_mode() 有什么区别？</h2>

**难度评分：⭐⭐⭐（3/5）| 考察频率：⭐⭐⭐⭐⭐（5/5）**

**一句话结论：**`train()/eval()`切换模块行为；`no_grad()/inference_mode()`控制是否记录梯度。评估通常需要二者同时使用：`model.eval()` 保证 Dropout/BatchNorm 行为正确，`torch.inference_mode()`（或 `no_grad()`）节省推理开销。

### 对比表

| API | 改变什么 | 是否构图 | 典型用途 |
|---|---|---|---|
| `model.train(True)` | 将模型及子模块的 `training` 设为 `True` | 不决定，默认仍可构图 | 训练 |
| `model.eval()` / `train(False)` | 将 `training` 设为 `False` | 不决定，默认仍可构图 | 验证、测试、推理 |
| `torch.no_grad()` | 上下文内关闭梯度记录 | 不构图 | 验证、推理、冻结模块的前向 |
| `torch.inference_mode()` | 关闭梯度并进一步省略版本计数等 autograd 元数据 | 不构图，限制更严格 | 纯推理服务和离线特征提取 |

### 哪些层会受 train/eval 影响

- **Dropout**：训练时随机丢弃并做缩放，评估时关闭随机丢弃。
- **BatchNorm**：训练时使用当前 batch 统计量并更新 running mean/variance；评估时使用累计统计量。
- 某些 RNN 模块的 dropout 等自定义层也可能读取 `self.training`。
- **LayerNorm、GroupNorm** 通常没有 running statistics，训练和评估行为相同；不能笼统地说所有归一化层都会变化。自定义模块是否变化取决于实现。

### 推荐写法

```python
# 训练
model.train()
for inputs, labels in train_loader:
    optimizer.zero_grad(set_to_none=True)
    loss = criterion(model(inputs), labels)
    loss.backward()
    optimizer.step()

# 验证/测试
model.eval()
with torch.inference_mode():
    for inputs, labels in val_loader:
        logits = model(inputs)
        # 计算 loss 和指标
```

### 常见误区

- 只写 `no_grad()` 不会关闭 Dropout，也不会让 BatchNorm 使用 running statistics；必须显式 `model.eval()`。
- 只写 `model.eval()` 仍可能构建计算图，验证时会浪费显存和时间。
- 验证后忘记 `model.train()` 会让下一轮训练继续处于评估模式。
- 如果验证阶段需要对输入求梯度（例如 adversarial evaluation、输入优化或 saliency），可以 `model.eval()` 但不要使用 `no_grad()`；这正说明两个 API 的职责不同。

<h2 id="p5-1-6">面试问题：PyTorch 分布式训练有哪些并行方式？DDP、FSDP/ZeRO、张量并行和流水线并行如何选？</h2>

**难度评分：⭐⭐⭐⭐（4/5）| 考察频率：⭐⭐⭐⭐⭐（5/5）**

**一句话结论：**模型能完整放入单卡时优先 DDP 做数据并行；模型/优化器状态放不下时使用 FSDP 或 ZeRO 分片；单层就放不下或需要扩展到超大模型时，再叠加张量并行、流水线并行，形成 2D/3D 并行。`DataParallel` 适合临时原型，不是生产首选。

### 1. 数据并行

#### `nn.DataParallel`（DP）

单进程多线程：每次 forward 临时复制模型、切分输入，在主卡汇总梯度。代码简单但有主卡聚合瓶颈、Python/GIL 和复制开销，不支持多节点，生产训练通常迁移到 DDP。

#### `DistributedDataParallel`（DDP）

DDP 通常“一卡一进程”，每个进程持有完整模型和优化器，在本地 batch 上前向/反向；反向过程中通过通信后端对梯度做 collective（常见实现是 AllReduce，但具体算法由后端和拓扑选择），各进程随后独立执行相同的参数更新。

```python
# train.py 的核心结构（省略异常处理）
dist.init_process_group("nccl")
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)
model = DDP(model.to(local_rank), device_ids=[local_rank])
sampler = DistributedSampler(dataset, shuffle=True)
loader = DataLoader(dataset, sampler=sampler, batch_size=per_gpu_bs)
```

用 `torchrun --nproc_per_node=4 train.py` 启动；每个 epoch 调 `sampler.set_epoch(epoch)`。GPU 通信优先 NCCL，CPU 或特定环境使用 Gloo；多节点还要正确配置 rendezvous 地址、端口、防火墙和网络带宽。

### 2. 参数/梯度/优化器状态分片

- **FSDP（FullyShardedDataParallel）**：对参数、梯度和优化器状态做分片，forward/backward 需要时 all-gather 参数，完成后再释放或重新分片，显著降低显存，适合单卡放不下完整状态但仍可按层计算的模型。
- **DeepSpeed ZeRO**：ZeRO-1 分片优化器状态，ZeRO-2 再分片梯度，ZeRO-3 连参数也分片；还可结合 CPU/NVMe offload。FSDP 与 ZeRO 的思想相近，具体选型看生态、检查点和运维习惯，避免重复叠加两个分片封装。

### 3. 模型并行

- **张量并行（TP）**：把线性层、注意力投影等矩阵按列/行切分，多卡协同完成一个层。通信频繁，要求高速互联，适合单层或单个 Transformer block 就很大的模型。
- **流水线并行（PP）**：按层切成多个 stage，输入再拆成 micro-batch；可提高大模型可训练性，但有 pipeline bubble、stage 负载不均和调度复杂度。PyTorch 新版提供 `torch.distributed.pipelining`，第三方框架也有成熟实现。
- **数据并行 + TP + PP**：在不同维度组合成 3D 并行；Megatron-LM、DeepSpeed 等提供相应实现。还可能加入 sequence/context parallel，应根据序列长度和互联拓扑设计。

### 选择与工程检查

| 场景 | 首选方案 | 主要代价 |
|---|---|---|
| 单卡可放下模型，多卡提吞吐 | DDP | 每卡都有完整模型，显存不节省 |
| 参数可分层加载，但优化器状态占满显存 | ZeRO-1/2 或 FSDP | collective 通信与配置复杂度增加 |
| 完整模型参数本身放不下单卡 | FSDP/ZeRO-3 + 必要的 TP/PP | all-gather、检查点和调度复杂 |
| 超长序列/超大模型 | TP + PP + DP（必要时 sequence/context parallel） | 对网络拓扑、micro-batch 和负载均衡敏感 |

全局 batch 的定义是 `每卡 batch × GPU 数 × gradient accumulation steps`；学习率是否线性放大要结合优化器、训练步数、warmup 和验证结果，不能机械地按卡数相乘。还要检查随机种子、梯度同步、混合精度、checkpoint（保存 rank-0 或分片格式）、故障恢复和通信/计算重叠。


<h1 id="p5-2">2. PyTorch 以外的深度学习框架与生态工具概览</h1>

<h2 id="p5-2-1">面试问题：TensorFlow/Keras、JAX、PaddlePaddle 与 MindSpore 分别有什么特点，如何选择？</h2>

**难度评分：⭐⭐⭐（3/5）| 考察频率：⭐⭐⭐⭐（4/5）**

**一句话结论：**不要按“哪个框架绝对最好”回答，要按团队已有代码、硬件/云平台、算子与部署生态、分布式能力和人才储备选择。PyTorch 适合研究与大模型生态，TensorFlow/Keras 强在成熟生产链路，JAX 强在函数式变换和 XLA 加速，Paddle/MindSpore 在国产硬件和本土产业生态中更有优势。

| 框架 | 主要特点 | 适合场景 | 需要注意 |
|---|---|---|---|
| TensorFlow + Keras | `tf.data`、`tf.distribute`、SavedModel/TFLite/TF Serving 形成完整链路；Keras 提供高层 API | 企业生产、移动/边缘部署、已有 TF 资产 | eager 调试与 `tf.function` 图模式之间要处理 retrace、签名和算子兼容 |
| JAX | 函数式数组计算；`jit`、`grad`、`vmap`、`pmap`/sharding 可组合，常由 XLA 编译 | 科学计算、TPU、大规模函数式训练、需要高性能变换的研究 | 状态管理、随机数 key、可变对象和 Python side effect 要遵守函数式约束；生态训练封装不如 PyTorch 统一 |
| PaddlePaddle | 动静统一、动态图易用，产业套件和中文资料较丰富 | 国内 CV/OCR/NLP、飞桨硬件与产业平台 | 迁移 PyTorch 时需核对算子、权重格式、数据管道和第三方库覆盖 |
| MindSpore | 面向图编译和自动并行，适配昇腾等国产硬件 | 国产算力、企业级训练与推理 | 需确认目标硬件、版本、算子和社区组件是否满足项目需求 |

### 选型步骤

1. 先确定硬件和目标运行时：CUDA/ROCm/TPU/昇腾，以及是否要 TFLite、TensorRT、CANN 等部署后端。
2. 核对关键算子、量化/混合精度、分布式和检查点能力，而不是只比较 API 风格。
3. 用真实模型做小规模基准：收敛速度、稳态吞吐、显存、编译时间、P99 延迟和故障恢复。
4. 评估团队维护成本和生态复用。已经有大量 PyTorch/Hugging Face 代码时，迁移的收益必须足以覆盖转换和验证成本。

Keras 适合快速搭建高层模型；需要对训练循环、并行策略或大模型内存做精细控制时，通常使用更底层的 PyTorch/JAX/TF API。面试中应强调“以约束和基准测试做决定”，不要把动态图/静态图当作唯一标准。

<h2 id="p5-2-2">面试问题：Hugging Face、DeepSpeed 与 Megatron-LM 分别解决什么问题，如何配合使用？</h2>

**难度评分：⭐⭐⭐⭐（4/5）| 考察频率：⭐⭐⭐⭐⭐（5/5）**

**一句话结论：**Hugging Face 主要解决模型/数据/Tokenizer 和应用训练接口的复用；DeepSpeed 主要解决显存、并行和训练系统效率；Megatron-LM 主要解决 Transformer 大模型的张量/流水线等模型并行。三者可以组合，但必须明确谁负责模型实现、谁负责分布式封装、谁负责数据与训练循环。

### 各自职责

- **Hugging Face Transformers**：提供预训练模型配置、权重、Tokenizer、Trainer/生成接口；`Datasets` 负责数据集缓存与处理，`Accelerate` 统一多 GPU/混合精度启动，`PEFT` 提供 LoRA/Adapter，`TRL` 覆盖偏好优化等训练。
- **DeepSpeed**：提供 ZeRO-1/2/3、CPU/NVMe offload、梯度累积、混合精度、通信和 checkpoint 优化。它既可包装普通 PyTorch 模型，也可被 Transformers Trainer/Accelerate 调用。
- **Megatron-LM**：围绕 Transformer 预训练实现高效的 tensor parallel、pipeline parallel、sequence/context parallel、融合 kernel 和高吞吐数据管道。它的模型定义、数据格式和 checkpoint 约束比通用 Transformers 更强。

### 常见组合

1. **中小模型微调**：`Transformers + Datasets + Accelerate/Trainer + PEFT`；单机多卡通常 DDP 足够。
2. **大模型全参数微调**：`Transformers + DeepSpeed ZeRO-3` 或 Transformers 原生 FSDP，结合 BF16、梯度检查点和分片 checkpoint。
3. **超大模型预训练**：Megatron-LM 负责模型并行和高性能训练，DeepSpeed/Megatron-DeepSpeed 负责 ZeRO、优化器和系统能力；数据与 Tokenizer 可复用 Hugging Face 资产，但需转换格式。
4. **应用推理**：训练阶段使用 Transformers 权重，之后根据目标延迟导出到 vLLM、TensorRT-LLM、ONNX Runtime 等专用运行时；这不等于继续用训练框架直接承载线上流量。

### 面试追问要点

- 先区分**数据并行、参数分片、张量并行、流水线并行**，再谈工具；工具名称不等于并行原理。
- LoRA 只训练低秩增量参数，不能自动解决基础模型本身放不下的问题；仍可能需要量化、FSDP 或 ZeRO。
- Transformers 的 `Trainer`、Accelerate、DeepSpeed/FSDP 不要重复初始化进程组或重复包裹模型；统一由一个入口管理 rank、device、精度和 checkpoint。
- 以验证集 loss/任务指标、吞吐、显存、通信占比和可恢复性评估组合是否有效，而不是只看 GPU 利用率。
