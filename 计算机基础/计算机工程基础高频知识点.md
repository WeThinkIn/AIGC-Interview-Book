<h1 id="q-001">1.版本、环境与交付产物</h1>

<h2 id="q-002">面试问题：Git、GitLab 与 SVN 分别解决什么问题？</h2>

<a id="1.git，gitlab，svn的相关知识"></a>

<a id="user-content-1.git，gitlab，svn的相关知识"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Git 与 SVN 是版本控制系统，GitLab 是围绕 Git 提供代码托管、权限、评审与流水线的平台。它们不处于同一分类层级，平台提供权限功能也不能单独证明某种工具更安全。

Git 的本地仓库通常拥有提交历史，可以离线提交、建分支和比较版本；团队常约定一个远端作为协作中心，但这不改变其分布式模型。SVN 通常以中央仓库管理版本，提交需要连接服务器。具体工作流的效率取决于仓库规模、二进制文件、权限与团队约定。

Git 中工作区是正在编辑的文件，暂存区记录下一次提交准备包含的内容，提交形成可引用的快照，push 再把对象与引用更新发送到远端。`git add` 不等于提交，`git commit` 不等于推送，`git fetch` 也不会自动把远端变化合并进当前分支。

AI 项目应同时记录代码提交、配置、数据版本与模型权重标识。大权重通常放制品库或对象存储，在 Git 中保留哈希和清单；使用 Git LFS 时，仓库中的指针与实际大文件也要一起管理。密钥即使在后续提交删除，仍可能留在历史中，需要撤销凭据并按实际情况清理历史。

评审与发布应围绕可复现提交，而非一个持续移动的分支名。版本控制保存的是变更关系，测试和验收决定某个版本是否值得交付，二者不能互相代替。

<h2 id="q-003">面试问题：AI 项目的 POC 应验证哪些假设，怎样避免只展示成功样例？</h2>

<a id="2.poc验证测试的概念"></a>

<a id="user-content-2.poc验证测试的概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

POC 是概念验证，目标是在有限投入内判断关键方案是否可行。它可以用于供应商选型，也可以用于内部技术路线选择；重点是验证决定后续投入的假设。

先把业务目标转成验收条件。例如文档问答系统需要同时验证答案正确性、证据可追溯、权限隔离、延迟与单次成本。数据应包含典型样本、边界样本和失败样本，并将开发调试集与最终评测集分开，避免演示样例被反复优化后失去代表性。

<div align="center">

| 要验证的假设 | 可留存的证据 |
| --- | --- |
| 功能满足需求 | 固定用例、输入输出与失败分类 |
| 性能满足预算 | 硬件、并发、输入规模、延迟分位数与成本 |
| 能接入现有系统 | API、权限、网络和数据格式集成记录 |
| 能持续运维 | 故障恢复、部署步骤、版本与回滚验证 |
| 商务可成立 | 许可、服务边界、报价与必要的履约核查 |

</div>

供应商演示、团队实测与第三方报告应分别标注。对生成模型，同一输入可能有随机差异，应固定或记录采样参数，必要时多次运行并报告波动。不能用一条漂亮答案代替总体质量，也不能只报平均延迟掩盖长请求。

POC 结束时给出通过、带条件通过或停止投入的判断，并列出仍未覆盖的生产风险。原型能工作是起点，真实流量、长期状态和故障恢复往往需要另一个验收阶段。

<h2 id="q-004">面试问题：Docker 镜像、容器与仓库是什么关系？</h2>

<a id="3.docker的相关概念及常用命令"></a>

<a id="user-content-3.docker的相关概念及常用命令"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

镜像提供文件系统层与运行配置，容器是在这些基础上创建的运行实例，registry 保存并分发镜像。repository 是 registry 中的一组相关镜像名称，tag 指向某个版本，digest 则标识具体内容。`latest` 只是标签，不保证最新或稳定。

Linux 容器通常共享宿主机内核，通过 namespace、cgroup 等机制组织隔离与资源控制。容器可以共享网络、挂载和内核接口，不能说彼此“没有任何接口”。Docker Desktop 常在虚拟机中运行 Linux 容器，其设备与网络路径又多了一层。

```bash
docker ps -a
docker image ls
docker inspect model-api
docker logs --tail 100 model-api
docker exec -it model-api /bin/sh
docker stop --time 30 model-api
```

`run` 创建新容器，`start` 启动已有容器；`exec` 在运行容器里新建进程，`attach` 连接主进程的标准流，信号与退出行为取决于进程和配置。`docker tag` 操作的是镜像引用，不是给容器改名字，`docker cp` 可用容器名或可识别的 ID，无需强求完整 ID。

容器可写层随容器删除而丢失，持久结果使用卷、绑定挂载或外部存储。`--mount` 对路径错误的行为更明确；只读权重挂载有助于防止运行期间误改。`docker commit` 可保存临时状态，但很难替代可评审、可复现的 Dockerfile，也可能把敏感文件一起带入镜像。

选择容器是为了固定用户态交付边界，宿主机驱动、CPU 架构、外部配置和数据版本仍需管理。

<h2 id="q-005">面试问题：AI 项目里的配置、数据、权重与交换格式怎样选择？</h2>

<a id="4.深度学习中常用的文件格式汇总"></a>

<a id="user-content-4.深度学习中常用的文件格式汇总"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

文件后缀只是入口，真正要确认的是格式规范、schema、数值类型、版本和加载行为。两个 `.pt` 文件可能保存完全不同的对象，不能凭后缀就知道怎样安全加载。

<div align="center">

| 用途 | 常见格式 | 需要关注 |
| --- | --- | --- |
| 配置 | JSON、YAML、TOML | 类型、默认值、schema 验证与安全解析 |
| 文本记录 | CSV、JSONL | 分隔转义、编码、逐条读取和缺失值 |
| 批量分析数据 | Parquet、Arrow | 列类型、压缩、分区与兼容 |
| 数组与张量 | NPY/NPZ、HDF5、safetensors | dtype、shape、端序、随机读取与元数据 |
| 框架检查点 | PyTorch checkpoint 等 | 保存对象、运行时代码与恢复所需状态 |
| 模型交换 | ONNX、协议描述与权重 | 算子集、动态 shape、运行时支持 |

</div>

Protobuf 描述并序列化结构化消息，ONNX 使用它组织模型，但“使用 Protobuf”不意味着所有模型语义都已兼容。YAML 解析器的构造能力和 pickle 类对象反序列化可能执行代码，未知来源不能默认信任。safetensors 主要保存张量，降低任意对象反序列化风险，但仍需验证大小、数值和应用层资源限制。

大数据选择还取决于访问模式。JSONL 方便按行流式处理，Parquet 适合列裁剪与分析扫描，成千上万小文件则可能被元数据开销拖慢。压缩降低字节量，也消耗 CPU，不能只比较磁盘大小。

交付模型时将权重、配置、tokenizer、前后处理和校验清单成套管理。文件可读取不代表语义正确，还要用已知输入验证数值、输出格式和版本对应关系。

<h2 id="q-006">面试问题：Conda 环境隔离与依赖锁定怎样保证可复现？</h2>

<a id="5.conda创建管理虚拟环境的命令大全"></a>

<a id="user-content-5.conda创建管理虚拟环境的命令大全"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Conda 同时管理环境和包，环境隔离可以避免不同项目直接改写同一套依赖，但不隔离宿主机内核、GPU 驱动和系统服务。可复现还需要记录平台、解释器、渠道与具体包版本。

```bash
conda create -n model-api python=3.12
conda activate model-api
python -m pip --version
conda list
conda env export --from-history > environment.yml
conda list --explicit > conda-explicit.txt
```

Python 版本应按实际框架兼容要求选择。`--from-history` 保存直接请求的依赖，便于表达环境意图，但不会锁定全部传递依赖；显式清单更精确，却通常绑定平台与构建。完整导出也可能含本地路径和平台特定包，不能保证换台机器原样可用。

混用 pip 时，先完成 Conda 依赖解析，再在该解释器中使用 `python -m pip` 安装必要包，记录锁定结果。后续反复用两个求解体系修改同一个环境，可能覆盖彼此依赖。需要升级时，新建环境验证后切换，比直接在生产环境中 `update --all` 更容易回退。

非交互服务不必依赖终端已经执行过 activate，可用明确的解释器路径或 `conda run -n model-api ...`。启动时核对 `sys.executable` 与关键包版本，避免“终端显示了环境名，实际进程却用了另一个 Python”。

环境文件之外，还要保留模型哈希、外部工具和最小推理验证。只复制一个环境目录可能涉及硬编码路径与平台二进制，不能等同于经过验证的部署包。

<h2 id="q-007">面试问题：Dockerfile 怎样做到可复现、可缓存和便于维护？</h2>

<a id="6.通过Dockerfile构建镜像"></a>

<a id="user-content-6.通过Dockerfile构建镜像"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Dockerfile 记录镜像构建步骤，镜像可复现程度取决于基础镜像、依赖与构建输入是否固定。写了 Dockerfile 但每次下载“最新包”，仍可能构建出不同产物。

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.lock ./
RUN python -m pip install --no-cache-dir -r requirements.lock
RUN useradd --create-home --uid 10001 appuser
COPY --chown=appuser:appuser . /app
USER appuser
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

这是结构示例，正式发布还应固定已验证的镜像 digest 和依赖哈希。先复制依赖清单、后复制业务代码，可让代码变更尽量复用依赖安装层；`.dockerignore` 排除缓存、Git 历史、密钥和不必要的大权重，缩小构建上下文。

`RUN` 在构建阶段执行，`CMD`/`ENTRYPOINT` 决定运行时入口，`EXPOSE` 只是端口声明，不会自动在宿主机发布端口。`COPY` 适合明确的文件复制，`ADD` 的额外功能应在需要时使用，不能为省几个字符引入隐式行为。多阶段构建可把编译器和构建产物分开，减少运行镜像内容。

密钥不要写进 `ARG`、`ENV` 或 COPY 后再删除，历史层仍可能保留信息；构建中需要凭据时用相应 secret mount。镜像也不应把可变运行数据当作唯一副本。

验收至少包括干净环境构建、以预期非 root 身份启动、健康检查、一次真实推理和退出信号处理。构建缓存命中只能说明复用了产物，不能证明产物仍符合当前安全与功能要求。

<h2 id="q-008">面试问题：Docker Compose 怎样组织服务、网络、卷和健康检查？</h2>

<a id="7.docker-compose的使用"></a>

<a id="user-content-7.docker-compose的使用"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Compose 用声明式配置描述多个容器及其网络、卷和启动参数，适合开发、集成验证和部分单机部署。它减少重复启动操作，但不自动提供跨主机调度、数据库高可用或完整生产治理。

```yaml
services:
  api:
    image: example/model-api:1.0
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      REDIS_URL: redis://cache:6379/0
    depends_on:
      cache:
        condition: service_healthy
  cache:
    image: redis:7.4
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 2s
      retries: 10
```

示例镜像需替换为实际验证过的版本。现代 Compose 常用 `docker compose` 命令，顶层 `version` 不再用于选择旧式文件语义。默认网络中服务可按名字互相发现，因此 api 连接 `cache:6379`，无需经宿主机发布端口。

普通 `depends_on` 主要处理启动顺序，健康条件能等待依赖健康，但运行过程中依赖仍会故障，应用必须有重连、超时与错误处理。Redis 的 `PING` 只证明基础服务响应，也不证明业务权限、数据或复制状态全部正常。

持久数据显式放卷或外部存储，删除容器与删除卷是不同动作。GPU、共享内存和资源限制按运行环境核验；不要默认启用 host IPC 或特权模式。发布前用 `docker compose config` 检查最终配置，再检查端口、卷、身份和日志。配置中引用的密钥应通过受限渠道注入，避免提交到仓库。

<h2 id="q-013">面试问题：切换 Git 分支前，怎样保护工作区并理解远端分支？</h2>

<a id="12.如何使用Git将AI项目切换到特定分支？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

分支是指向提交的可移动引用，切换分支会改变当前提交和相应工作区内容。远端跟踪分支如 `origin/main` 是本地记录的远端状态，需要 fetch 才更新，不是实时读取服务器。

```bash
git status --short
git diff
git branch -avv
git fetch origin
git switch feature-a
```

先确认未提交修改和未跟踪文件，再选择保留、提交、stash 或独立 worktree。Git 会在某些切换冲突时阻止操作，但“没报错”并不意味着修改自动属于新分支；允许携带的工作区修改会跟着切换结果出现，需要理解归属。

本地没有目标分支时，可用 `git switch --track origin/feature-a` 创建跟踪分支。临时查看某个提交可用 detached HEAD，想保留后续提交就创建分支。需要并行维护不同版本时，`git worktree` 能减少反复切换对当前工作的干扰。

`git reset --hard`、`git checkout .` 和 `git clean` 可能丢弃修改或未跟踪文件，不能放进每次服务启动脚本当作固定清理步骤。stash 也要明确是否包含未跟踪文件，恢复时可能发生冲突；它不是远端备份。

部署应固定提交或制品 digest，不在启动过程中临时 `git pull` 决定线上代码。这样代码来源、测试结果和运行版本才能一一对应。

<h1 id="q-101">2.调用、执行与服务生命周期</h1>

<h2 id="q-009">面试问题：同步、异步、阻塞和非阻塞为什么不能画等号？</h2>

<a id="8.计算机中同步调用和异步调用有哪些区别？"></a>

<a id="user-content-8.计算机中同步调用和异步调用有哪些区别？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

同步与异步描述操作完成结果如何交付，阻塞与非阻塞描述调用在暂时无法完成时是否等待。日常 SDK 常把同步接口实现为阻塞调用，但这不是四个词天然等价。

非阻塞 socket 的 read 在没有数据时可以立即返回 `EAGAIN`，应用以后再读，仍由应用执行读操作。异步 I/O 则可以先提交请求，通过完成通知取得结果。一个返回 Future 的函数允许调用者稍后等待，但调用者立即 `.result()` 仍可能阻塞当前线程。

Python 中 `await fetch_a(); await fetch_b()` 仍按依赖顺序等待两次操作；只有创建并调度独立任务，才有机会重叠等待。`async def` 里的同步 HTTP 客户端或 CPU 循环也会阻塞事件循环。异步接口改善等待安排，不保证计算更快或所有任务同时执行。

设计异步业务还要定义结果保存位置。例如视频生成 API 返回任务 ID 后，请求结束，任务仍由后台 worker 执行；客户端通过查询或事件获取结果。这是业务层异步，与底层是否使用 epoll 没有一一对应关系。

异步带来生命周期责任：超时由谁处理、失败在哪里记录、取消是否传播、队列是否有界、进程退出后任务能否恢复。轻量通知可以放进进程内后台任务，重要长任务应使用持久化任务记录与可恢复队列。只在接口上加 `async` 不能补齐这些保证。

<h2 id="q-010">面试问题：并发与并行有什么区别，为什么增加 worker 可能更慢？</h2>

<a id="9.计算机中串行操作和并行操作有哪些区别？"></a>

<a id="user-content-9.计算机中串行操作和并行操作有哪些区别？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

并发表示多个任务在一段时间内交错推进，并行表示多个任务在同一时刻执行。单核可以通过切换和 I/O 等待实现并发，多核与设备则提供并行执行条件；具体程序还受运行时和依赖约束。

若一个流程有比例 s 必须串行，其余部分能理想分到 P 个执行单元，Amdahl 定律给出的理想加速上限为 `1 / (s + (1-s)/P)`。例如串行部分占 20%，即使并行资源无限，理想上限也只有 5 倍。实际还会增加通信、同步、调度与数据复制，往往达不到这个上限。

并行化前先画依赖：独立图片可并行预处理，同一个任务中后一步依赖前一步输出则不能直接同时运行。共享写入需要同步，归并结果需要定义顺序与错误行为；任务并行不等于结果可以任意覆盖。

AI 系统特别容易出现嵌套并行。多个 Web 进程各自加载模型或启动 BLAS 线程池，可能造成显存重复、CPU 超额竞争和内存带宽饱和。传统 GIL 构建中的纯 Python 线程也不保证 CPU 并行，而原生库释放 GIL 的部分行为不同。

评估时同时看单请求延迟和总吞吐。batch 增大可能提升吞吐，却增加等待；worker 增加可能摊薄空闲，却拉高尾延迟。应以稳定负载和业务目标选择配置，不能只凭任务数量推断收益。

<h2 id="q-011">面试问题：二进制补码为什么多表示一个负数？</h2>

<a id="10.为什么有符号INT数据类型可表示的负数比正数多1？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

N 位补码的最高位权重为 `−2^(N−1)`，其余位权重依次为正的二次幂。它不是简单拿一位记录正负、剩下的位记录绝对值；那是另一种表示思路。

以 8 位为例，`01111111` 为 127，`10000000` 为 −128，`11111111` 为 −1，`00000000` 为 0。总共有 256 种位模式，其中 128 种表示负数，剩下 128 种表示 0 到 127。由于零只需要一种表示，正数数量就比负数少一个。

负数可以通过对应正数按位取反再加一获得，例如 1 的位模式为 `00000001`，取反加一得到 `11111111`。这样加减法可复用模 `2^N` 的二进制运算结构。但最终语言对溢出的规则还需单独理解，不能从硬件位模式直接推导 C/C++ 有符号溢出总会合法回绕。

最小负数尤其值得注意：8 位的 −128 取相反数需要 +128，超出同一类型范围，因此 `abs(INT_MIN)` 一类操作可能溢出或产生语言特定行为。将计数、长度或索引在有符号和无符号之间转换时，也可能把负数变成非常大的值。

工程中应在运算前扩大类型或检查范围，尤其是图像尺寸乘积、张量元素数和字节数计算。结果赋给更宽变量之前，表达式可能已经在窄类型里溢出，单纯改接收变量类型不一定足够。

<h2 id="q-012">面试问题：一个可靠的服务启动脚本，应该承担哪些职责？</h2>

<a id="11.介绍一下AI行业中规范的AI服务启动Shell脚本"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

启动脚本负责把一个确定版本的程序，以确定环境和配置启动起来，并正确传递退出状态与信号。代码更新、构建、清理工作区和发布切换应有各自步骤，不能每次启动都拉最新分支并强杀占用端口的进程。

```bash
#!/usr/bin/env bash
set -euo pipefail
service_root=${SERVICE_ROOT:?缺少服务目录}
service_python=${SERVICE_PYTHON:?缺少解释器路径}
service_config=${SERVICE_CONFIG:?缺少配置路径}
test -x "$service_python"
test -r "$service_config"
cd -- "$service_root"
exec "$service_python" -u -m app.server --config "$service_config"
```

示例依赖实际存在的 `app.server` 入口。显式检查路径与参数后，用 `exec` 让服务直接接收管理器发来的信号。日志写到标准输出或约定位置，由外部系统负责轮转；凭据从受限配置读取，不在日志中完整打印环境。

长期运行交给 systemd、容器运行时或相应编排器，设置工作目录、运行用户、资源限制、重启策略和退出等待时间。脚本成功启动一个后台 PID，不代表模型已经加载完成，更不代表服务可以处理请求。

就绪检查应验证模型与必要依赖初始化，存活检查应区分进程异常和暂时过载，避免慢启动触发反复重启。停止时先停止接新请求，再处理在途任务与结果状态，超过期限才强制终止。错误处理从脚本开头生效，不能在后台启动完成以后才安装一个从未覆盖前面失败的 trap。

<h2 id="q-016">面试问题：AI API 的契约应该包含哪些工程语义？</h2>

<a id="15.介绍一下AI行业中的API以及具体的作用"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

API 是软件之间约定的交互接口，既可以是本地函数，也可以是网络服务。工程设计关心调用者能依赖哪些行为：输入、输出、错误、版本、权限、限额和执行副作用。

对生成任务，至少定义输入 schema、模型或策略版本、大小限制、超时、幂等键、请求 ID 与结果生命周期。长任务可以返回任务 ID，明确 `pending/running/succeeded/failed/cancelled/unknown` 等状态，而不是一个模糊的“已接受”字符串。

错误应可分类：非法参数无需重试，额度不足按策略等待，服务过载可以退避，结果未知需查询。HTTP 状态码与业务错误体相互补充；返回 200 但 body 里写失败，会让监控、缓存与客户端误判。

兼容性需要给调用者时间。增加可选字段通常比改字段类型更容易兼容，但客户端也要容忍未知字段；删除枚举值、改变 token 计量方式或默认模型行为，可能在 URL 没变时破坏业务。记录 schema、模型与工具版本才能还原一次调用。

API 接入不自动带来数据安全或合规。身份验证、数据保留、访问区域、审计与外部副作用仍需按实际服务约定。传输过程与协议分层见[网络章的 API 请求路径](计算机网络高频知识点.md#q-011)，本题重点是可依赖的接口行为。

<h2 id="q-017">面试问题：Gunicorn 的 master 与 worker 如何协作？</h2>

<a id="16.介绍一下Gunicorn的原理，并举例其在AI行业的作用"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Gunicorn 采用预分叉进程管理模型，master（也称 arbiter）负责管理 worker、处理信号与重启异常进程，worker 负责具体请求。监听 socket 可以由父进程建立后交给 worker，但 master 通常不逐条 accept 客户端连接再分配给空闲 worker，连接接受与调度由 worker 和内核机制共同完成。

worker 类型决定并发方式。默认 sync worker 每次处理一个请求；gthread 在进程内使用线程池；异步 worker 使用相应事件循环或协作调度机制。WSGI 与 ASGI 是应用接口约定，需要选择匹配的 worker，不能把 FastAPI 应用直接当成普通 WSGI callable 运行。

```bash
gunicorn wsgi_app:app --bind 127.0.0.1:8000 --workers 2
```

这是 WSGI 部署示例，worker 数需依据负载测量。ASGI 可使用适配的 worker；Uvicorn 已将旧 `uvicorn.workers` 路径标为弃用，采用独立 `uvicorn-worker` 包时应固定版本并按其文档配置，避免继续复制过时入口。

AI 服务需特别留意预加载与模型副本。CPU 只读页可能利用写时复制，但每个 worker 修改后会产生私有页；GPU 初始化与 fork 的组合有运行时约束，不能假定 `--preload` 会共享一份显存模型。多 worker 还可能将数据库连接池和线程池数量成倍放大。

超时、优雅退出与最大请求数等参数服务于具体故障模型。把 timeout 调大可以容忍长请求，却不会解决无界排队或 worker 卡死。外层反向代理、应用入口和模型调度分别需要容量控制，进程管理器也不能替代持久化任务系统。

<h2 id="q-018">面试问题：Uvicorn 与 ASGI 怎样处理 HTTP、WebSocket 和应用生命周期？</h2>

<a id="17.介绍一下Uvicorn的原理，并举例其在AI行业的作用"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

ASGI 通过 `scope`、`receive`、`send` 描述连接上下文、输入事件和输出事件，并提供 lifespan 等生命周期约定。Uvicorn 实现协议服务与事件循环调度，FastAPI、Starlette 等应用框架在这个接口上处理业务。

Uvicorn 可以选择 asyncio 或可用的 uvloop，以及不同 HTTP 解析实现，不能把某个可选加速依赖说成所有平台的必需组件。它的事件循环能重叠许多网络等待，但阻塞代码和长时间 CPU 工作仍会拖住同一执行线程。

```bash
python -m uvicorn main:app --host 127.0.0.1 --port 8000
```

开发自动重载与多 worker 模式有不同用途，`--reload` 和 `--workers` 不能随意同时使用。Uvicorn 自带多进程管理使用 spawn，区别于 Gunicorn 的 pre-fork 模型；每个应用进程仍需按自己的生命周期初始化模型与连接池。

GPU 推理宜交给明确的调度与执行层，入口协程负责校验、等待和流式返回。`asyncio.to_thread` 可以隔离部分阻塞调用，但默认线程池不是无限容量的推理调度器，也不负责模型并发安全。FastAPI BackgroundTasks 属于进程内任务，进程崩溃后没有自动持久恢复保证，长训练任务不宜只靠它托管。

启动时在 lifespan 中完成必要初始化，就绪后再接流量；关闭时停止接单、处理取消、释放池和设备资源。位于代理后方时，还要限制可信代理来源，避免任意客户端伪造转发头改变来源 IP 或协议判断。

<h2 id="q-024">面试问题：怎样停止一个 Python 服务，而不误伤同机其他任务？</h2>

<a id="23.Linux中有哪些查看Python进程和关闭Python进程的命令？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Python 只是解释器名称，同一台机器上的训练、Notebook、API 和运维任务都可能以它运行。`pkill -f python` 会把模糊名称当作服务边界，无法保证只停止目标项目。

先用服务管理器识别目标，或者查询完整命令行、工作目录、父子关系和监听端口：

```bash
pgrep -af 'app.server'
ps -p 12345 -o pid,ppid,lstart,stat,args
ss -lntp
```

确认后优先执行对应的 `systemctl stop`、容器 stop 或编排器终止流程，由它们处理进程组和退出期限。手动发送 SIGTERM 时，要确认 PID 未被复用；持久脚本应使用可靠进程句柄或管理器，不能只保存一个永不过期的 PID 数字。

服务收到终止请求后，先让 readiness 退出接流量，再停止接收新任务，等待或取消在途任务，保存必要状态，关闭连接并回收子进程。队列中的未完成任务应保留可重新领取状态，已经执行外部副作用的任务则要核对结果。

超时仍不退出再考虑 SIGKILL，并接受清理逻辑不会执行的后果。只关闭主进程也可能留下子进程；端口消失不代表 GPU worker 或后台任务都已结束。验证应覆盖进程树、设备占用、监听端口与业务状态，信号原理见[操作系统章节](操作系统高频知识点.md#q-005)。

<h2 id="q-025">面试问题：硬件热插拔、服务热更新与模型冷启动有什么区别？</h2>

<a id="24.介绍一下计算机中热插拔式和冷启动的相关概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

硬件热插拔是在系统运行时插入或移除设备，需要接口、电气设计、驱动和操作系统协同支持。软件热更新是在不完全停止服务的情况下切换代码、配置或模型；模型冷启动则指实例缺少就绪状态，需要加载与初始化。这三件事不能因为都带“热”“冷”就混为一谈。

硬件支持热插拔也不代表应用可以无损继续。移除磁盘前要处理写入和挂载，设备被计算任务占用时要先协调释放。GPU 是否可热插拔依赖具体硬件与软件栈，NVLink 或集群新增节点并不能单独证明运行中的 GPU 卡可以随意拔插。

模型冷启动可能包括拉镜像、下载权重、校验、加载主内存和显存、编译算子、分配缓存与预热。应分别计时，才能判断预拉镜像、共享缓存、预编译或保留热实例解决的是哪一段。启动探针要给初始化留出合理时间，就绪探针则防止尚未加载完成的实例接单。

模型热更新常用双版本共存：先加载新版本并验证，再切换流量，旧版本排空后释放。这会产生临时额外显存与内存需求，不能忽略更新峰值。只替换磁盘文件不会让已加载的权重自动改变。

自动扩容还需考虑启动时间与突发流量。缩到零节省空闲成本，却把等待转移给下一次请求；预热池提高响应速度，也增加常驻成本。选择取决于延迟目标、流量规律与资源预算。

<h2 id="q-026">面试问题：Dockerfile 的 CMD 与 ENTRYPOINT 怎样组合，信号为什么重要？</h2>

<a id="25.Dockerfile中CMD和ENTRYPOINT的区别"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

exec 形式的 ENTRYPOINT 定义主程序，CMD 提供默认命令或默认参数。运行时传入镜像名之后的参数通常替换 CMD，并追加到 ENTRYPOINT 后；ENTRYPOINT 本身也可由 `--entrypoint` 显式覆盖。

```dockerfile
ENTRYPOINT ["python", "-m", "app.server"]
CMD ["--port", "8000"]
```

默认执行 `python -m app.server --port 8000`；运行 `docker run image --port 9000` 则改用 9000。若镜像只有 CMD，没有 ENTRYPOINT，镜像名后提供的命令会替换整个默认命令。

exec JSON 形式直接执行参数，不经过 Shell，因此不会自动展开环境变量、管道或重定向。Shell 形式通常经 `/bin/sh -c`，变量会被解释，但信号与参数行为也随之变化。需要初始化脚本时，脚本最后应 `exec` 主程序，避免 Shell 留在 PID 1 且没有正确转发 SIGTERM。

容器生命周期跟随主进程。把真正服务放到后台后让启动脚本退出，容器可能立即结束；为了保活加一个无关的 `tail -f`，又可能掩盖服务已死。主进程应直接代表实际服务，或由真正负责监督的管理器承担。

多条 CMD 只保留最后一条有效配置，不表示依次执行多个命令。镜像入口、Compose command/entrypoint 和运行时覆盖应一起检查最终结果，避免开发启动方式与生产实际执行参数不同。

<h1 id="q-102">3.设备、网络入口与运行数据</h1>

<h2 id="q-014">面试问题：Docker 怎样使用 GPU，驱动与 Toolkit 分别在哪一层？</h2>

<a id="13.docker中如何使用gpu？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

NVIDIA GPU 容器依赖宿主机驱动，以及将设备与必要驱动接口交给容器的 NVIDIA Container Toolkit。容器镜像通常携带 CUDA 用户态运行时和框架依赖，不能通过在容器里随意安装另一套内核驱动来替代宿主机配置。

先在宿主机执行 `nvidia-smi` 确认驱动，再按发行版和官方文档安装、配置 Toolkit，最后使用已验证兼容的 CUDA 镜像运行一个小测试。Toolkit 配置可能改变 Docker runtime，需要遵循服务重载或重启要求，不能照搬多年以前的 apt-key 和仓库地址。

```bash
docker run --rm --gpus all your-validated-cuda-image nvidia-smi
```

这里的镜像名需替换为团队固定的版本。看到 nvidia-smi 输出，只证明相应驱动管理路径可用；还要验证框架能分配张量、执行 GPU 运算和完成一次推理。`nvidia-smi` 显示的 CUDA 版本通常是驱动可支持的兼容能力，不等于容器安装的 toolkit 版本。

`--gpus`、设备 UUID、MIG 及编排器设备插件决定资源分配，环境变量负责部分可见性。只设置 `CUDA_VISIBLE_DEVICES=0` 不会凭空将设备挂进容器，也不构成强隔离。不同容器若访问同一设备，仍会争用显存和计算。

遇到设备不可见、驱动不匹配、算子加载失败时分别检查运行时、驱动、用户态库与框架构建。把所有问题归成“CUDA 版本不一致”，会错过权限、架构或镜像缺少依赖的真正原因。

<h2 id="q-015">面试问题：容器访问摄像头与显示画面需要跨过哪些边界？</h2>

<a id="14.docker中如何使用摄像头并显示画面？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐ (3/5)**

摄像头输入与图形显示是两个独立路径。Linux 上常见 USB 摄像头通过 V4L2 暴露为 `/dev/video*`，容器需要设备访问权限和相应驱动接口；显示画面则涉及 X11、Wayland 或远程编码输出。

```bash
docker run --rm --device /dev/video0:/dev/video0 camera-app:validated
```

示例只展示设备映射，实际还需核对容器用户所属组、设备权限、像素格式和是否被其他进程占用。设备编号可能在重连后变化，可通过稳定设备路径或明确的 udev 配置管理。Docker Desktop 中 Linux 容器位于虚拟机，不能直接假设宿主机摄像头等价于容器里的 `/dev/video0`。

X11 显示通常涉及 DISPLAY、Unix socket 与认证 Cookie；仅挂载 `/tmp/.X11-unix` 不等于完成授权。`xhost +` 会广泛放开显示访问，不应作为常规教程默认步骤。Wayland 又有自己的 socket、用户身份与权限模型，不能套用同一组 X11 参数。

对服务器部署，通常更适合容器捕获并编码视频，通过受控 HTTP、WebSocket 或实时媒体协议输出，再由浏览器显示，减少直接共享桌面会话的耦合。需要本地 GUI 时，只开放所需设备与显示授权，不默认启用 `--privileged`。

验收分三步：能打开设备、能获取并解码帧、能在目标显示路径正常呈现。GPU 加速还要独立验证，摄像头可读并不证明硬件解码或显示加速已经启用。

<h2 id="q-021">面试问题：迁移 Docker 数据目录时，为什么只改 data-root 可能不够？</h2>

<a id="20.如何迁移docker服务所在路径？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

迁移前要确认实际存储后端。传统 storage driver 的镜像、容器等数据通常集中在 Docker 数据根目录；采用 containerd image store 的部署，还可能把镜像内容与快照放在 containerd 的独立目录。Docker 的 `data-root` 不会自动迁移这些 containerd 数据，具体位置需按当前版本与配置查询。

可靠流程是先盘点镜像、容器、卷、绑定挂载和运行状态，准备足够容量与兼容文件系统，备份配置，然后在约定窗口停止相关工作负载和写入服务。仅停止 Docker daemon 也要考虑 socket activation、live-restore 与其他 containerd 用户，不能在数据仍变化时认定复制一致。

复制需保留所有权、权限、硬链接、ACL 与扩展属性，并核对源目录尾部斜杠的含义。可按文件系统能力选择 `rsync -aHAX --numeric-ids` 等参数，但必须验证双方支持与退出状态。Docker Desktop、rootless 和系统级 Docker 的路径与管理方式不同，不能统一套 `/var/lib/docker`。

修改 daemon.json 时合并现有配置，避免覆盖 registry、runtime、代理等设置；containerd 若单独迁移也要按其配置处理。启动后检查实际目录、镜像列表、卷内容、网络、GPU runtime 和一次业务请求。

原有 `docker info` 截图只能帮助识别字段，不能证明本机迁移已经成功：

![docker info 中 Docker Root Dir 字段的历史示例](./imgs/docker_info.png)

</div>

验收通过前保留旧数据和回退配置。不要直接删除旧目录，更不要把两个运行中的 daemon 指向同一数据目录。容量问题如果来自未设上限的日志，迁移之后仍会再次发生。

<h2 id="q-022">面试问题：两个服务互调时，监听地址、访问地址和容器端口怎样设置？</h2>

<a id="21.计算机中两个AI服务，一个AI服务调用另外一个AI服务时，该如何设置两者ip地址和端口号？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

被调用服务的监听地址决定接受哪些本地接口上的连接，调用方使用的地址则必须从它所在网络可达。`0.0.0.0` 常用于绑定所有 IPv4 接口，不能作为稳定的远端服务地址发给客户端。

<div align="center">

| 部署关系 | 调用方常用地址 | 要检查的条件 |
| --- | --- | --- |
| 同一主机、同一网络命名空间 | `127.0.0.1:8000` | 服务监听回环或相应接口 |
| 同一 Compose 网络 | `model-api:8000` | 服务名解析和容器内部端口 |
| 宿主机访问容器 | 宿主机发布地址与端口 | `-p` 映射和监听范围 |
| 跨主机 | 服务 DNS、内网或公网地址 | 路由、防火墙、认证和 TLS |

</div>

两个容器中的 localhost 各指向自己，即使在同一物理机上，也不能自动互通。宿主机映射 `127.0.0.1:8080:8000` 时，主机本地使用 8080，同网络其他容器通常直接访问服务名的 8000，不必绕宿主机。

端口冲突要结合协议、地址与网络命名空间判断，同机不同 IP 可以绑定同一个端口，TCP 与 UDP 也分别管理。仅绑定 `0.0.0.0` 不保证外部可达，云安全组、宿主机防火墙和 NAT 仍可能阻断。

调用端设置连接、读取和总预算，并限制连接池。服务地址通过配置或服务发现管理，不硬编码易变化的容器 IP。即使是内网调用，也应按数据敏感度验证服务身份和权限；网络能通只是接口可用的第一步。

<h2 id="q-023">面试问题：Nginx 反向代理怎样影响路由、流式输出和超时？</h2>

<a id="22.Nginx的使用介绍"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Nginx 可以承担统一入口、TLS 终止、反向代理、负载分配和静态资源服务。统一入口便于管理域名、证书与访问规则，但不是因为服务器只能开放一个端口，实际开放范围取决于部署策略。

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000/;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_buffering off;
    proxy_read_timeout 120s;
}
```

这个例子放在已有 server 配置内。末尾 `/` 很重要：在该普通前缀 location 中，`/api/tasks` 会按替换规则转给上游 `/tasks`；没有 URI 部分的 proxy_pass 通常保留原路径。包含正则、变量等情况时规则又有差异，要用实际请求验证。

对 SSE，代理响应缓冲可能让上游逐段输出在客户端变成整块到达，因此按路由关闭缓冲，并检查应用、压缩和其他网关层。`proxy_read_timeout` 主要限制两次上游读取之间的间隔，不是整个任务总时长。心跳可以维持连接，却不能代替业务 deadline。

WebSocket 需要正确处理 Upgrade 与 Connection 头，不能只照搬普通 HTTP 路由。信任来源 IP 时也要限定可信代理链，避免客户端伪造转发头。上传大小、连接数与请求速率应有明确限制。

修改后先 `nginx -t` 检查配置，再受控 reload，并验证路由、证书、错误响应和流式行为。语法通过只证明配置能解析，不证明后端可达或业务正确。

<h1 id="q-103">4.安全、发布与诊断</h1>

<h2 id="q-019">面试问题：加密、哈希、数字签名和密码存储有什么不同？</h2>

<a id="18.常用加密算法介绍"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

加密保护机密性，哈希将数据映射成摘要，数字签名验证来源与完整性，密码存储则需要抵抗离线猜测。它们不能用“把数据加密一下”概括。

对称加密用共享密钥处理数据，常见方案使用 AES-GCM 或 ChaCha20-Poly1305 这类认证加密，同时校验密文是否被篡改。nonce 必须遵守算法要求，同一密钥下重复使用可能严重破坏安全。ECB 会暴露重复明文块模式，不应作为通用业务加密示例。

```python
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

key = AESGCM.generate_key(bit_length=256)
nonce = os.urandom(12)
aad = b"model-artifact:v1"
ciphertext = AESGCM(key).encrypt(nonce, b"payload", aad)
plaintext = AESGCM(key).decrypt(nonce, ciphertext, aad)
```

示例演示 API，生产密钥需安全保存与轮换，nonce 与密文可一起存储，aad 提供完整性绑定但不加密。非对称密码包含加密、签名和密钥协商等不同用途；数字签名不是对所有算法都适用的“拿私钥加密原文”。TLS 通常通过握手建立密钥，再用对称机制保护流量。

用户密码应使用带独立盐、可调成本的密码哈希，如按要求配置的 Argon2id；不能只用快速 SHA-256，更不应存可解密的密码供登录比较。普通摘要没有密钥，不能单独证明消息来自谁；HMAC 才提供共享密钥下的认证。

OAuth 主要是授权框架，身份登录通常还涉及 OpenID Connect 等机制。算法正确也不能弥补密钥泄漏、错误证书验证或越权接口，安全属性要沿完整路径检查。

<h2 id="q-020">面试问题：Unicode、UTF-8、Base64、URL 编码与压缩有什么区别？</h2>

<a id="19.常用编码方法介绍"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Unicode 定义字符与码点等规范，UTF-8/UTF-16 是把码点编码成代码单元或字节序列的方式。Unicode 不能简单定义为“每个字符固定 16 位或 32 位”，用户看到的一个字形也可能由多个码点组成。

Python 的 `str` 表示文本，`bytes` 表示字节。`text.encode('utf-8')` 得到字节，反方向用对应编码解码。错误编码、重复解码或将字节长度当字符长度，都可能导致中文截断和乱码；数据库字段限制还要明确按字节还是字符计算。

Base64 将二进制映射为可打印文本，常见长度约增加三分之一，并不加密，也不提供完整性或压缩。JWT 的部分内容通常是 Base64URL 编码，任何拿到它的人都可能解码查看内容；签名保护篡改不等于内容保密。

URL 百分号编码按字节表达保留或非安全字符，通常先按 UTF-8 得到字节，再编码成 `%XX`。应分别处理路径段与查询参数，避免对整个 URL 一次性编码后破坏分隔符。HTML 转义、JSON 转义和 SQL 参数化又是不同上下文，不能互换。

gzip 等压缩减少冗余，哈希用于摘要校验，加密保护机密性。一个系统可以先序列化、压缩、加密，再用 Base64 放进文本协议，但每一步都有成本和边界。实际 API 能直接承载二进制时，不必为了“看起来可读”把大图或视频全部 Base64 化。

<h2 id="q-027">面试问题：一份可执行的工程 SOP 应包含哪些内容？</h2>

<a id="26.介绍一下计算机领域的SOP概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

SOP 是标准操作程序，将反复执行的工作明确为输入、步骤、检查点、异常处理和责任。它的价值在于不同操作者能得到可核对的结果，而不是把一组命令排成编号列表。

以模型发布为例，输入应包括代码提交、镜像 digest、模型与配置哈希、目标环境和变更范围。每一步写清执行身份、前置条件、命令或操作、预期输出以及失败后是否继续。涉及数据迁移时，还要说明可逆性和恢复条件。

<div align="center">

| 环节 | 检查点 |
| --- | --- |
| 发布前 | 依赖、容量、备份、模型评测和回滚制品齐备 |
| 启动 | 模型校验、设备初始化、探针状态与版本一致 |
| 灰度 | 按流量分组检查质量、错误率、延迟和成本 |
| 回滚 | 流量切回，核对状态与 schema 兼容 |
| 收尾 | 保存证据、清理临时资源、更新运行记录 |

</div>

标准应来自业务约束和验证数据，不应凭空写“准确率达到 93% 即可上线”或引用没有来源的企业收益。复杂操作先人工走通，再自动化稳定步骤；自动化脚本也要有输入检查、失败退出和可追溯记录。

SOP 需要版本、负责人、适用环境与定期演练。依赖升级后未更新的操作手册可能比没有手册更危险。遇到超出前提的状态，应明确停止或转入诊断路径，不能让操作者一路机械执行到删除或覆盖关键数据。

<h2 id="q-028">面试问题：模型 demo 怎样进入能够持续运行的生产服务？</h2>

<a id="27.AIGC服务从本地demo到生产部署的工程链路是什么？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

生产化需要把模型能力放进可预测的请求与状态系统。固定输入能生成一次结果之后，还要证明不同负载、失败和版本切换下，系统仍能正确响应与恢复。

先冻结可复现制品：代码、镜像、权重、tokenizer、前后处理与配置。再定义接口契约和任务状态，决定同步、流式或异步交付。根据输入规模、并发、输出长度建立容量模型，测排队、首响应、总时长、内存峰值与成本。

随后补齐接入鉴权、参数限制、配额和资源隔离；对长任务使用持久化队列与幂等操作 ID。监控需要把请求、工具调用、模型执行和数据版本关联起来。上线前不只测正常路径，还应演练进程退出、下游超时、设备 OOM、存储失败与客户端断开。

发布采用明确的流量切分和回滚阈值。质量回归与基础设施健康是两条验收线：HTTP 200、GPU 正常，却回答错误，也属于发布失败。新旧版本若共享数据库，还要保证 schema 和状态可以兼容，回滚应用镜像不一定能撤销数据变更。

规模小可以先用单体服务加清晰模块边界，不必一开始拆成大量微服务。是否引入队列、编排或多存储，应由恢复要求与真实瓶颈决定。生产系统的成熟度，体现在出现预期外情况时能否保留事实、限制影响并恢复，而不只体现在架构图里有多少组件。

<h2 id="q-029">面试问题：镜像、驱动、CUDA、cuDNN、TensorRT 与模型版本怎样匹配？</h2>

<a id="28.Docker镜像模型权重CUDAcuDNNTensorRT版本如何匹配？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

兼容关系是一张约束图，不能把所有组件都改成同一个版本号。宿主机驱动、容器 CUDA 用户态库、框架构建、GPU 架构、算子插件和模型格式分别提出条件，需要选出经过验证的组合。

驱动通常在宿主机，框架 wheel 或镜像可能自带所需 CUDA 运行库，不一定使用系统 `nvcc` 对应的 toolkit。`torch.version.cuda`、`nvcc --version` 与 nvidia-smi 的 CUDA 字段含义不同，出现不同数字并不自动意味着错误。

TensorRT engine 的可移植性与构建版本、设备架构、精度、shape、插件及所启用兼容模式有关。某些版本和模式支持有限兼容，不能无条件跨平台复用，也不能笼统宣称所有 engine 都绝对绑定单一 GPU 型号。部署时保留源模型和可重建配置，必要时在目标环境重建并验证数值。

<div align="center">

| 需记录的信息 | 作用 |
| --- | --- |
| GPU 型号、驱动、设备能力 | 确定硬件和驱动条件 |
| 镜像 digest、框架与库版本 | 还原运行环境 |
| 权重、tokenizer、config 哈希 | 避免组件错配 |
| engine 构建参数与插件 | 判断兼容与重建方式 |
| 验证输入、容差和性能 | 证明既能运行，也符合预期 |

</div>

启动检查先验证版本与设备，再执行最小运算和代表性推理。加载成功不证明算子全部正确，也不证明量化精度可接受。升级一项依赖后重新验证相关组合，避免以“能 import”作为最终验收。

<h2 id="q-030">面试问题：可观测性怎样把指标、日志、追踪与质量评测连接起来？</h2>

<a id="29.模型服务可观测性如何设计？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

指标描述总体状态，日志记录离散事件，追踪连接一次请求经过的组件，评测样本帮助判断输出质量。它们需要共享请求、任务、模型和版本标识，才能从“错误率上升”走到“哪些请求为何失败”。

LLM 服务应区分排队时间、首 token 延迟、prefill、decode、输出 token 数和端到端时长。token/s 可以按单请求或全服务统计，两者不能混报；长短请求混合时，平均延迟也容易失真。指标维度应保留模型、部署版本、请求类型等有限标签，避免把 request_id 或完整 prompt 放进高基数标签。

追踪在网关、检索、重排、模型和工具调用之间传播上下文，异步队列可用相应 link 或父子关系表达。请求失败时，需要区分网络、限流、模型输出、工具拒绝和业务约束，不要统一记录成“AI 调用失败”。

质量采样保存经过授权和必要脱敏的输入输出、引用和评测版本，敏感全文可用受控引用代替。采样策略会影响结论，线上失败样本适合诊断，却不能直接代表全部用户的总体准确率。

告警围绕用户症状和 SLO 设置，再用资源指标解释原因。高 GPU 利用率不一定告警，持续排队与延迟超标才可能需要行动。可观测性本身也有成本，控制采样、日志体积和保留时间，并测试遥测链路断开时会怎样显示。

<h2 id="q-031">面试问题：Agent 的沙箱、权限、审计与回滚应该落在哪些层？</h2>

<a id="30.Agent沙箱权限审计灰度和回滚如何做？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Agent 会把不可信输入转换为工具操作，因此权限必须由系统执行，不能只靠提示词要求模型自觉遵守。认证身份来自可信会话，工具网关根据用户、租户、目标资源与动作判断是否允许，再把有限权限交给执行环境。

沙箱需要明确文件系统、网络、进程、CPU、内存、执行时长和凭据边界。普通容器共享内核，挂载宿主机 Docker socket 或启用特权模式会显著扩大权限；不可信代码执行可能需要更强隔离、专用内核代理或虚拟机方案，取决于威胁模型。

工具参数先按 schema 验证，再做业务授权。删除、发消息、支付等副作用可以按风险要求确认或审批，确认应绑定具体参数与有效期，避免审批后参数被替换。工具返回、网页和文档都是数据来源，不能自行提升权限。

审计记录动作 ID、授权主体、目标、参数摘要、结果状态与版本，避免保存可直接复用的密钥。超时结果未知时保留状态，查询后再决定补偿或重试。网络出站也需控制重定向、私网访问与云元数据路径，不能只校验最初 URL 字符串。

灰度应同时观察任务成功率、越权拒绝、成本和错误副作用。回滚模型、prompt 和工具 schema 可以改变未来行为，但无法自动收回已发送邮件或转账；外部动作需要独立补偿与核对。这是 Agent 发布与普通无状态接口最大的恢复差异之一。

<h2 id="q-032">面试问题：服务启动失败时，怎样按交付边界组织 Linux 排查？</h2>

<a id="31.Linux工具链在AI工程中的高频排查命令有哪些？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

工程排查先还原正在运行的版本和配置，再定位失败阶段。相同的“启动失败”可能发生在解释器、动态库、模型文件、设备初始化、端口绑定或依赖连接，所需证据不同。

```bash
systemctl status model-api
journalctl -u model-api -n 100 --no-pager
docker inspect model-api
docker logs --tail 100 model-api
ss -lntp
```

按实际部署方式选择命令，不必同时执行全部。容器退出信息要结合 OOM、信号与应用日志解释；监听端口已存在时先确认所属服务，不要自动杀掉它来“修复”冲突。

如果依赖加载失败，比较运行时解释器、架构、动态库搜索路径与锁定清单；模型找不到则检查实际工作目录、挂载、权限与哈希；GPU 初始化失败再拆成驱动、设备可见性和用户态依赖。首次请求失败而启动正常，还需检查懒加载与输入触发的算子路径。

证据包应包含时间、请求或任务 ID、发布版本、已脱敏错误、关键资源状态与最近变更。避免导出整个环境变量或全部配置，把凭据混进排障记录。性能问题继续进入[资源与等待链分析](操作系统高频知识点.md#q-041)，网络问题进入相应章节，不在每章重复一套命令清单。

修复后重新执行原来的失败路径，并补一个代表性业务请求。只看到进程重新出现或日志不再报错，不能证明依赖和结果都恢复正常。

<h2 id="q-050">面试问题：制品签名、SBOM 与构建来源证明如何降低供应链风险？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

部署模型服务时，需要回答“运行的字节是什么、由谁构建、用了哪些依赖、是否经过批准”。digest、签名、SBOM 与 provenance 分别提供不同证据，不能把其中任何一项视为万能安全认证。

digest 标识具体内容，能发现字节变化，但单独拿到一个哈希不知道它是谁发布的。签名把内容与某个密钥或受信身份绑定，验证时必须检查预期签发者、身份、证书和策略，不能只确认“有签名”。SBOM 列出软件组件，便于依赖和漏洞影响分析，但清单可能不完整，也不证明没有漏洞。

构建来源证明记录制品与源码、构建器和构建过程的关系。SLSA 提供相应保证层级与要求；Sigstore/Cosign 等工具可以支持签名与身份验证。其价值依赖受信构建环境和验证策略，攻击者控制构建器后生成的签名并不会自动变成可信代码。

AI 制品还应绑定权重、tokenizer、配置、原生插件和量化 engine 的哈希，避免镜像已验证，运行时又从可变 URL 下载另一份权重。发布清单引用不可变对象，启动时核对，变更后重新评测。

可落地的流程是：受控提交触发构建，产生镜像与清单，验证后签名，在部署入口校验身份、digest 和策略，再保留运行记录。准入失败应有明确诊断和回退路径。供应链证据帮助判断来源与过程，功能、数值与权限测试仍需独立完成。

<h2 id="q-051">面试问题：背压、准入控制与结构化并发怎样防止服务在高负载下失控？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

请求到达速度长期超过处理能力时，队列必然增长。无限增加协程或后台任务，只会把等待转成内存占用、超时与重复工作。准入控制决定接收多少工作，背压把下游压力传回上游，结构化并发则管理一组子任务的生命周期。

先为入口并发、任务队列、模型在途请求和输出缓冲设置容量。达到限制时明确拒绝、降级或返回可稍后查询的任务，而不是继续接收后在后台丢失。限制应按实际成本设计，长上下文与短请求不能只按同一个 QPS 等价计费。

稳定系统中 Little 定律可写成 `平均在途数量 = 到达率 × 平均逗留时间`，单位与统计范围必须一致。它能帮助检查容量和等待关系，但不保证任意突发流量下队列稳定，也不能直接推出 P99 延迟。靠加大超时容纳积压，往往只是让在途数量继续增长。

结构化并发把子任务限制在明确作用域内，父任务退出时等待或取消子任务，异常有清晰传播路径。例如同时检索两个独立来源，超时后应回收未完成任务，而不是让它们脱离请求继续耗费连接。取消仍需客户端与下游协作，不能撤销已经发生的外部副作用。

端到端 deadline 应在各阶段扣减，重试另有预算。输出流遇到慢客户端时，有界缓冲会迫使生产者减速或停止。监控排队长度、等待分位数、拒绝比例与取消后的资源释放，才能判断系统是在受控降级，还是只是表面上仍然接收请求。
