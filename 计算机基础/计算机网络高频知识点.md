<h1 id="q-001">1.协议分层与传输语义</h1>

<h2 id="q-002">面试问题：TCP/IP 四层模型怎样解释一次网络请求？</h2>

<a id="1.tcpip四层模型的相关概念"></a>

<a id="user-content-1.tcpip四层模型的相关概念"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

TCP/IP 分层把一次通信拆成几个职责明确的问题：应用要交换什么、数据怎样交给远端进程、包怎样跨网络到达目标、当前这一跳怎样发出去。理解这些职责，排障时才能知道“失败发生在哪一层”。

<div align="center">

| 层次 | 解决的问题 | 常见对象 |
| --- | --- | --- |
| 应用层 | 定义消息格式与业务语义 | HTTP、DNS、SSH |
| 传输层 | 在端点间传输数据，按端口分用 | TCP、UDP；QUIC 在 UDP 上实现传输能力 |
| 网际层 | 寻址和跨网络转发 | IPv4、IPv6、ICMP |
| 链路层 | 在当前链路上传输帧，并完成介质接入 | 以太网、Wi-Fi；四层模型通常将物理传输归入此层 |

</div>

以 HTTP/1.1 over TLS 为例，应用先生成 HTTP 消息，TLS 对应用数据提供机密性和完整性保护，TCP 将其作为字节流传输；IP 包携带源、目的 IP，链路层再把包封装为当前链路上的帧。经过路由器时，下一跳的链路层地址会变化，IP 负责继续选择路径。遇到 NAT，IP 地址和端口也可能被改写。

接收端逐层解析相应头部并分发数据，这叫**解封装**。只有真正启用了 TLS、IPsec 等保护的层次才涉及解密；增加 TCP、IP 或以太网头部本身不会让内容保密。ARP 用于 IPv4 本地链路上的地址解析，通常放在链路层或层间讨论，不能把它当成跨网路由协议。

分层也不是现实系统的硬边界。QUIC 把流、可靠性与 TLS 握手结合起来，代理可能终止连接再建立新连接。排障时仍可用这张地图：域名解析成功不代表 TCP 可达，TCP 建立不代表证书通过，HTTP 返回成功也不代表生成任务已经执行完毕。

<h2 id="q-003">面试问题：OSI 七层模型有什么用？与 TCP/IP 如何对应？</h2>

<a id="2.osi七层模型的相关概念"></a>

<a id="user-content-2.osi七层模型的相关概念"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

OSI 是分析网络职责的参考模型。它把通信拆得更细，方便描述设备、协议和故障的位置，但互联网软件通常并不严格实现七个独立模块。

<div align="center">

| OSI 层 | 主要职责 | 与 TCP/IP 的大致对应 |
| --- | --- | --- |
| 7 应用层 | 应用服务的通信语义 | 应用层 |
| 6 表示层 | 数据编码、表示转换等 | 常由应用库、序列化库等完成 |
| 5 会话层 | 会话建立、维护、恢复 | 常融入应用协议与运行库 |
| 4 传输层 | 端到端传输与分用 | 传输层 |
| 3 网络层 | 逻辑寻址与路由 | 网际层 |
| 2 数据链路层 | 成帧、本地链路寻址与介质接入 | 链路层 |
| 1 物理层 | 比特对应的电、光、无线信号 | 链路层包含的物理基础 |

</div>

例如模型请求超时：网线未连接偏向物理层问题；VLAN 隔离可能阻断链路访问；路由错误影响 IP 可达性；连接被拒绝涉及传输端点；鉴权失败、参数不合法则发生在应用层。一个“网络超时”字符串不能直接指出是哪一层，必须结合具体观测。

“四层负载均衡”通常依据地址、端口等信息分发连接；“七层负载均衡”可以理解 HTTP 路径、Header 等应用内容。后者若要路由 HTTPS 中的路径，通常需要终止 TLS 或依赖其他能看到明文的组件。直接透传加密流量的设备看不到完整 HTTP 内容。

不要把 TLS 永远钉死在 OSI 某一层，再由层号推导全部行为。TLS 与 HTTP、QUIC 的组合方式不同；工程上更有价值的问题是：谁建立连接、谁能读明文、谁负责认证、谁保留状态。七层模型帮助提出这些问题，不能代替查看实际的数据路径。

<h2 id="q-004">面试问题：TCP 和 UDP 有什么区别？可靠传输是否等于业务成功？</h2>

<a id="3.tcp和udp的区别？"></a>

<a id="user-content-3.tcp和udp的区别？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

TCP 提供连接内可靠、有序的字节流；UDP 提供尽力交付的数据报。两者的差异主要在**传输语义与机制由谁承担**，不能简单归结为“TCP 慢、UDP 快”。

<div align="center">

| 维度 | TCP | UDP |
| --- | --- | --- |
| 数据边界 | 字节流，不保留应用每次写入的边界 | 保留数据报边界，但接收缓冲过小可能截断 |
| 可靠性 | 序号、确认、重传、去重和有序交付 | 协议本身不保证到达、顺序或去重 |
| 控制机制 | 接收窗口控制流量，拥塞控制约束发送 | 应用或上层协议须承担相应控制 |
| 连接状态 | 需要建立与维护连接 | 协议层无握手；socket 的 connect 仍可记录默认对端 |
| 报头 | 最小 20 字节，可带选项 | 8 字节，不包含 IP 头 |

</div>

TCP 的“可靠”是有条件的服务承诺：在连接能够继续工作时，把已接收数据按序交给应用；遇到持续故障，连接仍会超时或报错。发送端 `write()` 成功可能只代表数据进入本机缓冲；收到 TCP ACK 也通常只说明对端协议栈接收了字节，无法证明数据库提交、账单扣款或视频生成已经完成。

UDP 适合允许部分丢失、重视时效性的消息。例如过期的实时音频包可能没有重传价值。但应用仍需控制速率、处理抖动与拥塞，不能因 UDP 自身没有拥塞控制就无限发送。QUIC 运行在 UDP 上，却自行提供可靠流和拥塞控制；“底层用 UDP”不意味着上层服务不可靠。

TCP 连接通常由源地址、源端口、目的地址、目的端口区分，并结合传输协议形成常说的五元组。UDP 可以用于单播、组播，以及受网络限制的 IPv4 广播，但“支持一对多”不等于跨互联网广播可用。选型应先确定消息能否丢失、能否过期、是否需要顺序，以及现有客户端和网络设备支持什么。

<h1 id="q-030">2.服务器访问与数据传输</h1>

<h2 id="q-005">面试问题：如何配置两台服务器之间的 SSH 密钥登录？</h2>

<a id="4.如何让两台服务器之间ssh免密通信？"></a>

<a id="user-content-4.如何让两台服务器之间ssh免密通信？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

SSH 密钥登录验证的是：客户端是否持有某个公钥对应的私钥。私钥留在发起连接的一端，目标账号的 `authorized_keys` 保存允许登录的公钥。A 能登录 B 与 B 能登录 A 是两个独立授权关系，不需要把双方私钥复制到一起。

下面以 A 上的普通用户连接 B 的 `deploy` 用户为例，`server-b.example` 是待替换的示例主机名：

```bash
# 在 A 上生成专用密钥；已有同名文件时不要覆盖
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_deploy -C "deploy-to-server-b"

# 将公钥安装到 B 的 deploy 账号，需要已有合法登录方式
ssh-copy-id -i ~/.ssh/id_ed25519_deploy.pub deploy@server-b.example

# 使用对应私钥发起连接
ssh -i ~/.ssh/id_ed25519_deploy deploy@server-b.example
```

首次连接要通过可信渠道核对 B 的主机密钥指纹。主机密钥证明“连接的是哪台服务器”，用户公钥证明“谁有资格登录”，两者不能混为一谈。更换主机密钥时应先查明原因，不能把关闭 `StrictHostKeyChecking` 当成日常修复方法。

交互使用可给私钥设置口令，并通过 `ssh-agent` 暂存解锁状态。自动任务应使用专用账号和受限凭据，按需要限制来源、可执行命令与转发能力；不是所有自动化都必须使用无口令、全权限 root 密钥。Ed25519 在某些合规或旧系统环境中不可用时，按组织策略选择现代 RSA 等受支持算法，避免照搬旧 DSA 配置。

如果公钥正确却仍被拒绝，检查目标账号、目录属主、`~/.ssh` 与 `authorized_keys` 权限，以及服务端认证日志。常用目录权限是 700、文件权限是 600，还要避免上级目录可被他人任意写入。`ssh -v` 有助于确认客户端实际提供了哪把密钥，排查时注意不要外传包含敏感路径和账号的日志。

<h2 id="q-006">面试问题：两台 Linux 服务器传文件，scp、rsync、sftp 应该怎么选？</h2>

<a id="5.两个Linux服务器之间数据传输的命令有哪些？"></a>

<a id="user-content-5.两个Linux服务器之间数据传输的命令有哪些？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

偶尔复制一个文件可用 `scp`，重复同步目录优先考虑 `rsync`，需要交互式浏览与上传下载可用 `sftp`。先确定数据是否允许覆盖、是否需要断点恢复和校验，再选择工具。

```bash
# 单文件复制，-P 是远端 SSH 端口
scp -P 2222 model.bin deploy@server-b.example:/srv/models/incoming/

# 先预览目录同步；源目录末尾的 / 表示同步其内容
rsync -avhn -e 'ssh -p 2222' ./models/ deploy@server-b.example:/srv/models/incoming/

# 检查预览后执行，保留中断时的部分文件以便后续处理
rsync -avh --partial --info=progress2 -e 'ssh -p 2222' ./models/ deploy@server-b.example:/srv/models/incoming/

# 交互式传输
sftp -P 2222 deploy@server-b.example
```

现代 OpenSSH 的 `scp` 默认使用 SFTP 协议传输；命令名称保留，并不代表仍使用旧 SCP 线协议。`rsync` 经 SSH 工作时，两端通常都要安装 rsync；daemon 模式又有不同的认证与传输配置，不能假定自带 SSH 加密。

rsync 默认用大小和修改时间判断哪些文件可能变化，再按传输模式应用增量算法；它不会无条件扫描每个文件的完整内容。需要内容级比较时可用 `--checksum`，但会增加读盘和计算成本。`-a` 保留一组常用文件属性，不包含所有 ACL、扩展属性或硬链接需求；`--delete` 会删除目标侧多余文件，应在确有镜像需求时结合 dry-run 使用。

大模型权重常已是较紧凑的二进制内容，开启压缩未必更快。若源文件正在变化，传输成功也可能得到不一致快照。发布时宜传到独立临时目录，依据可信清单校验 SHA-256，再由发布流程切换模型版本；哈希只能验证与清单一致，清单本身的可信来源仍需保证。中断续传也须确认远端对象版本未变，不能把旧文件前半段与新文件后半段拼接。

<h2 id="q-007">面试问题：AI 项目访问云端失败，怎样区分网络故障与服务错误？</h2>

<a id="6.在AI项目中，从云端读取传输信息失败，显示网络不可用，一般可以怎么解决呢？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

先保存原始错误、目标地址、发生时间和请求 ID，再按请求走过的路径定位。SDK 统一包装的“网络不可用”可能来自解析、连接、TLS、代理，也可能只是鉴权失败或服务限流。

<div align="center">

| 观察到的现象 | 能支持的判断 | 下一步 |
| --- | --- | --- |
| 域名无法解析 | 当前解析路径没有得到可用结果 | 查域名、DNS 配置、代理的解析位置 |
| 连接被拒绝 | 路径上某节点明确拒绝了连接 | 查监听地址、端口、转发与拒绝规则 |
| 连接超时 | 规定时间内没有完成连接 | 查路由、丢包、过滤与目标负载，不能单凭超时定性 |
| TLS 证书错误 | 安全握手未通过校验 | 查主机名、系统时间、CA 与证书链 |
| 401/403 | 返回响应的组件拒绝认证或授权 | 查凭据、权限、签名或代理限制 |
| 429/503 | 返回响应的组件限流或暂不可用 | 结合 Retry-After、配额、服务状态和幂等条件处理 |

</div>

可先对不含敏感信息的健康地址做一次有界请求：

```bash
curl --connect-timeout 5 --max-time 20 -sS -o /dev/null \
  -w 'http=%{http_code} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first=%{time_starttransfer} total=%{time_total}\n' \
  https://api.example.com/health
```

这些时间是从开始请求起算的累计节点，不能全部直接相加；连接复用和代理路径也会改变解释。某些服务不支持 HEAD，因此 `curl -I` 失败不能直接证明 GET 不通。HTTP 状态码还可能由代理或网关产生，需要看返回来源和链路日志。

检查环境变量代理、SDK 专属代理、容器内部地址以及 `NO_PROXY` 是否一致。连接 HTTP 代理访问 HTTPS 目标时，代理 URL 经常仍是 `http://...`，目标 URL 的 scheme 不能直接决定代理协议。不要用关闭证书校验掩盖问题；对未知结果的付费提交也不要无条件重试。具体重试语义见[超时与幂等](#q-051)，分层连通性检查见[网络诊断](#q-019)。

<h2 id="q-008">面试问题：AI 服务之间通信，最重要的设计约束有哪些？</h2>

<a id="7.在AI行业中两个服务器之间的通信有哪些注意事项？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

服务器间通信需要同时处理三种差异：两端处理速度不同、状态提交时间不同、故障发生位置不同。连接能建立，只解决了其中很小一部分。

以“网关提交视频任务，GPU 服务生成，结果写入对象存储”为例，先把控制信息与大数据分开。任务消息传递模型版本、输入引用和任务 ID；大型视频或权重通过适合断点恢复、校验的存储通道传输。把几 GB 数据塞进频繁重试的 RPC，会放大内存、超时与重复传输成本。

其次确定接口契约：字段单位、编码、张量布局、模型版本、兼容策略与错误码必须明确。二进制序列化能减少部分体积和解析开销，但序列化协议不能自动保证数值含义一致。双方都把一个字段解码成整数，并不意味着一方的毫秒与另一方的秒能够互换。

再规定失败后的动作。调用方要传递 deadline 和请求身份；执行方要限制队列与并发，明确任务取消和结果查询机制。长任务可先持久化任务记录，再返回任务 ID，客户端通过查询或事件获取结果。队列投递、数据库提交和对象存储写入跨越不同系统时，还需要幂等、Outbox 或补偿策略，不能由 TCP 或消息队列名称直接推导“恰好执行一次”。

最后处理身份、权限与观测。TLS 保护某段传输，mTLS 可验证两端证书，但业务授权仍需检查调用者可以访问哪个租户、模型和数据。TLS 在网关终止后，后半段链路是否加密要单独确认；静态存储加密也是另一项职责。日志、指标和 trace 应能关联同一任务，并避免记录原始密钥与敏感输入。

跨地域或边缘网络下，要把带宽、往返时间、断线窗口与数据驻留要求纳入方案。压缩、并行分片和缓存只有在对应瓶颈存在时才有收益；协调元数据可以使用一致性系统，大模型权重的分发则需要版本化存储，不能指望 Raft 自动同步全部模型文件。

<h1 id="q-031">3.地址、接口与名称解析</h1>

<h2 id="q-009">面试问题：0.0.0.0、127.0.0.1 和 0.0.0.0/0 分别表示什么？</h2>

<a id="8.介绍一下计算机中“0.0.0.0”ip地址的意义"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

`0.0.0.0` 的含义取决于使用位置。作为服务器的 IPv4 绑定地址，它表示通配本机 IPv4 地址；作为未配置主机在特定协议中的源地址，它表示尚未指定地址；`0.0.0.0/0` 则是一个匹配全部 IPv4 地址的网段，常用于默认路由。

<div align="center">

| 写法 | 常见语境 | 需要注意的边界 |
| --- | --- | --- |
| `127.0.0.1:8000` | 仅绑定本机回环地址 | 同一网络命名空间内访问 |
| `0.0.0.0:8000` | 在本网络命名空间中通配 IPv4 本地地址 | 可达性仍受路由、防火墙、映射约束 |
| `0.0.0.0/0` | 默认路由、访问控制中的全地址范围 | 更具体路由按最长前缀匹配优先 |
| `[::]:8000` | IPv6 通配绑定 | 是否兼容 IPv4 取决于系统与 socket 配置 |

</div>

例如在远程服务器上把 API 绑定为 `127.0.0.1`，本机 curl 能访问，另一台机器却访问不到。改为通配绑定后，服务有机会接受其他接口来的连接，但仍需确认云安全组、宿主机规则与容器端口发布。`0.0.0.0` 不是给远端客户端使用的正常目标地址；客户端应连接服务器的实际 IP 或域名。

容器中的 `127.0.0.1` 指向容器自身所在的网络命名空间，通常不指向宿主机。容器里监听 `0.0.0.0` 也不自动等于向公网开放，宿主机映射和网络拓扑会决定访问范围。反过来，容器发布端口时若宿主机绑定全部地址，原本只想本地调试的服务也可能被外部访问。

因此排查这类问题要同时看三个地址：进程绑定地址、客户端连接地址、网络转发后的目标地址。只记住“0.0.0.0 等于所有 IP”容易把绑定语义、路由前缀和真实远端地址混在一起。

<h2 id="q-010">面试问题：端口号如何区分网络服务？一个端口能对应多个连接吗？</h2>

<a id="9.什么是计算机中的端口号？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

端口是 TCP、UDP 等传输协议用于分用数据的 16 位编号，范围是 0—65535。它属于通信端点的地址信息，不是进程的永久身份证。一个进程可以使用多个端口，多个进程在特定复用机制下也可以共享监听端口。

服务器通常监听固定地址与端口，客户端由系统分配临时端口。若客户端 `192.0.2.10:53000` 连接服务器 `198.51.100.20:443`，双方的地址、端口及传输协议共同标识通信流。服务器的 443 端口可以同时服务大量客户端，因为远端地址和端口不同；不能把一个监听端口理解成只能接待一个用户。

<div align="center">

| 端口区间 | IANA 分类 | 实际使用中的注意点 |
| --- | --- | --- |
| 0—1023 | System Ports | 0 在 socket bind 中常表示请系统自动分配；低端口权限依系统配置而定 |
| 1024—49151 | User Ports | 注册用途是约定，不代表进程身份已验证 |
| 49152—65535 | Dynamic / Private Ports | 操作系统实际临时端口范围可以不同 |

</div>

TCP 443 和 UDP 443 是不同的协议端点，例如 HTTPS 可以使用 TCP，也可通过 HTTP/3 使用 UDP 上的 QUIC。常见默认端口还有 SSH 22、DNS 53、HTTP 80、PostgreSQL 5432，但应用可修改监听端口；看到 443 不能直接推断内容一定是安全 HTTP。

“端口开放”至少涉及进程是否监听、监听在哪个地址、网络策略是否允许到达。客户端连接很多却失败，还可能耗尽临时端口、文件描述符或 NAT 连接表。此时增加服务端监听端口数量未必有效，要先明确耗尽的是哪一类资源。`ss -ltnp` 适合看 TCP 监听，`ss -tan` 可继续看连接状态，两者回答的问题不同。

<h2 id="q-011">面试问题：一次 AI API 请求怎样从客户端到达模型服务？</h2>

<a id="10.介绍一下AI行业中API的原理与作用"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

API 是软件间约定的操作与数据契约，既可以是本地函数接口，也可以是远程服务接口。远程 AI API 通常定义端点、认证方式、输入输出、错误语义和生命周期；HTTP 只是常用承载方式之一。

以一次 HTTPS 生成请求为例，客户端解析域名、建立或复用连接、完成安全握手，然后发送方法、路径、请求头与正文。网关校验身份、权限、参数与配额，按模型版本路由到服务。服务可能直接推理，也可能先排队，再返回完整结果、流式事件，或供后续查询的任务 ID。

这条链上存在多种“成功”：HTTP 连接成功、请求被接受、任务持久化、推理完成、结果可下载。比如 `202 Accepted` 通常表示已接受处理，不能当作结果已经完成；`200 OK` 的具体业务含义也要结合接口契约。客户端应读取约定的任务状态和错误字段，不能仅凭一个状态码认定整条业务链完成。

一个可靠契约至少需要交代：

1. **输入边界**：支持格式、大小、编码、字段单位、模型参数范围，以及未知字段如何处理。
2. **任务身份**：请求 ID 用于追踪，幂等键用于识别重复操作，两者的职责不完全相同。
3. **时间语义**：连接、读取和总 deadline；取消后是否仍可能产生费用或结果。
4. **兼容与授权**：字段演进、版本固定、租户范围；持有 API Key 不代表可以访问所有资源。
5. **结果生命周期**：生成文件的有效期、下载权限、回调认证、失败后如何查询与恢复。

Bearer token 是持有即可使用的凭据，需避免进入 URL、前端公开代码和原样日志。OAuth 主要解决授权委托，不会自动让一个设计不当的接口安全。API 的长期价值在于把模型能力变成可调用、可观测、可恢复的服务边界，而不是把一个推理函数简单包成 HTTP。

<h2 id="q-012">面试问题：HTTP 与 SSH 有什么异同，能按“效率”和“安全性”直接二选一吗？</h2>

<a id="11.计算机中http协议与ssh协议有哪些异同？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

HTTP 定义请求、响应、资源与缓存等语义，SSH 提供经过认证的安全通道，并在其中承载远程命令、终端、文件传输或端口转发。两者服务于不同接口需求，不能用“HTTP 快、SSH 安全”作为选型依据。

<div align="center">

| 比较项 | HTTP / HTTPS | SSH |
| --- | --- | --- |
| 常见用途 | 网页、API、内容分发、流式响应 | 远程管理、SFTP、隧道 |
| 安全机制 | HTTPS 使用 TLS；认证授权由协议机制和应用共同实现 | 协议包含服务端认证、用户认证与加密通道 |
| 身份校验 | 常见为 CA 证书和主机名，也可配置 mTLS | 常见为主机密钥、用户公钥或密码等 |
| 传输 | HTTP/1.1、HTTP/2 通常基于 TCP；HTTP/3 基于 QUIC | 常见 SSH 实现基于 TCP |
| 接口形态 | 资源操作、方法、状态码与消息体 | 多个逻辑 channel 承载终端、命令、转发等 |

</div>

HTTP 的无状态语义不等于服务器无法识别用户，也不等于底层连接没有状态。Cookie、token、服务端会话都能建立应用身份；HTTP/2 还会维护连接与流状态。SSH 支持多种认证方式，但“支持密码和公钥”不表示默认要求两者同时通过，多因素认证需明确配置。

分发大规模模型文件时，HTTPS 便于结合对象存储、Range 请求和 CDN；维护服务器、执行受限远端任务时，SSH 更自然。二者都可能使用成熟的对称加密，实际速度取决于实现、CPU、并发、磁盘和链路，不能只按协议名称排序。

通过 SSH 隧道访问内部 HTTP 服务也是常见组合，但加密边界通常到 SSH 远端为止。隧道出口到最终服务的连接若仍是明文 HTTP，那一段不会因为前半段用了 SSH 就自动加密。设计时应画清连接终止位置，再判断哪里需要 HTTPS、访问控制或额外认证。

<h2 id="q-013">面试问题：DNS 怎样完成解析？递归、迭代、缓存与加密分别解决什么？</h2>

<a id="12.介绍一下计算机中DNS（Domain-Name-System）的概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

DNS 是分布式的名称系统。它不只把域名转换成 IP，还保存别名、邮件路由、权威服务器和服务定位等记录。一次访问成功依赖得到合适的记录，但 DNS 不负责保证目标服务健康。

典型流程是应用或系统的 stub resolver 向递归解析器请求最终答案。解析器若没有缓存，通常依次向根、顶级域、权威服务器发起查询，沿转介关系找到答案。客户端请求递归服务，递归解析器在上游进行迭代查询；不能把“客户端自己不断查根服务器”当成普通终端的默认行为。

<div align="center">

| 记录 | 含义 | 工程关注点 |
| --- | --- | --- |
| A / AAAA | IPv4 / IPv6 地址 | 两条网络路径的可用性可能不同 |
| CNAME | 名称别名 | 需要继续解析，最终仍受目标记录和缓存影响 |
| NS / SOA | 区域权威与管理信息 | 判断由谁负责该区域 |
| MX / SRV | 邮件路由 / 指定服务端点 | 客户端必须理解对应记录语义 |
| TXT / PTR | 文本记录 / 反向名称 | TXT 常承载验证信息；PTR 不等于身份凭证 |

</div>

缓存减少查询次数，TTL 约束记录的缓存有效期；负响应也可能被缓存。故障切换时，即便权威记录已更新，客户端仍可能使用缓存或已经建立的连接，因此 DNS 切换不是即时的逐请求调度。根系统有 13 个命名身份，不是全球只有 13 台物理服务器。

DNSSEC 用签名验证 DNS 数据的来源与完整性，不负责隐藏查询内容；DoH、DoT 加密到解析服务的传输，也不能自动证明该解析器可信或所有答案都经过 DNSSEC 验证。这是不同的信任问题。

```bash
dig api.example.com A
dig api.example.com AAAA
getent ahosts api.example.com
```

`dig` 适合检查 DNS，`getent` 更接近 Linux 系统名称服务的实际结果，还可能受 hosts、NSS 等配置影响。浏览器或代理若使用独立 DoH、远端解析，结果可能与终端不同。排查要确定“谁解析、问谁、缓存在哪里”，不能因为某个 DNS 工具返回了 IP，就断定所有应用使用同一地址。

<h1 id="q-032">4.性能、排障与访问控制</h1>

<h2 id="q-014">面试问题：带宽、吞吐量、有效吞吐量和延迟有什么区别？</h2>

<a id="13.介绍一下计算机中带宽的概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

在数字网络的工程语境中，带宽通常指链路可提供的数据传输容量；吞吐量是实际传过的速率；有效吞吐量进一步只计算应用关心的有效数据。延迟描述一项操作需要多久，不能与每秒传多少数据互换。物理通信理论中的带宽还可以指频谱宽度，单位为 Hz，需与 bit/s 的数据率区分。

例如标称 1 Gbit/s 的链路，换算得到 125 MB/s，这是按十进制字节计算的原始速率上限。IP、传输协议、链路封装、重传和共享流量都会占用容量，文件下载速度通常低于该数值。MB 与 MiB 也不同，前者为一百万字节，后者为 2 的 20 次方字节。

若要传送大小为 $`S`$ 字节的数据，理想的持续传输时间下界可写为：

```math
T_{\mathrm{transfer}} \geq \frac{8S}{B}
```

其中 $`B`$ 是可用于该方向的比特率。10 GB 文件在理想 1 Gbit/s 专用链路上至少需要约 80 秒；这没有计入握手、排队、磁盘和校验时间。应用实测有效吞吐量应明确统计口径，例如完整成功下载的字节数除以端到端耗时，不存在统一的“95% 置信区间值就是带宽”的定义。

实时媒体还要区分原始数据率与编码码率。3840×2160、RGB 每像素 24 bit、60 帧/秒的未压缩画面，数据率约为 11.94 Gbit/s；编码后码率依内容、质量和编码器变化，不能沿用未压缩数值。增加并行摄像头时，还要给突发和协议开销留空间。

对模型服务，低请求延迟与高总吞吐可能互相牵制：增大 batch 能提高 GPU 吞吐，却可能增加等待时间。网络、PCIe、内存和显存带宽也属于不同通道，不能把某一张 GPU 的显存带宽当成跨服务器传输速度。应先指出数据经过哪条通路，再讨论带宽是否构成瓶颈。

<h2 id="q-015">面试问题：数据传输速度由哪些因素决定？如何识别真正的瓶颈？</h2>

<a id="14.计算机中数据传输速度和哪些因素有关？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

传输速度取决于整条流水线最慢的持续环节，以及各环节能否有效重叠。源磁盘、CPU 压缩和加密、内存复制、网络、目标解码与写盘都可能限制结果；提高网卡速率不会自动提高端到端吞吐。

<div align="center">

| 环节 | 常见限制 | 有价值的观测 |
| --- | --- | --- |
| 源数据读取 | 小文件元数据开销、随机 I/O、共享磁盘竞争 | IOPS、读延迟、队列和缓存命中 |
| 协议传输 | RTT、丢包、拥塞窗口、接收窗口、链路容量 | RTT、重传、窗口、单流与多流差异 |
| CPU 与内存 | 编解码、加密、复制、NUMA 远端访问 | CPU 分布、内存带宽与热点栈 |
| 目标接收 | 写盘、校验、解压、消费速度 | 写入延迟、缓冲占用、消费者吞吐 |

</div>

一个重要量是带宽时延积 BDP，近似为链路比特率乘 RTT。10 Gbit/s、RTT 为 40 ms 的路径，BDP 约为 400 Mbit，即 50 MB。若想让单条可靠连接充分使用该路径，需要容许足够的数据在途，同时受拥塞控制、接收窗口和实际丢包情况约束；不是把 socket 缓冲改大就一定能跑满。

可以分层测量：先测磁盘和 CPU，再用受控的网络测试判断链路容量，最后跑实际传输。单个大文件快、数十万小文件慢，往往提示元数据与往返开销；单流慢、多流快可能涉及窗口、限流或连接级竞争，也可能只是多流抢到了更多共享带宽。网络测试结果不能替代带鉴权、压缩、存储写入的业务测量。

压缩适合可压缩数据且 CPU 有余量的情况；更多并发会增加争用；零拷贝减少某些复制与系统调用，也不消除所有内存移动。RDMA、GPU Direct 等路径需要硬件、驱动、拓扑与软件配合，收益必须在相同数据规模和部署条件下测量。优化后至少比较有效吞吐、CPU、尾延迟与失败率，避免只看峰值曲线。

<h2 id="q-016">面试问题：HTTP 与 gRPC 应如何比较？为什么不能说“gRPC 替代 HTTP”？</h2>

<a id="15.http网络协议和grpc协议有哪些异同？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

HTTP 是应用层协议，gRPC 是远程调用框架及其协议体系，主流原生 gRPC 使用 HTTP/2 承载调用。因此实际比较通常是“HTTP + JSON 的接口”与“gRPC + Protobuf 的接口”，两者并不处在完全相同的抽象层。

gRPC 通过 IDL 定义服务和消息，生成多语言桩代码，把序列化、调用状态、metadata、deadline 和流式通信纳入统一契约。它支持 unary、客户端流、服务端流和双向流。Protobuf 是常用默认消息格式，字段号是兼容演进的重要身份，删除字段后不应随意复用其编号。

<div align="center">

| 选择维度 | HTTP + JSON 接口 | gRPC 的常见方案 |
| --- | --- | --- |
| 客户端生态 | 浏览器、curl 与第三方集成方便 | 内部跨语言调用与代码生成方便 |
| 契约 | 可用 OpenAPI 等工具约束 | proto 定义与生成代码提供明确结构 |
| 消息 | JSON 易读，但可使用其他表示 | Protobuf 紧凑，需工具解码 |
| 流与控制 | 依赖选定的 HTTP 使用方式与应用约定 | 框架提供 streaming、deadline 等机制 |
| 部署要求 | 入口和代理普遍支持 | 要确认 HTTP/2、trailer、负载均衡和客户端支持 |

</div>

HTTP/2、HTTP/3 使用二进制帧，HTTP 正文也可承载图片或其他二进制内容，所以“HTTP 基于文本，gRPC 才是二进制”并不准确。原生 gRPC 也不是默认可自由切换到裸 TCP、UDP 或 WebSocket；gRPC-Web 等浏览器方案具有自己的代理和能力边界。

性能比较要包括业务计算、序列化、连接复用、消息大小与并发。一次耗时数十秒的生成任务，换消息格式未必显著影响总耗时；高频小消息的内部检索服务则可能更受益于明确契约和低开销。还要检查 gRPC status，不能把 HTTP 200 自动当成 RPC 成功。合理选择来自调用边界和实测，而不是给协议贴上固定的快慢标签。

<h2 id="q-017">面试问题：DoS 与 DDoS 的本质是什么？AI 服务应保护哪些资源？</h2>

<a id="16.介绍一下计算机中DOS攻击的概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

拒绝服务的本质是让合法用户无法获得系统资源。DDoS 强调攻击流量来自分布式来源；DoS 是更广的类别，不必然要求大流量，也不一定需要利用软件漏洞。正常流量突增、重试风暴也可能产生类似的过载结果，排查时需要区分原因。

<div align="center">

| 被耗尽的资源 | 典型现象 | 防护位置 |
| --- | --- | --- |
| 接入带宽与包处理能力 | 链路满载，正常连接也无法进入 | 上游清洗、边缘过滤与容量规划 |
| 连接及协议状态 | 半连接、慢连接或大量长连接占用资源 | SYN 防护、连接限额、阶段超时 |
| 应用计算与存储 | 请求格式合法但计算代价很高 | 身份校验、成本限额、并发控制、缓存 |
| GPU 与任务预算 | 超长上下文、超大图像或大量长任务积压 | token/像素/时长配额、排队上限与准入控制 |

</div>

SYN flood 利用服务端握手状态与资源分配机制施压，SYN cookies 等措施能缓解部分状态耗尽，却不能增加已被塞满的上游带宽。缓慢发送请求或缓慢读取响应，也可能长期占住连接与缓冲，因此需要区分连接、请求头、请求体、空闲与总处理期限。

AI 接口尤其需要按成本限流。同样一秒一个请求，短文本分类与数分钟视频生成的资源开销相差很大。按 IP 限流只能提供一部分保护，还需结合账号、租户、模型、输入规模、并发和全局预算。反向代理接受的转发 IP 头必须来自可信代理，否则客户端可以伪造限流身份；共享出口用户也可能被粗糙的 IP 限流误伤。

扩容、CDN 与负载均衡各有作用，但动态推理结果不能随意跨用户缓存，也不能靠无限扩容吸收成本攻击。系统应能在资源紧张时拒绝新任务、提供可解释的重试信息，并确保管理与恢复通道仍可用。防护效果要在授权的压测中观察正常请求成功率和尾延迟，而不只是阻断数量。

<h2 id="q-018">面试问题：上行和下行带宽如何影响下载、上传与服务器间通信？</h2>

<a id="17.计算机服务器的上行带宽与下行带宽对数据传输速度的影响？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

上行和下行是相对于观察对象而言的。客户端从服务器下载文件时，是服务器发送、客户端接收；若站在服务器角度，主要消耗上行，站在客户端角度则消耗下行。同一段传输换一个观察位置，方向名称就会改变。

对 A 向 B 传输，持续速率受 A 的可用发送能力、B 的可用接收能力、沿途瓶颈和其他处理环节共同限制。比如 A 上行 200 Mbit/s，B 下行 1 Gbit/s，途中可用容量 100 Mbit/s，那么在其他条件理想时也只能以不超过 100 Mbit/s 的速率传送，即约 12.5 MB/s。

<div align="center">

| 业务 | 主要数据方向 | 容易遗漏的因素 |
| --- | --- | --- |
| 用户下载生成视频 | 服务端或对象存储 → 用户 | 服务端出口被多用户共享 |
| 上传训练素材 | 用户 → 服务端或对象存储 | 用户上行、服务端入口与写盘 |
| 双向实时语音 | 两端持续互发 | 抖动、丢包、排队和时限 |
| 跨区域复制权重 | 源区域 → 目标区域 | 跨区路径容量、费用和存储速度 |

</div>

1 Gbit/s 出口被 100 个下载连接共享时，不能保证每个连接平均分得 10 Mbit/s，实际还受拥塞控制、RTT、调度与客户端条件影响。20 路每路 5 Mbit/s 的视频也只是恰好用尽 100 Mbit/s 的数学容量，生产规划应预留码率波动、封装与重传空间。

TCP 的接收确认会走反方向，因此反向链路严重拥塞也可能拖慢正向传输。实时游戏、语音和交互 API 的体验通常更依赖 RTT、抖动和排队，不能看到“上行”二字就断定它决定所有延迟。云厂商对公网出入方向、峰值和共享带宽的计费或限额也可能不同，应结合产品定义解释监控值。

<h2 id="q-019">面试问题：怎样用一组有边界的检查定位 Linux 网络问题？</h2>

<a id="18.计算机服务器如何检查网络是否正常？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

网络诊断应让每条命令回答一个具体问题，并明确它不能证明什么。先用真实目标与同一运行环境复现，再从本地配置走向远端服务，避免通过另一个网站的连通性替目标系统下结论。

```bash
# 本机接口与路由；示例 IP 需替换为真实目标
ip -br addr
ip route
ip route get 198.51.100.20

# 应用实际使用的名称解析与具体 DNS 记录
getent ahosts api.example.com
dig api.example.com A
dig api.example.com AAAA

# 目标 TCP 端口与 TLS 握手
nc -vz -w 5 api.example.com 443
openssl s_client -connect api.example.com:443 -servername api.example.com -verify_hostname api.example.com -verify_return_error </dev/null

# 用实际 HTTP 路径检查应用响应
curl --connect-timeout 5 --max-time 20 -v https://api.example.com/health
```

接口显示 UP 不代表公网路由可用；有默认路由也不代表数据一定到达。`nc` 成功通常只说明连接建立；TLS 握手还要检查证书与主机名；HTTP 健康接口成功也不能保证特定模型加载、数据库或任务队列正常。携带凭据的 verbose 输出需脱敏。

`ping` 使用 ICMP，目标或中间设备可能过滤它。ping 失败不能证明 TCP 443 不通，ping 成功也不能证明 API 可用。`mtr` 或 traceroute 中某一跳不回复，可能只是设备限制探测响应；只有结合后续节点与端到端结果，才能讨论该跳是否实际转发异常。

容器、宿主机、Notebook、浏览器和代理可能处在不同网络命名空间或使用不同 DNS 配置，应在出错的进程环境中检查。IPv4 正常而 IPv6 失败时，可分别测试路径；短请求正常而大响应停滞时，需要考虑 MTU、丢包、代理缓冲与读取时限。防火墙检查包括宿主机、容器转发、云安全组和上游策略，不能只看一处 `ufw status`。

最后把证据收敛成可复现描述：哪个源、哪个目标、哪种协议、何时开始失败、在哪一阶段失败、是否仅某一环境发生。这比“外网不通”更有助于下一步定位，也能减少无依据重启网络服务带来的中断。

<h2 id="q-020">面试问题：Linux 端口应该如何管理，怎样避免误杀进程或锁死远程访问？</h2>

<a id="19.Linux系统中如何优雅的进行端口管理？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

端口管理要把服务身份、监听配置与网络访问策略放在一起看。遇到端口占用，先查清进程与所属服务，再决定调整配置或优雅停止；不能把“找到 PID 后 kill -9”写成启动脚本的默认动作。

```bash
# TCP / UDP 监听及进程信息，部分进程详情需要相应权限
ss -ltnp
ss -lunp
ss -ltnp 'sport = :8000'

# 查看 TCP 连接状态，而不只看监听 socket
ss -tan
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

核对进程后，还要查 systemd、容器或其他 supervisor 是否会自动拉起它。直接杀子进程可能立刻被重启，真正需要调整的是服务单元与端口配置。`TIME_WAIT` 是 TCP 连接生命周期的一部分，不是一个等着被杀掉的业务进程；端口复用选项也有各自语义，不能随意打开来掩盖冲突。

防火墙应使用系统已有的管理入口，如 nftables、firewalld 或 ufw，避免几套工具同时改同一组规则。运行配置和持久配置可能不同，容器端口发布还可能涉及独立转发链。确认来源网段、目标接口与 IPv4/IPv6 的访问范围，比仅记录“开放了 8000”更准确。

远程修改 SSH 或管理服务时，应先验证新配置、准备新端口的网络规则，在保留旧会话的同时建立第二条连接验证，再收回旧入口。是否需要 reload 或 restart 取决于服务支持的方式；不能一律先重启，再补放行规则。

systemd socket activation 可以由 systemd 先监听，再把 socket 交给服务，但程序必须支持相应的文件描述符或 inetd 风格接口。`Accept=yes` 与 `Accept=no` 对服务实例方式有不同要求，不是贴一个 `.socket` 文件就能让任意 Python 服务按需启动。日常审计宜记录端口、协议、绑定地址、服务负责人和暴露范围，并从真实访问路径验证，而不是把 localhost 扫描称作“外部视角”。

<h1 id="q-033">5.流式服务与分布式调用</h1>

<h2 id="q-021">面试问题：LLM 服务为什么需要流式传输？SSE、WebSocket、gRPC 流怎么选？</h2>

<a id="20.LLMAIGC服务为什么需要流式传输SSEWebSocketgRPC怎么选？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

流式传输让已经产生的结果尽早到达用户，改善首段可见时间，也便于展示进度与处理中途取消。它不会自动加快模型计算；如果网关或客户端一直缓冲，模型逐 token 输出，用户仍可能最后一次性看到全部内容。

<div align="center">

| 方式 | 交互特点 | 常见合适场景 | 需要补齐的机制 |
| --- | --- | --- | --- |
| SSE | HTTP 响应上的服务端事件流，UTF-8 文本 | 文本输出、任务进度 | 重连恢复、事件编号、认证与取消 |
| WebSocket | 持续双向消息通信 | 实时语音、双向控制、协作 | 消息协议、心跳、背压与恢复 |
| gRPC streaming | 强类型服务流，常基于 HTTP/2 | 网关到内部推理或检索服务 | deadline、取消传播与消费速度控制 |

</div>

标准浏览器 `EventSource` 通常发起 GET，不能像普通 fetch 那样自由指定任意请求体和认证头。许多生成接口用 POST 加 `fetch` 读取流，并按 SSE 格式解析；这不等于浏览器原生 EventSource 的重连机制也会自动生效。

SSE 事件通过空行分隔，同一事件可以有多行 `data:`。一次网络读取可能包含半个事件或多个事件，甚至截断 UTF-8 字符，需要增量解码与缓存完整帧。`id` 与 `Last-Event-ID` 可以协助恢复，但服务端必须真的保存可重放事件，才能避免断线丢失或重复展示。

服务器要及时 flush，代理需正确配置缓冲和空闲超时，心跳应处在协议允许的位置。发生业务错误时，如果 HTTP 响应头已经发出，通常需要通过流内错误事件、约定状态或连接终止表达，而不能事后改成另一个 HTTP 状态码。

客户端取消后，应把信号传到排队任务与推理调度器，释放可释放的资源。已经执行的计算、已提交的外部操作未必能撤销。大文件最终结果通常适合落对象存储，流中返回状态与受控下载地址；把视频完整二进制塞进文本事件会增加编码、缓冲与重试成本。

<h2 id="q-022">面试问题：REST、RPC、gRPC、WebSocket 在 Agent 系统中如何分工？</h2>

<a id="21.RESTRPCgRPCWebSocket在Agent系统中如何分工？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这些名词描述不同层面的设计选择：REST 是架构风格，RPC 是远程调用抽象，gRPC 是具体框架，WebSocket 是双向通信协议。把它们看成四个完全互斥的产品选项，会错过真正需要设计的服务边界。

以一个带检索和工具调用的 Agent 为例，外部用户提交任务、查询状态、下载结果，可用清晰的 HTTP 资源接口；网关调用内部 embedding 或 rerank 服务，可用带明确消息契约的 gRPC；浏览器接收文字可用 SSE，需要不断发送音频和中断事件时可用 WebSocket。长时间沙箱任务还可能通过消息队列异步交付结果。

<div align="center">

| 边界 | 优先考虑的问题 | 常见选择 |
| --- | --- | --- |
| 第三方集成与公开接口 | 易调试、兼容、权限与版本演进 | HTTP API；是否完整遵循 REST 另行判断 |
| 内部稳定服务契约 | 类型、语言、延迟、deadline | gRPC 或团队已有的 RPC 体系 |
| 浏览器双向实时交互 | 连续输入、事件顺序、断线恢复 | WebSocket |
| 后台长任务 | 持久化、重试、积压与消费状态 | 任务 API + 消息系统或状态查询 |

</div>

HTTP 返回 JSON 并不自动构成 REST；RPC 也不等于高性能，更不等于本地函数调用。远程调用会出现部分失败：服务端已经执行，客户端却没收到结果。因此接口必须显式处理时间预算、幂等、取消和版本兼容，不能让生成的客户端桩把这些问题隐藏掉。

Agent 的模型层可以选择要调用的工具，执行层仍要验证身份、参数与权限。协议只负责把消息送到边界，无法替代工具授权。选择时还应把团队的代理支持、日志追踪、故障定位与运维成本算进去：低频管理接口未必需要新增一套 RPC 栈，同一个 WebSocket 也不应无限承载所有大文件与后台任务。

<h2 id="q-023">面试问题：TCP 字节流、心跳、重连和背压怎样影响模型服务？</h2>

<a id="22.TCP粘包心跳重连和背压在模型服务中有什么影响？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

TCP 交付的是有序字节流，应用两次 `send()` 不保证对应两次 `recv()`。一个消息可能被分多次读取，多个消息也可能一次读到；所谓“粘包、拆包”通常是应用没有正确处理消息边界，并非 TCP 把数据传坏。

自定义协议可使用固定长度、分隔符或长度前缀。例如先发送 4 字节网络字节序长度，再发送正文，接收方需要循环读取直到收齐相应字节，并设置最大允许长度。否则一个异常长度就可能诱导巨额内存分配。使用 HTTP、WebSocket 或 gRPC 时，交由成熟协议实现解析边界，业务层继续验证消息内容和大小。

心跳用于在规定时间窗口内判断连接或对端是否仍有响应。TCP keepalive、WebSocket Ping/Pong、应用心跳所证明的范围不同：能回答心跳不意味着 GPU 任务没有卡住；没收到心跳也可能只是网络或调度延迟。超时阈值应结合正常尾延迟与误判代价设置。

重连只恢复传输通道，不能恢复业务进度。客户端需要事件序号、任务 ID 或确认游标才能知道从哪里继续，服务端则需明确重放窗口和去重策略。重连时采用有上限的退避与随机抖动，避免所有客户端在同一时刻冲击刚恢复的服务。

背压处理“生产快、消费慢”的矛盾。TCP 接收窗口可以限制网络发送，但如果模型仍持续生成并塞入应用队列，内存仍会增长。应限制每连接和全局缓冲，决定暂停生产、合并非关键进度、取消任务或让慢消费者重连；不能任意丢弃影响语义的 token。

流式生成还需考虑资源之间的牵连：一个慢客户端占着长上下文状态，可能让其他请求无法进入。网络缓冲上限、调度队列与模型取消机制要共同设计，具体准入和结构化并发见[工程基础](计算机工程基础高频知识点.md#q-051)。

<h2 id="q-024">面试问题：DNS、CDN、负载均衡与 API Gateway 分别负责哪段稳定性？</h2>

<a id="23.DNSCDN负载均衡和API-Gateway对AI服务稳定性有什么作用？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

这些组件分别处理入口定位、内容分发、实例分流与应用治理。它们可以由同一个产品组合提供，但故障语义与状态边界仍然不同。

<div align="center">

| 组件 | 主要职责 | 对 AI 服务的限制 |
| --- | --- | --- |
| DNS | 将名称映射到入口 | 缓存与已有连接使切换不能瞬间完成 |
| CDN | 在边缘缓存和分发适合缓存的内容 | 个性化、鉴权响应不能随意共享缓存 |
| 负载均衡 | 把连接或请求分配给可用实例 | 长连接、模型版本和设备容量影响调度 |
| API Gateway | 认证、配额、路由、协议处理与观测 | 不能代替数据库授权和后端最终资源控制 |

</div>

一次生成请求可以先经过 DNS 找到入口，再由网关鉴权与分配租户预算，负载均衡选择已经加载目标模型的实例。生成结果写入对象存储后，可由 CDN 分发。这样拆开后，文本流和视频下载不用争夺同一套长连接与内存缓冲。

健康检查要区分进程活着、实例能接新请求、模型已加载且依赖可用。只探测端口开放，可能把流量送到仍在加载权重的实例；过于敏感的健康检查又可能在短暂抖动时摘掉过多节点。发布时还需连接排空：停止接受新任务，让已有流在限定时间内完成或按契约迁移。

AI 负载均衡不能只按请求数平均。不同上下文长度、生成长度、分辨率与模型版本的代价不同，还要看排队时间、活跃序列、KV Cache 和 GPU 余量。依赖会话状态的请求可能需要路由亲和性，但这会降低调度灵活性，应有状态恢复方案。

网关、SDK 和内部 RPC 若同时自动重试，会把一次失败放大成多次执行。共享缓存也需正确区分身份、请求内容与版本，签名 URL 不能被当作任意公开文件。稳定性来自各层明确的职责和一致的限制，不是堆叠组件数量。

<h2 id="q-025">面试问题：Agent 的 Prompt Injection 与 SSRF 有何区别？工具执行怎样建立安全边界？</h2>

<a id="24.Prompt-Injection和网络安全在Agent工具调用中如何防护？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Prompt Injection 试图通过不可信内容改变模型的指令判断；SSRF 则是让服务端代替请求者访问其可到达的网络资源。Agent 读取网页后自动调用工具，可能把两者串在一起：网页诱导模型请求某个 URL，执行器再访问了本不应暴露的内网服务。

提示词可以帮助模型识别风险，但关键限制必须由执行器和网络层实施。模型只提出调用意图，执行器依据真实调用者、工具定义、资源权限与预算决定是否执行。网页文本、检索结果和工具返回内容都不应获得修改系统权限的能力。

URL 访问需要比“检查字符串前缀”更严格的处理：限定协议和必要目标，使用一致的解析方式，检查 IPv4、IPv6 与解析后的地址，阻断不被允许的回环、私网、链路本地和云元数据地址；重定向后重新验证目标，并处理 DNS rebinding 导致的校验与实际连接不一致。仅检查域名第一次解析出的一个 IP 不能覆盖这些情况。

工具凭据按租户、资源和操作分配，避免把通用高权限 token 放进所有 Agent 的上下文。文件操作需校验实际解析路径及符号链接后的访问范围；SQL 使用参数化查询并依赖数据库授权；命令执行优先结构化参数与受控程序入口。统一“做转义”无法替代不同解释器的安全规则。

高影响操作应绑定明确授权与可审阅参数，审计记录包含调用身份、目标、参数摘要和结果，但不能原样存储密钥。沙箱还需限制出站网络、文件系统、执行时间和资源；容器隔离并不自动给出全部这些策略。

这两类攻击都要用真实执行结果评估：模型是否识别了恶意文字只是一个信号，更关键的是执行器能否阻止越权请求、网络是否真正隔离、日志是否可追溯。具体 Agent 提示与上下文设计属于 Agent 板块，本题关注外部内容跨入工具和网络时的系统边界。

<h2 id="q-050">面试问题：HTTP/3 与 QUIC 解决了什么问题？为什么仍可能出现阻塞与重试风险？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

HTTP/3 将 HTTP 语义映射到 QUIC，QUIC 在 UDP 上实现安全连接、可靠流、流量控制和拥塞控制。它的跨周期价值在于重新划分传输层的职责，让多路复用、丢包恢复和安全握手更紧密地配合，而不是简单“把 TCP 改成 UDP”。

HTTP/2 可以把多个请求复用到一条 TCP 连接，但 TCP 向上交付一个有序字节流。当前面一段字节丢失时，即使后续字节属于另一个 HTTP/2 流，也要等缺口恢复后才能按序交付，这构成传输层的跨流队头阻塞。

QUIC 为不同流维护可靠有序交付。流 A 的数据缺失，不必阻止流 B 已完整收到的数据交给应用；但同一流内仍需等待缺失字节，多个流仍共享连接级拥塞控制和链路容量。HTTP/3 的头部压缩依赖或业务层顺序关系也可能引入等待，所以不能宣称它消除了所有队头阻塞。

QUIC 使用 TLS 1.3 建立安全上下文，并可在有既往会话信息时使用 0-RTT 提前发送数据。0-RTT 具有重放风险，不应把产生不可重复副作用的请求仅因“连接加密”就放心放入早期数据。业务幂等与防重放策略仍然重要。

连接 ID 让连接身份不必完全绑定原来的网络地址与端口，配合路径验证，可支持客户端地址变化后的连接迁移。但是否允许主动迁移、负载均衡如何路由连接 ID、网络是否放行 UDP，都影响实际结果；它不等于任意服务端地址之间都能无缝迁移。

部署 HTTP/3 时应同时观察握手成功率、丢包下的尾延迟、CPU、UDP 可达性和回退行为。只开放 TCP 443 的网络可能使 QUIC 失败；成熟客户端的回退能缓解可达性问题，但掩盖问题前仍应知道实际用了哪种协议。依据 RFC 9000 与 RFC 9114 掌握这些机制，比记忆某个浏览器版本的默认开关更有长期价值。

<h2 id="q-051">面试问题：超时、重试、幂等与“结果未知”应怎样一起设计？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

远程调用超时只说明调用方没有在预算内拿到期望结果。请求可能尚未发出、正在执行，也可能已经提交成功而响应丢失。尤其是扣费、创建任务、发消息等操作，必须先处理这种不确定性，再决定是否重试。

时间控制应区分连接超时、连续读取等待、空闲超时和总 deadline。一个每次读取都在超时前收到少量数据的流，可能一直持续下去，因此 read timeout 不能自动限制整个任务的总时长。调用链要向下传递剩余预算，避免每一层重新给自己完整的 30 秒。

<div align="center">

| 状态 | 合理动作 |
| --- | --- |
| 确认请求未被应用 | 在剩余预算内重试 |
| 明确的限流或暂不可用 | 按接口契约、Retry-After 与幂等条件决定是否重试 |
| 请求可能执行，但没有结果 | 用任务 ID、幂等键或业务键查询与恢复 |
| 确定的参数、认证、权限错误 | 修复原因，重复相同请求通常无效 |
| 流已部分返回 | 根据事件游标和恢复协议处理，不能默认从头重复业务 |

</div>

幂等表示同一操作重复执行，对目标业务状态的预期效果与执行一次相同，不要求每次响应字节完全一致。HTTP 的 PUT、DELETE 等具有幂等语义约定；POST 也能通过业务设计实现幂等，但不能仅凭方法名或 SDK 自动重试就假定安全。

创建付费任务时，客户端可发送稳定幂等键，服务端把“租户 + 操作 + 幂等键”作为唯一约束，并在同一事务中记录请求指纹、任务状态与需要原子保护的业务更新。重复请求若参数不同，应明确拒绝；相同请求若仍在执行，返回可查询的状态。幂等记录的保留期限要覆盖可能重试的窗口。若副作用在外部系统，还需把该身份继续传递，或借助 Outbox、状态机与补偿；本地唯一键不能自动保证外部扣款只发生一次。

重试要设置次数与总预算，采用有上限的指数退避和随机抖动，并避免客户端、网关、服务端多层相乘。比如三层各自允许三次尝试，最坏可能放大到 27 次下游调用。取消也应传播，但取消成功不意味着已经提交的业务能回滚。

对付费生成等不可轻易重复的调用，拿到任务 ID 就先保存；响应丢失时优先查询任务或联系服务端恢复。只有确定重复操作受到幂等保障，或确定原操作没有生效，才重新提交。这套机制适用于传统支付、消息系统，也适用于持续增长的 Agent 工具调用。
