<h1 id="q-001">1.操作系统与 Linux 工程实践</h1>

<h2 id="q-002">面试问题：训练与推理任务常用的 Linux 命令，应该怎样组织起来？</h2>

<a id="1.深度学习中常用的linux命令汇总"></a>

<a id="user-content-1.深度学习中常用的linux命令汇总"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

记命令时最好跟着一次任务的生命周期走：确认环境、定位数据、启动任务、观察进度、保存结果。这样遇到问题时，能够知道下一条命令要验证什么。

<div align="center">

| 阶段 | 常用命令 | 需要确认的信息 |
| --- | --- | --- |
| 确认位置与环境 | `pwd`、`ls -lah`、`command -v python`、`python --version` | 当前目录、解释器、隐藏配置 |
| 查找输入 | `find`、`rg`、`stat`、`du -sh` | 文件路径、内容、时间和占用 |
| 查看文本 | `head`、`tail`、`less` | 数据格式、日志与错误上下文 |
| 观察运行 | `ps`、`top`、`nvidia-smi`、`df -h` | 进程、CPU、GPU 与文件系统容量 |
| 归档与传输 | `tar`、`rsync`、`sha256sum` | 文件集合、增量同步和内容完整性 |

</div>

例如，启动训练前先确认 `command -v python` 指向预期环境，再用 `df -h /data` 检查训练目录所在文件系统，用 `nvidia-smi` 查看设备与现有进程。训练中查看 `tail -n 100 -F train.log`，结束后保存配置、代码版本、环境信息和输出校验值。

几个小细节会直接影响可靠性：`cat` 直接输出内容，通常不是按 `q` 退出的分页器；`less` 才适合交互翻页。`touch` 会更新已有文件的时间戳，并非总是创建一个新文件。`>` 会截断目标文件，`>>` 才是追加。查找 Python 文件用 `find . -type f -name '*.py'`，比解析 `ls` 的展示文本更可靠。

权限错误应检查用户、目录与挂载条件，不能把 `chmod -R 777` 当作通用修复。长期服务交给进程管理器；临时任务可以使用终端复用器或 `nohup`，但后者不负责失败重启与健康检查。命令的价值在于验证状态，不能以“命令执行了”代替“任务完成了”。

<h2 id="q-003">面试问题：多线程与多进程有什么区别，应该怎样选择？</h2>

<a id="2.计算机多线程和多进程的区别？"></a>

<a id="user-content-2.计算机多线程和多进程的区别？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

进程通常拥有独立虚拟地址空间和资源边界；同一进程中的线程共享地址空间、打开文件等资源，同时各自保留栈、寄存器状态和线程局部数据。Linux 调度的对象是可运行的任务实体，用户看到的进程与线程对应不同的资源共享关系。

共享地址空间使线程交换数据方便，也意味着一个线程越界写内存可能破坏整个进程。进程隔离能限制这类破坏，但进程仍可能通过共享内存、文件或外部服务影响彼此。多进程同样可以共享变量，只是需要显式的共享机制与同步，不能说“需要共享就只能用线程”。

<div align="center">

| 维度 | 多线程 | 多进程 |
| --- | --- | --- |
| 数据共享 | 直接访问同一地址空间 | IPC、共享内存、文件等 |
| 故障隔离 | 一个严重内存错误可影响整个进程 | 地址空间隔离更强，外部资源仍可能连带受影响 |
| 成本 | 常见创建与切换成本较低 | 启动、地址空间与 IPC 成本更明显 |
| 主要风险 | 数据竞争、锁竞争、死锁 | 序列化、复制、重复加载与状态同步 |

</div>

选择时看执行环境。C/C++ 的 CPU 计算可以用线程并行；传统启用 GIL 的 CPython 中，纯 Python CPU 循环通常需要多进程或释放 GIL 的原生计算库。网络等待可用线程或异步 I/O。不同语言和运行时的限制不能概括成“CPU 密集一定多进程”。

在 GPU 服务中，多开进程还可能重复加载模型、占用显存。常见设计是少量模型进程配合有界队列，前端处理网络并发，GPU worker 负责批处理。最后用吞吐、P95 延迟、内存和故障恢复时间验证选择，进程数和线程数都不是越多越好。

<h2 id="q-004">面试问题：Linux 的 R、S、D、T、Z 等进程状态分别意味着什么？</h2>

<a id="3.linux中的进程状态种类"></a>

<a id="user-content-3.linux中的进程状态种类"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

进程状态描述调度与等待情况。看到进程还在 `ps` 列表中，只能证明内核仍保留相应记录，不能证明它正在做有效工作。

<div align="center">

| 状态 | 含义 | 常见判断 |
| --- | --- | --- |
| R | 正在运行或就绪等待 CPU | 多个 R 长期排队可能有 CPU 竞争 |
| S | 可中断睡眠 | 等网络、定时器或事件很常见 |
| D | 不可中断睡眠，常见于某些内核 I/O 等待 | 检查存储、NFS、设备与内核栈 |
| T / t | 作业控制停止 / 被调试跟踪停止 | 核对信号、终端与调试器 |
| Z | 已退出但尚未被父进程回收 | 检查父进程的 wait 逻辑 |
| I | 空闲内核线程，部分工具和内核显示 | 不应直接当成普通业务进程卡死 |

</div>

`ps -eo pid,ppid,stat,wchan:24,comm` 可以同时看父进程、状态和等待位置。`STAT` 还可能带附加字符，例如 `l` 表示多线程，`s` 表示会话首进程，`+` 表示前台进程组；它们不是新的主状态。

`kill -9` 不能让所有 D 状态立即消失。信号可能要等相关内核等待返回后才能生效，强行反复发送信号没有诊断价值。Z 状态则已经不运行用户代码，也通常不再持有原来的地址空间，杀它本身无法让父进程回收退出状态。

负载升高也不等同于 CPU 使用率升高。Linux load average 包含可运行任务和部分不可中断等待任务，磁盘卡住可能让负载很高、CPU 却不忙。状态要与 CPU、I/O 和持续时间一起读。

<h2 id="q-005">面试问题：怎样用 ps、pgrep 和信号准确查看、停止进程？</h2>

<a id="4.linux中ps-aux指令与grep指令配合管理进程"></a>

<a id="user-content-4.linux中ps-aux指令与grep指令配合管理进程"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

`ps aux` 是 BSD 风格选项组合，用于查看较完整的进程列表；`ps -ef` 是另一组常用格式。不要随意写成 `ps -aux`，它在不同实现中可能产生歧义。输出字段取决于选项，`ps aux` 默认不会包含所有想得到的字段。

```bash
ps -eo pid,ppid,user,stat,pcpu,pmem,rss,etimes,args
pgrep -af 'python.*train.py'
ps -p 12345 -o pid,ppid,lstart,stat,args
```

第一条显式选择字段；第二条按完整命令行匹配候选；第三条核实某个 PID 的身份与启动时间。`ps aux | grep '[p]ython'` 可以避免把 grep 自己也匹配出来，但字符串匹配仍可能选到其他项目。自动化停止服务时，应优先使用服务管理器或可靠的进程身份记录，而不是对模糊匹配结果批量发送信号。

`RSS` 是当前驻留物理内存的统计，可能包含共享页；`VSZ` 是虚拟地址空间大小，不能当成实际占用。`ps` 的 CPU 百分比通常是进程生命周期内的比率，与 `top` 的采样区间含义不同。`NI` 影响调度优先级，但不会直接指定 CPU 占用百分比。

普通退出先发送 `SIGTERM`，给程序停止接单、保存检查点和关闭资源的机会；超过明确的等待时间仍无法退出，再考虑 `SIGKILL`。后者不能被捕获，程序来不及执行清理。多进程服务还应处理子进程和进程组，避免主进程退出、GPU 子进程仍在运行。

排障输出可能含命令行中的令牌、路径或用户信息。查看完整环境变量尤其容易暴露凭据，只在确有需要时采集，并在共享前脱敏。

<h2 id="q-006">面试问题：Linux 内核、发行版、用户态与文件系统怎样配合？</h2>

<a id="5.linux系统的相关概念"></a>

<a id="user-content-5.linux系统的相关概念"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Linux 严格来说是内核。发行版把内核、运行库、包管理、服务管理和用户工具组合起来。应用在用户态运行，通过系统调用请求内核操作文件、网络、内存和设备；驱动把内核操作连接到具体硬件。

“一切皆文件”是理解统一接口的入口：普通文件、设备、管道和套接字中的许多对象都能通过文件描述符访问，但它们的语义并不相同。套接字通常不能像普通文件一样任意定位读写，进程也不是一个可以完整复制的普通文件。

<div align="center">

| 路径 | 主要用途 | 容易误解的地方 |
| --- | --- | --- |
| `/etc` | 系统与服务配置 | 密钥、密码相关文件须有相应权限 |
| `/var` | 日志、缓存、可变状态 | 日志和容器数据可能挤满系统盘 |
| `/home`、`/root` | 普通用户与 root 的主目录 | `/root` 不等于根目录 `/` |
| `/usr`、`/opt` | 程序、库与第三方软件 | 现代发行版可能将 `/bin`、`/lib` 链接到 `/usr` 下 |
| `/proc`、`/sys` | 内核暴露的进程和设备接口 | 很多内容按读取时动态生成 |
| `/dev` | 设备节点等 | 设备访问仍受权限与驱动控制 |
| `/tmp` | 临时文件 | 清理策略由系统决定，不能存放唯一结果 |

</div>

挂载把不同文件系统接入同一目录树，路径看起来相邻，不代表数据位于同一块磁盘。容器还可能有独立的挂载视图，因此“宿主机看到某个文件”不能保证容器里能读到。

发行版选型关注支持周期、驱动与框架兼容、软件源和运维能力。不能继续把所有 CentOS 版本都描述成当前 RHEL 的免费重编译替代品；具体产品定位和维护状态需要按版本核验。操作系统基础的长期价值，在于理解接口与资源边界，而不是记住某一时期的发行版排名。

<h2 id="q-007">面试问题：Linux 与 Windows 的差异，怎样放到 AI 开发中判断？</h2>

<a id="6.linux系统和windows系统的区别？"></a>

<a id="user-content-6.linux系统和windows系统的区别？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

二者都支持多用户、权限隔离、网络服务和并行计算。稳定性、安全性与性能取决于版本、配置、驱动、负载和维护，不能直接归纳成“Linux 一定更安全、更快”。

Linux 在服务器、容器、自动化部署及开源计算工具链中有成熟生态，很多 AI 框架和集群工具首先在这一环境适配。Windows 在桌面应用、设备厂商工具与部分图形工作流中有优势，原生环境与 WSL2 又是不同的运行路径。选择时应验证实际需要的 CUDA、编译器、摄像头、推理后端和部署目标。

文件路径、大小写、换行符、权限模型和进程信号也会影响项目迁移。Linux 文件名是否区分大小写最终由文件系统及挂载行为决定；跨平台代码不应依赖两个只差大小写的文件。Shell 脚本、动态库后缀和依赖二进制也不能直接互换。

开发机与生产机可以不同，但应尽早在目标环境做集成验证。WSL2 方便开发，却不能证明宿主机所有设备能力都已等价透传；容器能固定用户态依赖，也不能消除宿主机内核与驱动差异。

面试中更有分量的回答，是给出具体约束：团队用什么工具链、服务部署在哪里、依赖支持什么平台、如何复现和维护。把操作系统变成身份偏好，无法帮助解决工程问题。

<h2 id="q-008">面试问题：主机 IP 与 BMC 管理地址有什么区别？</h2>

<a id="7.什么是主机ip和BMC信息？"></a>

<a id="user-content-7.什么是主机ip和BMC信息？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐ (3/5)**

主机 IP 属于操作系统可见的网络接口，用于 SSH、API、训练数据传输等业务通信。一台机器可以有多个接口与多个地址，IP 也可以被 NAT 改写，因此不能把它当成永远唯一的硬件身份。

BMC 是服务器上的独立管理控制器，常提供电源控制、温度与风扇监测、远程控制台和硬件日志。它可以拥有专用管理网口，也可能通过共享网口保持独立的逻辑管理通道。主操作系统无法启动时，只要 BMC 供电和管理网络仍正常，管理员仍可能查看控制台和重启机器。

```bash
ip -br address
ip route get 192.0.2.10
sudo ipmitool lan print 1
```

前两条分别查看接口地址及访问某个目标的路由选择。第三条是支持 IPMI 的服务器上查询某个 LAN 通道的示例，通道号、权限和工具支持依硬件而定；不是所有设备都使用通道 1。厂商管理界面或 Redfish API 也常用于查询，普通个人电脑未必有 BMC。

管理网应与业务网合理隔离，使用独立身份、受控访问和更新策略。BMC 能控制电源甚至远程介质，权限通常比一个普通业务 API 更强。排查“SSH 不通”时，BMC 只能帮助确认硬件与控制台状态，不能自动修复操作系统路由、防火墙或 SSH 配置。

记录资产信息时，应分别标注业务地址、管理地址、网卡或设备标识、所属网络与访问方式，避免将管理地址误当成模型服务入口。

<h2 id="q-009">面试问题：find 如何组合文件名、时间、大小与目录排除条件？</h2>

<a id="8.Linux中的find命令使用大全"></a>

<a id="user-content-8.Linux中的find命令使用大全"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

`find` 遍历目录树，对每个条目计算表达式。条件和动作可以组合，因此关键是理解匹配顺序、逻辑优先级与文件名的处理方式。

```bash
find ./data -type f -name '*.jsonl'
find ./runs -type f -mmin -30
find ./data -type f -size +100M
find . -path './.git' -prune -o -type f -name '*.py' -print
find . -type f \( -name '*.txt' -o -name '*.md' \) -print
find ./data -type f -name '*.jsonl' -exec wc -l -- {} +
```

通配符用引号包起来，让 `find` 在遍历时匹配，避免 Shell 提前展开。`-a` 的优先级高于 `-o`，组合“且”和“或”时要用括号；括号还需转义，防止被 Shell 当作语法。`-prune` 阻止进入匹配目录，右侧的 `-print` 只输出需要的条目。

GNU find 的 `M`、`G` 以二进制单位计数，而且 `-size` 会按单位向上取整。`-size 1G` 并不等于文件恰好有 1 GiB；需要精确字节数时用 `c` 单位。`-mtime` 也按完整的 24 小时区间取整，分钟级条件用 `-mmin` 更直观。

文件名可以包含空格和换行。批量操作优先使用 `-exec ... {} +`，需要管道时使用 `-print0` 配合支持空字符分隔的工具。不要把输出交给默认按空白切分的 `xargs`。

删除前先用同一条件 `-print` 核实范围，再改成删除动作。跟随符号链接的 `-L`、跨挂载遍历和 GNU/BSD 选项差异都可能改变结果，处理训练集或模型文件时先限定起点目录，比一上来扫描整个 `/` 更可靠。

<h2 id="q-010">面试问题：CPU 与 GPU 的架构差异，为什么会影响 AI 任务分工？</h2>

<a id="9.CPU和GPU的区别？"></a>

<a id="user-content-9.CPU和GPU的区别？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

CPU 通常重视单个执行流的低延迟，使用复杂控制逻辑、分支预测、多级缓存和乱序执行处理多样任务。GPU 将更多资源投入高吞吐的并行执行与内存访问，适合把大量相似计算分配到许多线程和专用矩阵单元。

GPU 的“核心数”不能直接与 CPU 核数比较，二者计数单位和能力不同。GPU 线程按组协同执行，分支分歧可能让同组线程分批走不同路径；不规则访问、很小的算子或频繁同步也会降低效率。GPU 还需要足够并行工作来隐藏内存等待，并非每条指令都比 CPU 更快。

例如，一个矩阵乘法包含大量可复用的数据和规则乘加，容易利用 GPU；解析小 JSON、决定下一步工具调用、处理网络控制逻辑则常由 CPU 承担。若 CPU 解码图像太慢，GPU 会等待输入；若每一步都把结果搬回 CPU 判断，也可能被设备同步与传输拖住。

判断瓶颈要区分算力、内存带宽、设备间传输和任务粒度。可以用每字节数据对应多少运算来理解计算强度：数据复用高的算子更可能受算力限制，复用低的算子更可能受带宽限制。具体边界仍由硬件、精度和实现决定。

AI 系统通常让 CPU 管理请求、预处理和调度，让 GPU 执行大规模张量计算，再通过批处理、流水线和缓存减少等待。对整体性能负责，需要看完整请求路径，而不是只看 GPU 型号或瞬时利用率。

<h2 id="q-011">面试问题：tail 如何持续跟踪日志，为什么轮转后可能看不到新内容？</h2>

<a id="10.Linux中的tail命令使用大全"></a>

<a id="user-content-10.Linux中的tail命令使用大全"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

`tail -n 100 app.log` 读取文件末尾 100 行，`tail -n +5 app.log` 从第 5 行开始，`tail -c 1024 app.log` 按字节读取末尾。持续观察日志时，最容易忽略的是“跟踪打开的文件”与“跟踪这个名字当前指向的文件”的区别。

GNU tail 的 `-f` 默认跟随文件描述符。日志轮转如果把旧文件改名，再创建新的 `app.log`，原描述符仍可能指向旧文件。`-F` 相当于按名称跟踪并重试，更适合这类轮转：

```bash
tail -n 100 -F app.log
tail -n 100 -F app.log | grep --line-buffered 'ERROR'
```

第二条让 GNU grep 按行输出，减少管道缓冲导致的“日志迟迟没出现”。如果源程序本身缓冲输出，调整 tail 并不能让尚未写入文件的日志出现；Python 可根据场景使用无缓冲输出或正确配置日志处理器。`Ctrl+C` 用于停止实时跟踪。

`tail` 看不到日志，也可能是路径不对、进程写入另一个工作目录、文件权限不足，或日志被发送到 journald、容器标准输出。对应地检查 `journalctl -u service -f` 或 `docker logs -f container`，不要反复盯着一个并未被写入的文件。

实时日志只适合快速观察，不能代替结构化日志、请求 ID 与告警。一次请求跨多个进程时，需要按时间与关联 ID 还原链路；只搜索最后一个 `ERROR` 可能错过真正起因。

<h2 id="q-012">面试问题：du、df 与 ls 显示的空间大小为什么不一致？</h2>

<a id="11.Linux中有哪些常用的查看文件夹占用空间的命令？"></a>

<a id="user-content-11.Linux中有哪些常用的查看文件夹占用空间的命令？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

`du` 遍历可见文件统计占用，`df` 查询文件系统整体空间，`ls -l` 主要显示单个文件的逻辑长度。它们回答不同的问题，因此数字不一致不一定是错误。

```bash
df -h /data
df -i /data
du -xhd 1 /data | sort -h
du -sh /data/checkpoints
du --apparent-size -sh /data/checkpoints
```

以上以 GNU 工具为例。`df -i` 检查 inode 使用量，`du -x` 避免跨到其他文件系统，深度限制便于逐层定位大目录。`--apparent-size` 统计表观长度，可用于对比稀疏文件的逻辑大小与实际分配块。macOS/BSD 的选项有所不同，不能原样假定兼容。

常见差异来自几类情况：已删除文件仍被进程打开，`du` 找不到目录项，`df` 仍计算其占用；权限不足使 `du` 少统计；挂载覆盖隐藏了下层目录；文件系统快照、共享块、元数据或保留空间也会影响统计。硬链接与稀疏文件同样不能简单按 `ls` 的长度相加。

排查时先确认目标路径对应哪个挂载点，再在那个文件系统内逐层缩小范围。交互工具 `ncdu` 适合浏览，但扫描大目录也会产生元数据 I/O，清理动作要核实。文件数量极多时，容量未满也可能因为 inode 耗尽而无法创建文件。

`tree -h` 展示的目录条目大小并不是整个目录递归总量，解析 `ls` 再按空格取第九列也会误处理特殊文件名。明确统计口径，比换一个“更漂亮”的工具更重要。

<h2 id="q-013">面试问题：Shell 脚本怎样处理解释器、参数、退出码和信号？</h2>

<a id="12.介绍一下Linux系统中的Shell脚本"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Shell 适合把现有程序组织成可重复的流程。可靠脚本需要明确输入、工作目录、错误处理和退出行为，不能只把交互终端里执行过的命令粘到一起。

`#!/usr/bin/env bash` 表示直接执行脚本时使用 PATH 中的 Bash；`bash script.sh` 显式选择 Bash；`sh script.sh` 会使用 sh，即使文件第一行写了 Bash，也不会自动切换。`/bin/sh` 在不同发行版可能指向不同实现，数组、`[[ ... ]]`、`pipefail` 等能力不能当成通用 POSIX sh 语法。

```bash
#!/usr/bin/env bash
set -euo pipefail
input_path=${1:?用法: run.sh 输入目录 输出目录}
output_path=${2:?缺少输出目录}
test -d "$input_path"
mkdir -p -- "$output_path"
exec python -u prepare.py --input "$input_path" --output "$output_path"
```

变量展开加双引号，避免空格分词和通配符展开。转交完整参数列表时使用 <code>"&#36;@"</code>，需要动态构造命令时使用 Bash 数组，避免 `eval`。上例假定当前目录有 `prepare.py`；正式脚本可以先计算脚本目录并显式定位入口。

`set -e` 在条件判断、某些逻辑列表和管道中有例外，不能保证任何命令失败都退出。`pipefail` 让管道更容易暴露前段失败，但预期的非零状态仍需显式处理，例如 grep 没匹配到返回 1。退出码应代表真实成功或失败，不要最后用一条成功的 `echo` 覆盖了前面的错误。

`exec` 用目标进程替换 Shell，便于信号直接传到服务；需要管理多个子进程时，应安装 `trap`、转发信号并 `wait` 回收。临时文件可用 `mktemp` 创建并在退出时清理，但不要假定 `SIGKILL` 也会触发 trap。`set -x` 会打印展开后的参数，处理凭据时不要开启全局跟踪。

<h2 id="q-014">面试问题：符号链接与硬链接有什么区别，怎样正确使用 ln？</h2>

<a id="13.Linux中如何创建软连接？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

符号链接保存一个目标路径，访问时再沿路径解析；硬链接是同一文件 inode 的另一个目录项。符号链接可以跨文件系统、可以指向目录，也可以在目标不存在时创建；普通硬链接不能跨文件系统，通常不允许用户给目录创建硬链接。

```bash
ln -s /data/models/model-v2 ./current-model
readlink ./current-model
ls -li weights.bin weights-copy.bin
```

第一条将当前目录下的 `current-model` 指向绝对路径。相对符号链接按**链接所在目录**解释目标，不按访问者当前工作目录解释。例如在 `/srv/app` 中创建目标为 `../models/v2` 的链接，它解析到 `/srv/models/v2`。相对链接适合整体移动的目录树，绝对链接适合位置固定的资源，不能笼统要求所有链接都使用绝对路径。

符号链接本身需要保存路径及元数据，会占用资源，只是通常很小。删除链接目录项通常不会删除目标；执行删除时不要随手加尾部斜杠或递归选项，应先确认操作对象。硬链接删除其中一个名字后，只要还有链接或打开的文件引用，数据并不立即消失。

模型发布常把稳定入口链接到某个版本目录。但切换链接只影响后续路径解析，已经打开的文件描述符或映射仍可能访问旧版本。可靠发布还要配合实例重载、版本校验与回滚，不能把 `ln -s` 当作完整的模型热更新协议。

<h2 id="q-015">面试问题：CPU 使用率、load average 与 iowait 应该怎样一起看？</h2>

<a id="14.Linux中如何查看CPU的使用率？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

CPU 使用率描述某个采样区间内 CPU 时间的分配；load average 描述一段时间内可运行及部分不可中断等待任务的平均数量。前者是时间比例，后者是任务数量，不能直接比较百分数。

```bash
top
mpstat -P ALL 1
pidstat -u -t 1
vmstat 1
```

`mpstat` 看每个逻辑 CPU，`pidstat` 将消耗归到进程或线程，`vmstat` 同时观察运行队列、交换和块设备活动。这些 sysstat 工具可能需要单独安装。部分工具第一行是自启动以来的统计，要看后续采样区间。

单线程程序占满一个核心时，整机平均 CPU 使用率仍可能很低；多线程进程在某些工具口径下可超过 100%。`us`、`sy`、`id`、`wa` 等时间分类有助于区分用户计算、内核工作、空闲和 I/O 等待，但 `iowait` 不是磁盘忙碌率，也不能精确归属某个进程。

虚拟机还要关注 steal time，容器则检查 CPU quota 和 throttling。宿主机 64 核并不意味着容器拥有 64 核计算预算；配额耗尽后，进程可能在等待下一周期，平均使用率看起来不高，尾延迟却变差。

例如负载高、CPU 空闲且 D 状态多，应沿存储路径检查；单核满、其他核闲，先检查串行热点；系统时间和上下文切换异常，则关注过量线程、系统调用或锁竞争。每次调整前后使用相同负载采样，才能判断瓶颈是否真正移动。

<h2 id="q-016">面试问题：怎样观察 GPU 状态，为什么显存占满不代表算力用满？</h2>

<a id="15.Linux中可视化GPU使用情况？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

GPU 至少要分开看显存容量、计算活动、内存带宽、功耗温度和进程归属。模型权重常驻显存时，即使没有请求，显存也可能占用很高；某个采样区间有内核运行，也不等于所有计算单元都达到峰值吞吐。

```bash
nvidia-smi
nvidia-smi --query-gpu=index,name,utilization.gpu,memory.used,memory.total,power.draw,temperature.gpu --format=csv -l 1
nvidia-smi pmon -c 1
```

这些命令针对 NVIDIA 设备，字段和进程可见性受驱动、硬件、权限及分区方式影响。`nvitop`、`nvtop` 提供更便于观察的终端界面，核心仍是这些指标的含义；监控本身也有开销，不能保证任意采样频率都完全无影响。

显存统计还要区分框架分配、缓存保留和其他进程占用。PyTorch 的 reserved memory 与 allocated memory 不同，清空缓存也不会释放仍被张量引用的内存。持续增长可能来自保留计算图、缓存无上限或请求生命周期管理错误，不能只靠重启解决。

若 GPU 利用率周期性跌落，结合 CPU 预处理、数据加载、H2D 传输、批大小和请求到达情况分析。需要准确解释内核间空隙、同步或算子耗时时，再使用 profiler 与时间线；异步 GPU 调用不能只用 CPU 侧函数返回时间估计执行时间。

模型服务还应把 GPU 指标关联到排队时间、首 token 延迟、每 token 时间和失败率。设备看起来很忙，仍可能在执行不必要的复制或小批任务，最终用户体验才是优化的检验标准。

<h1 id="q-101">2.内存、I/O 与资源管理</h1>

<h2 id="q-017">面试问题：怎样比较缓存、内存、存储、网络和 GPU 传输的性能？</h2>

<a id="16.在计算机中有哪些常用的读写操作，每个读写操作的性能是什么样的？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

性能比较首先区分延迟和带宽。读取很少的数据常由固定开销主导，传输大块数据更容易受持续带宽限制；并发度、缓存状态、访问模式和持久化语义又会改变结果。

<div align="center">

| 路径 | 常见限制 | 应测什么 |
| --- | --- | --- |
| CPU 缓存与 DRAM | 命中率、依赖链、内存带宽 | 访问延迟、缓存未命中、持续带宽 |
| SSD / HDD | 随机 I/O、队列深度、设备延迟 | IOPS、吞吐、尾延迟、读写混合 |
| 文件系统 | 页缓存、元数据、同步写回 | 冷热缓存、文件大小、fsync 成本 |
| 网络 | RTT、拥塞、丢包、窗口 | 有效吞吐、重传、P95 延迟 |
| CPU 与 GPU | 总线、固定传输开销、同步 | 传输方向、字节数、与计算重叠程度 |
| 数据库 | 查询计划、锁、日志与底层 I/O | 事务吞吐、查询延迟、恢复承诺 |

</div>

缓存通常比 DRAM 更低延迟，DRAM 通常比持久存储更低延迟，但不能给所有机器套一张固定纳秒表。文件读可能命中页缓存，根本没有访问磁盘；数据库查一次索引也可能全在内存。写调用返回也未必意味着数据已落到能抵抗断电的介质。

对简单单次传输，可用“固定延迟 + 数据量 / 有效带宽”形成初步估计。实际还有排队、协议、编码和同步开销；并发流量共享瓶颈时，每条流不能独占标称带宽。GPU 显存内部访问与 CPU 到 GPU 的 PCIe 传输是两条不同路径。

测试报告应写明硬件、数据规模、顺序或随机、缓存冷热、并发度、读写比例和同步要求。一次热缓存读取不能证明磁盘很快，异步提交完成也不能替代真实完成时间。没有这些前提的性能数字很难指导工程决策。

<h2 id="q-018">面试问题：Linux 用户、组与 sudo 权限怎样分工？</h2>

<a id="17.Linux中修改用户权限的命令有哪些？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

用户和组决定进程以什么身份访问资源，文件权限决定资源允许哪些身份做哪些动作，sudo 则按策略允许用户以另一个身份执行命令。把三者混在一起，容易出现“给文件改了权限，却仍然没有服务操作权限”的误判。

```bash
id
getent passwd appuser
getent group modelreaders
sudo -l
```

先查当前 UID、主组和附加组，以及实际 sudo 策略。添加附加组常用 `usermod -aG group user`；`-a` 表示追加，漏掉它可能替换原有附加组集合。组关系修改后，已运行进程通常不会自动刷新，需要新的登录会话或重启相应服务。

服务账号应拥有明确用途，数据目录按组授予读写权限。给用户加入 Docker 管理组通常意味着获得非常强的宿主机控制能力，不能当成一个普通“读取 GPU”的权限开关。允许少量运维命令时，应通过受限 sudo 规则表达，使用 `visudo` 检查语法，并留意可执行任意子命令的程序造成的权限扩大。

身份与路径权限之外，还可能有 ACL、SELinux/AppArmor、只读挂载、容器 UID 映射和远程文件系统策略。排查失败要看具体拒绝在哪一层发生，不能不断加 sudo 或递归开放整个目录。

本题关注账号与授权；文件 `rwx`、目录遍历、umask 和 ACL 的具体语义见[文件权限问题](#q-029)。两者一起决定请求是否被允许，但应分别配置和核验。

<h2 id="q-019">面试问题：AI 训练与推理的 I/O 开销主要出现在哪些环节？</h2>

<a id="18.AI行业中计算机I/O开销主要体现在哪里？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

I/O 开销要沿数据路径观察：远程对象或本地文件进入主内存，CPU 解码与预处理，再传到 GPU，计算结果还可能回到 CPU、数据库或网络。分布式训练另有梯度、参数与激活通信，保存检查点则形成反向的数据搬运与持久化路径。

数据读取和预处理不是同一种瓶颈。大量小文件可能受目录与元数据操作限制，压缩视频可能受 CPU 解码限制，远程对象可能受 RTT 与请求并发限制。即使 GPU 等待输入，也不能直接推断“磁盘太慢”。

GPU 传输中，频繁的小块复制和同步常比一次大块搬运更难摊薄成本；分布式通信还受拓扑与慢节点影响。检查点除权重外，可能包含优化器状态、随机数状态、调度器与训练进度，写入量不能只按模型权重估算。一般不要求每次都保存梯度，具体取决于恢复设计。

诊断可以记录一次迭代中的读数据、CPU 处理、H2D、计算、通信与输出时间，并查看它们是否重叠。如果阶段严格串行，总时间近似各阶段之和；形成有效流水线后，稳态吞吐更接近最慢阶段的能力，但仍有启动、收尾和资源竞争开销。

PyTorch DataLoader 的 `num_workers > 0` 通常启动多个工作**进程**，不应写成自动多线程加载。增加 worker 可能同时增加内存、文件句柄、解码线程和存储压力。找准哪个阶段供给不足，才知道应该加缓存、换布局、限并发还是调整计算。

<h2 id="q-020">面试问题：怎样降低 I/O 开销，又不牺牲数据质量与恢复能力？</h2>

<a id="19.AI行业中如何降低计算机I/O开销？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

先减少不必要的数据，再改善访问布局，最后考虑并发和硬件。仅增加并发，可能把一个慢请求变成一群互相排队的慢请求。

可把大量小文件组织为适当大小的数据分片，减少打开和元数据操作，同时保留索引、校验与随机采样能力。压缩减少传输字节，却增加解码计算；JPEG 等有损格式还会改变训练信息，不能只按文件大小选择。缓存放在内存或本地 NVMe 时，应定义容量、版本和淘汰策略，避免命中旧数据。

预取允许加载下一批与当前计算重叠，但预取队列必须有界。页锁定主机内存常有利于异步 H2D 传输，实际重叠仍取决于硬件、stream、依赖关系与调用方式。滥用 pinned memory 会减少操作系统可调度内存，`non_blocking=True` 也不是自动获得重叠的保证。

检查点可以异步写入、分片保存或按增量保存，但必须保证读取的是一致快照，明确何时才算持久化成功。降低保存频率会增加故障重算成本，应结合故障概率、保存耗时与允许丢失进度，而非单纯追求训练曲线更快。

分布式通信可通过梯度累积、通信计算重叠和更合适的拓扑降低开销，但梯度压缩会引入误差，批量调整会改变优化行为。传输批次与训练有效 batch size 也不必绑定，应分别评估。

优化后同时看吞吐、P95 延迟、内存峰值、数据一致性和恢复演练。一个把 I/O 隐藏在后台却不断积压数据的方案，短时 benchmark 可能很好，持续运行仍会失败。

<h2 id="q-021">面试问题：CPU 核数与工作进程数应该怎样匹配？</h2>

<a id="20.介绍一下CPU核数与程序进程数设置之间的关系"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

先区分物理核心、逻辑 CPU 与当前任务真正可用的 CPU 预算。SMT 让一个物理核心暴露多个硬件线程，但它们共享部分执行资源，吞吐不会按逻辑 CPU 数等比例增长。容器配额、CPU 亲和性和 cpuset 又可能进一步限制可用能力。

对于单线程的 CPU 密集进程，可以从接近可用核心数的 worker 开始测量。但“启动 N 个进程”并不保证每个独占一核，调度器还要服务其他任务；每个进程内部若调用多线程 BLAS，实际可运行线程数可能是进程数与内部线程数的乘积。

例如容器只有 8 核预算，配置 8 个预处理进程，每个又启用 8 个 OpenMP 线程，就可能产生 64 个计算线程争抢资源。吞吐不增，反而因为上下文切换、缓存失效和内存带宽竞争变慢。要一起限制进程并发与库内线程数。

I/O 密集型任务可在等待期间执行其他任务，但并发上限还受远端限流、连接池、磁盘队列和内存约束。没有通用的“逻辑核数乘 2 或 3”最优公式。单核也能通过重叠等待改善吞吐，只是不能同时执行多个独立 CPU 指令流。

GPU worker 数更不能直接按 CPU 核数推导：一个 worker 可能独占一份模型显存，进程之间还需协调批处理和公平性。采用递增并发压测，寻找吞吐开始趋平、尾延迟和资源开销明显上升的位置，通常比一开始开满 worker 更可靠。

<h2 id="q-022">面试问题：线程池大小、等待比例与嵌套并行有什么关系？</h2>

<a id="21.介绍一下CPU核数与程序线程数设置之间的关系"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

线程池控制同时保留多少执行上下文；CPU 核数只限制其中可真正并行计算的部分。线程等待网络时可以让出 CPU，但每个线程仍会占用栈、运行时和调度资源，过多线程会增加内存与上下文切换。

在任务行为较稳定、没有其他瓶颈的简化模型中，可以用 `线程数 ≈ 可用核心数 × 目标利用率 × (1 + 等待时间/计算时间)` 形成起点。这是估算，不是配置定律：锁等待不能简单靠加线程消除，远端限流、队列与内存约束也会让公式失效。

例如一次调用计算 5 ms、网络等待 45 ms，理论上可通过多个线程重叠等待。但如果下游只允许 20 个并发，就应由下游容量确定上限，并设置有界队列与超时。无限提交任务只会把压力藏进内存。

AI 工具链常有嵌套线程池：Web worker、图像解码、NumPy/BLAS、OpenMP 各自并行。应根据实际库配置 `OMP_NUM_THREADS` 等参数，检查线程总量；不要对每一层都使用全部核心。内存带宽敏感的计算甚至可能在核心尚未满载前就达到吞吐上限。

还要区分语言运行时。启用 GIL 的 CPython 对纯 Python 计算有限制，原生库释放 GIL 时可以并行，free-threaded 构建则有新的兼容与同步要求。最终压测应记录任务分布、队列长度、P95 等待和有效吞吐，不能只记录线程数与平均 CPU。

<h2 id="q-023">面试问题：协程怎样并发执行，为什么仍然会发生竞争与阻塞？</h2>

<a id="22.协程的相关概念"></a>

<a id="user-content-22.协程的相关概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

协程可以在执行到特定位置时挂起，保留继续执行所需的状态，稍后再恢复。以 Python asyncio 为例，事件循环在等待 I/O 的间隙运行其他任务，在一个线程内组织大量并发连接，减少为每个连接分配一个系统线程的成本。

`async def` 并不会自动把其中所有操作变成异步。协程执行阻塞文件读写、同步 HTTP 调用或长时间 CPU 循环时，仍可能占住事件循环，让其他请求无法及时推进。可选择真正异步的客户端，把阻塞调用放到有界线程池，或把 CPU 工作交给合适的执行器。具体协程运行时也可能跨多个线程调度，不能把所有语言的协程都定义为“只在一个线程”。

单线程事件循环没有同一时刻的线程并行写入，也仍有跨 `await` 的逻辑竞争。例如先查询余额，挂起等待远端服务，再扣减余额；另一个协程可能在挂起期间修改了余额。需要异步锁、事务或原子状态操作维护不变量。普通线程锁若以阻塞方式等待，反而可能卡住整个事件循环。

```python
import asyncio

async def fetch_limited(client, item, semaphore):
    async with asyncio.timeout(5):
        async with semaphore:
            return await client.fetch(item)
```

这里由调用方传入同一事件循环中共享的信号量，限制同时执行的请求；外层超时把等待信号量和执行请求一起纳入 5 秒预算，示例使用 Python 3.11 起提供的 `asyncio.timeout` 与异步客户端。即使设置了信号量，也不要一次创建百万个等待任务；入口队列同样要有界。

取消通常在可取消点传播，不能保证远端动作撤销。应在 `try/finally` 或异步上下文管理器中释放资源，避免吞掉取消异常。协程的价值是安排等待与生命周期，CPU 计算速度并不会因为添加 `async` 自动提高。

<h2 id="q-024">面试问题：文件锁与线程锁为什么会死锁？四个必要条件如何理解？</h2>

<a id="23.介绍一下计算机文件系统的死锁原理"></a>

<a id="user-content-23.介绍一下计算机文件系统的死锁原理"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

死锁是参与者互相等待，使相关操作无法继续推进。文件锁只是一个例子，线程互斥锁、数据库行锁和设备资源也可能出现同样问题。普通 `open` 或同时写文件不会自动形成互斥；没有正确同步时，更可能发生竞争和数据破坏。

经典死锁条件包括互斥、持有并等待、不可抢占和循环等待。例如进程 A 持有锁 X 并等待锁 Y，进程 B 持有锁 Y 并等待锁 X，两者都不会先释放已有锁，就形成了环。

```text
进程 A：持有 X -> 等待 Y
进程 B：持有 Y -> 等待 X
```

文件锁还需明确语义。Linux 常见 `flock` 或 `fcntl` 锁在许多环境中属于建议锁，参与者必须遵守协议；不能以为一个进程加锁后，其他任意程序的读写都会被内核阻止。不同锁机制的归属、继承与释放规则不同，网络文件系统的支持又可能不同。

资源分配图有环是否充分，取决于模型。每类资源只有一个实例的经典模型中，环能判定死锁；存在多个实例时，有环未必已经死锁。线程等待图也需要包含真实持有者和依赖，不能把所有长等待都当成死锁。

死锁与活锁、饥饿要分开：活锁中的参与者不断改变状态却没有进展，饥饿是某个任务长期抢不到资源。磁盘损坏导致的 D 状态等待也未必有循环依赖。排查时记录各线程栈、锁持有者与等待顺序，证据比“程序卡住了”的描述更能指导修复。

<h2 id="q-025">面试问题：如何预防、检测与恢复死锁？超时能保证安全吗？</h2>

<a id="24.解决计算机文件系统死锁的经典方法有哪些？"></a>

<a id="user-content-24.解决计算机文件系统死锁的经典方法有哪些？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

最常用的预防方式是规定全局锁顺序。需要 X、Y 两个资源的操作，都先获取 X 再获取 Y，从设计上消除相反的等待方向。还应缩短临界区，避免持锁调用未知代码、等待网络或等待另一个需要同一锁的任务结束。

避免死锁则在分配前判断系统是否仍能完成所有任务，银行家算法是经典模型。但它需要事先知道最大资源需求，真实文件操作和动态服务往往难以满足前提，因此不宜把它描述成日常 Linux 文件锁的普遍实现。

检测恢复常见于数据库：维护等待关系，发现循环后中止某个事务，回滚并由应用重试。重试需要限制次数、退避和幂等；只重新执行最后一条 SQL，可能破坏整个事务的语义。一般文件操作没有自动回滚事务，不能直接套用数据库的恢复保证。

超时能让等待者放弃，但必须释放已持有资源并修复中间状态。两个任务超时后同时立即重试，可能反复碰撞形成活锁；随机退避和统一顺序通常比单纯加大超时更有效。高优先级进程也不能随意“抢走文件锁”而假定被保护的数据仍然一致。

读写锁允许多个读者并行，不会自动消除死锁；锁升级、嵌套获取和写者饥饿都需处理。分布式锁还会遇到租约过期与旧持有者继续写入，需要资源端版本校验或 fencing。

故障发生时先保存线程栈和等待证据，再按预案中止最小范围的任务。恢复成功之后还要检查数据不变量，否则只是让进程重新运行，错误状态仍会继续传播。

<h2 id="q-026">面试问题：整数溢出、浮点溢出、下溢与舍入误差有什么区别？</h2>

<a id="25.计算机中计算导致溢出（overflow）的原因有哪些？"></a>

<a id="user-content-25.计算机中计算导致溢出（overflow）的原因有哪些？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

整数溢出是计算结果超出类型可表示范围；浮点溢出是指数范围不足；下溢发生在结果过于接近零时；舍入误差则来自有限有效位，结果可以仍在表示范围内。它们的成因与修复方式不同。

N 位二进制补码有符号整数范围为 `−2^(N−1)` 到 `2^(N−1)−1`，无符号整数为 `0` 到 `2^N−1`。语言语义也很重要：C/C++ 的无符号运算按模回绕，普通有符号溢出属于未定义行为；Python 的内置整数可扩展精度，但 NumPy 等固定宽度数组仍有自己的溢出规则。不能把所有语言都解释为自动回绕。

浮点数范围与精度分别由指数和有效位决定。FP16 与 BF16 都是 16 位，但指数范围和有效精度不同。过大结果可能产生无穷值，`0/0` 等无效运算可能产生 NaN；NaN 不等同于溢出。下溢可能先进入次正规数，某些硬件或模式还会把很小的值冲为零。

例如 softmax 直接计算 `exp(x)` 容易溢出，可以先减去最大值再指数化，这不改变数学上的归一化结果。大量求和可用更高精度累加或稳定算法；混合精度中的 loss scaling 主要缓解小梯度下溢，并不是随意增大所有数值来治疗溢出。

排查 NaN 时检查第一处非有限值，区分输入异常、除零、对负数取对数、梯度爆炸和类型转换。扩大类型只能处理部分范围问题，无法修复错误公式。边界值测试、有限性检查与数值稳定写法比事后替换 NaN 更可靠。

<h2 id="q-027">面试问题：LVM 的 PV、VG、LV 怎样组织磁盘，扩容时要检查什么？</h2>

<a id="26.Linux中的存储空间管理之LVM"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

LVM 在物理设备与文件系统之间增加卷管理层。PV 是纳入管理的物理卷，VG 把一个或多个 PV 组织为容量池，LV 从容量池分配逻辑块设备；文件系统建立在 LV 上，再挂载到目录。

```text
磁盘或分区 -> PV -> VG -> LV -> 文件系统 -> 挂载目录
```

这意味着“逻辑卷变大”和“文件系统能使用新增空间”是两个步骤。先用只读命令确认布局：

```bash
lsblk -f
pvs
vgs
lvs -a -o +devices
findmnt /data
```

如果 VG 有空闲空间，可按计划扩展目标 LV，再调整文件系统；若 VG 无空闲，需要先扩容底层设备或纳入经过确认的新 PV。`lvextend -r` 可在支持的组合中协助调整文件系统，但仍要核实工具、挂载状态和错误结果。ext4 常用 `resize2fs`，XFS 扩展通常对挂载点运行 `xfs_growfs /data`，不能把设备路径与挂载点混用。

缩容比扩容约束更多。必须先确认文件系统支持缩容，并先缩小文件系统再缩 LV；XFS 不支持常规原地缩小，不能照搬 ext4 的步骤。对正在使用的错误设备执行 `pvcreate`、`mkfs` 或缩卷会破坏数据，因此操作前要核对设备身份、备份和恢复路径。

LVM 快照可保留某个时刻的块视图，但不等于独立备份，也不自动保证应用一致性。快照空间或 thin pool 元数据耗尽会造成严重问题。跨盘线性 LV 也不自动提供冗余，一块盘损坏可能影响整个卷，可靠性需要另行设计。

<h2 id="q-028">面试问题：出现 No space left on device，为什么不能直接开始删文件？</h2>

<a id="27.介绍一下Linux中“No-space-left-on-device”问题的解决方案"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

这条错误表示相应操作缺少某类可分配资源，首先要确定失败路径和系统调用。最常见的是文件系统块空间或 inode 耗尽，但 tmpfs、容器可写层、共享内存和某些内核资源也可能产生类似报错。

```bash
findmnt -T /data/output
df -h /data/output
df -i /data/output
du -xhd 1 /data
sudo lsof +L1
```

先定位挂载点，再分辨容量与 inode。`df` 很满而 `du` 找不到足够大的文件时，检查已删除但仍打开的文件、被挂载隐藏的目录、快照及保留空间。`lsof +L1` 帮助找出链接数为零而仍被打开的文件；通常需要相关进程关闭或重新打开文件后，空间才会释放。

还有几类容易漏查的限制：`/tmp` 或 `/dev/shm` 是单独的 tmpfs；容器层或项目配额有自己的上限；LVM thin pool 的数据或元数据耗尽；程序使用 inotify 等接口时触及相应内核上限。配额常返回 `Disk quota exceeded`，因此要保留完整错误文本，不能只凭应用的一句总结判断。

确认后再选清理对象、调整日志保留、迁移数据或扩容。不要默认执行 `docker system prune -a -f`，它可能删除后续回滚需要的镜像；也不要清空所有日志，丢失故障证据。保留最近成功的检查点和可验证备份，再依据生命周期清理。

长期治理要监控剩余字节、inode、增长速度与写入失败。定时任务应采用正确的 cron 或 systemd timer 格式，写清路径、身份、退出状态和保留规则；把一条 crontab 时间表达式直接写进 `/etc/cron.weekly` 并不会变成有效的可执行脚本。

<h2 id="q-029">面试问题：chmod、目录权限、umask、ACL 和特殊位如何配合？</h2>

<a id="28.介绍一下Linux中修改文件权限的命令"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

普通文件的 `r/w/x` 分别控制读取内容、修改内容和执行；目录的含义不同：`r` 允许列出名字，`x` 允许遍历并按名字访问条目，`w` 配合 `x` 允许创建、删除或重命名条目。删除文件通常主要取决于父目录权限，不能认为文件只读就一定不能被删除。

```bash
chmod 640 model.safetensors
chmod 750 run.sh
chgrp modelreaders model.safetensors
namei -l /srv/models/model.safetensors
getfacl /srv/models/model.safetensors
```

八进制 4、2、1 分别对应读、写、执行。权重文件通常不需要执行权限；路径上任意父目录缺少遍历权限，都可能导致最终文件不可读。`namei -l` 可逐级检查，ACL 则能为特定用户或组表达超出三组权限的授权，ACL mask 还可能限制其有效权限。

umask 从程序请求的初始模式中屏蔽权限，通常可理解为按位清除，不是简单算术相减。默认 ACL 也会影响新文件权限。共享目录设置 setgid 可让新条目继承组，但还要结合 umask 或默认 ACL 确保组可写。

sticky bit 常用于共享可写目录，限制普通用户删除或重命名他人的条目；文件所有者、目录所有者及特权进程有相应例外。它不限制文件内容写入，也不能表达“只有运维组才能删除所有日志”。setuid 程序会涉及执行身份提升，不能把它解释成一般容器权限继承。

出现拒绝后按 UID、组、完整路径、ACL、挂载与强制访问控制逐层排查。递归修改前区分目录与普通文件，避免给所有数据文件增加执行位，或去掉目录必需的遍历权限。

<h2 id="q-030">面试问题：内网迁移训练数据时，怎样验证完整性并控制切换风险？</h2>

<a id="29.两台服务器之间如何进行内网传输数据？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

内网传输同样需要认证、完整性与一致性。高速链路只解决搬运速度，不能保证目标目录包含的是某个一致版本的数据。先确定源数据是否还在写入，是否需要快照或短暂停写，再选择传输工具。

对目录增量迁移，rsync over SSH 常见用法是：

```bash
rsync -a --partial --info=progress2 ./dataset/ user@192.0.2.20:/data/dataset/
```

这里源目录尾部 `/` 表示复制其中内容。`-a` 保留常见文件属性，但 ACL、扩展属性和硬链接需要按需求额外设置，并依赖双方权限与文件系统支持；不能把它理解为所有元数据都无条件一致。`--delete` 会删除目标多余文件，只有明确做镜像同步时才使用，并先预演。

完整性检查最好在固定版本目录中生成相对路径清单，校验 SHA-256、文件数和必要元数据。校验清单本身也要来自可信路径。文件传输成功不证明它符合数据 schema，必要时再检查样本可解码、索引引用和分片完整性。

大数据可先全量复制，再在约定的停写窗口完成最后增量与校验，最后切换读入口，并保留旧版本以便回退。复制过程中持续改写同一个大文件会破坏一致快照，应使用版本目录或写临时文件后发布。

SFTP/scp 适合交互或一次性复制；命令与 SSH 认证细节见[网络章节](计算机网络高频知识点.md#q-006)。加密传输只是安全措施之一，不能据此声称自动满足某项隐私或行业合规标准。

<h2 id="q-031">面试问题：RAM 的随机存取是什么意思，容量与带宽又有什么区别？</h2>

<a id="30.什么是RAM？"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

RAM 是 Random Access Memory，随机存取表示可以按地址访问不同位置，不必像顺序介质那样先走过前面的全部数据。“随机”描述访问方式，不表示数据是随机的，也不保证所有地址实际访问延迟完全相同，缓存和 NUMA 就会造成差异。

常见主内存使用 DRAM，需要刷新来维持电荷；CPU 缓存常使用 SRAM，以更高成本和较低密度换取速度。二者通常都易失，断电后不能保留普通运行数据。但“RAM”这个词本身不严格等于“易失存储”，还有非易失随机存取技术；讨论电脑内存时，通常指实际安装的 DRAM 容量。

容量决定能同时容纳多少工作集，带宽决定持续搬运数据的能力，延迟决定一次依赖访问需要等待多久。增加容量可以减少换页或容纳更大缓存，但不会自动提升单次计算速度。内存通道数量、频率、布局与访问局部性同样影响性能。

AI 任务中的主内存常用于数据加载、解码、缓存和模型加载过程；GPU 的权重与激活则可能主要放在显存，也可能通过 offload 或统一内存机制分布到其他位置。不能把所有模型中间结果都归到 CPU RAM。

容量评估应考虑数据 worker 的副本、预取队列、批次张量、模型加载临时缓冲和页缓存，最好测峰值。显存不足与主内存不足是不同错误，给机器加 RAM 未必能解决 CUDA OOM，除非同时改变计算和存储策略。

<h2 id="q-032">面试问题：主内存、缓存、显存、虚拟内存与 swap 有什么关系？</h2>

<a id="31.计算机的内存和RAM是一个概念吗？详细介绍内存各种类型的作用"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

日常说“电脑内存”通常指主内存；讨论存储层次时，才会进一步区分寄存器、CPU 缓存、DRAM、显存与持久存储。这里有硬件介质，也有操作系统抽象，不能把它们全放在同一层当成互斥的产品分类。

虚拟内存为每个进程提供地址空间，通过页表把虚拟页映射到物理页、文件等后备对象，并提供隔离、共享和按需分配。**没有 swap，系统仍然使用虚拟内存**。swap 只是将某些匿名页移到后备存储的机制之一，不能把虚拟内存定义为“硬盘模拟 RAM”。

<div align="center">

| 概念 | 主要职责 | 常见误区 |
| --- | --- | --- |
| CPU cache | 缓存近期使用的数据和指令 | 与浏览器磁盘缓存不是同一个层级 |
| 主内存 | 承载进程工作集和页缓存 | 空闲少不必然表示内存不足 |
| GPU 显存 | 承载设备端数据与状态 | 分配、保留和实际活跃使用不同 |
| 页缓存 | 缓存文件内容，减少存储访问 | 文件读快可能只是缓存命中 |
| 虚拟内存 | 地址转换、隔离、共享和按需映射 | 虚拟地址空间大不等于物理内存占用大 |
| swap | 为部分页提供换出位置 | 容量增加不能替代主内存带宽 |

</div>

页错误也不都等于磁盘读取：按需分配、写时复制可能产生无需存储读取的 minor fault；需要从后备存储取回数据的 major fault 则更可能有明显等待。持续换入换出可能造成抖动，使系统忙于搬页而无法推进业务。

ROM 与 Flash 主要涉及固件或持久数据存储，现代固件常用可重写的 Flash；SSD 本身也常以 NAND Flash 为介质，不能说 Flash 的速度“介于 RAM 和 SSD 之间”。先确定讨论的是介质、缓存策略还是地址抽象，术语才不会越解释越乱。

<h2 id="q-033">面试问题：curl、wget 与多连接下载工具怎样可靠下载模型文件？</h2>

<a id="32.介绍一下Linux中下载命令的使用大全"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

下载的完成标准包括正确状态码、完整字节、可信校验和及可解码内容。HTTP 200 可能返回登录页或错误页面，文件名叫 `model.bin` 也不证明内容是模型。

```bash
curl --fail --location --show-error --connect-timeout 10 \
  --retry 3 --output model.bin.part https://example.com/model.bin
sha256sum model.bin.part
```

示例 URL 需替换为真实来源。`--fail` 将常见 HTTP 错误视为失败，`--location` 跟随重定向，连接超时不等于总下载时限。与可信源给出的校验值比较通过后，再将临时文件发布为正式文件；只计算一个本地哈希却不与预期值比较，不能验证来源一致性。

`wget -c`、`curl -C -` 支持续传，但依赖服务器范围请求能力，且必须保证远端文件版本没有改变。应使用不可变 URL、版本号、ETag 或最终校验，防止把旧文件前半段和新文件后半段拼在一起。签名链接过期后，应刷新同一版本的下载地址，而不是盲目重试到无限期。

aria2、axel 可通过多个连接或分片利用链路，但收益受服务端限流、Range 支持和本地写盘限制。aria2 的 `-s` 是分片相关设置，不能简单等同于操作系统线程数；也没有普遍“快 3 到 5 倍”的保证。现代 curl 也支持多传输并行，工具边界应按版本理解。

证书错误先检查时间、CA、证书链与代理配置，不能默认关闭验证。不要将未验证下载直接管道交给 Shell 执行，也不宜让不可信归档直接覆盖工作目录。认证信息从受限配置读取，详细网络日志共享前移除凭据与签名参数。

<h2 id="q-034">面试问题：Linux 文本处理、二进制检查和调试工具怎样配合？</h2>

<a id="33.AI行业中必备的Linux命令大全"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

入门命令负责导航与运行，进阶工具用于把问题缩小到内容、依赖或系统调用。选择工具前先提出一个可验证的问题，例如“加载了哪一个动态库”“哪个文件打开失败”“等待发生在哪个系统调用”。

<div align="center">

| 问题 | 工具 | 解释边界 |
| --- | --- | --- |
| 查找源码或日志内容 | `rg`、`grep` | 正则匹配不等于理解结构化格式 |
| 文本提取与聚合 | `awk`、`sed`、`sort`、`uniq`、`wc` | `uniq` 只合并相邻重复项，列切分要考虑分隔格式 |
| JSON 内容 | `jq` | 比用正则拆嵌套 JSON 更可靠 |
| ELF 架构和依赖 | `file`、`readelf`、`objdump` | 检查文件结构，不需要直接运行未知程序 |
| 系统调用与信号 | `strace` | 可能显著改变时序，并暴露路径或参数 |
| 调用栈与性能热点 | `gdb`、`perf`、运行时 profiler | 权限、采样与暂停都会影响结果 |
| 内存映射和打开资源 | `pmap`、`lsof`、`/proc` | 映射大小不等于独占物理内存 |

</div>

例如 Python 导入扩展失败，先用 `file` 确认 CPU 架构，再用 `readelf -d` 查看依赖名称与搜索路径，必要时观察动态加载器日志。不要先把所有 `.so` 文件复制到系统目录，这会制造更难追踪的版本污染。

`ldd` 对可信二进制很方便，但不应对未知不可信程序默认执行；静态检查依赖时可先用 `readelf`。`strace` 则适合验证 `ENOENT`、`EACCES`、连接失败等系统调用结果，它无法单独解释一个 GPU kernel 的内部效率。

采集证据时限定进程、时间窗口和输出量，保留命令、环境与时间。网络操作优先使用 `ip`、`ss` 等现行工具，同时理解旧环境中的 `ifconfig`、`netstat`，避免工具名变化掩盖了相同的底层问题。

<h2 id="q-035">面试问题：僵尸进程与孤儿进程有什么区别，容器中怎样正确回收？</h2>

<a id="34.什么是僵尸进程？如何处理僵尸进程？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

僵尸进程已经退出，内核保留 PID、退出状态与少量记账信息，等待父进程调用 `wait`/`waitpid` 回收。它不再执行用户代码，地址空间等大部分资源已释放，但仍消耗内核资源，所以不能说它“完全不占内存”。

孤儿进程则是父进程先退出，子进程仍可能正常运行。Linux 会把它交给相应的 subreaper 或 PID 命名空间中的 init 角色；接管者仍需正确执行回收逻辑。“成为孤儿”与“成为僵尸”是不同阶段和关系。

```bash
ps -eo pid,ppid,stat,args
```

查看 `STAT` 为 Z 的记录与其 PPID，定位没有回收子进程的父进程。对僵尸本身发送 `SIGKILL` 没用，它已经退出。应修复父进程的等待逻辑，必要时按服务预案重启父进程并确认接管者能回收。

程序管理多个子进程时，要循环收集已经退出的子进程，考虑 `EINTR` 等情况，避免一个 `SIGCHLD` 只回收一个孩子。Python 的 `Process.join()`、子进程上下文管理和 `communicate()` 等接口有相应生命周期语义；`daemon=True` 不是通用的自动回收保证。

容器 PID 1 需要处理信号与子进程回收，可以采用合适的 init 进程或框架管理器。`PR_SET_CHILD_SUBREAPER` 让进程承担接管角色，不会自动替它调用 wait。大量进程创建失败时还要检查 PID/cgroup 上限与内存，不能把所有 `fork` 错误都归到僵尸堆积。

<h2 id="q-036">面试问题：时间复杂度与空间复杂度能告诉我们什么，又不能告诉我们什么？</h2>

<a id="35.介绍一下计算机中的空间复杂度和时间复杂度的概念"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

复杂度描述资源消耗随输入规模增长的趋势。大 O 表示渐近上界，Θ 表示同阶界，Ω 表示下界；**大 O 本身不等于最坏情况**，可以分别分析最好、平均、最坏或摊销成本。

对 N 条记录求前 K 大，排序后截取通常需要 `O(N log N)` 时间，维护容量 K 的堆约为 `O(N log K)` 时间与 `O(K)` 辅助空间。哈希表查询常说期望 `O(1)`，还依赖哈希分布和实现，不能把最坏情况也无条件写成常数。

空间复杂度应声明口径：统计总空间还是额外辅助空间，是否计入递归栈与输出。原地快速排序通常有递归栈成本，常见平均深度为 `O(log N)`，不良划分可退化；归并排序的数组实现通常需要线性辅助空间。忽略递归栈会低估峰值占用。

AI 中，长度 N、维度 D 的普通密集注意力，其两次核心乘法有 `O(N²D)` 量级的计算，朴素注意力矩阵需要 `O(N²)` 空间。分块实现可避免完整矩阵常驻，降低内存流量与峰值，但精确密集注意力的算术量并不因此自动变成线性。完整 Transformer 还包括投影和前馈网络，不能把一个子模块公式当作全模型成本。

复杂度不直接给出秒数、显存 GB 或某个产品的速度。常数、并行度、精度、缓存、通信和内核实现会改变实际性能。LoRA 减少可训练参数，也不等于删掉了底座模型的大部分参数。先用复杂度排除不可扩展方案，再通过真实规模和硬件测量判断，是更可靠的分析顺序。

<h2 id="q-037">面试问题：静态链接与动态链接怎样影响部署、共享和升级？</h2>

<a id="38.Linux系统中静态链接与动态链接的优缺点有哪些？"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

静态链接通常在链接阶段把需要的库对象代码合入可执行文件；动态链接保留对共享库的依赖，由加载器在启动或运行过程中装入并解析符号。动态加载插件与模型参数加载又是不同概念，加载 LoRA 权重不必然涉及操作系统动态链接。

<div align="center">

| 方面 | 静态链接 | 动态链接 |
| --- | --- | --- |
| 交付 | 较少外部库依赖，文件可能更大 | 需要兼容共享库及正确搜索路径 |
| 更新 | 通常重新链接并发布程序 | 可单独更新库，但要守住 ABI 和部署一致性 |
| 共享 | 同一可执行文件的只读页也可共享 | 同一主机上相同库文件的只读页可共享 |
| 风险 | 固化漏洞依赖、平台与系统接口仍有限制 | 符号、ABI、搜索路径与版本冲突 |

</div>

共享库不会跨 10 台服务器自动只占一份磁盘，每台仍需安装或通过明确的共享存储访问。库的可写数据通常也不被进程无条件共享。因此，动态链接节省的是特定场景中的重复文件或物理页，不能用跨机器相加的错误算式夸大收益。

静态可执行文件仍依赖 CPU 指令集、内核接口和构建方式，一些运行库功能还可能涉及动态组件，不能保证“复制到任意服务器即可运行”。GPU 驱动相关依赖尤其需要按部署平台核对。

动态库替换也不等于所有运行进程立即热更新：已映射的旧文件可能继续使用，通常需要重启或明确的重载机制。排查时检查 ELF 依赖、RPATH/RUNPATH、实际加载路径与 ABI，避免在全局 `LD_LIBRARY_PATH` 中堆放多个冲突版本。可复现构建与受控发布，比简单偏好某一种链接方式更重要。

<h1 id="q-102">3.高并发服务与隔离边界</h1>

<h2 id="q-038">面试问题：AI 服务怎样分配进程、线程、协程与 GPU worker 的职责？</h2>

<a id="39.AI服务中进程线程协程和GPU-worker如何分工？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

一条请求通常经历网络接入、校验与预处理、排队、设备计算、后处理和流式输出。不同阶段的瓶颈不同，应让并发单元围绕资源职责组织，而不是一收到请求就新建进程加载模型。

Web 层可用协程承接大量等待中的连接；阻塞 SDK 或 CPU 预处理进入有界执行器；推理层由明确拥有模型与显存状态的 GPU worker 处理批次。GPU worker 是架构角色，可由一个进程管理一张或多张 GPU，也可有其他受控共享方式，不是操作系统新增的一种调度对象。

层之间需要有界队列与请求状态。排队过长时拒绝、降级或延后接单；客户端取消时传播取消意图，释放未执行任务和输出缓冲。已经提交的 GPU 工作未必能立刻取消，但完成后可以丢弃无用结果，并尽快释放请求状态。

多进程 Web server 会复制应用状态。若每个进程启动时都加载同一模型，显存需求可能倍增。CUDA 初始化后再随意 fork 也可能产生运行时问题，应遵守框架支持的进程启动方式，并在合适的 worker 中初始化设备。

还要明确故障边界：网络连接断开不应让整个模型进程崩溃，模型 worker 重启后前端应识别在途请求的结果未知状态，重试不能重复扣费。扩容入口线程不一定提高 GPU 吞吐；应根据最慢阶段、批处理效率和延迟预算决定容量。

<h2 id="q-039">面试问题：Pipe、消息队列、共享内存和 mmap 在推理服务中怎样选择？</h2>

<a id="40.共享内存mmap消息队列和Pipe在推理服务中如何选择？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

IPC 的选择取决于数据体积、消息边界、同步方式和生命周期。小控制消息可以直接传递，大图像或张量则常采用“传引用、共享数据”的方式，减少序列化和复制。

<div align="center">

| 机制 | 语义 | 主要代价 |
| --- | --- | --- |
| Pipe / Unix stream socket | 字节流 | 需要定义消息边界，处理部分读写与背压 |
| 消息队列 | 由具体实现提供消息边界与调度 | 可能序列化、复制，持久性不一定存在 |
| 共享内存 | 多进程映射同一批内存页 | 同步、所有权、越界与回收 |
| mmap 文件映射 | 将文件或匿名对象映射到地址空间 | 缺页、同步、映射方式与持久化语义 |
| 网络 socket | 可跨机器传输 | 协议、超时、认证与故障恢复 |

</div>

“消息队列都由内核维护”不准确，Python 队列、POSIX 队列和 Redis Streams 的实现与保证差别很大。`mmap` 也不表示无需 I/O，首次访问可能触发缺页；`MAP_PRIVATE` 的修改不回写为共享文件更新，`MAP_SHARED` 的可见性与持久化又需区分。

共享张量时，可传共享段 ID、偏移、长度、shape、dtype 与版本，让消费者验证边界后读取。生产者写完再发布可读状态，消费者确认使用完成后才允许复用；需要锁、信号量或有明确内存顺序的原子协议。共享内存本身不解决并发安全。

进程崩溃可能留下共享段，也可能让引用计数无法归零；队列满时要能限速，取消后要能回收。GPU IPC 句柄还具有设备、进程与分配生命周期限制，不能当成一个跨机器通用指针。降低复制必须与可恢复的所有权协议一起设计。

<h2 id="q-040">面试问题：select、poll、epoll 与 io_uring 的接口模型有什么区别？</h2>

<a id="41.selectpoll-epoll和io_uring有什么区别？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

select、poll、epoll 主要提供就绪通知：告诉应用某个描述符现在有条件执行读写，应用仍需真正调用 read/write。io_uring 以提交和完成队列组织操作，应用提交请求后，通过完成项取得结果；它也支持 poll 等操作，不能把每个 opcode 都理解成相同的异步路径。

<div align="center">

| 接口 | 工作方式 | 适用与边界 |
| --- | --- | --- |
| select | 传入描述符集合，返回就绪集合 | 常见 libc 的 FD_SETSIZE 限制，集合处理成本 |
| poll | 传入 pollfd 数组并检查结果 | 没有 select 同样的位图上限，仍受资源限制且需扫描 |
| epoll | 注册关注集合，再取得就绪事件 | 适合大量连接、少量活跃；维护与事件处理仍有成本 |
| io_uring | SQ 提交、CQ 完成，可批量处理 | 依赖内核、操作类型、文件系统与运行时支持 |

</div>

epoll 并不是对任何规模都严格 `O(1)`，性能取决于注册变更、活跃事件数和应用处理成本。普通磁盘文件也不能简单按网络 socket 的方式注册到 epoll 就获得真正异步文件读写。

io_uring 的共享环减少部分系统调用与复制开销，一些操作由内核异步推进，另一些路径可能借助工作线程处理。它不自动等于零拷贝，也不保证无需系统调用。注册缓冲区、polling、零拷贝发送等是额外机制，有各自前提与资源成本。

选型先看瓶颈。如果请求的大部分时间在模型计算或远端 API，替换 I/O 接口未必改善端到端延迟。需要评估内核版本、容器限制、取消与缓冲区生命周期、维护复杂度，并用目标负载比较。成熟运行时已经封装这些机制时，业务代码更应关注背压和任务边界。

<h2 id="q-041">面试问题：模型服务变慢时，怎样按资源与等待链定位问题？</h2>

<a id="42.Linux资源排查在AIGC服务中怎么做？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

先把“变慢”变成可比较的现象：影响哪些请求、从何时开始、是排队还是执行、P50 与 P95 怎样变化。同步查看流量、最近发布和错误率，避免把需求突然增加误判成单台机器性能退化。

<div align="center">

| 证据 | 进一步检查 | 不应直接得出的结论 |
| --- | --- | --- |
| CPU 高、GPU 低 | 解码、tokenization、线程与数据队列 | 一定需要更强 GPU |
| CPU 不高、延迟高 | I/O 等待、锁、下游、CPU throttling | 机器资源充裕 |
| 显存持续升高 | 请求状态、KV cache、模型副本、引用 | 一定是框架泄漏 |
| 磁盘等待增加 | 存储队列、随机 I/O、日志与 checkpoint | `util=100%` 对所有设备都等价饱和 |
| FD 接近上限 | socket、文件、连接池和泄漏趋势 | 把上限调大即可解决 |

</div>

可先采样 `vmstat 1`、`iostat -x 1`、`pidstat -u -d -w 1` 和 GPU 指标，再缩小到目标进程。FD 数可以观察 `/proc/PID/fd` 与 `/proc/PID/limits`；`lsof -p PID` 包含映射等多种记录，简单按行计数并不严格等于文件描述符数量。

如果 CPU、磁盘都不忙，线程栈或追踪可能显示正在等待锁、连接池或下游响应。对容器还需读取 cgroup 配额和压力，宿主机指标可能掩盖租户被限速。高 TIME_WAIT 也不一定是泄漏，它可能来自正常短连接，应结合端口资源和连接复用判断。

每次只验证一个假设，记录调整前后的同口径结果。排查的目标是找到等待链上的限制环节，不能把重启后的短暂恢复当成根因证据。

<h2 id="q-042">面试问题：容器的 CPU、内存、GPU、共享内存与 FD 限制如何影响服务？</h2>

<a id="43.容器中的CPU内存GPU和文件句柄限制如何影响模型服务？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Linux 容器通常共享宿主机内核，namespace 改变进程可见的资源视图，cgroup 管理资源分配与使用。它们提供不同维度的边界，镜像中能看到很多 CPU，不代表进程可以持续使用全部算力。

CPU quota 限制一段周期内可用的 CPU 时间，cpuset 限定可以运行在哪些 CPU 上，CPU weight 则在竞争时影响相对份额。三者含义不同。cgroup v2 的 `cpu.max`、`cpu.stat` 可帮助判断配额与 throttling。

内存限制涉及匿名页、页缓存及相应记账。接近上限时可能先回收和等待，再发生 cgroup OOM；进程被 SIGKILL 后退出码常见 137，但仅凭 137 不能证明 OOM，应结合 `memory.events` 和容器运行时状态。`/dev/shm` 的大小单独影响共享内存和多进程数据加载。

GPU 可见性通常由容器运行时和设备插件管理，`CUDA_VISIBLE_DEVICES` 主要控制应用可见设备，不是强安全隔离。普通 cgroup 内存限制也不自动等价于显存硬配额；显存隔离需结合设备能力、MIG 或服务调度等机制。

FD 限制受进程软硬上限约束，容器运行时还可能设定进程数量、临时存储与日志限制。模型服务应把 CPU、主内存、显存、共享内存、队列长度和连接数放在同一容量模型里。资源规格只写“一张 GPU”，不足以保证数据预处理、网络和日志都能跟上。

<h2 id="q-043">面试问题：Reactor、Proactor 以及 epoll 的 LT/ET 应怎样理解？</h2>

<a id="44.ReactorProactorepoll-LTET在高并发AI服务中如何理解？"></a>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

Reactor 在资源就绪时分发事件，处理器执行非阻塞读写；Proactor 先提交操作，再根据完成通知处理结果。区别是回调接收到“可以尝试操作”还是“某项操作已经完成”，不应简单按有没有线程池来分类。

epoll 的 LT 是水平触发：只要描述符仍满足就绪条件，后续等待还可能报告。ET 是边缘触发：依赖状态变化通知，应用如果没有消耗完已就绪数据就去等待下一次边沿，可能错过继续处理的机会。通常配合非阻塞 FD，读写直到 `EAGAIN`，或由运行时明确保存待处理状态。

读就绪不代表一定能读到完整消息，可能只有部分数据，也可能是连接关闭或错误；写就绪也不代表可以一次发送所有缓冲。程序需保存部分读写进度，并处理其他线程竞争导致的状态变化。

ET 并不天然比 LT 更快。它可能减少重复通知，也增加状态管理难度；单个连接一直有数据时，无限处理到耗尽还可能影响其他连接公平性，需要配合批次预算与内部就绪队列。`EPOLLONESHOT` 是另一个独立选项，使用后需适时重新启用通知。

模型服务的事件处理器应快速完成解析、状态更新和投递，避免直接执行长时间推理。输出方向设置有界缓冲，客户端读慢时暂停生产或取消；否则网络层“支持高并发”也会被无界 token 缓冲耗尽内存。I/O 模型决定怎样等待，资源调度决定系统能承受多少工作。

<h2 id="q-047">面试问题：kubectl 如何定位 Pod 无法启动、重启与服务不可达？</h2>

<a id="36.kubectl操作集群常用命令"></a>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

kubectl 是 Kubernetes API 的客户端，首先确认 context 和 namespace，避免在错误集群操作。诊断时优先查询期望状态、实际状态与事件，再决定是否修改资源。

```bash
kubectl config current-context
kubectl get pods -n ai -o wide
kubectl describe pod model-worker -n ai
kubectl logs model-worker -n ai -c worker --tail=100
kubectl logs model-worker -n ai -c worker --previous --tail=100
kubectl get events -n ai --sort-by=.metadata.creationTimestamp
```

Pending 可能来自调度资源、节点约束或存储卷；ImagePullBackOff 需要检查镜像地址、凭据与网络；CrashLoopBackOff 表示容器反复退出后的退避状态，真正原因要看退出信息与前一次日志。Pod 为 Running 也不表示应用 ready，应检查探针和 Service 的 EndpointSlice。

`kubectl exec` 在容器中执行命令，需要对应权限，镜像也未必包含 Bash。`port-forward` 适合临时本地验证，但会绕开部分外部入口路径；转发成功不能证明 Ingress、负载均衡或公网 DNS 正常。

变更通常使用声明式清单，先检查 diff，再 apply，并通过 rollout status 观察是否达到期望。删除受 Deployment 管理的 Pod，控制器往往会再创建一个；这不是删除整个服务。强制删除 API 对象也不保证旧节点上的进程已经停止，不能把它作为有状态任务的默认修复。

GPU 调度还需查看节点资源、设备插件、镜像运行时和请求限制。不要把 `livenessProbe` 当成节点重启机制：它通常影响容器生命周期；readiness 决定是否接流量，startup probe 则适合较慢的模型初始化。

<h2 id="q-048">面试问题：Grafana、指标存储与告警系统各自负责什么？</h2>

<a id="37.什么是grafana"></a>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Grafana 主要提供查询、展示、探索与告警组织能力，通过数据源连接指标、日志和追踪后端。Prometheus、Loki 等系统分别负责相应数据的采集、存储或查询链路，不能把安装一个仪表盘等同于完成监控。

Grafana 本身会保存仪表盘、用户、数据源配置等元数据，因此“Grafana 完全不存数据”过于绝对；更准确的说法是，它通常不承担外部时序数据源的原始指标存储职责。Grafana Cloud 等产品组合又包含其他托管能力，应按实际部署组件区分。

模型服务的面板可以按请求量、错误率、排队、首 token 延迟、GPU 状态和下游依赖组织。每个图都要知道查询口径、聚合窗口和单位。平均值会掩盖尾延迟，多实例的 P95 也不能简单取平均作为全局 P95；直方图需按相应规则聚合。

告警应指向需要行动的症状，例如可用性下降、错误预算消耗或队列持续增长，再通过标签和关联链接进入日志与追踪。对瞬时尖峰设置合适持续时间，对“无数据”与“查询失败”明确处理，避免监控断流时反而显示一切正常。

共享看板还要限制数据源权限和敏感维度，不能把用户提示词或密钥做成标签。高基数标签会增加存储和查询成本。看板是否漂亮不是验收标准，真正要验证的是异常发生时能否及时发现，并找到足够证据定位问题。

<h1 id="q-103">4.值得持续掌握的系统机制</h1>

<h2 id="q-050">面试问题：Python free-threading 改变了什么，为什么不能直接删除所有锁？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

free-threaded CPython 允许多个线程在不同 CPU 核心并行执行 Python 代码，改变了过去依赖全局解释器锁限制执行并行度的条件。Python 3.13 引入可选构建，PEP 779 将 Python 3.14 的这一构建推进到正式支持阶段；这不表示所有 Python 安装都默认关闭 GIL。

应同时确认构建能力与运行状态。在支持的版本中，`sysconfig.get_config_var("Py_GIL_DISABLED")` 可用于检查构建，`sys._is_gil_enabled()` 可检查当前进程是否仍启用 GIL。某些未声明支持的扩展模块导入后可能重新启用 GIL，所以只检查版本号不够。

移除 GIL 不会让业务复合操作自动具备原子性。先查缓存、发现没有、再写入，多个线程仍可能重复执行；共享计数、状态机和文件更新同样需要明确同步。内置容器为部分内部操作提供保护，也不能推导任意跨操作不变量都安全。

性能收益取决于负载。纯 Python CPU 工作可能获得新的并行空间，已在原生库中释放 GIL 的矩阵计算则未必同等受益；更多线程还会竞争内存带宽、对象锁和分配器。模型服务同时要验证 NumPy、框架与 C 扩展的 wheel 和 ABI 支持，不能只替换解释器就上线。

合理迁移是先审计共享状态与扩展依赖，再用代表性负载比较正确性、吞吐、P95 延迟和内存；保持可回退环境。这项变化的长期意义，是让“Python 线程是否能并行”成为需要根据构建和实际代码回答的问题，而非一句固定结论。

<h2 id="q-051">面试问题：PSI 为什么比单看内存使用率更能反映资源压力？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

利用率描述资源被使用了多少，压力描述任务因为资源不足而停顿了多久。Linux PSI（Pressure Stall Information）统计 CPU、内存和 I/O 的停顿时间，使我们能区分“缓存用得很多但任务顺畅”与“占用尚未到顶但任务持续等待”。

```bash
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
```

`some` 表示至少有部分任务因该资源停顿的时间比例；`full` 表示相关非空闲任务同时停顿的时间比例。`avg10`、`avg60`、`avg300` 反映不同窗口的趋势，`total` 累计停顿微秒数。CPU 的系统级 full 有特殊定义与兼容行为，不能机械照搬内存 full 的解释。

cgroup v2 还可提供组内压力信息，适合区分哪一个容器或租户正在承受竞争。`memory.high` 常用于触发回收与节流，`memory.max` 则是更硬的上限，无法回收时可能触发 OOM；因此服务在 OOM 前就可能因回收而出现严重尾延迟。

例如内存使用率保持 85%，但 memory some 与 major fault 持续升高，可能是工作集反复被回收。此时减少预取、限制并发或扩大可用内存可能比重试请求更有效。IO pressure 上升则需结合设备队列、吞吐和进程 I/O 分析，PSI 本身不告诉你具体哪个文件慢。

压力可以作为容量预警或负载控制信号，但阈值应由业务延迟目标和实测关联确定。它补充了利用率视角，不能取代应用指标、资源配额和调用链证据。

<h2 id="q-052">面试问题：NUMA、页锁定内存与零拷贝为什么都要结合数据位置理解？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

在 NUMA 系统中，不同 CPU 节点访问本地与远端内存的成本可能不同，GPU 与网卡也连接到特定 PCIe 或互联拓扑。进程能访问一块内存，不表示访问成本处处相同。

操作系统通常依据分配策略和首次实际访问等因素放置物理页。可用 `numactl --hardware`、`numastat -p PID` 和设备拓扑信息观察，再决定是否绑定 CPU 与内存。只绑线程、不控制内存分配位置，可能仍然大量访问远端节点；过度绑定又可能牺牲负载均衡和可用容量。

页锁定内存让相关主机页不被常规换出，便于设备 DMA 及某些异步传输。它与“数据已经在 GPU 显存”不同，也不表示 CPU/GPU 自动共享缓存一致性。必须管理容量、访问时机和缓冲区生命周期，确保设备使用完成前不复用数据。

零拷贝是相对于某条路径减少了某次复制。例如 `sendfile` 可减少文件到 socket 的用户态往返，mmap 可避免显式 read 到用户缓冲区，但仍可能发生磁盘读取、内核复制或设备传输。GPU 直接访问主机内存也依赖平台，频繁远端访问可能比先复制到显存再重复计算更慢。

比较方案时画出数据从哪里来、由谁读写、通过哪条总线、何时同步，再测吞吐与尾延迟。减少一次复制值得关注，但只有在访问局部性、所有权和完成通知都正确时，才会成为稳定的收益。
