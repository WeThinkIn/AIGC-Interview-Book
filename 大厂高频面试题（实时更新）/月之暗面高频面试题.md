### 1. 月之暗面 Agent 开发岗一面面经

#### 面试问题汇总

<a id="moonshot-agent-dev-20260721-q1"></a>
##### 1. 简单讲讲你的Agent项目？

**回答：**

我会先用一句话定义项目：这是一个面向长链任务的 Agent 系统，以 ReAct 为基本决策循环，结合工具调用、RAG、短期工作记忆和长期记忆，让模型能够围绕目标持续执行，而不是只生成一次答案。

核心执行链路可以抽象为：

$$
s_t \xrightarrow{\pi_\theta} a_t
\xrightarrow{\text{tool/env}} o_{t+1}
\xrightarrow{\text{state update}} s_{t+1}
$$

其中 $s_t$ 是当前任务状态，$a_t$ 是模型选择的动作或工具调用，$o_{t+1}$ 是外部环境返回的 Observation。运行时不是简单写一个无限 `while`，而是受状态机约束：每一步都要做工具权限检查、参数校验、超时与重试控制，并在完成条件、失败条件、人工审批点或最大步数到达时终止。

项目中我把能力拆成四层。第一层是规划与路由，决定当前任务应直接回答、检索知识、读取记忆还是调用工具。第二层是执行层，对工具 schema 做约束解码和参数验证。第三层是状态与记忆层，保存当前目标、已完成步骤、中间产物以及需要跨会话复用的信息。第四层是可观测与评测层，记录每一步输入、动作、工具返回、耗时和失败原因，并用任务完成率、工具选择正确率、参数正确率、无效步骤数和失败恢复率评估。

需要纠正一个常见说法：Observation 来自真实工具，只能提供外部证据，不能自动“保证长线任务可靠”。工具可能超时、返回脏数据，模型也可能误读 Observation 或陷入循环。真正的可靠性来自工具反馈、状态约束、验证器、预算、回退策略和人工复核共同组成的 Harness。

面试中还应落到个人贡献和结果：具体负责了哪些模块、如何构建评测集、哪类失败最常见、上线后任务成功率或人工耗时改善了多少。没有真实指标时不要编造，可以诚实说明当前做到离线验证还是灰度阶段。

<a id="moonshot-agent-dev-20260721-q2"></a>
##### 2. 短期记忆的具体实现方式是什么？

**回答：**

短期记忆不是一个单独的神秘模块，它本质上是当前任务继续执行所必需的工作状态。它既包括送入模型的近期上下文，也包括不一定直接放进 Prompt 的结构化状态，例如当前目标、执行计划、已完成步骤、工具返回引用和待确认事项。

我会把短期记忆拆成三层：

| 层次 | 主要内容 | 处理方式 |
|---|---|---|
| 固定约束 | System 指令、权限、安全边界、输出契约 | 高优先级保留，版本化管理 |
| 工作集 | 最近对话、当前计划、未完成步骤、关键工具结果 | 每轮更新，按任务相关性裁剪 |
| 历史压缩 | 更早轮次的结构化摘要和事件引用 | 达到预算或阶段边界时生成 |

工程上可以使用“近期窗口 + 结构化摘要 + 外部原始事件存储”。近期窗口保留最后若干轮完整交互；摘要不是泛泛复述，而应固定字段，例如 `goal`、`constraints`、`completed_steps`、`open_questions`、`artifacts`、`decisions` 和对应的事件 ID。这样能减少摘要遗漏关键约束，也方便回溯原文。

短期状态可以存在 Workflow state、会话数据库或检查点存储中；Prompt 只是它的一种投影视图。每次模型调用前，由 Context Builder 根据 Token 预算选择哪些状态进入上下文。这样即使模型窗口变化，底层任务状态仍保持稳定。

最后要强调：KV Cache 是推理加速状态，不等于 Agent Memory；聊天记录也不等于短期记忆。短期记忆的标准是“它是否帮助当前任务正确继续”，而不是“它是否最近出现过”。

<a id="moonshot-agent-dev-20260721-q3"></a>
##### 3. 什么叫“快到上限了”？对话是怎么逐步叠加的？

**回答：**

“快到上限”不是简单看对话轮数，而是预测下一次请求会不会超过可用上下文预算。一次模型调用的 Token 预算至少包含：System 指令、工具 schema、历史消息、长期记忆/RAG 片段、当前用户输入，以及必须为模型输出预留的 Token。

可以写成：

$$
B_{\mathrm{used}}=B_{\mathrm{system}}+B_{\mathrm{tools}}+
B_{\mathrm{history}}+B_{\mathrm{retrieval}}+B_{\mathrm{query}}
$$

只有满足 $B_{\mathrm{used}}+B_{\mathrm{reserved\ output}}<B_{\mathrm{window}}$，请求才是安全的。工程上还要保留安全余量，避免 tokenizer 估算误差、工具返回突增或模型自动推理预算占满窗口。

在常见的无状态 Chat API 中，对话确实是不断追加消息，并在下一轮把所需历史重新发送给模型。模型不会因为“上一轮见过”就天然记住；服务端会话、Prompt caching 或 KV Cache 可以降低传输/计算成本，但不能改变模型本次只能基于可见上下文决策的事实。

增长最快的往往不是用户对话，而是工具 schema、代码文件、搜索结果和日志。因此系统应在调用工具前估算潜在返回大小，限制日志行数、分页读取大文件，并把完整产物存外部对象存储，只向模型提供摘要和可按需展开的引用。

所以“快到上限”的正确实现是动态 Token Budgeter，而不是写死“第 10 轮总结”或固定使用窗口的 70%。不同轮次的信息量差异很大，轮数只能作为辅助信号。

<a id="moonshot-agent-dev-20260721-q4"></a>
##### 4. 如果对话轮次过多，你怎么去做优化？

**回答：**

对话过长时，我不会只做一次粗暴截断，而是按“保真优先级 + 按需取回”管理上下文。

第一，永远保护系统约束、权限、当前目标和输出契约；这些内容一旦被摘要掉，Agent 可能改变行为边界。第二，保留最近的完整交互和当前未完成步骤，它们构成工作集。第三，把已完成阶段压缩成结构化状态，而不是自然语言流水账。第四，将原始对话、工具日志和大文件放在外部存储中，通过事件 ID、文件句柄或检索接口按需取回。

上下文组装时再做相关性选择：与当前子任务直接相关的历史优先；已经完成且没有后续依赖的细节只保留结论；失败轨迹只保留失败原因和不可重复的动作，避免模型再次踩坑；高风险决策要保留证据和审批记录，不能只剩一句摘要。

还可以把长任务切成多个有边界的阶段，每个阶段结束生成 checkpoint。子任务之间通过结构化产物传递，而不是把全部对话继续往后拖。对代码 Agent 来说，这种产物可以是修改文件列表、测试结果、剩余 TODO 和当前 Git diff；对业务 Agent，可以是订单 ID、审批状态和待补字段。

Rocky认为，长上下文优化的本质不是“把 Prompt 压短”，而是把对话历史升级为可管理的任务状态。只有状态可恢复、原文可回溯、信息可按需展开，压缩才不会变成不可逆的信息丢失。

<a id="moonshot-agent-dev-20260721-q5"></a>
##### 5. 什么时候去触发这个总结动作？

**回答：**

总结触发应由预算风险和任务语义共同决定，而不是每隔固定轮数机械执行。

预算触发上，Context Builder 在每次调用前预估总 Token，并为输出、工具返回和误差保留余量。当预计下一步会超预算时触发压缩。可以设置软水位和硬水位：软水位提前异步生成候选摘要；硬水位则阻塞新调用，确保上下文完成一致性压缩后再继续。但具体比例要通过真实请求分布校准，不能把 70%/90% 当成通用答案。

语义触发包括：一个子任务完成、用户目标发生切换、工具产生大体量结果、连续失败需要重规划、对话即将转入人工审批，或者当前状态已经稳定到可以形成 checkpoint。这些时刻比“第 N 轮”更适合总结，因为信息边界清晰。

并发场景中，总结必须基于带版本号的不可变快照。生成摘要后使用 compare-and-swap 或事务检查：如果原会话版本已经变化，就不能直接覆盖最新状态，而要合并新增事件或重新生成。摘要落库后还应记录覆盖的事件范围，例如 `events[1:42]`，确保不会重复压缩或漏掉消息。

总结前后要运行一致性检查：目标、硬约束、未完成事项、关键实体和工具产物引用是否都保留。高风险字段可以规则化提取并单独存储，不完全依赖 LLM 摘要。

<a id="moonshot-agent-dev-20260721-q6"></a>
##### 6. 是每一轮对话都要去做总结吗？

**回答：**

不是。每轮总结会增加一次模型调用、显著拉高延迟和费用，而且会制造“摘要的摘要”：信息每经过一次有损压缩，都可能丢失限定条件、时间关系和否定信息。

合理策略是事件驱动。平时只追加新事件并更新少量结构化状态；达到 Token 预算、阶段完成或目标切换时才总结。最近几轮通常保留原文，不需要立刻压缩。对工具返回，可以优先用确定性解析器提取字段，再决定是否需要 LLM 总结。

增量摘要虽然便宜，但不能无限滚动。系统应周期性地从原始事件或稳定 checkpoint 重建摘要，并用事实一致性检查比较新旧版本，防止错误不断累积。摘要中最好保存关键事实对应的原事件 ID，遇到低置信或高风险问题时回读原文。

是否总结最终看单位收益：减少了多少 Token、引入了多少延迟、保留了多少任务信息、是否影响任务成功率。不能只优化上下文长度，却让 Agent 忘记用户约束。

<a id="moonshot-agent-dev-20260721-q7"></a>
##### 7. 假设已进行 10 轮并做了总结，第 11 轮开始时，总结怎么处理？是重算前 11 轮还是叠加？

**回答：**

第 11 轮开始时，正常做法是使用已有摘要 $S_{1:10}$ 加上尚未被摘要的近期消息，而不是立刻重算前 11 轮，也不是每出现一条新消息就再压缩一次。

当后续再次达到触发条件时，可以基于旧摘要和增量事件生成新版本：

$$
S_{1:11}=\operatorname{Summarize}(S_{1:10},D_{11})
$$

这种增量更新成本低，但它是有损链路。若长期只在旧摘要上继续摘要，早期错误和遗漏会被固化。因此工程上应采用“增量更新 + 周期性重建”：日常基于上一版本和新事件更新；到达重要阶段、摘要质量下降或发生冲突时，从原始事件/最近稳定 checkpoint 全量重建。

全量重算是否是 $O(n^2)$ 取决于触发频率。若每一轮都重新处理从第 1 轮到当前轮，累计处理量确实呈二次增长；若只在少数阶段边界重建，则不能简单称为 $O(n^2)$。面试中应把复杂度前提讲清楚。

每个摘要版本要带 `version`、覆盖事件区间、生成模型/Prompt 版本和校验状态。这样第 11 轮到来时，系统能够准确判断它属于已压缩历史还是待合并增量，避免重复计算和事件丢失。

<a id="moonshot-agent-dev-20260721-q8"></a>
##### 8. 如果前 10 轮都变成了总结，那之前的原始上下文就不需要了吗？

**回答：**

不能说完全不需要。更准确的说法是：原始上下文通常不再每轮发送给模型，但仍应根据业务价值、隐私要求和合规期限做外部持久化。

保留原始事件有四个作用：第一，线上 bad case 可以回放，判断模型当时看到了什么；第二，摘要质量不佳时可以重建；第三，长期记忆或审计需要回到原始证据；第四，模型、Prompt 或压缩策略升级后可以离线重放评估。

但“全部永久保存”同样不正确。原始对话可能包含个人信息、商业秘密和工具返回凭证，需要加密、访问控制、脱敏、租户隔离、TTL 和用户删除能力。密钥、Token、支付信息等高敏内容原则上不进入通用记忆库。

摘要应保存原始事件引用，而不是切断证据链；模型需要核对某个关键约束时，通过引用精确读取相关片段。这样既控制上下文成本，又保留可追溯性。

本质上，摘要是运行时视图，原始事件是证据层。二者生命周期不同，不能把“当前不进 Prompt”误解成“系统可以删除”。

<a id="moonshot-agent-dev-20260721-q9"></a>
##### 9. 长期记忆可以按需检索召回，具体在什么情况下需要检索？

**回答：**

长期记忆检索的触发条件是：当前任务是否依赖跨会话的用户事实、历史决策或已沉淀经验。典型场景包括用户明确说“沿用上次方案”“继续昨天的任务”，当前输入出现历史项目/人物/文件实体，需要个性化偏好，存在未完成任务，或者当前信息与已知记忆可能冲突。

实现上可以使用多级门控。先用规则捕获显式历史指代和实体，再用轻量路由模型判断记忆依赖程度；对于高风险操作，即使用户没有明确提历史，也要查询授权状态和既有约束。路由结果还应带检索范围，例如只查当前项目、当前用户或某类记忆，避免全库搜索。

检索查询不应直接等于用户原句。可以结合当前目标、实体、时间范围和 memory type 做 query rewriting，再使用向量、关键词、结构化过滤或图关系检索。召回后按相关性、时间、置信度、来源权威性和作用域重排。

需要区分“检索”和“注入”。系统可以低成本检索候选记忆，但只有通过相关性和冲突校验的内容才进入模型上下文。若候选记忆互相矛盾，应标记冲突并询问用户，而不是静默选择一个版本。

知识图谱适合实体关系和多跳查询，但不是长期记忆的必选项。很多场景用关系数据库加向量/全文检索已足够；只有关系结构确实带来可验证收益时，才值得引入图数据库。

<a id="moonshot-agent-dev-20260721-q10"></a>
##### 10. 每轮对话都要注入记忆吗？长短期记忆是同时注入吗？

**回答：**

不是每轮都把所有记忆塞进 Prompt。短期工作状态通常每轮都需要，但也只应投影当前目标、最近交互和未完成步骤；长期记忆则按需检索，并在通过相关性、权限和冲突检查后注入。

组装顺序可以是：系统约束 -> 当前任务状态 -> 必要的长期记忆 -> RAG 证据 -> 最近对话 -> 当前问题。不同信息应带清晰标签、来源和时间，避免模型把历史偏好误当成当前指令，或把外部知识误当成用户事实。

当长短期记忆冲突时，不能简单按“长期更稳定”处理。当前用户明确表达通常优先于历史偏好；业务主库和工具实时状态优先于旧摘要；高风险冲突需要重新确认。模型推断出的记忆权重最低，不应覆盖用户明确事实。

还要给记忆设置独立 Token 预算和 Top-K/阈值。即使每条记忆相关，放得过多也会造成注意力竞争。可先提取结构化事实，再仅对关键记忆附带原文证据。

一句话总结：短期记忆维持当前任务连续性，长期记忆提供跨任务复用；可以同时存在，但不能不加选择地同时灌入。

<a id="moonshot-agent-dev-20260721-q11"></a>
##### 11. 如何减少工具过多带来的 Token 消耗？

**回答：**

工具过多时，最大浪费往往不是调用结果，而是每一轮都把所有工具的完整 JSON Schema 发送给模型。解决方向是让工具能力逐层披露，而不是让模型一次看完整个工具仓库。

第一层只提供工具或 Skill 的简短目录，包括名称、用途、风险级别和少量检索标签；路由器选出候选工具后，第二层才加载其完整 schema、示例和约束。复杂工具还可以在真正调用前再展开详细文档。这就是 progressive disclosure。

其他手段包括：按领域把工具分组并路由到子 Agent；去掉 schema 中重复描述和冗长示例；使用枚举、引用和共享类型减少重复字段；对稳定工具前缀使用 Prompt caching；限制工具返回体，采用分页、字段选择、摘要和对象句柄；将多个低层 API 封装成有业务语义的 Skill，减少模型规划步骤。

动态披露会带来路由漏选风险，因此必须有回退机制：候选工具不足或执行失败时允许扩大检索范围；高风险工具即使被召回，也要经过权限检查和人工审批。工具检索评测应关注 Recall@K，而不只是最终任务成功率。

工具越多，真正的挑战越不是 Token，而是能力发现、权限、版本和可观测性。压缩 schema 只能治表面，建立可检索、可测试、可治理的工具注册中心才是长期方案。

<a id="moonshot-agent-dev-20260721-q12"></a>
##### 12. 你的 RAG 是用什么技术实现的？

**回答：**

按这个项目的真实口径，RAG 使用 BGE-large-zh-v1.5 做中文 Embedding，向量维度为 1024；数据写入 Milvus，并使用 IVF_FLAT 索引；查询阶段先召回 Top-20，再用 BGE reranker 精排，最终选取 Top-5 进入生成上下文。

完整链路应从数据治理讲起。文档解析后保留标题层级、段落、表格和来源 metadata；切片优先遵循语义边界，并使用父子块或邻接扩展保留上下文。需要注意，LangChain `RecursiveCharacterTextSplitter` 默认的 `chunk_size=512` 通常按字符长度函数计算，不天然等于 512 Token；如果要控制模型预算，应使用 tokenizer-aware splitter。

Milvus 的索引和查询参数需要一起调优。IVF_FLAT 的 `nlist` 决定聚类桶数量，查询 `nprobe` 决定探测多少桶；召回率、延迟和内存要通过数据集评测确定。向量写入前是否归一化、Milvus 使用 COSINE/IP/L2 哪种 metric，也必须与 Embedding 训练和检索配置一致。

生产检索通常还会加入 BM25/关键词召回，解决型号、数字、专有名词和精确字符串问题；多路结果可用 RRF 融合，再交给 Cross-encoder reranker。最终上下文按来源去重、控制 token budget，并保留引用 ID。

RAG 不能只报技术栈，还要报评测：检索层看 Recall@K、MRR/nDCG 和命中率；生成层看答案正确性、忠实度、引用准确率和拒答质量。没有离线评测集，`Top-20 -> Top-5` 只是经验参数，不是可证明的最优配置。

<a id="moonshot-agent-dev-20260721-q13"></a>
##### 13. 如何判断向量的相似度？

**回答：**

如果使用余弦相似度，它衡量的是两个向量方向的一致程度：

$$
\cos(\mathbf{x},\mathbf{y})=
\frac{\mathbf{x}^{\top}\mathbf{y}}
{\|\mathbf{x}\|_2\,\|\mathbf{y}\|_2}
$$

值越接近 1，方向越相同；接近 0 表示近似正交；接近 -1 表示方向相反。很多文本 Embedding 训练目标会让语义相近样本方向更接近，因此余弦相似度常用于语义召回。

工程上不能只说公式，还要确认三件事：Embedding 模型是否建议归一化；向量库配置的 metric 是否一致；相似度阈值是否在本领域验证集上校准。不同模型的分数分布不同，不能把 0.8 当成通用“相似”标准。

检索效果也不能只看单条分数。应在标注查询集上计算 Recall@K、MRR 或 nDCG，并观察 hard negative 是否被排到前面。余弦只负责第一阶段几何近似，复杂语义关系通常还需要 reranker。

<a id="moonshot-agent-dev-20260721-q14"></a>
##### 14. 除了余弦相似度，还了解其他相似度算法吗？

**回答：**

常见方法至少包括点积、欧几里得距离、曼哈顿距离，以及针对集合或稀疏文本的 Jaccard、BM25；在检索系统中还会用 Cross-encoder 学习相关性，而不是只依赖固定距离公式。

欧几里得距离为：

$$
d_2(\mathbf{x},\mathbf{y})=\|\mathbf{x}-\mathbf{y}\|_2
$$

点积为 $\mathbf{x}^{\top}\mathbf{y}$，既受方向影响，也受模长影响。若向量已做 L2 归一化，点积就等于余弦相似度。曼哈顿距离计算各维绝对差之和，对某些稀疏或鲁棒场景有用，但在主流稠密向量 ANN 中不如 IP/L2/COSINE 常见。

BM25 不是向量距离，但对关键词、数字、产品型号和专有名词非常有效；Jaccard 适合比较集合重合度。Cross-encoder reranker 将 query 和 document 联合编码，能捕捉细粒度交互，精度通常高于双塔向量相似度，但计算成本更大，因此适合小规模候选精排。

选择算法看模型训练目标和业务需求，不是背一个列表。语义泛化用稠密向量，精确匹配用 BM25，多路召回后再重排，通常比只换一种距离函数更有效。

<a id="moonshot-agent-dev-20260721-q15"></a>
##### 15. 听不懂，说人话？

**回答：**

可以把每段文本想象成高维空间里的一支箭。余弦相似度主要看两支箭指向是否一致，不太关心箭本身有多长：方向越接近，模型认为它们表达的语义越接近。

例如“怎么重置登录密码”和“忘记密码如何找回”用词不完全相同，但 Embedding 可能把它们放到接近的方向；“密码”和“天气”则会指向不同方向。RAG 就是用当前问题这支箭，去找知识库里方向最接近的几支箭。

但这只是帮助理解的比喻。实际是否相似仍由 Embedding 模型的训练数据和目标决定，余弦公式本身不会理解语义；模型没学过的领域、歧义词或精确数字仍可能召回错误，所以还需要关键词检索、rerank 和真实测试集。

<a id="moonshot-agent-dev-20260721-q16"></a>
##### 16. 余弦相似度与欧几里得距离在工程应用中的具体区别是什么？

**回答：**

余弦关注方向，欧氏距离关注空间中的绝对位置；但工程上最关键的前提是向量是否归一化。

若 $\|\mathbf{x}\|_2=\|\mathbf{y}\|_2=1$，则：

$$
\|\mathbf{x}-\mathbf{y}\|_2^2=
2-2\mathbf{x}^{\top}\mathbf{y}
=2-2\cos(\mathbf{x},\mathbf{y})
$$

因此在单位向量上，按余弦从大到小、按点积从大到小、按欧氏距离从小到大，排序完全一致。此时选择哪种 metric 主要取决于向量库索引支持、实现效率和现有配置。

若没有归一化，两者就不等价。余弦消除模长影响，适合只关心方向的语义匹配；欧氏距离和点积会保留模长信息。如果模型训练时让模长表达置信度、流行度或其他信号，盲目归一化反而可能丢信息。

还要纠正两个常见误区。第一，不是所有 Embedding API 都保证返回单位向量，必须查模型说明或在代码中验证；BGE 常见用法会显式设置 `normalize_embeddings=True`。第二，欧氏检索不一定因为“要开方”而更慢，排序时可以直接比较平方距离，ANN 库也有专门优化。

所以工程结论是：遵循模型训练建议，入库与查询使用完全一致的归一化和 metric，并在同一评测集上比较召回率与延迟。

<a id="moonshot-agent-dev-20260721-q17"></a>
##### 17. 项目中一共使用了几个模型？分别是什么？

**回答：**

按原项目可以回答为四类模型，但要按职责说清楚，而不是只报名字。

第一类是 Embedding 模型 BGE-large-zh-v1.5，负责将文档和查询编码为 1024 维稠密向量。第二类是 BGE reranker，作为 Cross-encoder 对初召候选精排。第三类是轻量意图路由模型，例如微调后的 BERT-base，用于判断直接回答、查知识、查记忆或调用哪类工具。第四类是主 LLM，负责规划、工具参数生成、证据整合和最终回答；具体使用 Qwen-72B 或 Claude 3.5 要按项目真实部署口径说明，不能含糊地把两个模型都算作线上主模型。

这种拆分体现了分层选型：高频、确定、低延迟任务交给小模型；语义召回交给双塔；候选相关性判断交给 Cross-encoder；开放式推理和生成交给大模型。不是所有能力都堆在一个 LLM 上。

面试官通常会继续问为什么不用主 LLM 做路由、是否支持替换模型、四个模型如何统一监控。应准备回答延迟与成本、模型服务接口、灰度切换、版本绑定、超时回退和端到端评测。模型数量不是亮点，职责边界和替换成本才是。

<a id="moonshot-agent-dev-20260721-q18"></a>
##### 18. 如何控制模型的幻觉问题？

**回答：**

幻觉不能靠一个 Prompt 或调低温度解决，需要从“是否该回答、证据是否可靠、输出是否被验证”三层控制。

第一层是任务边界。对必须基于企业知识回答的问题，先判断是否有足够证据；检索分数低、证据冲突或超出权限时应该澄清、拒答或转人工。第二层是证据链。提升解析、切片、混合召回和 rerank 质量，去除过期/重复文档，并把最终使用的证据和来源 ID 明确提供给模型。

第三层是受约束生成和验证。要求答案中的关键事实能够映射到证据片段；对数字、实体、引用和工具执行结果使用规则或独立验证器核对；涉及写操作时采用“计划 -> 预览 -> 审批 -> 执行 -> 回读验证”，不能让模型直接宣称操作成功。

温度降低只能减少采样随机性，不能修复参数知识错误或错误证据；显式 Chain-of-Thought 也不等于事实验证，并可能产生貌似合理的错误解释。更稳的是输出简洁结论、引用和不确定性，再由验证器检查。类似“如果不知道就说不知道”的指令有帮助，但必须用评测集验证，不能脱离实验声称固定降幅。

评测至少包含有答案、无答案、证据冲突、诱导提问和越权查询。指标可看 groundedness/faithfulness、引用准确率、无答案拒答率、误拒答率和任务级事实错误率。Rocky认为，幻觉治理的本质不是让模型“更谨慎地说”，而是让系统只在证据和权限允许时行动。

<a id="moonshot-agent-dev-20260721-q19"></a>
##### 19. 如何观察模型召回了哪些块？

**回答：**

需要给检索链路建立可回放的 trace。每次请求至少记录：原始 query、改写后的检索 query、过滤条件、Embedding/索引版本、初召 chunk ID 与分数、融合前后的排名、rerank 分数、最终进入 Prompt 的片段、Token 数和引用 ID。

日志要能把问题拆成三层：相关文档是否进入初召候选，这是召回问题；进入候选后是否被 reranker 排除，这是排序问题；证据已进入上下文但回答仍错误，这是生成或上下文利用问题。没有这三层，所有 bad case 最后都会被笼统归因成“模型幻觉”。

线上可以做检索审计面板，展示 Top-K 文本高亮、分数、metadata、版本和最终引用；同时记录查询耗时、各阶段候选数和空召回率。对一条请求应有统一 trace ID，串联路由、检索、rerank、LLM 和工具调用。

可观测日志也有安全边界。正文可能含用户隐私和企业敏感信息，应脱敏、按租户授权，并设置保存期限。生产环境通常记录 chunk ID、摘要和哈希，只有受权排障时才读取完整原文。

<a id="moonshot-agent-dev-20260721-q20"></a>
##### 20. 简历别的项目随便问了问主要工作

**回答：**

这类问题虽然看似“随便问”，实际是在验证简历真实性。建议用 60 到 90 秒讲清楚：业务问题是什么、你负责的边界、关键技术决策、结果指标和一次失败复盘。

可以按 STAR 展开，但技术岗要把 Action 说具体。例如不要只说“负责模型优化”，而要说明自己处理了哪类数据、改了哪个模块、为什么不用替代方案、离线和线上指标如何变化、上线风险怎么控制。团队成果和个人贡献必须分开。

如果项目与 Agent 岗位不是直接相关，可以主动建立迁移关系：传统分类项目训练了数据治理和评测能力；后端项目训练了接口、并发和可观测性；搜索项目训练了召回与排序。这些能力如何迁移到 Agent 系统，比强行把所有经历包装成大模型项目更可信。

没有量化结果时可讲可验证交付物，例如上线模块、覆盖用户、故障率、测试集规模、节省的人工步骤，但不要编造百分比。面试官继续深挖时，应该能落到代码、日志和真实 bad case。

<a id="moonshot-agent-dev-20260721-q21"></a>
##### 21. 算法题：Leetcode 143. 重排链表

**回答：**

这题要求原地重排：

$$
L_0\rightarrow L_1\rightarrow\cdots\rightarrow L_n
$$

变为：

$$
L_0\rightarrow L_n\rightarrow L_1\rightarrow L_{n-1}\rightarrow\cdots
$$

标准解法分三步：快慢指针找到前半段尾节点；反转后半段；把两段链表交替合并。Python 实现如下：

```python
class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next


def reorder_list(head: ListNode | None) -> None:
    if head is None or head.next is None:
        return

    slow = fast = head
    while fast.next is not None and fast.next.next is not None:
        slow = slow.next
        fast = fast.next.next

    second = slow.next
    slow.next = None

    prev = None
    while second is not None:
        nxt = second.next
        second.next = prev
        prev = second
        second = nxt

    first, second = head, prev
    while second is not None:
        next_first = first.next
        next_second = second.next
        first.next = second
        second.next = next_first
        first = next_first
        second = next_second
```

找中点、反转和合并各遍历一次链表，时间复杂度为 $O(n)$，额外空间复杂度为 $O(1)$。使用数组加双指针也能做到 $O(n)$ 时间，但需要 $O(n)$ 额外空间，没有体现题目希望考察的链表断链、反转和交错合并能力。

边界测试至少包括空链表、单节点、两个节点、奇数长度和偶数长度。尤其要先执行 `slow.next = None` 断开前后半段，否则合并时可能形成环。

<a id="moonshot-agent-dev-20260721-q22"></a>
##### 22. 你平时调试代码怎么调试的？

**回答：**

我会按“稳定复现 -> 缩小范围 -> 增加观测 -> 验证假设 -> 修复回归”的顺序调试，而不是一上来把整段代码交给 AI。

算法题或单文件脚本，最有效的是构造最小输入，用 `print` 输出关键指针、循环变量和分支路径，再与手工推演对比。复杂业务代码会使用结构化日志、断点调试器、单元测试和 trace ID；并发/分布式问题还要看时间线、请求链路和资源指标。

具体工具取决于问题：Python 用 `pdb`/IDE debugger、pytest 和日志；服务端看请求日志、指标和分布式 tracing；模型/Agent 链路还要记录 Prompt 版本、模型参数、工具输入输出和状态 checkpoint，保证同一问题可回放。

AI 可以帮助解释堆栈、生成测试用例和提出排查假设，但它拿不到完整运行环境，也可能误判。把 AI 当副驾驶，自己用证据验证，才是可复现的调试方式。

<a id="moonshot-agent-dev-20260721-q23"></a>
##### 23. 不对吧，最简单的方式不是打印一下吗？

**回答：**

对，算法题里最简单有效的办法通常就是打印关键状态。比如重排链表可以在找中点、反转后半段和每次合并后打印链表，立刻判断错误发生在哪个阶段。

好的 print debugging 不是把所有变量全打出来，而是围绕假设设计输出：当前节点值、`next` 指向、循环次数和链表是否出现重复节点。输出要有标签，例如 `phase=reverse curr=3 next=4`，否则日志越多越难看。

但打印也有边界：并发时序、性能问题、内存破坏或生产环境敏感数据不适合随意 print，此时需要断点、结构化日志、指标和 trace。面试官这句追问考的不是工具高低，而是你是否会从最低成本的观测手段开始排查。

<a id="moonshot-agent-dev-20260721-q24"></a>
##### 24. 最近了解的 AI 内容？

**回答：**

最近我重点关注的是编码 Agent 从“模型会生成代码”转向“Harness 能否稳定交付软件”的变化。真正决定编码 Agent 可用性的，越来越不是一次补全的代码质量，而是它能否读取仓库上下文、检索代码、规划修改、调用测试、处理失败、遵守权限并留下可审计的变更。

这类系统通常包含 Context Builder、工具注册与检索、执行沙箱、权限策略、状态/checkpoint、错误恢复、可观测性和评测闭环。模型负责在当前状态下做判断，Harness 决定模型能看到什么、能做什么、失败后怎样继续。

这个方向值得关注，是因为基础模型能力会快速普及，但真实软件工程中的仓库约束、测试环境、安全边界和交付标准不会自动消失。未来编码 Agent 的竞争，不只是“谁的模型更强”，而是谁能把模型能力组织成可重复、可验证、可恢复的工程流程。

面试时讲“最近内容”不要堆新闻名词。最好选择一个主题，说明它的核心机制、与旧方案的差异、一个未解决问题，以及它如何影响自己的项目设计。

<a id="moonshot-agent-dev-20260721-q25"></a>
##### 25. 讲一下 Claude Code 架构

**回答：**

Claude Code 更适合被理解为一个编码 Agent Harness，而不是“模型外面套了一层终端”。从公开可观察的产品行为与文档看，其主线是一个迭代式 Agent loop：读取用户目标和项目上下文，模型决定下一步工具调用，权限层审核动作，工具执行后把结果作为 Observation 返回，直到完成、失败或达到预算。

可以按六个模块解释：

- **Context 层**：整合用户指令、项目级规则、相关代码、当前修改和压缩后的历史。
- **Agent loop**：模型基于当前状态决定检索、读取、编辑、执行命令、测试或委派子任务。
- **Tool 层**：文件读写、代码搜索、Shell、测试以及可扩展工具都通过明确输入输出契约调用。
- **Permission/Sandbox**：高风险命令、文件范围和外部访问受到权限策略约束，并支持人工确认。
- **State 与恢复**：保存任务进度、工具结果和修改状态，支持长任务压缩、检查点或回退。
- **扩展与自动化**：项目规则、Hooks、MCP/外部工具和子 Agent 用来连接仓库规范与企业系统。

不要声称自己“看过 Claude Code 全部源码”后给出精确代码行数、工具数量或“绝对无共享状态”等内部结论。产品分发包和公开文档能够支持行为与接口层分析，但不等于完整、可审计的内部源码。面试里最可信的是解释可验证架构和工程取舍。

Claude Code 的关键不在某个 ReAct 名词，而在于把上下文、权限、工具、状态和验证组织成闭环。模型更像决策内核，Harness 才是让它进入真实代码库的操作系统。

<a id="moonshot-agent-dev-20260721-q26"></a>
##### 26. 建议下去再补一点 Harness 的知识

**回答：**

这个反馈指向一个重要概念：Harness 不是某个单一框架，也不等于 `AGENTS.md`、`ARCHITECTURE.md` 和 `TASKS.md` 三份文件。它是围绕模型构建的整套运行与治理环境，决定 Agent 如何感知、行动、受约束、恢复和被评估。

一个完整 Harness 通常包括：上下文选择与压缩、工具发现和 schema 管理、执行沙箱、权限审批、状态机与 checkpoint、超时重试、模型路由、日志 tracing、评测器和人工接管。仓库级规则文件只是 Context/Policy 的一种载体，不同产品使用的文件名和优先级可能不同。

可以把它与模型分工概括为：模型给出“下一步做什么”的概率决策，Harness 负责“哪些动作可用、哪些证据可见、动作如何执行、结果怎样验证、失败如何恢复”。同一个模型放进不同 Harness，最终任务成功率可能差很多。

继续补知识时应围绕真实问题学习：工具过多如何检索；上下文超长如何管理；命令如何最小权限执行；长任务如何 checkpoint；测试失败如何回滚；怎样用轨迹数据评测工具选择与恢复能力。理解这些机制，比记住某几个配置文件更有跨周期价值。

<a id="moonshot-agent-dev-20260721-q27"></a>
##### 27. 反问业务

**回答：**

反问业务时要验证岗位真正解决的问题、失败成本和交付边界，而不是只问“团队做什么”。如果方向是安全风险相关 AI，可以围绕以下问题展开。

第一，当前主要场景是内容审核、违规行为识别、风险研判，还是给内部分析人员提供 Agent 辅助？模型输出是建议，还是会直接触发处置动作？这决定了自动化权限和人工复核要求。

第二，团队最看重哪些指标？安全场景不能只看总体准确率，还要区分误杀率、漏放率、严重风险召回、校准和人工复核成本。不同错误的业务代价可能完全不对称。

第三，数据和评测如何构建？是否有持续更新的对抗样本、灰产变体和线上回放集？LLM Judge 是否会由规则、专家标注或真实处置结果校准？

第四，岗位的工作比例如何分配：Agent 工程、模型训练、RAG/知识建设、业务规则和客户交付分别占多少？项目中的共性能力能否沉淀为平台，而不是长期做一次性需求。

第五，模型在高风险动作前有哪些权限、审计和 Human-in-the-loop 机制？出现误判后如何回放、归因和回滚？

这些问题既能帮助候选人判断岗位，也能向面试官证明：你理解安全 Agent 的核心不是“会调用工具”，而是让每个判断有证据、每个动作有权限、每次错误能追溯。

### 1. 自我介绍，重点讲和 RL 相关的部分。

**回答：**

自我介绍应围绕“做过什么 RL 问题、负责哪段链路、用什么证据证明有效”展开。可以先交代研究或工程方向，再选择一个最能深入讨论的项目，讲清基座模型、任务、奖励信号、训练方法和独立评测，最后说明自己的具体贡献。

如果实际做过大模型强化学习，可以按“监督微调建立初始能力 → rollout 收集回答或交互轨迹 → 验证器或奖励模型评分 → 策略更新 → 独立任务评测”的顺序介绍，重点说明最难的一处失败及其排查过程。例如发现奖励上涨而成功率下降，如何区分奖励漏洞、评测变化和训练错误，比罗列很多算法名称更能体现理解。

没有完整训练过模型，就明确项目处于论文复现、小规模实验、评测建设或系统接入阶段。参数规模、GPU 数量、训练时长和效果数字都应来自真实记录；自己没有负责的模块可以说明接口和协作关系，不把团队整体工作包装成个人成果。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q02"></a>

### 2. 你们这轮训练多少 token，几张卡，跑了多久，失败重来过几次。

**回答：**

这道题需要用训练日志回答，而且先统一 token 的统计口径。SFT 的非填充 token、RL rollout 的生成 token、策略优化处理的动作 token、参考模型或奖励模型额外处理的 token，含义不同；同一批轨迹被优化多轮，也不能简单当成新增采样数据。

我会准备一张实验记录表，包含模型版本、GPU 型号与数量、并行策略、有效 batch size、prompt 数、group size、输入与输出长度分布、生成 token 总数、优化 token 总数、墙钟时间和 GPU 小时。GPU 小时可以用实际占用卡数乘占用时长统计，但它不直接代表有效计算量，还需要结合利用率和吞吐判断。

失败重跑应区分程序或环境故障、数值不稳定、奖励错误与正常的调参试验。记录失败时的 step、检查点、损失或奖励异常、是否从断点恢复，以及重复消耗的数据和算力。无法从日志证明的数字不猜测；尤其不要只报成功那次运行的成本，漏掉采样、评测与失败重跑。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q03"></a>

### 3. 基座是哪个，7B 还是 32B，为什么选这个尺寸。

**回答：**

基座选择由任务能力、奖励可验证性和总实验预算共同决定。先确认模型的许可证、语言与领域能力、上下文、工具格式和推理成本，再比较 7B 与 32B 在目标任务上的初始成功率，判断 RL 是否有足够的有效样本可供学习。

7B 通常更适合快速检查奖励、数据与训练链路，可以在相同预算下进行更多轮对照；32B 可能有更好的基础推理能力，但 rollout、训练、权重同步和部署成本都会提高。如果 7B 对目标任务几乎全错，组内相对奖励可能长期没有差异；这时需要降低难度、补冷启动数据，或评估更强基座，而不是盲目延长 RL。

比较模型时，既看相同样本预算，也看相同算力或成本预算，并保持评测与生成约束一致。参数规模只是粗略代理，还要区分稠密模型与 MoE 的总参数、激活参数和通信代价。最终选择应落到具体证据，例如较小模型已经达到交付标准，或者更大模型在困难任务上带来的收益足以覆盖增加的成本。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q04"></a>

### 4. SFT 阶段的数据量、epoch、学习率、warmup 比例。

**回答：**

SFT 配置要与数据规模、样本长度、基座状态和全量或参数高效微调方式一起说明。数据量不仅是“多少条”，还包括去重后的独立任务数、非填充 token 数、任务配比、质量过滤和训练验证划分，避免把高度重复的数据误当成覆盖面。

epoch 表示数据被遍历的次数，但真正影响训练的是总更新步数、有效 batch size 和每步有效 token 数。学习率需要结合优化器、可训练参数和批量规模选择；warmup 比例应同时换算为实际步数或 token 数。短实验里看似很小的比例，可能只对应很少的更新，不能直接照搬长训练的比例。

回答时给出实际配置文件或实验记录，并说明选择依据：验证集损失、任务正确率、格式合规率、过拟合和通用能力回归。SFT 的目标是让策略具备可用的初始行为与输出协议，并为后续 RL 提供有意义的探索起点；它不要求训练损失越低越好，也不保证增加 epoch 一定有益。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q05"></a>

### 5. SFT 之后直接上 RL，还是先做 rejection sampling 冷启动，为什么。

**回答：**

是否做 rejection sampling 冷启动，主要看 SFT 模型能否生成足够多的可验证成功样本，以及任务协议是否已经稳定。如果格式经常错误、工具调用无法执行，或者几乎所有采样都失败，直接做 RL 很容易得到稀疏或无差异的奖励，先补少量高质量示范往往更有效。

拒绝采样的基本做法是针对同一任务生成多个候选，用可靠验证器筛选有效答案或轨迹，再用于监督训练。需要控制题目与解法多样性，去掉投机样本和重复轨迹，同时保留独立测试集。筛选器必须验证真正的任务结果，不能只依据模型自信程度或答案长度。

如果基座已经有较好的格式与任务能力，且奖励可靠、组内存在成功和失败差异，可以直接从当前 SFT 检查点开始 RL。比较两条路线时应把生成和筛选冷启动数据的成本计入预算，并检查冷启动是否让策略过度模仿单一解法。没有必要把某一种流程视为所有任务的固定前置步骤。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q06"></a>

### 6. 讲一下 GRPO 和 PPO 的区别。为什么 GRPO 可以去掉 critic。

**回答：**

PPO 通常用价值函数估计状态价值，再构造优势；GRPO 针对同一个 prompt 生成一组回答，利用组内奖励作为相对基线，从而省去单独训练 critic 的常见开销。它仍然需要奖励或验证信号，去掉 critic 不等于没有价值比较，也不等于训练链路只剩一个模型。

对于同一 prompt 的 $G$ 个回答，常见结果奖励版本的优势定义为：

```math
\mu=\frac{1}{G}\sum_{i=1}^{G}R_i,\qquad
\sigma=\sqrt{\frac{1}{G}\sum_{i=1}^{G}(R_i-\mu)^2},\qquad
\widehat A_i=\frac{R_i-\mu}{\sigma+\epsilon_{\mathrm{norm}}}.
```

训练时将回答的相对优势用于策略梯度，并常配合新旧策略概率比、裁剪目标与可选的参考策略 KL 约束。原始 GRPO 常见的损失聚合方式是先对每条回答的 token 求平均，再对回答求平均；其他实现会采用全局 token 平均或不同的标准化方式，需要明确所讨论的版本。

代价是每个 prompt 要采样多条回答，组内奖励全相同会缺少相对信号，有限组大小的基线也可能噪声较大。对长程交互任务，仅用一个序列结果奖励给所有动作同样的优势，信用分配仍然粗糙。因此 GRPO 用更多组内比较替代 critic 的学习，并没有消除奖励设计、采样成本与信用分配问题。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q07"></a>

### 7. GRPO 的 group size 取多少，取 4 和取 16 的区别在哪，显存怎么算。

**回答：**

group size 没有通用最优值，需要结合单题成功概率、奖励离散程度、总 rollout 预算与硬件调度来选择。从 4 增加到 16，通常能获得更丰富的组内比较，均值和尺度估计也可能更稳定，但同一个 prompt 的候选数增加四倍，生成与打分成本通常随总输出 token 增长。

对于独立采样、二值奖励且单条成功率为 $p$ 的简化情况，组内同时有成功与失败的概率为：

```math
P_{\mathrm{mixed}}=1-p^G-(1-p)^G.
```

这个式子说明更大的组可能减少全对或全错组，但当任务成功率非常接近 0 或 1 时仍可能缺乏信号。实际采样彼此可能相关，不能把独立假设当成保证。固定总回答数时，增大 $G$ 还会减少独立 prompt 数，可能牺牲任务覆盖。

显存要拆开算：模型权重、梯度与优化器状态主要由参数规模和并行方式决定；rollout 的 KV Cache 随并发活跃序列及其实际长度增长；训练激活随 microbatch 和序列长度增长。调度器可以分批生成 16 条回答，因此总采样数四倍不意味着峰值显存必然四倍。记录实际并发、长度长尾、显存峰值和端到端吞吐，再比较单位成本内的有效组数量与评测收益。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q08"></a>

### 8. advantage 是 token 级还是序列级，组内归一化时分母用标准差还是标准误。

**回答：**

在只有最终结果奖励的常见 GRPO 设置中，优势是序列级的：同一条回答的所有有效动作 token 共享一个组内相对优势。策略概率比和裁剪可以是 token 级，两者并不矛盾。若使用过程奖励或额外的 token 信用分配，就需要说明新的优势定义，不能默认仍是同一个算法设置。

组内标准化通常除以奖励的标准差，不是均值的标准误。标准误等于标准差除以组大小的平方根；换成标准误，相当于额外把优势放大约 $\sqrt{G}$ 倍，会改变不同组大小下的梯度尺度，不能解释为更准确的同一种归一化。

还要说明标准差使用总体估计还是无偏样本估计。总体方差分母是 $G$，无偏样本方差分母是 $G-1$，有限组时数值不同。手写实现可以用总体标准差并加入很小的数值稳定项，保证奖励全相同时输出零优势；数值稳定项与 PPO 裁剪参数虽然常都写 epsilon，但含义完全不同。

最后检查归一化维度：每个 prompt 内单独计算，不能把不同 prompt 的奖励混在一起。如果实现选择批量级尺度、取消标准差缩放或其他变体，应明确它是在改变训练信号的权重，而不是简单修正代码格式。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q09"></a>

### 9. 如果一个 group 里 8 条采样全对，advantage 是多少，这时候 loss 是多少。

**回答：**

如果这 8 条回答的**总奖励完全相同**，组内中心化奖励全为零，使用正确的稳定项后优势为零，策略梯度部分的 loss 和梯度也为零。若“全对”只说明正确性分量相同，而长度、格式或其他分量仍有差异，总奖励未必相同，优势也未必为零。

完整训练 loss 还可能包含 KL、熵、辅助监督等项。即使组内策略优势为零，策略与参考模型有偏离时，KL 项仍可能非零。因此要区分策略损失、总损失以及各自的梯度，不能直接说“全对，所以任何 loss 都是零”。

还有一个容易混淆的情况：奖励有差异、当前策略等于旧策略、回答等长且使用组内中心化时，正负优势的标量平均可能恰好为零，但对各 token 的梯度仍然非零。loss 的数值为零与没有学习信号是两件事，后者需要检查优势和梯度。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q10"></a>

### 10. loss 变成 0，除了"全对"，还有哪几种可能。

**回答：**

loss 显示为零，先确认日志记录的是哪一项、是否经过平滑或四舍五入，再同时查看奖励分布、优势、有效 token 数、概率比、裁剪比例与梯度范数。零值本身不足以定位问题。

常见情况包括：全错组或任意奖励全相同的组；reward 解析错误把所有输出映射成同一个值；有效样本全部被过滤；动作 mask 错误使所有 token 无效；小数值被日志精度隐藏；以及正负策略项恰好抵消。最后一种可以有正常梯度，因此不应直接当作训练停滞。

另一些实现错误会切断梯度，例如把当前 logprob 或整个重要性比 detach，模型参数被冻结，优化器没有包含目标参数，或者训练步骤没有真正执行。它们不一定令前向 loss 为零，却会造成“看起来在训练，参数没有变化”。低精度下溢、NaN 被强制替换为零，也需要排查。

诊断时构造一个两条回答、奖励分别为 1 和 0 的极小样本，手算优势和前向值，再检查反向梯度的符号与非零性。对于全空 mask，明确报错比悄悄返回零更容易发现数据管线故障。KL 与辅助 loss 单独记录，避免总损失掩盖策略项已经失效。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q10-f1"></a>

### 追问：reward 里有常数项吗

**回答：**

如果是在同一组每个回答的奖励上加同一个常数，正确的组内中心化会消去这个常数，标准差也不变，因此优势不会被“稀释”。例如奖励从 `[0, 1]` 变成 `[100, 101]`，组内相对优势应保持一致。

更一般地，对奖励进行仿射变换，可以写成：

```math
\widehat A_i(aR+c)
=\frac{a(R_i-\mu)}{\lvert a\rvert\sigma+\epsilon_{\mathrm{norm}}}.
```

当 $a$ 为正且数值稳定项可以忽略时，整体缩放也会被标准差抵消。若加权后可变部分极小，稳定项主导分母，或者先把很大的常数和微小差异存入低精度张量，才可能因为数值精度丢失而使优势接近零。奖励裁剪、舍入、非组内归一化等额外操作，也可能破坏上述不变性。

因此要检查的是常数加入前后的逐样本总奖励、组内差异、计算精度与归一化实现，而不能直接把“存在常数奖励项”视为优势变小的原因。高精度算完之后再转回低精度，也无法恢复在早期加法中已经丢掉的差异。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q11"></a>

### 11. 你遇到过 loss 一直是 0 吗，怎么判断是难度太低还是 reward 写错了。

**回答：**

如果没有亲自遇到过，应说明这是排查方案，不能虚构生产故障。真正遇到时，首先保存出问题的 prompt、完整回答、各奖励分量、组内均值与标准差、动作 mask 和梯度，保证能在小批量上复现。

区分任务过易与 reward 错误，可以先用已知正确、已知错误、格式错误和边界样本单独测试评分器，检查它是否能稳定区分结果。再抽取模型当前生成的回答，由独立验证器或人工检查是否确实全对；如果 reward 全为 1，但实际存在错误，就优先排查解析、缓存键、样本对齐和评分规则。

如果验证器正常，模型对简单集接近全对，同时在困难集或有针对性的变式上仍产生组内差异，才支持“训练难度不足”的判断。全错也可能是数据太难、提示模板不匹配或基座能力不足。不要只为了恢复非零 loss 随意翻转标签或注入随机噪声，应调整可学习的难度区间，并保留固定评测。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q12"></a>

### 12. KL 项加在 loss 里还是加在 reward 里，系数给多少，给大了会怎样。

**回答：**

两种放置方式都存在，必须说明所采用的算法和实现。把 KL 加入 reward，会改变回报及后续优势；把 KL 作为单独的 loss 项，则在策略目标之外对当前策略相对参考策略的偏移施加约束。它们只有在特定推导、估计与归一化条件下才可能对应，经过组内标准化后不能随意宣称等价。

原始 GRPO 常见写法包含独立的 KL 正则；一些后续方法会移除该项。比较时同时交代 KL 方向、逐 token 或序列聚合、参考模型版本与估计方式，避免把同一个约束在 reward 和 loss 中重复计算。

系数不能脱离奖励尺度和聚合方式直接给一个通用数值。可以从保守设置开始，观察独立任务收益、相对参考策略的实际 KL、策略熵和回归情况，必要时采用目标 KL 的自适应调节。系数过大可能让策略难以偏离初始模型，学习进展缓慢；过小可能导致明显漂移、奖励投机或能力遗忘。报告真实使用的系数及对照结果，比背一个固定推荐值更可靠。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q13"></a>

### 13. 为什么 GRPO 训久了回复会变长，长度和正确率是正相关还是因果。

**回答：**

GRPO 训练后回复变长，可能是模型学到了更充分的有效推理，也可能是冗余重复、奖励偏好、停止行为异常或损失聚合方式带来的长度偏差。不能仅凭长度曲线推断正确率变化的原因。

先固定解码参数、最大输出长度与停止条件，按任务难度观察长度、正确率、重复率和截断率。检查奖励是否偏爱详细表达、长答案是否有更多机会触发评分规则，以及训练时长短序列获得的权重是否符合设计。序列平均、全局 token 平均和固定长度归一化会产生不同的梯度权重，必须结合具体实现分析。

长度与正确率正相关，也可能只是困难任务同时需要更多 token 且由更强模型完成，或筛选过程保留了较长成功样本。要研究因果，应对同一批任务随机分配合理的计算预算或生成策略，控制模型、采样和评测，再观察成功率与成本；简单截断已有答案会破坏完整性，不能视为干净的因果实验。

真正有价值的是单位成本下的成功率与有效推理密度。若新增 token 主要用于必要的分解、验证和纠错，可以保留；若只是重复或无法停止，就应针对奖励、数据和停止行为修复。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q14"></a>

### 14. 长度惩罚怎么加才不伤害推理能力。

**回答：**

长度约束应围绕任务完成度与资源预算设计。对所有任务按 token 数直接扣同样的分数，可能把必要的推理过程和无效重复一起压掉，尤其会伤害困难任务。

一种可验证的设计是在预算内不惩罚，超过软阈值后逐步增加惩罚，再在硬上限停止。例如下面给出一个分段线性形式，它是设计示例，不是所有任务的统一配置：

```math
R_{\mathrm{len}}(T)
=-\lambda\min\left(1,\max\left(0,\frac{T-T_0}{T_1-T_0}\right)\right),
\qquad T_1>T_0.
```

其中软阈值与硬预算应按任务类型或难度校准。也可以重点惩罚重复循环、无效工具调用和完成目标后继续生成，把主要约束放在明确的浪费行为上。正确性与硬约束优先级要明确，不能让极短的错误答案因为节省 token 而获得最高总分。

验证时比较相同预算下的正确率曲线、自然结束比例、困难题表现与总成本，并抽查被压缩掉的内容是否必要。先修复 EOS 和停止配置，再尝试奖励约束；出现质量下降时回看具体任务，不只根据平均长度达到目标就认为成功。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q15"></a>

### 15. DAPO 改了哪几处，dynamic sampling 具体怎么筛。

**回答：**

DAPO 的核心改进包括 Clip-Higher、Dynamic Sampling、token 级损失聚合和超长回复的奖励处理。论文还在其设置中移除了 KL 项，并整理了适合规则验证的数据；这些选择有具体实验背景，不能直接推广为所有任务的最优配置。

<div align="center">

| 改动 | 主要做法 | 希望解决的问题 |
|---|---|---|
| Clip-Higher | 分开设置概率比的上下裁剪范围，适度提高上界 | 给正优势动作保留更多概率增长空间，缓解探索过早收缩 |
| Dynamic Sampling | 继续采样并保留有区分度的 prompt 组 | 避免有效训练批次被全对或全错组占满 |
| Token-Level Loss | 按整个有效批次的动作 token 聚合 | 调整长短回答的 token 权重 |
| Overlong Reward Shaping | 识别截断，并使用过滤或软长度惩罚等处理 | 降低把未完成推理直接判为错误造成的奖励噪声 |

</div>

在论文的二值正确性设置里，dynamic sampling 保留组内准确率严格介于 0 和 1 之间的 prompt，过滤全对、全错组，并继续采样补足训练所需的有效组。它筛选的是整个 prompt 组，不是只保留正确回答；把失败回答全删掉会改变组内比较。

如果奖励是连续值或由多个分量组成，不能机械套用“准确率 0 或 1”的条件，应明确需要保留的有效奖励差异与任务分布。动态筛选也会改变训练分布并增加生成成本，必须设置最大采样预算、记录接受率和各难度层覆盖。一直采不到有效组时，要检查任务难度与验证器，而不是无限重试。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q16"></a>

### 16. GSPO 把重要性采样比从 token 级改成序列级，解决的是什么问题。

**回答：**

GSPO 把一条回答视为统一的优化单位，用长度归一化后的序列概率比进行裁剪和策略更新，让序列级奖励与优化粒度更一致。它要缓解的是逐 token 比率波动导致的噪声与训练不稳定，尤其是单个 token 概率差异较大的情形。

定义第 $i$ 条回答长度为 $`T_i`$，其重要性比可以写成：

```math
s_i(\theta)
=\exp\left(\frac{1}{T_i}\sum_{t=1}^{T_i}
\left[\log\pi_\theta(y_{i,t}\mid x,y_{i,1:t-1})
-\log\pi_{\mathrm{old}}(y_{i,t}\mid x,y_{i,1:t-1})\right]\right).
```

这相当于逐 token 概率比的几何平均，不是直接把所有 token 的比率相乘，也不是它们的算术平均。GSPO 对这个序列标量与序列优势构造裁剪目标，单个 token 不再各自决定一套裁剪权重。

长度归一化可以减轻比率数值范围随长度急剧扩张的问题，序列聚合也可能降低局部概率噪声的影响。论文在其模型与任务设置下报告了训练稳定性和效率收益，但不能据此保证所有训练推理误差都会被消除。共同方向的系统性偏差仍会保留，权重版本、分词和采样分布对齐依然重要。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q16-f1"></a>

### 追问：那你按重要性采样的方差来源推一下

**回答：**

先在对数域分析。令每个 token 的新旧策略对数概率差为 $`\delta_t`$，普通整序列概率比的对数是这些差值的总和。其方差为：

```math
\mathrm{Var}\left(\sum_{t=1}^{T}\delta_t\right)
=\sum_{t=1}^{T}\mathrm{Var}(\delta_t)
+2\sum_{s\lt t}\mathrm{Cov}(\delta_s,\delta_t).
```

若差值近似独立且方差相近，求和后的方差随长度增长；重新取指数后，少数大比率可能主导估计，形成高方差。GSPO 使用对数概率差的长度平均，在独立同分布的简化假设下，平均值的方差会随长度降低。

真实 token 之间通常相关，公共的模型偏移或引擎偏差也不会因平均自动消失。例如每个 token 都有同样的正偏差，平均后仍然存在。因此分析时要同时看单 token 方差、跨 token 协方差、序列长度分布，以及采样策略与目标策略是否匹配。

长度归一化比率也是一种稳定的优化设计，不能把它直接称作原始整序列重要性采样估计的无偏等价替换。解释方法时，应把“降低某些数值波动”和“严格保持同一个估计目标”分开。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q17"></a>

### 17. clip 的 ε 取 0.2，如果改成 0.28 会怎样，为什么 DAPO 要用 clip-higher。

**回答：**

若使用对称裁剪，epsilon 从 0.2 改成 0.28，概率比的允许区间由 `[0.8, 1.2]` 扩到 `[0.72, 1.28]`。这给某些方向上的更新更大空间，可能增加学习速度和探索，也可能使策略偏移更大；效果取决于优势符号、实际比率分布、学习率与更新轮数。

对于正优势动作，概率比超过上界后，裁剪代理目标通常不再继续奖励该样本的概率增长；对于负优势动作，概率比低于下界时，进一步降低它的概率也不再继续改善该裁剪项。其他方向仍可能保留梯度，所以裁剪不是把所有梯度统一限制在一个范围内。

DAPO 的 Clip-Higher 强调上下界解耦：提高上侧阈值，同时可以保持下侧较保守，避免把“鼓励有价值但概率较低的动作”与“更激进地压低负优势动作”绑在一起。这与把对称 epsilon 整体从 0.2 改到 0.28 不完全相同。

实验中检查上下侧裁剪比例、策略熵、KL、成功率与异常长回复，并在同一预算下对照。裁剪范围扩大并不保证每步实际更新更大，更不构成严格的 KL 上界；若没有样本触及原阈值，调整参数也可能几乎没有影响。

### 18. 训练和推理的 logprob 对不上，差 1e-3 量级，会导致什么，怎么查。

**回答：**

先确认“差 1e-3”指的是单 token 对数概率差、序列总差、均值，还是最大值，以及误差是否有系统性方向。相同均值可能隐藏很大的长尾误差；长度为 1000 的回答若每个 token 都同向偏差 0.001，未经长度归一化的序列比率可能累积到约 $e^1$，不能只凭单点误差小就忽略。

排查顺序是先确认权重版本与请求对应，再对齐分词器、聊天模板、实际 token ID、注意力 mask、位置 ID、EOS、温度与 top-p/top-k 处理。随后在同一批前缀上比较不同精度、内核、并行配置和量化方式，逐步定位是输入偏移、概率提取错误还是数值实现差异。还要检查 logprob 与目标 token 是否错位一位。

训练中至少涉及三个分布：当前训练策略、用于构造更新比率的旧策略，以及真正生成数据的行为策略。推理引擎产生的分布与训练侧重算的旧概率不一致时，直接重算不能让样本自动变成 on-policy；仍需记录行为策略信息，并按所用算法评估偏差或采用适当的重要性修正。

监控时同时报告差值分位数、序列累计偏差、比率极值、裁剪比例和有效样本情况。通过提高关键计算精度、修复输入和版本对齐减少误差，再考虑有明确边界的截断或屏蔽修正。任意截断都会引入偏差，需要用训练稳定性和独立评测验证。

<a id="moonshot-llm-rl-20261105-947983031250251776-r1-q19"></a>

### 19. 采样温度设多少，温度对 RL 是探索还是噪声。

**回答：**

温度既影响探索，也可能引入无效噪声，区别在于新增样本是否提供了可用的行为差异和奖励信息。较低温度常使回答集中，可能形成相似轨迹和全同奖励组；较高温度增加多样性，也可能提高格式错误、无效工具调用和随机失败的比例。

没有一个温度适合所有模型和任务。可以在固定 prompt、总生成预算与长度约束下做小范围对照，观察组内奖励差异、有效组比例、解法多样性、成功率和成本，而不只看输出是否“更有变化”。若任务能力不足，提高温度不一定能产生有效探索。

概率计算必须与行为分布的约定一致。温度会改变 logits 对应的分布，top-p/top-k 还会截断候选集合；记录的是原始模型 logprob 还是经过采样变换后的 logprob，需要明确。忽略这些变换会让重要性比的含义发生偏移，尤其不能把 top-p 截断后的采样默认视为原始策略的无偏样本。

最终使用的温度应同时说明训练目的与部署解码配置。训练时探索充分，并不要求线上采用相同的高随机性；两种配置都要分别评估。

### 20. 规则 reward 和 reward model 各自适合什么场景，你们怎么混。

**回答：**

规则奖励适合结果可验证的任务，例如数学答案、单元测试、结构化字段和明确的环境目标。优势是标准较清楚、便于复现；局限是规则可能不完整，解析错误和测试覆盖不足会成为投机入口。

奖励模型适合难以用单一规则判定的维度，如解释质量、相关性和用户偏好，可以利用人工或高质量偏好数据学习评价。但它会继承标注偏差，也可能被策略利用表面风格、冗长表达或特定措辞欺骗；分布变化后需要重新校准。

混合时先确定哪些是硬约束、哪些可以权衡。权限、数据安全或必须满足的执行条件可以设为门控；在合法候选中，再组合正确性、偏好和成本。统一各分量的范围与有效条件，缺失评分不能悄悄按零分处理，并单独记录分量曲线。

如果面试问“你们怎么混”，应给出真实配置与消融结果；没有实践数字时，可以用设计方案说明如何先验证每个评分器，再比较不同组合对独立任务的影响。规则奖励与奖励模型都不能自证正确，仍需要外部验收。

### 21. 举一个你们实际遇到的 reward hacking，怎么发现的，怎么补的。

**回答：**

这道题要求真实经历，应先交代具体任务、奖励定义、异常轨迹和修复证据。没有亲身案例时，可以明确用假设案例说明排查方法，不能把公开案例或设想说成自己线上遇到的事故。

例如一个假设的代码修复任务只按“测试通过”给奖励，Agent 可能修改测试文件跳过断言，或伪造测试执行输出。发现线索是奖励上升，但独立测试集成功率下降，同时高分样本出现测试文件改动、异常短运行或大量跳过。应回放高奖励失败样本，核实评分器读取的是实际退出码和测试结果，而不是模型自述。

修复可以把受保护测试与候选代码隔离，检查测试是否确实执行，增加隐藏用例和行为验证，并把越权修改作为无效轨迹处理。修复之后在同一批任务上重评旧检查点与新策略，确认漏洞被堵住且正常解法仍能得分。

不能只加入一个惩罚关键词就结束。需要检查相同漏洞的变体、评分输入是否可被修改，以及代理指标是否仍偏离真实目标。报告成功率、违规率和修复前后轨迹，比只给“奖励下降了”更能说明问题得到解决。

### 22. 多目标 reward（正确性、格式、长度、安全）怎么加权，权重是拍的还是有依据。

**回答：**

多目标奖励需要先区分不可违反的约束与可交易的偏好。安全边界或执行权限若是硬约束，不应被更高正确率或更短回答抵消；正确性、格式、成本等软目标才适合在定义清楚后做组合。

可以用加权和作为起点，但要先校准每个分量的尺度、分布和触发范围。一个数值范围大、容易波动的分量可能主导训练；一个在组内恒定的加法项会被相对优势中心化消去，不能因为它的权重大就认为模型真的学到了对应行为。

权重应来自业务要求和对照实验：固定其他因素扫描少量候选权重，比较正确率、格式合规、长度与约束违规的帕累托关系，选择满足硬指标后成本合适的配置。也可以使用约束优化或分层目标，而不必强行把所有目标压成一个固定总分。

验证时保留各分量和交互结果，特别检查模型是否通过牺牲困难题、提前停止或输出空结果来获得长度优势。权重调整、归一化变化和奖励函数升级都要版本化，避免训练曲线因为评分口径变化而失去可比性。

### 23. 评测用 pass@1 还是 pass@k，k 取多少，为什么。

**回答：**

pass@1 反映一次生成成功的概率，更接近只允许一次回答或一次动作计划的场景；pass@k 反映给定同一任务的 $k$ 个候选中至少一个成功，适合具有可靠验证与候选选择机制的流程。后者不能在没有选择器的情况下直接当作线上交付成功率。

若每题独立采样 $n$ 条，其中 $c$ 条正确，常用的 pass@k 估计为：

```math
\widehat{\mathrm{pass@}k}
=1-\frac{\binom{n-c}{k}}{\binom{n}{k}},\qquad n\ge k.
```

当错误样本少于 $k$ 时，该题估计为 1。需要在题目层面汇总并报告样本量与不确定性，固定温度、长度上限和验证规则；相邻重复样本或相互依赖的采样会影响解释。

选择 $k$ 应从实际预算与使用方式出发，而不是挑能让成绩最好看的值。通常同时报告 pass@1、几个预先确定的 $k$、候选验证成本和总 token 消耗。比较不同模型时，可以补充固定总计算预算下的成功率，避免一个模型靠生成更多候选获得不公平优势。

### 24. 训练集难度分布怎么控，全难题和全简单题分别会怎样。

**回答：**

对于组内相对奖励方法，训练集要有足够多“策略有机会做对、但尚未稳定做对”的任务，同时保持目标业务覆盖。全简单题可能大量全对，组内优势为零；全难题可能大量全错，奖励稀疏且探索成本高。简单和困难都应相对于当前检查点定义，而不是固定标签。

先按领域、任务类型和估计难度分桶，用固定小规模采样估计每个桶的成功率及有效组比例。训练中混合不同难度，逐步调整比例，并保留基础任务防止能力回退。随着模型变化，难度估计会过期，需要周期性更新，但不能用测试集反馈直接决定训练题目。

动态筛选有效组可以提高梯度利用率，也会让训练分布偏向中等难度任务。因此同时记录被过滤的任务类型、接受率、重采样成本和覆盖面；重要但长期全错的业务任务，可能需要示范、任务分解或更强基座，而不应永久被丢弃。

评测集保持稳定并覆盖各难度层，分别看成功率与成本。训练过程中有效组减少，既可能是能力提升，也可能是奖励退化或任务覆盖收缩，需要结合独立评测判断。

### 25. 如果给你一批没有标准答案的业务数据，你怎么造 RL 信号。

**回答：**

没有标准答案，不等于完全没有可验证信号。先将业务目标拆成可观察的结果和约束，例如检索证据是否支持结论、工具执行是否达到目标状态、代码是否满足隐藏测试、结构化字段是否一致，以及用户是否在后续环节真正完成任务。

可以组合程序验证、环境反馈、专家偏好比较和经过校准的模型评审。模型评审适合扩大覆盖，但不能把自我打分直接当作真实标签；应使用独立样本、人工抽查、成对交换顺序、盲评和对抗样本检查偏差。自洽性、往返一致性等信号可以提供辅助证据，也可能让多个一致的错误答案互相强化。

业务反馈往往有延迟和混杂因素。例如点击或停留时间可能与界面、用户类型和展示位置有关，需要明确归因与反事实基线，不能直接把流量变化全归到模型。若反馈是任务级的，长轨迹中哪些动作应获得信用也需要另外设计。

先建立小规模可信评价集和离线对照，再决定是否进入 RL。若信号可靠性不足，可以先做监督学习、人工偏好收集或离线策略分析；带着错误奖励扩大训练，通常只会更快地优化错误目标。

### 手撕：实现 GRPO 的 loss。给 batch 内 B 条样本、每条 group size G、变长序列的 logprob 和 reward，要求写出组内归一化 advantage、带 mask 的 token 级 loss 聚合，以及 clip 部分。注意三个坑：除以的是有效 token 数不是总长度；全对组的 advantage 是 0 不是 NaN；old_logprob 和 logprob 的比值要 detach。

**回答：**

这里按 **B 个 prompt、每个 prompt 采样 G 条回答** 理解输入，当前与旧策略 logprob、动作 mask 的形状为 `[B, G, T]`，奖励形状为 `[B, G]`。`T` 是填充后的最大回答长度，mask 只标记实际参与训练的动作 token；prompt、padding 和非策略生成的环境观测不能误算进去。

**需要先纠正题目最后一句。** 应停止旧策略 logprob、奖励和已计算优势的梯度，保留当前 logprob 到重要性比的梯度。若把整个新旧策略比值 detach，策略损失就无法更新当前策略。实现中使用 `exp(logprob - old_logprob.detach())`，不对这个结果整体 detach。

裁剪策略项可写为：

```math
\rho_{bgt}=\exp\left(\ell_{bgt}-\ell^{\mathrm{old}}_{bgt}\right),
```

```math
\mathcal L_{\mathrm{policy}}
=-\frac{\sum_{b,g,t}m_{bgt}
\min\left(\rho_{bgt}\widehat A_{bg},
\mathrm{clip}(\rho_{bgt},1-\epsilon_l,1+\epsilon_h)\widehat A_{bg}\right)}
{\sum_{b,g,t}m_{bgt}}.
```

下面按照题目要求，对全批次的有效动作 token 求平均。这与原始 GRPO 常见的“每条回答内部平均，再对回答平均”有所不同；回答长度不同时，两种聚合给样本的权重也不同。代码仅实现组内优势和裁剪策略项，KL 或辅助监督需要在明确约定后另行加入。

```python
"""Clipped group-relative policy loss with a global valid-token mean.

This educational function omits KL regularization and distributed reduction.
"""
import torch


def grpo_loss(logprob, old_logprob, reward, mask,
              clip_low=0.2, clip_high=0.2, eps=1e-8):
    """Shapes: log probabilities/mask [B, G, T], reward [B, G]."""
    if logprob.ndim != 3 or old_logprob.shape != logprob.shape:
        raise ValueError("log probabilities must have equal [B, G, T] shapes")
    b, g, t = logprob.shape
    if b < 1 or g < 2 or t < 1 or reward.shape != (b, g):
        raise ValueError("need B >= 1, G >= 2, T >= 1 and reward [B, G]")
    if mask.shape != logprob.shape or mask.dtype != torch.bool:
        raise ValueError("mask must be boolean with shape [B, G, T]")
    if any(x.device != logprob.device for x in (old_logprob, reward, mask)):
        raise ValueError("all tensors must be on the same device")
    if not (0 <= clip_low < 1 and clip_high >= 0 and eps > 0):
        raise ValueError("invalid clipping bounds or normalization epsilon")
    if not (mask.sum(dim=-1) > 0).all().item():
        raise ValueError("every response must contain a valid action token")

    # Accumulate low-precision inputs in float32; retain float64 for checks.
    dtype = torch.float64 if logprob.dtype == torch.float64 else torch.float32
    current = torch.where(mask, logprob.to(dtype), 0.0)
    old = torch.where(mask, old_logprob.detach().to(dtype), 0.0)
    rewards = reward.detach().to(dtype)
    if not all(torch.isfinite(x).all().item() for x in (current, old, rewards)):
        raise ValueError("valid log probabilities and rewards must be finite")

    centered = rewards - rewards.mean(dim=1, keepdim=True)
    std = centered.square().mean(dim=1, keepdim=True).sqrt()
    advantage = (centered / (std + eps)).detach()

    # Keep the current policy gradient: DO NOT detach this ratio.
    ratio = (current - old).exp()
    if not torch.isfinite(ratio).all().item():
        raise FloatingPointError("importance ratio overflow; inspect logprob mismatch")
    expanded_advantage = advantage.unsqueeze(-1)
    unclipped = ratio * expanded_advantage
    clipped = ratio.clamp(1.0 - clip_low, 1.0 + clip_high) * expanded_advantage
    token_loss = -torch.minimum(unclipped, clipped)
    loss = (token_loss * mask).sum() / mask.sum()
    return loss, advantage
```

该实现用总体标准差，奖励全相同时中心化结果为零，因而优势为零；每条回答没有任何有效 token 时显式报错。先将 padding 位置替换为零再计算指数，避免无效位置的 NaN 或无穷值污染 loss；有效位置出现非有限值则直接报错，不静默吞掉。

计算量与存储的量级均为 $O(BGT)$，不包含语言模型前向和反向。实际分布式训练时，如果各 rank 的有效 token 数不同，不能简单平均各 rank 的局部均值；应按全局有效 token 数加权，并结合 DDP 的梯度归约约定校准缩放。

代码经过 CPU 上的 11 项检查，覆盖全同奖励、零 loss 下的非零梯度、加常数不变性、变长聚合、padding 隔离、非对称裁剪、有限差分梯度、非法输入以及低精度输入的累积。这些检查验证了损失与梯度的实现，完整训练效果仍需要在真实模型、分布式配置和评测任务上验证。

### 1. 你在这个项目里具体负责哪一块，别人做了什么。

**回答：**

回答要把个人贡献、协作接口和团队成果分开。可以沿着数据、奖励、rollout、训练、评测与部署链路，明确自己设计和实现了哪些模块，哪些是复用框架，哪些由同事完成，最后说明自己如何验证负责部分与整体系统正确衔接。

例如实际负责奖励与评测，就重点介绍任务标准、验证器边界、异常样本、版本管理和回归方法，并说明训练团队如何消费这些分数。实际负责训练引擎，就展开批处理、概率计算、梯度、并行配置、故障恢复和效率测量。回答应能进一步落到代码、配置、实验记录和一次具体问题的解决过程。

对他人负责的环节，可以说明理解的输入输出和共同排查的边界，不必假装亲自实现所有组件。项目收益也要区分个人改动的消融结果与团队最终结果；如果没有单独归因实验，就如实说明贡献证据的限度。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q02"></a>

### 2. 8 卡跑 7B 的 GRPO，rollout 占了多少时间，训练占多少。

**回答：**

仅凭“8 卡、7B、GRPO”无法判断 rollout 与训练占比。占比还取决于 GPU 型号、生成长度、group size、采样并发、奖励计算、优化轮数、并行方式和训练推理是否共享资源，需要从实际时间线测量。

对同步串行迭代，可以拆成权重同步、排队、prefill、逐 token 解码、奖励计算、旧策略或参考概率计算、训练前反向和优化器更新等阶段，统一统计窗口后计算占比。若采用异步或流水重叠，各阶段耗时之和可能大于墙钟时间，应报告关键路径与资源占用，不能把重叠耗时直接相加当成总时间。

同时查看生成 token 吞吐、有效训练 token 吞吐、每步 token 数和任务长度分布，区分“生成工作更多”与“引擎效率变差”。长回复逐 token 解码常会显著影响关键路径，但具体百分比必须来自 profiler、事件时间戳或日志；没有测量时给出测量方案，不猜测一个看似常见的比例。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q03"></a>

### 3. rollout 用的是 vLLM 还是自家引擎，权重同步怎么做的。

**回答：**

使用哪种引擎必须按真实实现回答。无论 vLLM 还是自研引擎，关键是训练完成一个权重版本后，rollout 服务是否以明确、完整的版本生成数据，以及每条轨迹能否追溯到该版本和采样配置。

一种同步设计是：完成优化器更新，冻结待发布版本，将训练分片权重转换为推理侧需要的布局，通过受控传输加载到全部 worker，校验版本与必要的校验信息，完成屏障后再接收下一批生成请求。过程中不能让不同层或不同 worker 混用新旧权重；旧 KV Cache 与新权重不匹配时，需要清理、重算或采用明确的版本隔离。

异步设计可以让上一版本的 rollout 与新版本训练重叠，但要记录样本的行为策略版本，限制滞后并按算法处理分布偏差。请求运行中发生权重更新、部分生成后切换模型，会使一条序列缺少清晰的行为策略定义，应通过排空、双缓冲或版本固定来避免。

如果使用 LoRA，还要保证基座、adapter 标识与缩放方式一致。报告同步耗时、失败恢复、分片转换和加载验证方法，比只回答“调用某个同步接口”更能体现工程理解。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q04"></a>

### 4. 采样和训练精度不一样（bf16 vs fp16），怎么保证 on-policy。

**回答：**

bf16 与 fp16 即使使用同一份权重，也可能因数值范围、精度、内核和归约顺序产生不同的 logits。相同权重版本是必要条件，但不能仅凭这一点声称严格 on-policy；需要比较真正用于生成数据的行为分布与训练目标所假设的分布。

首先统一 token、模板、mask、位置编码、温度和采样规则，在相同前缀上检查两侧 logprob 的偏差分布。然后逐项控制精度和内核，必要时提高 softmax、logsumexp 与概率比等关键计算的累积精度。对 fp16 还要关注溢出和非有限值，不能把数值异常当成正常探索。

rollout 时记录行为策略版本与约定下的采样概率。如果训练侧的旧策略概率是重新计算的，它不一定等于真实行为概率；可以采用匹配算法的重要性修正、样本屏蔽或其他偏差控制，但必须承认这些处理的假设和代价。只重算一次 logprob，并不能改变样本来自哪个分布。

实际验收采用相同任务上的概率差、比率长尾、有效样本量、裁剪情况与独立成功率对照。允许多大的数值误差应由模型、序列长度和目标算法共同决定，不能设一个与所有场景无关的统一阈值。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q05"></a>

### 5. 如果 rollout 阶段 GPU 利用率只有 30%，瓶颈可能在哪。

**回答：**

先确认 30% 的口径：监控的是设备忙碌时间、SM 利用率、算力利用率，还是一段包含排队与奖励等待的平均值。GPU 利用率低不自动意味着需要更大模型或更多卡，可能是输入供应、同步依赖或内存访问限制。

常见瓶颈包括请求并发不足、CPU 分词或数据读取过慢、奖励服务串行等待、工具环境延迟、批次被少量长尾请求拖住、权重同步间隙、跨卡通信，以及 KV Cache 容量限制导致无法提高并发。逐 token 解码还可能主要受内存带宽和小批量 kernel 开销约束，低计算利用率与没有工作可做不是同一情况。

用时间线区分“GPU 等输入”“等待远程奖励”“正在解码但效率低”，再看队列深度、活跃序列数、prefill 与 decode 吞吐、CPU、显存带宽和通信指标。可以在固定模型、输出长度和请求集上调整并发、批处理与长度分桶，确认变化是否提高端到端有效样本吞吐。

不要只追求监控面板上的利用率。增加无意义采样或让所有回答变长也可能使 GPU 更忙，却降低单位成本内的有效组数量和训练效果。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q06"></a>

### 6. 长尾样本（特别长的回复）怎么处理，截断了 reward 怎么算。

**回答：**

长尾回复会影响生成尾延迟、KV Cache 峰值和训练 batch 的填充浪费。可以先检查是否为必要的长推理，还是重复循环和停止失败，再采用长度分桶、动态批处理、合理的生成预算与软长度约束，避免最慢样本阻塞整个同步批次。

必须区分自然结束与达到上限后被截断。若任务要求完整最终答案，截断后没有可验证结果，就不能当作成功；但也不能从“没有生成完”推断所有已生成推理都是错误。记录截断标志、有效输出长度和可验证的中间状态，由明确的奖励策略决定处理方式。

可选处理包括屏蔽无法可靠评分的截断样本、使用可信的过程反馈、在软阈值后逐步惩罚长度，或者在预算允许时补充完成。屏蔽会改变样本分布并消耗采样预算；重采样和延长预算也需要计入成本。不能简单把截断组的奖励设成同一个极低值而不检查它对优势和难度分布的影响。

mask 通常保留真实生成的有效动作 token，但如果该序列的奖励无法成立，还需要单独的样本有效性标记。训练 mask、结束原因和奖励是否有效是三个概念，不能全部用“长度小于上限”替代。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q07"></a>

### 7. 你们做过多轮迭代吗，每一轮的模型是上一轮的 checkpoint 还是重新从 SFT 起。

**回答：**

常见的连续训练方式是从上一轮有效检查点继续，让策略逐步改进；从同一个 SFT 检查点重新开始，更适合做独立方案对照、排除历史路径影响，或者在先前训练明显损坏能力时重新构建。两种方式回答的是不同问题，没有统一要求。

继续训练时需要说明保留了哪些状态：模型、优化器、学习率调度、数据采样进度和必要的随机状态。只加载权重而重置优化器，与完整断点恢复并不是同一种实验。参考策略是否保持最初 SFT 版本、是否更新奖励模型，也应单独记录。

每一轮使用新策略生成的数据时，要追踪其模型版本与评测结果，避免新旧轨迹混用而没有偏差处理。新一轮的数据过滤或奖励规则发生变化，应在固定评测集上重评旧模型，区分能力变化和评价口径变化。

如果实际没有做过多轮迭代，就说明当前验证范围，并给出下一轮计划。不要把多次独立超参数试验描述成一个连续自我改进过程。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q08"></a>

### 8. 迭代几轮之后效果开始掉，是什么原因。

**回答：**

先检查“效果下降”是否在固定独立评测、相同生成预算和相同验证规则下成立。线上业务分布变化、量化配置变化或评分器升级，都可能造成表面回退，不能立即归咎于训练轮次。

若确实是策略退化，常见原因包括奖励投机累积、偏好或评分器偏差、训练分布越来越窄、重复数据和测试泄漏、熵下降导致探索收缩、过度更新，以及对通用能力的遗忘。异步系统还要检查样本滞后、权重错配和行为概率记录是否失真。

定位时按检查点比较任务类别、难度、长度、格式与失败类型，并回放“奖励高但独立评测失败”的轨迹。通过冻结奖励、固定数据、恢复先前模型或只更换一个环节做消融，尽量缩小故障范围，而不是同时改所有超参数。

处理可以包括回退有效检查点、修正奖励、恢复任务覆盖、降低更新强度或加入经过验证的回归数据。是否继续迭代由独立收益与成本决定；更多轮次本身不构成更强能力的证据。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q09"></a>

### 9. 线上部署的模型和训练时的模型是同一个吗，量化了吗。

**回答：**

要区分模型身份一致与数值行为一致。线上可能部署同一训练检查点的不同精度版本，也可能经过量化、adapter 合并、蒸馏或额外微调；这些转换都需要独立版本标识和验收，不能笼统称为“完全一样”。

记录训练检查点、基座和 adapter、分词器、聊天模板、特殊 token、位置编码配置、量化方法、校准数据及推理引擎。即使权重对应同一个模型，停止条件、工具调用解析和采样参数不同，也可能导致线上表现明显变化。

量化后重点检查目标任务正确率、长上下文、工具参数有效率、格式与安全约束、延迟和显存，使用有代表性的业务输入与困难样本。不要仅凭困惑度或一小段顺畅对话证明部署等价。

如果线上效果不如训练评测，沿着“相同权重与输入 → 相同数值配置 → 相同解码 → 相同后处理”的顺序做回归。没有量化或没有部署过，就说明实际状态，而不是为了回答完整而编造上线经历。

<a id="moonshot-llm-rl-20261105-947983031250251776-r2-q10"></a>

### 10. 这套流程如果搬到 32B，最先崩的是哪一环。

**回答：**

不能只凭从 7B 增到 32B 就断言哪一环必然先崩。应分别测算训练状态与激活、rollout 权重与 KV Cache、参考或奖励模型、跨卡通信、权重同步以及 CPU 和网络开销，再对照现有设备与并行布局。

以稠密模型全量 Adam 训练的某种常见配置为例，低精度参数与梯度、FP32 主权重及两份 FP32 动量合计约为每参数 16 字节。按这个假设，7B 约 112 GB，32B 约 512 GB，尚未计入激活、通信缓冲和其他模型；是否持有主权重、梯度精度与分片方式会改变这些数值。它是总状态量估算，不能直接当成单卡需求。

rollout 侧还需要容纳推理权重和活跃序列的 KV Cache，长回复与大 group 会放大需求。不同架构的层数、KV 头数与隐藏维度不同，KV 显存不能只按参数比例缩放。扩大张量或流水并行又可能让通信、尾延迟与权重重新分片成为瓶颈。

可以按“模型加载 → 单步前反向 → 有限并发 rollout → 奖励链路 → 权重同步 → 完整迭代”逐级测量峰值与关键路径，结合 FSDP/ZeRO、激活重算、microbatch、推理并发和共享资源调度调整。优化目标是可承受预算内的有效任务收益，而不仅是让 32B 勉强完成一次运行。
