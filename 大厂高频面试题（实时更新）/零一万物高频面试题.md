### 1.自我介绍

**回答：**

自我介绍围绕知识图谱与 Agent 开发岗位组织，用约一分钟交代教育背景、相关项目、个人贡献和希望深入的方向。与岗位最相关的经历可以是信息抽取、检索、自然语言处理、数据清洗、模型微调或后端工具开发，不必强行把每段经历都包装成知识图谱项目。

可以按真实情况表达：“我目前……，主要关注……。在……项目中，我负责……，核心工作是将……转成……，重点解决过……问题，并通过……验证。我对知识抽取、实体归一和可追溯的 Agent 流程比较感兴趣，希望进一步参与真实数据上的算法与工程工作。”所有省略处都应使用能够解释和验证的经历。

选一个可以深入追问的项目作为主线，提前准备数据格式、模型输入输出、失败案例和个人职责。没有线上数据或正式实习，就明确项目性质；没有做过的算法可以说明理解和设计思路，不把学习计划说成已经取得的结果。

### 2.实习介绍

**回答：**

按照“业务目标—个人任务—实现路径—难点—验证结果”介绍实习。先说明团队需要解决什么，再限定自己负责的模块，例如文档解析、实体识别、检索接口、评测数据或 Agent 工具接入，避免将团队全部工作描述为个人成果。

可以选择一个有细节的案例展开：某类实体由于简称和上下文不同出现错配，如何收集错误样本、定位到抽取或链接环节、提出修改并跑回归。结果应说明评测集、基线和统计口径，区分离线实验、灰度测试与正式上线；没有可靠量化结果时，展示可复现案例也比编造提升百分比更有效。

还应解释与导师、算法同学和工程同学如何协作，使用了哪些已有组件，以及自己能独立维护哪部分。没有正式实习就如实说明，并用相关研究或项目回答能力问题。

### 3.agent用的什么框架有了解吗

**回答：**

首先回答实际使用过的框架、版本范围和具体职责。如果只是读过示例，应明确区分了解与实践；如果没有采用框架，可以介绍由服务代码、模型 SDK、任务队列和状态表构成的实现。

理解框架时，重点看模型接入、工具契约、状态存储、节点编排、循环终止、人工介入和观测能力。LangChain 提供模型、工具、检索等应用构建与集成能力；LangGraph 强调显式状态和图式编排，可结合持久化支持中断与恢复。具体能力取决于版本和配置，接入框架不会自动解决工具权限、业务幂等或结果正确性。

可以用信息抽取任务说明选型：固定的“解析—抽取—校验—归一—入库”流程可先用普通工作流；若需要根据证据不足动态检索术语、等待专家确认再恢复，则持久化编排更有价值。多 Agent 只有在职责分离、并行收益或独立验证带来可测改善时才引入，不为展示框架复杂度拆分角色。

### 4.agent三次调用都报错，你会怎么办

**回答：**

三次报错后先停止无差别重试，查看调用轨迹，确认失败发生在模型服务、参数生成、工具执行还是结果解析阶段。记录错误码、请求标识、参数摘要、耗时与是否产生外部副作用，同时避免在日志中泄露密钥和敏感数据。

可恢复的网络超时、限流或服务暂时不可用，可以在总时间和次数预算内退避重试并加入抖动；限流遵守服务端提示。参数类型、字段缺失、枚举不合法等确定性错误，先依据工具 schema 和明确错误反馈修复参数；权限不足、资源不存在、依赖未配置时，应终止或转人工，反复调用相同参数通常不会改善。

对有副作用的调用尤其要谨慎。超时只代表没有及时收到响应，不代表操作未成功；提交任务、写入图谱或创建记录前后应有幂等键和状态查询，先核实执行结果，再决定是否重试。并发尝试还需防止多个分支重复执行相同操作。

如果已经连续失败，应触发熔断或切换明确可用的降级路径，例如只输出已验证的抽取候选、保留任务状态等待恢复，或要求补充必要信息。面向用户说明哪一步未完成，而不是把部分结果包装成成功。后续把失败样本纳入回归，检查是工具契约、提示词还是服务稳定性问题。

将错误处理落实到执行器时，可以使用下面的决策表。三次只是题目给定的现象，实际重试预算应由操作语义、总时限和服务约束决定。

<div align="center">

| 失败类型 | 下一步动作 | 关键检查 |
|---|---|---|
| 读操作遇到临时网络故障或限流 | 有界退避重试 | 总时限、限流提示、熔断状态 |
| 参数缺失或类型错误 | 按 schema 修复后重新校验 | 不重复发送相同错误参数 |
| 写操作超时，结果未知 | 先查询操作状态 | 幂等键是否稳定、操作是否已提交 |
| 权限不足或确定的业务约束冲突 | 终止该路径并反馈 | 不通过换参数绕过权限与约束 |

</div>

幂等键应标识同一次业务意图，并在该操作的重试中保持不变；每次重试都生成新键，会失去去重作用。真正的新任务则应使用新的业务身份。

### 5.你的agent调了哪些工具？调用工具时参数报错是怎么处理的？

**回答：**

工具清单必须来自实际项目。对于知识抽取 Agent，一个设计示例可以包含文件读取与解析、术语检索、图谱实体查询、结构校验和候选入库工具；这些是解释架构的例子，不能当作个人已经接入的事实。

每个工具定义名称、用途、输入 schema、输出 schema、错误分类和权限边界。模型产出的参数先做结构校验，例如字段是否存在、类型是否匹配、枚举和数值范围是否合法，再做业务校验，例如文档是否可访问、实体 ID 是否存在、关系类型是否被本体允许。结构化输出有助于约束格式，但不能保证参数具有正确业务含义。

参数错误应返回可操作的结构化信息，如字段路径、期望类型和允许取值，再让模型在限定次数内修复。确定性且无歧义的转换可以由代码处理，但不能静默把一个不确定的疾病名称改成另一个实体 ID。缺少关键上下文时应补查或询问，而不是猜测。

工具执行成功后还要验证返回格式、数据版本和任务目标是否满足。写操作增加授权与幂等检查，读工具也限制范围和结果规模。分别统计参数合法率、执行成功率和任务正确率，防止“参数合法”掩盖语义错误。

<a id="01ai-kg-intern-20261021-de81855b-q06"></a>
### 上下文太长怎么办？记忆和上下文是怎么处理的

**回答：**

上下文是当前一次模型调用实际可见的内容；记忆是跨调用保存的状态、事实或经验，只有被选择并注入后才进入当前上下文。长期记忆可以保存在数据库、文档或向量索引中，不意味着模型会自动记住全部历史。

先建立 token 预算，为系统规则、当前问题、关键状态、工具证据和输出留空间。近期必要对话可以保留原文，已完成步骤压缩成结构化摘要，长文档和日志保存在外部，仅按需读取。工具调用与对应返回结果应成对保留或按接口约定整体压缩，避免产生不合法的消息序列。

知识抽取任务的工作记忆应优先保存当前文档版本、抽取范围、本体版本、已确认实体映射、待解决歧义和未完成操作。长期记忆只写入经过确认的事实，并附带时间、适用范围、证据和权限，支持更新、撤回与冲突处理。模型对自身输出的总结不能直接变成可信事实。

摘要会丢细节，向量检索也可能漏召回，所以关键证据应保留可回读定位。对实体归一等高风险决策，应重新读取原始语境与术语定义。评测除了 token 节省，还要看约束保持、跨轮一致性、错误记忆传播和权限隔离。

### 6.介绍sft和dpo

**回答：**

SFT 是监督微调，使用输入与期望输出训练模型，常用于学习任务格式、回答方式和领域操作流程。对输入 x 和目标回答 y，典型自回归损失为：

```math
\mathcal{L}_{\mathrm{SFT}}=-\mathbb{E}_{(x,y)}\sum_t
\log\pi_\theta(y_t\mid x,y_{<t}).
```

指令微调常只对需要学习的回答 token 计算损失，是否包含其他部分由具体数据与训练目标决定。数据需要正确标注、去重、隔离测试集，并覆盖正常、无答案、歧义与错误处理，不能只收集格式漂亮的成功案例。

DPO 是直接偏好优化，数据通常为同一输入下的偏好回答 y_w 和较差回答 y_l。它相对于固定参考策略调整二者的相对概率，常见目标为：

```math
\mathcal{L}_{\mathrm{DPO}}=-\mathbb{E}_{(x,y_w,y_l)}
\log\sigma\left(\beta\left[
\log\frac{\pi_\theta(y_w\mid x)}{\pi_{\mathrm{ref}}(y_w\mid x)}
-\log\frac{\pi_\theta(y_l\mid x)}{\pi_{\mathrm{ref}}(y_l\mid x)}
\right]\right).
```

这里序列对数概率通常由回答 token 的条件对数概率求和，σ 是 sigmoid，β 控制该目标中的偏好尺度，并与其 KL 正则化推导相关。标准 DPO 不需要先单独训练显式奖励模型，也不需要 PPO 式的在线采样优化循环；数据生成和更新流程仍可能包含模型采样，不能据此说整个偏好学习系统永远不需要生成候选。

SFT 告诉模型“期望怎么做”，DPO 利用比较信号告诉模型“两个行为中更偏好哪个”。常见实践先 SFT 再做偏好优化，但二者并非必须绑定，DPO 也不能凭空补足缺失的知识和基本任务能力。实体抽取可以用 SFT 学习结构化输出，再用可靠偏好对减少无证据关系或错误合并；偏好标注必须控制长度偏差、噪声和伪规律。

评估应分别检查抽取精确率与召回率、格式合法率、证据支持、泛化及能力退化。优化损失下降或偏好胜率提高，不足以单独证明医学事实更正确。

### 7.lora原理

**回答：**

LoRA 假设适配任务所需的权重变化可以用较低秩矩阵近似，在冻结底座权重的同时，训练两个小矩阵形成增量。对于线性层：

```math
W'=W+\Delta W,\qquad \Delta W=\frac{\alpha}{r}BA,
\quad A\in\mathbb{R}^{r\times d_{\mathrm{in}}},
\quad B\in\mathbb{R}^{d_{\mathrm{out}}\times r}.
```

可训练参数为 r×(d_in+d_out)，而全量训练该矩阵需要 d_in×d_out 个参数。rank 控制增量表示容量，α/r 是标准 LoRA 的缩放；rank 更大不必然效果更好，也可能增加成本和过拟合。常见初始化令一个矩阵为零，另一个为随机值，使模型初始函数与底座一致；两个矩阵同时为零会妨碍初始梯度更新。

目标模块可以选择注意力中的若干投影层，也可以扩展到 MLP，具体取决于架构和任务。训练时底座参数不更新，但前向传播与必要的激活和反向链路仍存在，因此显存节省主要来自可训练参数、梯度和优化器状态减少，不等于总显存按参数比例下降。

在兼容精度与布局下，可将低秩增量合并到基础权重以部署；动态切换多个适配器时则可能保留额外计算。QLoRA 还引入量化底座等技术，不能简单解释为“LoRA 就是量化”。调参应固定数据划分，比较 rank、目标层、学习率与训练步数，并检查目标任务和通用能力。

### 8.有准备coding题目吗，讲讲爬楼梯的思路

**回答：**

先确认标准问题：共有 n 级台阶，每次走 1 或 2 级，求不同步序的数量。若允许步长不同、禁止连续走两级或要求取模，递推和实现需要相应调整；“有没有准备”这一部分应按个人情况回答。

最后一步只能来自第 n−1 级或第 n−2 级，两种情况互斥且覆盖全部方案，因此 f(n)=f(n−1)+f(n−2)。采用 f(0)=1、f(1)=1 的约定，零级表示不移动这一种空方案，于是 f(2)=2、f(3)=3。若题目只允许正整数 n，可在说明接口时明确；下面实现接受非负整数并拒绝负数及非整数。

```python
def climb_stairs(n: int) -> int:
    if isinstance(n, bool) or not isinstance(n, int):
        raise TypeError("n must be an integer")
    if n < 0:
        raise ValueError("n must be non-negative")
    prev, curr = 1, 1  # f(0), f(1)
    for _ in range(2, n + 1):
        prev, curr = curr, prev + curr
    return prev if n == 0 else curr
```

循环开始时两个变量保存相邻两级的方案数，更新后继续保持这个不变量，因此无需保存完整 DP 数组。按整数运算视为常数的常见口径，时间 O(n)，额外变量个数 O(1)；Python 任意精度整数的位数随 n 增长，精确位复杂度并非常数空间，极大 n 时还要考虑大整数加法成本。

朴素递归重复计算大量子问题，记忆化可以避免重复，但还增加递归栈和缓存。若需要极大 n 且题目要求模数，可以进一步讨论快速倍增或矩阵快速幂；不能为了展示技巧跳过最简单正确的递推、边界和验证。

### 栈和队列有什么区别

**回答：**

栈遵循后进先出，常见操作是在同一端压入、弹出与查看栈顶；队列遵循先进先出，通常从队尾进入、队头移出。二者是抽象数据结构，可以用数组、链表或其他容器实现，复杂度需要结合具体实现说明。

栈适合函数调用、括号匹配、撤销和深度优先遍历；队列适合广度优先遍历、任务排队和按到达顺序处理。对于无权图，BFS 使用队列逐层扩展可以寻找最短边数路径，而 DFS 的栈顺序不保证这一点。

Python 中 list 的 append 和末尾 pop 适合实现栈，通常为摊还 O(1)；list.pop(0) 会移动后续元素，通常为 O(n)。普通双端队列可用 collections.deque，append 和 popleft 在两端高效操作。线程间生产消费应考虑 queue.Queue 等带同步与阻塞语义的抽象，不能把普通容器的单个操作特性等同于整个复合业务逻辑线程安全。

工程任务队列还需要考虑容量、背压、超时和取消。先进先出只约束取出的顺序，多个消费者并发执行时，完成顺序未必与入队顺序相同；需要严格有序时应额外设计分区串行或结果排序机制。

<a id="01ai-kg-intern-20261021-de81855b-q11"></a>
### 9.平常用哪些ai辅助编程工具，有本地部署经验吗

**回答：**

先说明自己实际使用的 AI 编程工具及用途，例如补全、解释代码、生成测试、定位异常或辅助重构。回答重点是如何检查结果：阅读差异、运行测试、验证依赖与接口、检查边界条件，而不是只罗列产品名或声称生成代码无需理解。

本地部署需要明确部署对象。运行 IDE 插件、部署一个调用云端 API 的前端，与把模型权重下载到本机并运行推理服务是不同经历。若只做过前两者，应如实说明；确实本地推理时，则介绍模型规模、精度或量化、CPU/GPU、显存、推理运行时、接口方式和测量结果。

部署设计需要估算权重、KV Cache、激活与运行时开销，检查模型与 tokenizer、聊天模板的匹配，设置上下文和并发限制，再测试启动、首 token 延迟、吞吐和长请求稳定性。量化可能减少显存，但也可能影响质量和算子支持，不能简单认为位数越低越好。

如果从事知识图谱抽取，测试应包含结构化输出、中文与英文实体、罕见术语和长文档证据一致性。没有做过的部署环节可以给出计划和验证方法，但不编造设备型号、吞吐数据或生产经验。

<a id="01ai-kg-intern-20261021-de81855b-q12"></a>
### 10.本体了解吗

**回答：**

知识图谱语境中的本体，是对领域概念、关系、属性及其语义约束的明确描述，用来回答“系统允许哪些类型的对象和关系，以及它们意味着什么”。它通常包含类、类之间的层次、对象属性、数据属性和相应公理或约束，不能只等同于一张实体名称表。

以医学为例，可以定义疾病、症状、药物等类，以及“疾病具有症状”“药物用于治疗疾病”等关系，再规定关系参与者的类型、术语粒度和需要保存的证据。本体层描述概念与规则，实例层记录具体实体和事实；疾病类与某一种疾病概念如何建模，需要在项目中统一，不能随意混用。

OWL 2 提供形式化语义，RDF 常用于图数据表示，RDFS 提供基础词汇与模式能力。OWL 的推理规则与数据库校验不完全相同：例如 domain/range 可以推导主体或客体的类型，不一定像 SQL 约束一样直接拒绝一条数据；开放世界假设下，“没有记录”通常不等于“事实为假”。若需要检查必填属性或结构合法性，可以结合 SHACL 等约束验证机制。

本体设计先定义业务需要回答的能力问题，再选择足够细致的概念和关系，复用合适的领域标准，并制定版本与迁移机制。概念过粗会损失语义，过细则增加标注、消歧和维护成本。实际未使用过 OWL 时，可说明了解基本概念和应用边界，不声称完成过复杂推理系统。

<a id="01ai-kg-intern-20261021-de81855b-q13"></a>
### 11.对知识图谱了解哪些

**回答：**

知识图谱将实体及其关系组织成具有语义的图。基本事实可表示为“主体—关系—客体”三元组，实体也可以带属性；实际业务常需额外保存时间、证据、置信状态和适用范围。RDF 图与属性图是常见表示方式，二者的数据模型和查询方式存在差异，应按互操作、模式约束及查询需求选择。

典型构建流程包括本体或 schema 设计、数据接入、实体与关系抽取、实体链接与融合、质量验证、存储检索及持续更新。实体识别回答文本哪里提到了某个对象，实体链接回答这处提及对应哪个标准实体，关系抽取回答两个对象之间是否存在文本支持的关系，三者不能互相替代。

应用包括语义检索、多跳查询、实体画像、推荐和检索增强生成。图结构有利于沿明确关系组织证据，但抽取错边、实体误合并和过时事实会沿路径放大；图可查询不代表其中的事实天然正确。规则推理、嵌入相似度和大模型补全提出的结论也应区分证据强度。

评估可以拆为抽取的精确率、召回率与 F1，链接准确率，错误合并与拆分比例，关系类型合法率，以及业务查询成功率。对于医疗等领域，应保留可定位的原文证据和人工复核路径，不能把模型猜出的关系直接当成已证实事实。

<a id="01ai-kg-intern-20261021-de81855b-q14"></a>
### 12.让你设计一个从数据中提取实体的关系的agent你会怎么设计？

**回答：**

首先确认输入数据类型、领域和输出契约：文本、表格还是数据库记录，允许哪些实体和关系类型，是否需要否定、时间或条件修饰，以及哪些结果必须人工复核。题目中的“实体的关系”可以理解为同时抽取实体及其关系，设计中应分别给出产物和验证标准。

可采用“解析与定位 → 实体提及抽取 → 候选实体检索与链接 → 关系抽取 → 约束与证据校验 → 复核 → 版本化入库”的工作流。解析保留文档 ID、版本、段落和字符区间；分块时保留标题和必要邻近上下文；实体提及保留原文名称与位置，再关联规范实体 ID，不直接用名称作为永久主键。

模型按 schema 输出候选实体与关系，关系包含主体、谓词、客体和证据区间，必要时记录否定、时间与条件。代码检查 ID 引用是否存在、类型是否符合规则、证据区间是否有效，模型或人工再检查文本是否真正支持该关系。例如“尚无证据表明药物 A 可治疗疾病 B”不能抽成肯定治疗关系。

Agent 只在需要决策的环节动态调用工具，例如检索术语定义、补读交叉引用、对低置信度链接请求专家确认；固定格式校验和入库采用确定性逻辑。约束调用次数、权限和输出规模，为任务和写入设置幂等键，保存节点状态与产物引用，以支持失败恢复。

候选事实和已确认事实分开管理，入库采用稳定实体 ID 与事实身份规则，保留证据、抽取器和本体版本。矛盾事实应记录冲突及适用条件，不直接覆盖；错误合并应可撤回。每次更新后用人工标注集评估实体、关系、链接以及端到端查询，并把失败案例纳入回归。

<a id="01ai-kg-intern-20261021-de81855b-q15"></a>
### 13.这些过程中存在一些问题，比如实体抽取时，把同一疾病的中文名，英文名，别的称呼提取到了不同实体，如何解决？

**回答：**

这首先是实体归一与链接问题：文本中不同名称可能指向同一个概念，也可能是近义但不同的疾病。应保留每次提及的原文名称和位置，再将其链接到规范实体 ID；不要为了“去重”删掉原始提及，或只按字符串相似度合并。

第一步做可逆的表面规范化，例如空白、大小写、全半角和常见标点处理，并保留原始值。第二步利用领域术语库、已审核别名、缩写表、中英文词表及标准编码生成候选，向量检索用于补充候选。中文名、英文名和俗称只有在概念定义与语境一致时才归到同一 ID。

第三步做上下文消歧：比较实体类型、定义、伴随症状、上下位关系、编码和文本中的指代范围。名称相似的疾病可能属于不同亚型，简称也可能在不同专科具有不同含义；“糖尿病”与“2 型糖尿病”不能因为语义相近直接合并。同一个规范编码有时是强线索，但仍要确认编码体系、版本和映射粒度。

高置信度且满足约束的候选可以自动链接；低置信度进入人工复核，缺少合适候选时创建待确认实体或标记 NIL，而非强制选最近邻。不要直接对相似度阈值连边再取连通分量，因为 A 类似 B、B 类似 C 并不保证 A 与 C 是同一实体。大模型可辅助比较定义和证据，但其自报置信度需要校准。

合并后维护 canonical_id、alias、实体重定向和变更记录，更新关系端点并处理重复事实，保留每条事实的证据。合并应可逆，尤其医学领域错误合并可能比暂时重复更严重。评测除链接准确率外，还应分别统计误合并、漏合并和按实体簇计算的质量，人工抽检跨语言及罕见实体。

**记录结构示例。** 可以将一次提及保存为 `mention_id + document_id + document_version + span + surface_text`，将链接结果单独保存为 `mention_id + canonical_id + terminology_version + decision_status + evidence_ref`。其中 span 的起止位置必须约定字符或字节单位，证据位置始终绑定文档版本；decision_status 区分自动通过、待复核和人工确认，不能只保留一个无解释的分数。

例如，同一概念的中英文提及分别拥有各自的 mention_id，审核后共同指向一个 canonical_id；缩写在另一段落中表示不同概念时，则可以链接到另一实体或保留 NIL。这样既能统一查询，又保留原文与消歧依据。发生错误合并时，依据链接决策和变更记录恢复实体及关系端点，而无需重新猜测每条事实原本属于谁。

<a id="01ai-kg-intern-20261021-de81855b-q16"></a>
### 14.反问

**回答：**

反问可以围绕业务目标、实习职责和评价标准展开。优先选择能帮助判断岗位实际内容的问题，例如团队现在要解决的是图谱构建、知识检索还是基于图谱的 Agent 应用，实习生预计负责哪一段流程，以及如何判断工作达到交付要求。

准备两到三个问题即可，并根据前面已聊过的内容调整。如果面试官已经解释团队业务，就继续询问数据质量、导师协作或首个任务，不重复提问。交流中没有确认的业务安排与技术选型，不能写成公司事实。

<a id="01ai-kg-intern-20261021-de81855b-q17"></a>
### 组里业务？实习生来了是直接做知识图谱吗？还会做什么

**回答：**

这组问题可以按“业务场景—任务范围—协作方式”逐步询问。例如先了解图谱主要服务哪个应用，再问实习生是侧重实体关系抽取、实体对齐、评测，还是同时参与数据处理、Agent 工具与部署工作。

还可以进一步了解入职后的第一个可交付任务、是否已有本体和标注数据、遇到领域歧义时由谁复核，以及算法实验如何进入工程系统。这些问题能帮助判断岗位是以研究探索、算法迭代还是业务交付为主。

现有面试记录没有提供这组反问的具体答复，因此不推断团队内部业务、实习任务分配或入职后的安排。后续实际交流时，应记录面试官确认的信息，并将个人兴趣与明确职责对齐。
