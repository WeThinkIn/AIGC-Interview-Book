# 技术价值判断规范

本规范用于判断一个 AI 技术主题是否值得进入项目的长期知识主干，以及应该以什么深度、什么状态和什么方式呈现。

## 一、判断对象

判断对象可以是：

- 模型、模型架构和训练方法；
- 算法、损失函数、数据与评测方法；
- Agent 工作模式、工具协议、记忆和运行时机制；
- 多模态、图像生成、视频生成和数字人技术；
- 推理框架、部署方案、量化、并行和系统优化；
- AI 产品方法、岗位能力和职业路线；
- 能够影响上述方向的论文、源码、官方发布或产业实践。

不要把一个品牌名、版本号或 API 名称直接当成技术判断对象。首先要还原它背后的问题、机制和约束。

## 二、七个判断维度

### 1. 长期问题

它解决的是否是长期存在的问题，例如表示、泛化、数据质量、训练稳定性、评测、推理效率、可靠性、成本和人机协作。

### 2. 机制迁移

核心机制能否迁移到不同模型、任务、框架、公司和岗位。越依赖某个产品界面或版本 API，越不应直接视为跨周期主干。

### 3. 系统增量

相比已有方法，它是否改变了质量、成本、延迟、可控性、可靠性或交付方式等关键系统约束。

### 4. 产业证据

区分论文提出、开源发布、社区流行、真实项目使用、生产部署、岗位要求和面试高频。不同证据等级不能混写。

### 5. 学习杠杆

学习它能否帮助用户理解更多技术、解决更多问题，或形成可以迁移的项目和面试表达能力。

### 6. 替代风险

判断它是底层机制、通用范式、工程实现还是短期包装；同时记录可能替代它的方案和它可能替代的旧方案。

### 7. 证据质量

判断必须区分事实、实践、主编判断、社区观察和未知信息。证据不足时降低置信度，不用更强的语气弥补证据缺口。

## 三、最小判断结论

每个主题至少要形成以下四个结论：

1. **本质判断**：它解决的核心问题和机制是什么；
2. **周期判断**：它属于长期主干、结构性增量、产业验证中、阶段性跟进还是降低优先级；
3. **投入判断**：目标用户应该学什么、学到什么深度、哪些内容可以延后；
4. **边界判断**：当前证据不能证明什么，什么变化会促使我们修改结论。

没有这四项内容的文章可以作为技术资讯，但不能作为本工作区的正式价值判断。

## 四、证据优先级

优先顺序如下：

1. 论文、官方文档、官方源码、模型卡、版本说明和官方招聘页面；
2. 可说明时间、岗位、上下文和边界的本人实践或真实面试经历；
3. 多个独立样本能够交叉验证的社区反馈；
4. 有明确作者、日期和来源的高质量二手分析；
5. 个人推测和行业传闻。

最后一类只能标记为“观察”或“待验证”，不能写成已经确定的产业事实。

## 五、判断写作要求

采用以下叙事顺序：

```text
问题是什么
→ 为什么原有方法不够
→ 新方法的机制增量是什么
→ 它改变了哪些工程或产品约束
→ 哪些能力值得长期学习
→ 哪些细节可能快速过时
→ 当前应采取什么行动
```

避免以下表达：

- 只用模型名称、榜单分数或营销功能替代机制解释；
- 把一次发布、单篇论文或单次面试概括成行业共识；
- 把“当前没有进入主线”写成“完全没有价值”；
- 把闭源系统未披露的细节写成确定事实；
- 用“颠覆”“必然淘汰”“永久领先”等无法复核的绝对表述。

## 六、审核流程

1. **信号收集**：记录来源、日期、版本、主题和初步问题；
2. **机制整理**：去除宣传语，写出问题、机制和边界；
3. **证据核验**：核对一手资料，并区分事实与判断；
4. **主编判断**：由 Rocky Ding 确定状态、学习优先级和公开表述；
5. **内容连接**：关联主仓库章节、面试题、热门教程和学习路线；
6. **社区校验**：接受支持证据、真实案例和反例；
7. **周期复核**：按月观察，按季度复核，必要时即时降级或修正。

AI 工具可以辅助检索、去重、聚类和链接检查，但不能替代主编对技术机制、证据边界和长期价值的最终判断。

## 七、合规与更新边界

不得提交内部业务、未公开产品、受保密协议约束的信息、未授权聊天记录或个人隐私。招聘、薪资、技术版本和模型能力等时效内容必须写明来源和核验日期。

判断卡必须保留最近复核时间。结论改变时，不覆盖历史判断，而是在[判断变更记录](判断变更记录/README.md)中说明新证据和变化原因。
