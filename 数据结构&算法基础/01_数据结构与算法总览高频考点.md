<h1 id="q-001">1. 为什么 AI 算法岗仍然必须掌握数据结构与算法？</h1>

<h2 id="q-002">面试问题：数据结构和算法在 AIGC 系统中分别解决什么问题？</h2>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

**数据结构决定信息怎样组织，算法决定如何利用这种组织完成计算。** 两者要一起选择。例如从一百万篇文档里返回最相关的十篇，数组可以存向量，倒排表可以存关键词对应的文档 ID，图索引可以存向量之间的邻接关系；查询时再用扫描、图搜索、候选合并和重排把结果取出来。仅有一个“向量数据库”的名字，还没有解释系统为什么能快。

从问题到实现，可以分三步。先写出需要支持的操作：按 ID 查、按范围查、按相似度查，还是不断插入并取最大值。再看数据规模、更新频率和内存预算。最后选择表示与算法，并检查最坏输入。按 ID 精确查通常适合哈希表；有序范围查询适合有序树；最高优先级任务适合堆；文档之间的依赖适合图。同一份数据往往需要多个索引，它们增加了写入和一致性维护成本。

AI 系统把这些基础问题放大了：数据清洗要去重，训练要组织 batch，推理要分配缓存，检索要缩小候选集。一个模型调用前后出现的重复遍历、全量排序或无界队列，可能让 GPU 等待 CPU，也可能让内存先于算力耗尽。

面试回答应落到一条具体数据流。例如“文档 ID 通过哈希表定位原文，向量索引负责候选召回，大小为 K 的堆负责合并部分候选”。随后说明索引更新、重复 ID、无结果以及质量评估如何处理，答案才从名词解释进入工程设计。

<h2 id="q-003">面试问题：如何从 AI 工程场景选择合适的数据结构？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

先统计操作，再选择结构。读写比例、查询形态和数据分布，比“这个结构常用于 AI”更有判断力。假设缓存有一百万条记录，99% 的请求只按完整 key 查值，哈希表很合适；如果业务新增“查某个时间区间内的全部记录”，原来的哈希表就需要扫描或增加有序索引。

常见选择可以从以下几组约束展开。

<div align="center">

| 主要操作 | 常用结构 | 必须确认的条件 |
|---|---|---|
| 随机下标访问、批量计算 | 连续数组、Tensor | 类型、布局、是否发生隐式复制 |
| 按完整键精确查找 | 哈希表 | 键的哈希成本、冲突、扩容与并发 |
| 有序范围查询 | 平衡搜索树、跳表、B+ 树 | 数据在内存还是外存、更新频率 |
| 动态维护最小或最大元素 | 堆 | 是否还需要随机删除、更新优先级 |
| 前缀匹配 | Trie、Radix tree | 字符或 token 单位、共享前缀比例 |
| 依赖、连通性与路径 | 图及相应索引 | 边的方向、权重、环与更新方式 |

</div>

再检查代价是否被转移到了其他位置。缓存查询变快，可能以更多内存和失效逻辑为代价；向量量化节省内存，可能需要更大的候选池补偿距离误差。结构选择没有脱离工作负载的固定排名。

实际做法是先保留一个可信基线，例如数组扫描或标准库容器，再用真实分布测量吞吐、P95/P99、峰值内存和结果质量。小数据上连续扫描常常胜过指针繁多的索引；如果查询次数很少，建立索引的成本也未必能收回。发现瓶颈之后再增加结构，才能知道复杂性换来了什么。

<h2 id="q-004">面试问题：算法复杂度为什么会影响模型训练和推理成本？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

复杂度描述输入规模增长时工作量如何变化。讨论模型系统时，必须先说清变量：样本数 N、序列长度 L、隐藏维度 d、层数、batch size 和输出长度，往往会同时变化。只说某算法是“线性”而不说明对哪个量线性，无法估算成本。

以单层标准稠密注意力为例，QK 与 AV 的计算量随 $`L^2d`$ 增长。朴素实现显式保存注意力分数，相关中间内存随 $`L^2`$ 增长。分块的精确注意力可以减少显存读写、避免完整分数矩阵落到高带宽显存，但仍要完成对应的稠密交互；窗口或稀疏注意力则改变可见连接，其计算量还取决于窗口宽度或稀疏模式。这几类优化解决的瓶颈不同。

KV Cache 复用历史 token 的键值投影。自回归解码一步仍需要读取可见历史 KV，标准全注意力下，对历史长度的工作量仍会增长。缓存减少重复计算，同时增加常驻内存。不能把“用了 KV Cache”概括为所有生成计算都变成与上下文长度无关。

数据处理也有同样的放大效应。两两比较 N 条样本需要二次量级的比较次数；先用哈希或索引筛出候选，可以显著减少比较，但仍需核验碰撞和漏召回。百万条候选全部排序与只选前十条，所做的工作也不同。

复杂度适合排除无法扩展的方案。落地成本还取决于内存流量、并行度、批处理、通信和硬件实现。应先算规模，再用 profiler 找到实际占时的路径；复杂度分析和测量彼此补充。

<h1 id="q-005">2. 时间复杂度和空间复杂度应该如何分析？</h1>

<h2 id="q-006">面试问题：最好、最坏、平均和摊还复杂度有什么区别？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

四种口径回答的是不同问题。最好与最坏复杂度分别看同一规模下最容易和最困难的输入；平均复杂度需要给出输入分布或随机性假设；摊还复杂度把一串操作的总成本分摊到每次操作，通常不需要概率分布。

动态数组尾部追加是最清楚的例子。还有容量时，只需写入一个位置；容量耗尽时，要申请新空间并搬移已有元素，单次可能花 $`O(n)`$ 时间。若容量按固定倍数增长，从空数组连续追加 n 次，搬移总量形成几何级数，总时间为 $`O(n)`$，所以每次追加的摊还成本是 $`O(1)`$。这没有假设输入元素“平均比较幸运”。

哈希查询的期望常数时间则依赖哈希分布和负载控制；若所有 key 冲突到同一位置，朴素链式实现会退化。随机化快排的期望复杂度还来自 pivot 随机选择。回答时应说清期望是对输入分布取的，还是对算法的随机性取的。

空间复杂度也要统一口径：输入空间、辅助空间、输出空间分开计算。一个窗口算法可以只用 $`O(k)`$ 辅助存储，但返回全部窗口结果仍要 $`O(n)`$ 输出空间；递归栈属于辅助空间。大整数、长字符串的比较和哈希也未必是常数成本。

摊还界不能保证单次延迟。在线服务即使平均很快，也可能被一次扩容拖高 P99。预留容量、分批重建或限制单次工作量，解决的是延迟分布；这些措施需要额外内存或实现成本，不能仅凭复杂度符号做选择。

<h2 id="q-007">面试问题：为什么常数、缓存局部性和内存访问在 AI 系统中很重要？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

相同的大 O 复杂度，只约束增长阶，不保证实际耗时相近。连续扫描一百万个整数与沿一百万个随机分配的链表节点遍历，都可以是 $`O(n)`$；后者却可能多出缓存未命中、指针依赖、对象头和内存分配成本。

CPU 通常按缓存行搬运数据。连续数组能让一次读取服务多个相邻元素，也方便预取与 SIMD。链表下一地址由当前节点决定，处理器难以提前知道后续位置。Python list 连续保存的是对象引用，整数对象本身不一定连续；NumPy 的同类型数值数组与它有不同的内存行为。Java 装箱集合与基本类型数组也有类似差异。

在 GPU 上，内存访问是否合并、数据是否重复搬运、kernel 是否过小，都会改变效率。一个计算量较低的实现，若不断在 CPU 与 GPU 之间复制数据，可能输给计算更多但完全留在设备上的实现。

可以用“计算工作量除以计算速率”与“搬运字节数除以带宽”估算两类下界，实际还要考虑它们的重叠程度、缓存命中和同步。若瓶颈在内存带宽，减少临时数组或提高复用往往比少做几个加法有效；若瓶颈在分支或解释器开销，批处理和成熟原生库更值得优先尝试。

测量时保留输入规模、布局、线程数、是否预热以及峰值内存。仅把数据从“刚好装进缓存”扩大到“超出缓存”，算法之间的相对表现就可能变化，这也是性能结论必须写明范围的原因。

<h2 id="q-008">面试问题：如何理解空间换时间、预计算和缓存？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这三种做法都在复用已有工作，但复用发生的时间和条件不同。索引预先组织数据，预计算提前生成可能用到的结果，缓存保存已经实际计算过的结果。它们是否划算，取决于复用次数、更新频率和维护成本。

例如对静态数组做多次区间求和，先花 $`O(n)`$ 构建前缀和，之后每次只做两次访问与一次减法。若数组频繁单点更新，维护所有后续前缀和代价很高，此时可以改用树状数组；同样的“空间换时间”，因更新模式不同而换了结构。

缓存需要回答三个更细的问题。**什么结果可以复用**，决定 key 是否包含模型版本、输入、配置等影响输出的因素；**什么时候失效**，决定更新后会不会返回旧数据；**空间满了如何处理**，决定淘汰和容量预算。语义相近的输入不能自动共享要求精确一致的计算结果。

设原计算成本为 C，查缓存成本为 L，命中率为 h，忽略其他开销时，平均成本约为 $`L+(1-h)C`$。写入、淘汰、序列化与同步还会增加成本。低命中率且结果很大的缓存，可能同时浪费时间和内存。

KV Cache、检索结果缓存、embedding 缓存的失效条件并不相同。前者与模型和历史上下文紧密相关，后两者还受文档版本和权限变化影响。评价缓存时应同时看节省的计算、常驻字节数、命中分布和失效正确性，不能只汇报命中率。

<h1 id="q-009">3. 常用数据结构如何分类？</h1>

<h2 id="q-010">面试问题：数组、链表、栈、队列、哈希表、树、图分别适合什么场景？</h2>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

先区分抽象接口和存储表示。栈规定后进先出，队列规定先进先出；它们都可以用数组或链式结构实现。树和图描述元素之间的关系，也可以通过数组、邻接表或压缩表示存储。把这些名称当成互斥的七种容器，容易混淆设计层次。

数组适合按下标读取、顺序遍历和数值计算。链表适合在已经定位节点的前提下调整连接，例如 LRU 的访问顺序；若还要从头查找位置，查找成本不能省略。栈适合保存尚未完成的递归状态，队列适合管理按到达次序处理的任务。

哈希表适合完整键的精确访问，通常不支持高效有序区间扫描。搜索树通过顺序关系缩小范围；平衡机制控制树高，B+ 树还通过高分支降低外存访问层数。堆只保证父子之间的局部顺序，适合取堆顶，不保证整棵树中任意两个元素有序。

图表达任意关系。读图之前先确认边的语义：依赖、相似、调用、距离分别对应不同算法。相似度分数不能直接当成满足非负路径代价的边权；存在反馈的工作流也不能直接对全部节点做拓扑排序。

同一系统经常组合这些结构：哈希表定位节点，双向链表维护淘汰顺序；邻接表保存依赖，队列维护当前可执行任务。选择的关键是每一种结构负责什么操作，以及这些结构之间的一致性如何维护。

<h2 id="q-011">面试问题：哪些数据结构在大模型系统中最常见？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

可以沿推理请求的生命周期来回答。请求进入服务后，队列记录待处理工作；调度器结合 token 预算、显存占用和等待时间选取一批请求；输入 token、位置和模型权重最终以张量参与计算；生成结果再通过缓冲区流式返回。基础容器贯穿整个过程。

KV 管理通常还需要块池、请求到块的映射、引用计数和空闲队列。前缀缓存的索引可以采用压缩前缀树，也可以采用包含父块信息的哈希键。两条路线都必须区分“有相同的 token 片段”和“在相同上下文下可复用的 KV 状态”，具体原理见[前缀缓存问答](05_字符串与高级数据结构高频考点.md#q-022)。

检索增强系统会组合倒排索引、向量索引、文档 ID 映射及过滤集合。HNSW 是图搜索组织方式，IVF 是聚类后的候选分区方式，PQ 是向量压缩和近似距离计算方式，它们可以组合，不能简单排成互斥的三种“树”。

Tokenizer 也没有统一的数据结构答案。词表映射常用哈希表，某些词法匹配可用 Trie，BPE 还需要遵守合并优先级；不能把所有分词都等同于最长前缀匹配。模型执行中的数据依赖可形成 DAG，但带循环控制流的程序表示需要额外语义。

答题时最好抓住一项实现解释到底：它索引什么、存在哪里、何时更新、命中后省掉了什么计算。这样比罗列十个模型框架更能体现对系统的理解。

<h2 id="q-012">面试问题：刷题中的数据结构如何迁移到真实 AI 项目？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

迁移的第一步，是把题目的隐含条件改成接口契约。刷题平台可能保证输入有序、链表无环、边权非负；真实接口需要决定由调用者保证、入口检查，还是在错误发生时返回明确失败。下标单位、重复值、空输入和返回顺序也必须写清。

以 Top K 为例，题目常只要求找最大的 K 个数。检索服务还要处理相同分数的顺序、重复文档、权限过滤、分片合并、浮点 NaN，以及 K 大于候选数的情况。堆算法本身只解决候选选择，不能替代这些业务语义。

第二步是把正确性证明转成测试。二分查找可以用标准库插入位置作对照；窗口最大值可以与小规模暴力扫描比较；最短路可以在随机小图上与 Bellman–Ford 比较。极值、重复值和长链输入比仅测一个示例更容易暴露缺陷。三语言实现还要防止整数范围和字符串下标语义不同。

第三步是建立性能基线。先比较标准库或成熟项目，再决定是否手写特殊结构。Python 层手写归并排序即使复杂度正确，也通常不能据此推断快于原生排序。将一个教学实现搬到生产前，还要补上线程安全、资源释放、监控和失败恢复；这些能力不由单个算法自动提供。

本板块的[代码目录](codes/README.md)把接口约定、可执行实现、随机差分与性能测量放在一起。阅读时应先预测输出和复杂度，再运行测试、修改输入分布，观察原来的判断在哪些条件下仍然成立。

<h2 id="q-013">面试问题：怎样证明一个算法实现更快，性能结论才能复现？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

**性能比较先统一任务，再比较时间。** 一个实现返回无序 Top K，另一个返回有序结果，两者做的工作不同；一个计入拷贝，另一个原地修改输入，计时也不等价。测试前应固定输入、结果语义、是否允许破坏输入以及正确性标准。

随后选择能覆盖真实瓶颈的数据分布。排序要测随机、已排序、逆序、重复值；Top K 要改变 K/N；字符串匹配要包含大量重复前缀和不命中；哈希表要改变装载率、键长度和命中率。只测一种均匀随机输入，容易掩盖退化与分支开销。

测量需要报告机器、操作系统、语言版本、编译参数、线程数、输入规模和重复次数。计时区间应避开文件下载、进程启动和测试数据生成；Java 需要预热并保留结果消费，防止 JIT 尚未稳定或无用计算被优化。记录多次测量的中位数与离散程度，单次最小值不足以支持稳定收益。

正确性必须先过关。对近似检索，还应在同一召回率和过滤条件下比较延迟；对数值算法，要同时检查误差。占用更多内存、牺牲排序稳定性或改变误差指标换来的速度，应明确记入结论。

“这个实现在本机、这些输入上更快”是可检查的结论。平台、规模、分布和输出要求变化之后，需要重新测量。更有长期价值的成果是明确的优化原因和可运行的基准，而非一个没有比较范围的最快标签。
