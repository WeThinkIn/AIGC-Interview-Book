<h1 id="q-001">1. AIGC 时代的自进化 Agent 是什么？</h1>

<h2 id="q-002">面试问题：自进化 Agent 和普通长期记忆 Agent 有什么区别？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

长期记忆保存跨任务可用的信息，自进化强调系统根据经验改变后续行为，并验证这种改变是否有益。两者可以重叠：经过纠错和筛选的记忆本身就能帮助学习；安装了记忆库，也不代表系统已经建立可靠的改进机制。

例如Agent第一次修复项目时发现，测试应在特定环境中执行。保存“测试环境路径”是一条记忆；把环境检查、测试命令、失败定位整理成可复用流程，是程序性经验；再用其他任务检查这套流程是否减少错误，才有依据判断它改善了后续执行。若只把整段日志塞入检索库，噪声和错误也可能一起累积。

“自进化”还需要说明改变的是哪一层：

<div align="center">

| 更新对象 | 怎样影响后续任务 | 验证重点 |
| --- | --- | --- |
| 记忆与检索内容 | 提供新的事实、偏好或经验 | 来源、时效、作用域及错误召回 |
| Skill、提示和运行配置 | 改变任务步骤与工具使用方式 | 条件是否适用、收益是否稳定、权限是否保持 |
| 模型参数 | 通过训练改变模型行为分布 | 数据质量、训练目标、泛化和能力退化 |

</div>

前两类可以在不更新模型权重的情况下发生。参数训练也不必是在线训练，通常可以先积累数据，在离线流程中训练、评测，再发布新版本。不能因为系统会写Skill，就声称它完成了持续强化学习。

Hermes Agent提供经验Skill、记忆、历史会话检索和后台维护，是观察这一工程方向的具体项目。可迁移的思想是把任务证据转成有适用条件的候选资产，再经过验证投入后续任务；项目对自身能力的宣传不能替代独立效果评估。

衡量改进要在未参与经验提炼的任务上看成功率、成本、误用和退化。记忆更多、Skill更多、自我评价更高，都只是中间现象。系统能否持续纠正旧经验，并在条件变化时停止复用，比资产数量更能说明其长期价值。

<h2 id="q-003">面试问题：经验如何从一次任务沉淀为 Memory、Skill 和 Policy？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

任务经验应按**保存的是什么、谁可以修改、以后怎样使用**分流。事实、操作流程、测试样本和权限规则承担不同责任，不宜全部存进一份“长期记忆”。

假设Agent在生成财务报告时发现项目只接受某种表格模板，可以保留项目级格式偏好；若多次任务都需要校验单位、日期和缺失值，可以整理成Skill；一次把“万元”当成“元”的失败，则适合转成回归样本。三者可以引用同一段证据，但写入位置和有效范围不同。

<div align="center">

| 经验去向 | 适合保存的内容 | 必须保留的限制 |
| --- | --- | --- |
| Memory | 用户确认的偏好、稳定事实、带条件的经验 | 主体、来源、有效时间和作用域 |
| Skill | 一类任务的步骤、检查点、模板与脚本 | 前置条件、依赖版本、失败分支和结果判据 |
| Eval Case | 可复现的问题、初态和验收条件 | 数据授权、独立判据与训练评测边界 |
| Policy变更建议 | 对执行规则的修订理由 | 有权主体审核或既定发布流程 |

</div>

其中Policy尤其需要区别对待。Agent发现某种操作反复失败，可以提出更保守的重试策略；但它不能仅凭一次成功，就把“允许向外部发送客户数据”写成新的高优先级规则。业务授权来自有权主体和正式政策，经验只能提供修订证据。已经批准的规则可以由系统按授权流程自动发布，无需机械地要求每条低风险记忆都重新审批。

提炼时先核对任务是否真正完成、结果由什么证据支持，再删除密钥和无关个人信息。记录资产ID、来源事件、适用范围、依赖、版本及待验证状态；把固定客户名、临时目录和一次性的绕行步骤从通用流程中剥离出来。

候选Skill至少在适用任务和不适用任务上做检查。例如同一表格流程用于季度报告有效，不代表能直接用于审计底稿。验证通过后发布新版本，保留旧版本和失败样本；将来工具或业务规则变化时，可沿依赖关系重新检查受影响资产。

这种分流让事实便于更新、流程便于复用、失败便于回归，也避免模型生成的建议悄悄成为执行权限。

<h2 id="q-004">面试问题：为什么自进化 Agent 必须有防失控机制？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

经验更新会改变未来任务的输入与行动方式，因此错误可能跨会话持续传播。一次错误回答通常影响当前任务，一条错误Skill却可能反复指导后续任务，甚至把最初的猜测包装成“已有经验”。

典型故障是网页中的恶意指令被总结成操作建议，随后写入Skill。下次任务检索到这条Skill时，系统如果只看到“内部知识”标签，就可能赋予它不应有的可信度。知识存储位置改变了，原始内容的来源和权限并没有随之升级。

控制应落实在更新链路。维护任务只获得指定资产的读写能力，运行身份不能修改自身授权、凭证、评分器或审计记录。新增外部工具、扩大网络出口与修改执行规则，使用不同于普通文本整理的授权流程。内容扫描可以发现部分危险模式，无法单独保证自然语言指令安全。

更新先生成候选版本和diff，再按影响范围验证。已有明确规则允许自动维护的低风险资产，可以通过门禁自动发布；影响共享流程或扩大权限的变化，进入相应责任人的审核。没有必要把每次纠正错别字和每次修改付款流程视为同等风险。

发布时还要防止并发覆盖：候选基于版本v3生成，用户已将正式内容改为v4，就不能直接用候选覆盖。通过版本比较、合并或重新提案处理冲突；在途任务是固定旧Skill还是切换新版，也应有明确规则。紧急撤销权限不能等到任务自然结束才生效。

后台任务有时间、调用和费用预算，异常时可以暂停学习写入，同时保留正常任务执行能力。归档和版本回退便于恢复知识资产，但无法撤销此前泄露的数据或已经发送的消息，仍需核对实际影响。

“防失控”最终表现为可执行的边界：谁能改什么、依据什么验证、何时生效、怎样停用与恢复。模型的自我承诺和维护报告提供说明，运行时控制才落实这些规则。

<h1 id="q-005">2. 多平台 Agent Gateway 的核心价值是什么？</h1>

<h2 id="q-006">面试问题：CLI、TUI、IM、邮件、Webhook 等入口如何统一到同一个 Agent Runtime？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

多平台Gateway把不同消息入口转换为统一任务事件，再把运行结果交付回合适的位置。它既处理路由和配置，也经过消息、附件与回复的数据路径，不能笼统称为只负责管理的控制面。

平台适配器首先验证来源。IM使用平台签名和已验证账号信息，Webhook检查签名、时间窗与重放条件，邮件按实际认证与允许来源处理。用户名、消息正文中的“我是管理员”以及附件文件名都不能建立执行身份。

接着形成内部事件，例如包含`event_id、platform、tenant_id、actor_id、conversation_id、thread_id、attachments、received_at`。这是示意字段，不是通用协议。平台原始消息ID应保留，接收重试按来源和ID去重；相同文本由用户再次发送，可能是新的合法请求，不能只按文本哈希丢弃。

会话路由将事件关联到任务，Runtime负责上下文、模型与工具执行。入口适配可以处理展示和平台语法，但业务授权不能散落在每个平台自己的提示词里。CLI、网页和群聊触发同一个动作时，应经过同一组服务端约束。

审批回调需要绑定请求、操作者、动作参数版本、有效期与一次性标识。用户批准“将草稿发给A”，不能被后续参数变化解释为允许发给B；已有明确且仍有效的授权可以复用。平台无法安全展示详情或校验批准者时，应转到具备这些能力的界面。

交付层处理消息长度、Markdown差异、文件、语音和流式更新。任务完成与通知送达分别记状态：报告已经生成但IM发送超时，只重试通知或核对送达情况，不重新执行整份任务。若发送结果未知，还要考虑重复消息，不能假定平台提供严格一次交付。

统一入口的价值在于复用任务语义，同时保留平台差异。不同平台的按钮、线程和文件能力并不相同，应显式协商或降级，避免在接口层假装功能完全等价。

<h2 id="q-007">面试问题：多平台会话如何做 session、user、channel、workspace 隔离？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

会话隔离需要同时回答两个问题：哪些消息属于同一段工作，哪些主体有权看到或修改其中的数据。一个设计良好的session key只能解决关联问题，不能单独承担访问控制。

身份映射应基于平台提供且经过验证的稳定ID，并包含平台、租户或企业空间。同一个显示名出现在两个平台，不能自动合并为同一个人；跨平台连续会话需要可靠的账号绑定，以及明确允许共享的上下文范围。

群聊与私聊尤其容易串线。用户在私聊中上传的合同，不能因为同一用户在群里提问，就自动进入群聊回答。检索、工具和最终投递都应检查目标会话的可见范围；不仅正文，文件链接、任务标题和错误提示也可能泄露内容。

可按工作方式选择会话粒度：私人助理常按用户与项目分离，团队讨论按频道或线程组织，后台任务按独立任务保存状态。共享线程中不同成员仍有不同权限，不能把创建线程者的凭证交给所有参与者使用。并发请求需要排队、版本检查或明确分支，防止两轮对话互相覆盖计划。

任务、会话和工作区也不应混为一个ID。一个会话可以发起多个任务，同一任务可能在多个界面被观察；工作区是文件与资源的范围，不意味着其中全部数据都可被每个会话访问。后台任务的创建人、执行主体、授权范围与通知目标应分别保存。

恢复、转移和删除会话时，重新检查当前身份与权限。用户已离开团队，旧session和缓存不能继续保留有效访问能力；“重置聊天”是否删除记忆、文件和定时任务，则需按产品契约分别处理，不能含糊承诺一并消失。

验收时用同名用户、同名频道、私聊转群聊、跨租户恢复、旧附件链接和撤权后的后台任务构造测试。只有数据读取、执行动作和最终投递都守住范围，会话隔离才真正成立。

<h2 id="q-008">面试问题：为什么长期运行 Agent 需要 interrupt、resume、cron 和 background task？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

长期任务的寿命通常长于一次连接。interrupt、resume、cron和后台任务分别处理交互控制、状态恢复、定时触发与独立运行，需要共同依赖持久任务状态。

interrupt要区分暂停、取消和修改方向。用户停止当前对话，不一定表示撤销已经提交的远程任务；运行时需要停止新的动作，向支持取消的执行器发信号，并核对已经发生的效果。取消与完成可能竞争，最终状态应依据实际回执，而非界面上先显示哪个按钮。

resume从已保存的计划、输入、产物和未决调用继续。恢复前检查工具版本、凭证与业务状态：昨日尚未确认的订单，今天可能已付款或失效。若上次调用结果未知，先按业务标识查询，不能因为本地没有成功日志就重新提交。

cron需要真实调度器和持久化计划。保存“明天提醒我”的记忆不会自动产生唤醒事件。计划应说明时区、重复规则、漏触发补偿、并发策略、执行身份和费用上限；每次触发产生独立运行记录，并与计划ID关联。夏令时、服务重启和任务耗时超过周期时，处理规则必须明确。

后台任务由队列或执行器独立推进，前台连接只负责观察和控制。任务状态至少区分排队、运行、等待输入、成功、失败与取消；通知送达另外记录。任务完成但通知失败，不应触发重做业务。

Hermes当前Cron文档就区分执行回执和投递交接：已知终态可交给投递队列，发送结果未知或执行中断则有暂停核查规则。这是一个具体实现例子，其他系统不能直接继承其恢复保证。

调度锁、租约与事件去重有助于减少重复运行，仍不能独自保证外部效果仅发生一次。退款、预约等写操作还需业务幂等与权威状态核对。长期运行的关键，是在连接消失、进程重启或用户改变目标后，系统仍能解释自己做过什么、还欠什么。

<h1 id="q-009">3. 为什么生产级 Agent 需要 Provider Router 和 Tool Registry？</h1>

<h2 id="q-010">面试问题：工具注册表应该保存哪些元数据？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

工具注册表保存可调用能力的契约，帮助运行时发现、选择和检查工具。它需要描述“怎样调用”以及“调用后会发生什么”，仅有名称和参数Schema不足以支撑恢复与治理。

<div align="center">

| 信息组 | 典型内容 | 工程用途 |
| --- | --- | --- |
| 身份与版本 | 唯一名称、来源、维护者、契约版本、内容摘要 | 区分同名工具和追踪变更 |
| 输入输出 | 参数Schema、结果Schema、错误分类、结果大小 | 校验、展示与模型理解 |
| 执行语义 | 同步或异步、超时、取消、重试和幂等支持 | 处理长任务及结果未知 |
| 权限与影响 | 所需权限、作用域、外部副作用、数据出口 | 执行前授权和风险控制 |
| 运行依赖 | handler或服务引用、凭证引用、依赖检查 | 选择可用执行路径 |
| 证据与运营 | 审计脱敏规则、费用、健康状态 | 排障、限流和成本核对 |

</div>

具体字段取决于平台。注册表可保存本地handler或远程服务引用，但不应把密钥明文放入模型可见的工具说明。工具声明“只读”也需要实现与测试支撑：查询接口可能触发计费、日志或数据导出，风险不由名称决定。

发现、可用与有权调用要分开。依赖检查确认服务是否配置，认证确认调用主体，授权检查当前动作是否允许。健康检查可以短时缓存，撤权与敏感权限判断不能因为缓存还有效就一直放行。最终检查应在真实执行边界落实。

动态刷新时生成一致的目录快照，并保留版本引用。运行中的Agent可能已经根据旧Schema制定参数，若工具升级，应保持兼容、拒绝旧契约或显式迁移，不能悄悄把同名调用解释成新动作。工具删除后，已有队列和缓存也需要处理。

Provider Router与之配合，但职责不同：前者处理模型能力、凭证、预算与降级，后者描述动作契约。换模型后还要验证工具格式与行为；模型接口兼容，不保证同一组工具描述能得到相同调用质量。失败日志应能区分模型选择错误、参数不合规、授权拒绝和执行器故障。

<h2 id="q-011">面试问题：Skill Hub / Skill Marketplace 如何设计？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

Skill Hub负责分发可复用流程，并管理来源、版本、依赖与使用范围。Skill通常包含说明、参考资料和可选脚本；它会影响模型怎样行动，因此不能只按文档下载站治理。

一个报告Skill可能依赖表格解析工具、某个模板和组织数据口径。安装时应保存作者与来源、版本或内容摘要、许可证、适用任务、依赖、入口和文件清单。目录中存在某个Skill，不代表所有用户都能执行其脚本，也不代表它自动获得文档中要求的权限。

加载可以分层进行：先用简短元数据判断相关性，再读取具体流程和必要附件。匹配要检查任务范围与依赖，不应见到一个关键词就加载整包。流程被选中后仍遵守当前用户要求和运行时权限，不因“已安装”获得更高指令地位。

安装扫描需要覆盖路径穿越、符号链接、脚本、外部下载、敏感路径及可疑指令，执行时继续限制文件、网络和凭证。来源签名证明包来自哪个发布者，不能证明内容没有漏洞；静态扫描也无法穷尽自然语言中的误导。

升级应先查看差异，再按影响做回归。只改说明与新增上传工具不是同等变更；扩大权限需要相应授权，已授权且兼容的维护可以按既定策略自动推进。共享Skill最好固定发布版本，在途任务保留所用版本，避免运行到一半流程变化。

停用、归档、删除和撤权各有含义。停用通常阻止新的自动加载，归档保留可恢复内容，删除涉及存储与备份，撤权限制实际动作；它们不会天然互相替代。退出市场或下架后，还需明确已安装副本和正在执行的任务怎样处理。

使用次数与评分有助于发现候选资产，但受任务分布和曝光影响。一个低频灾难恢复Skill可能很重要，一个高频Skill也可能只因默认加载而被统计。长期价值取决于适用任务中的可靠收益、维护成本和边界清晰度。

<h2 id="q-012">面试问题：Plugin System 如何扩展平台、工具、记忆和可观测性？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

Plugin System通过稳定扩展接口接入新能力，使平台不用为每个渠道或工具修改核心逻辑。它可以扩展消息适配、工具执行、记忆存储、上下文处理和可观测性，但不同扩展点接触的数据与权限不同。

例如消息插件接触平台凭证与收发内容，记忆插件接触跨会话数据，日志插件可能看到工具参数和敏感回执。不能因为插件只“负责监控”，就默认它没有数据泄露风险；上下文压缩插件也能改变后续模型可见的证据。

插件清单需要声明标识、版本、兼容的核心接口、配置Schema、依赖和能力范围。加载过程完成校验、初始化和健康检查，卸载过程处理未决任务、连接与清理。密钥通过受控引用传入，不写进公开配置或插件报告。

权限声明只有被执行环境落实才有意义。插件在主进程中运行并继承全部文件与网络权限时，一份“只读”清单并不构成隔离。高影响扩展可以通过独立进程、受限RPC或沙箱提供服务；是否这样部署，要结合信任关系、性能和运维成本决定。

Hook应约定调用时点、输入输出、顺序、失败策略和可否修改状态。两个插件同时重写同一段上下文，或日志Hook抛异常阻断主任务，都需要可预测处理。异常是拒绝执行还是允许降级，应按职责决定，授权检查不能因插件故障而无条件放行。

升级测试覆盖接口兼容、状态迁移和历史任务恢复。插件停用不代表远程任务已停，删除代码也不会撤回已同步的记忆。审计记录插件版本、实际动作与数据去向，才能判断问题来自模型、核心运行时还是扩展。

扩展机制的目标是减少耦合，同时让责任更明确。并非每个小功能都要做成插件；稳定的模块接口通常已足够，独立分发和多实现替换确有需求时再引入完整生命周期。

<h1 id="q-013">4. Agent Curator 的本质是什么？</h1>

<h2 id="q-014">面试问题：自我维护型 Skill 系统如何做评分、合并、归档和回滚？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

Curator是经验资产的维护过程：检查哪些内容仍有效、哪些重复、哪些需要修订或暂时退出加载。它需要同时维护**内容正确性、依赖完整性和使用范围**，只按最近使用时间清理文件容易误伤重要流程。

可以把资产状态设计为候选、可用、待复核、归档与恢复，并保存状态原因。评分参考使用频率、成功与失败证据、用户指定、依赖可用性和维护成本，但不能把这些量简单加权后自动判定价值。低使用可能来自任务罕见、检索不到或刚安装，未必表示内容无效。

合并前核对适用范围。例如“个人报销”和“企业采购”都涉及发票，但审批权限、材料和完成条件不同，不能只因文本相似就合并。确有共同步骤时，可以提取公共检查并保留各自分支。脚本、模板、相对路径、定时任务引用和原始来源也要迁移，不能只拼接两份SKILL.md。

归档应记录理由和恢复位置，并检查反向依赖。一个很少手动使用、却被季度任务引用的Skill，不应因为近期无点击就被移走。恢复时再核对当前工具与政策，不能把旧版本恢复成功等同于它仍适用。

Hermes当前Curator提供一个具体对照：默认维护Agent创建的Skill，自动阶段依据闲置时间标记或归档；LLM合并默认关闭，需要显式启用。它会跳过被定时任务引用的Skill，归档保留恢复能力。其触发是闲置与间隔检查，不能泛称为固定cron作业。

同一项目中，`pin`会阻止某些自动状态变化和删除，但仍可编辑；`lock`才用于阻止Agent修改。内置Skill是否可被归档也受配置影响。这些状态名称没有跨框架统一语义，设计和选型时应阅读真实契约。

每次维护记录原版本、候选diff、验证结果和依赖变化，提交前检查用户是否已修改资产。回滚恢复选定资产与引用关系，不盲目覆盖维护之后的合法编辑。Curator只有在减少错误复用与维护负担时才产生收益，目录变整齐只是表面结果。

<h2 id="q-015">面试问题：背景复盘 fork 为什么要限制工具集？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

背景复盘fork在独立任务或上下文中整理运行经验，避免持续占用主会话。这里的fork描述任务分支，不保证它是操作系统进程，也不意味着自动复制了隔离环境。

复盘看到的材料可能包含网页、工具输出和用户文件。它们是分析对象，不能因为进入“历史记录”就成为维护指令。若复盘继承前台全部凭证和工具，原本用于总结的任务可能继续发送消息、改业务数据或下载执行代码，超出经验维护的目的。

权限应围绕具体工作给出。只提炼事实时，允许读取脱敏轨迹、查询相关资产并写候选；若要验证一个新脚本，可以给隔离测试环境和受控shell；若需要外部证据，可以给限定检索。不存在所有后台复盘都必须禁用shell的通用规则，关键在于测试是否隔离、动作是否授权、预算是否明确。

记忆和Skill写入本身也有副作用。它们会改变后续上下文，可能泄露信息或影响执行，所以不能只限制发邮件，却把知识写入视为天然安全。候选写入、审核、验证与正式生效可以分成不同权限，防止维护任务修改自身的规则和评分器。

后台上下文应包含必要证据和适用范围，避免把整段敏感历史复制一遍。记录所基于的版本；主会话或用户已经改过同一Skill时，复盘不能按旧快照覆盖新内容。发布时做版本比较，冲突则重新核对或合并。

最后给任务设置调用、时间、输出量和费用上限，禁止无界递归创建维护任务。完成标志是产生了可核对的变更或明确“无需更新”，不要求每次复盘都创造新记忆。没有足够证据时保留待验证状态，比为了体现学习能力而强行总结更可靠。

<h2 id="q-016">面试问题：Agent 如何避免把错误经验固化为长期知识？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

避免错误经验固化，需要保留从原始事件到长期资产的证据链，并让系统能够修正和停止使用错误内容。自我反思文本只是一种候选解释，不能直接作为事实证明。

写入时区分观察、用户明确偏好、推断和操作建议。例如“接口返回429”是观察，“服务限制每分钟20次”若未经文档或测试验证，只是猜测；成功重试一次也不足以推出某个固定等待时间总是有效。保存条件与不确定性，比把模糊经验改写成肯定句更有用。

冲突处理考虑来源、范围与有效时间。昨天的测试环境记录可能比今天随口提及的生产路径更适合当前测试；一条较新的网页内容也不能覆盖组织现行政策。当前用户要求应在其授权范围内优先处理，但不能越过更高层的正式约束。“总取最新”或“总信内部存储”都过于粗糙。

检索后要校验适用条件，而非直接拼入指令。例如“导出报告前跳过缺失字段”可能只针对一次临时分析，不应变成所有财务报告的默认规则。资产中引用的外部内容仍保留原始信任级别，恶意指令不能通过总结与再次检索洗成高优先级要求。

验证改进时，将旧资产和候选资产放在相互隔离的评测分支，使用未参与提炼的任务，固定其他条件并记录收益与新增失败。避免新分支写出的记忆污染旧分支，或把已见过的评测答案保存后继续报告“泛化提升”。反复调参的开发集应与最终保留集区分。

发现错误后，定位它生成的Skill、摘要、索引、缓存和派生记忆，逐项更正或停用。原始条目删除后，派生结论不会自动消失；长期任务恢复时也可能再次加载旧副本。严重问题需临时阻断相关资产，并检查已经影响的业务。

维护记录还应允许“经验不再适用”。工具接口、项目规则和用户需求都会变化，曾经正确的流程可以过期。持续改进的能力，既包括学会有效做法，也包括有证据地放弃旧做法。

<h1 id="q-017">5. 自进化多平台 Agent 的安全边界如何设计？</h1>

<h2 id="q-018">面试问题：文件安全、命令安全和 Tool Loop Guardrails 如何协同？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

文件安全、命令安全与循环约束分别检查访问对象、执行能力和连续行为。三者共同限制影响范围，但不能互相替代：阻止无限循环，无法阻止第一次调用就读取密钥。

文件访问应按已授权根目录、身份和操作检查，处理路径规范化、符号链接、挂载与敏感位置。单次`realpath`检查只说明检查时解析到了哪里；检查后路径可能被替换，形成检查与使用之间的竞态。需要结合操作系统提供的目录句柄、禁止跟随链接的打开方式、权限和隔离机制，具体实现随平台不同。

所有读写路径都要覆盖，不能只保护文件工具，却让shell和插件直接读同一敏感文件。拒绝列表可以拦截已知危险位置，允许范围与操作系统权限提供更基础的限制。即便文件只读，读取后通过网络发送仍可能泄露数据。

命令检查也不能只看首个单词。“运行测试”可能执行仓库中的任意脚本，安装依赖可能触发生命周期Hook；管道、重定向、环境变量和命令替换会改变效果。命令分类与审批是辅助，执行环境还需控制文件、网络、进程和凭证。用户已有明确授权的动作按授权执行，审批不能覆盖硬性禁止范围。

Tool Loop Guardrails观察是否出现重复失败、相同输入无新信息、互相撤销的操作或预算失控。触发条件应结合进展：异步任务轮询可能合理，需要退避与截止时间；重复提交付款则需要业务幂等和状态核对，不能等五次之后才靠循环检测拦住。

运行时可以依次采取结构化错误反馈、限制某工具、暂停任务或请求必要信息。不能只给模型一条“不要再重复”的提示，就声称循环被阻断；执行器要能落实调用上限和停机状态。

审计保存动作范围、授权依据、阻断原因和实际结果。验收用符号链接替换、测试脚本联网、间接文件访问、无进展轮询和重复业务提交等场景检查各层边界，避免只验证最明显的危险命令字符串。

<h2 id="q-019">面试问题：为什么 Worktree 隔离、Checkpoint 和 Rollback 对 Agent 很重要？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Worktree提供独立的Git工作目录，Checkpoint保存某个范围的状态，Rollback按约定恢复状态。它们有助于试验与错误恢复，但覆盖的对象不同，设计时必须先写清边界。

独立worktree便于让不同任务基于同一提交修改文件，比较候选补丁并减少直接覆盖。它不会自动包含用户当前未提交的修改，也不隔离进程、网络、环境变量、共享缓存或外部数据库；多个worktree仍共享仓库的部分元数据。需要的用户改动应显式转入任务起点并保留记录。

Checkpoint可以只保存Git diff，也可以包含未跟踪文件、数据库或完整环境快照。记录快照版本、覆盖范围和遗漏项；多处状态同时变化时，还要考虑快照一致性。只保存代码却不保存迁移后的测试数据库，恢复后可能处在代码与数据不兼容的状态。

回滚前核对当前内容与预期版本。如果用户在检查点之后修改了同一文件，不应直接整体还原；可以恢复本任务改动、生成逆向补丁或先解决冲突。大范围格式化与批量替换尤其需要保留任务前状态和可审查diff。

外部效果另行处理。回滚本地文件不能撤回邮件、恢复已删除的远程数据或取消已经结算的付款。业务接口支持补偿时，补偿也是新的授权动作，可能失败，并不总能让世界回到原样。结果未知时先核对回执与权威状态，避免反向操作扩大错误。

检查点频率按成本和恢复价值选择：只读分析通常不需要复制整个环境，依赖升级、数据迁移和多文件重构则更值得保存明确恢复点。恢复机制还要演练，确认可解码、可启动且与当前工具版本兼容。

环境分叉与恢复范围的图解见[第二章](02_编码Agent与AgentOS工程高频考点.md#q-201)。判断一个系统“可回滚”，应追问它具体恢复哪些对象、保留哪些用户修改，以及哪些效果必须单独核对。

<h2 id="q-020">面试问题：多平台 Agent 的可观测性和本地行为画像如何设计？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

多平台可观测性需要把入口事件、任务执行、知识更新和最终投递关联起来。用户只看到“没有回复”时，问题可能是消息未进入、Agent执行失败，或任务已成功而通知丢失，三者需要不同处理。

每次运行记录稳定的事件与任务标识，并关联租户、执行主体、会话、平台和线程。长任务产生子任务、重试与通知时保留父子关系和原因；时间戳帮助排序，但跨服务时钟偏差意味着不能仅靠先后时间推导因果。

业务证据包括工具参数与回执、授权检查、状态变化、产物及错误类别。学习证据则包括实际加载的Skill版本、记忆命中、候选更新与发布结果。模型费用、工具费用、等待时间和维护费用分别统计，避免把后台学习成本藏在主任务之外。

“Skill被加载”与“Skill有贡献”不是同一个指标。系统可能默认加载它却未使用，也可能在困难任务中使用它而仍失败。行为画像可以帮助发现检索不到的资产、重复工具链与高成本路径，但贡献判断还需任务难度、失败原因和受控比较。

日志设计遵循最少必要。用受控工件引用代替完整敏感正文，密钥在采集前过滤；哈希和ID若可与用户关联，也不自动等于匿名。隐藏思维链不属于必须收集的材料，使用可观察动作、结果与简要解释即可支持大部分诊断。

本地存储减少某些数据外传路径，仍需访问控制、加密、保留期、导出与删除机制。若日志、备份或插件会同步到云端，应如实记录数据流向。用于个人化建议的画像与必要安全审计可以有不同的开启和保留规则。

验收应覆盖采集丢失、跨租户查询、通知重复和删除传播。没有日志不能证明没有执行，统计上的高活跃也不能证明高价值。可观测性的作用是让团队和用户能够解释一次任务及其后续影响。

<h1 id="q-021">6. Agent 轨迹数据如何用于训练、评测和自我改进？</h1>

<h2 id="q-022">面试问题：Atropos / RL 环境对工具调用 Agent 有什么启发？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

交互式RL环境把模型放进会变化的任务状态中，让它选择动作、观察结果，再根据可核对的目标获得奖励。对工具调用Agent，训练对象因此包含多步决策与恢复，而不只是最后一句答案。

以代码修复为例：环境提供仓库初态和需求，模型读取文件、生成补丁并运行允许的检查；独立评分器验证功能、回归和禁止行为。模型生成的工具调用是动作，工具返回是环境观察，测试结果可参与奖励。奖励并不天然正确，测试缺漏、可修改评分文件或虚假日志都可能形成可利用的漏洞。

Atropos将环境组织为异步服务，通过trajectory API向训练器提供轨迹。环境、推理服务与训练器分别承担交互、采样和参数更新，不能把环境框架当作一套自动完成训练的系统。截至2026年11月，其官方仓库明确已归档、不再维护；这里保留的是架构启发，不将它作为无需维护评估的新项目推荐。

轨迹至少要关联任务与尝试ID、环境初态、模型和工具版本、可观察输入输出、状态变化、奖励及失败原因。需要训练token级目标时，还要按算法保存token、mask以及必要的采样概率等信息；普通文本日志通常不足以直接重建这些数据。

环境返回的文本不应默认作为模型必须模仿的输出。SFT通常监督选定的助手动作和回答，对工具观察等位置按方案屏蔽损失；RL还需区分策略动作、奖励和终止条件。异步采样会产生策略版本差异，训练端应按算法处理过旧数据，不能把所有历史轨迹混在一起当作同分布样本。

同一批轨迹的用途也要分开：合格演示可用于SFT，有明确环境与奖励的交互可用于RL，典型失败可用于诊断和回归。失败过程不必全删，但要有正确目标或评价，不能直接把错误动作作为正例。仅使用成功轨迹也会产生筛选偏差。

数据使用须有授权、脱敏与来源记录，不索取模型隐藏思维链。训练与保留评测按任务族、仓库或时间做适当隔离，防止相似实例泄漏。最终检查真实任务成功、约束遵循与成本；奖励升高但业务结果退化，说明优化可能钻了评分器的空子。

<h2 id="q-023">面试问题：为什么不同模型需要不同 Tool Call Parser？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

模型原始输出的工具格式可能不同，Parser把它转换为运行时理解的调用结构。差异来自训练模板、特殊token、参数编码与推理服务协议，不应仅按模型名字猜测格式。

如果服务已经返回结构化`tool_calls`，客户端通常校验并使用这些字段，不应再从普通回答正文里用正则搜索“像工具调用的文本”。否则模型在解释示例代码时，也可能被误当作真实行动。只有直接处理原始模型输出时，才需要按匹配的模板解析调用边界。

解析层需要保存工具名、参数、调用ID及其与结果的关联，区分普通文本和调用区域。多工具输出还要保留依赖语义：同时出现在一个响应中，不代表它们一定可并行执行，后一个动作若依赖前一个结果仍需顺序推进。

流式返回时，JSON可能跨多个分片。运行时应等服务或对应解析协议确认一个调用已经完整，再校验和执行；不能看到工具名就提前行动。截断、格式错误或版本不匹配应形成明确错误，不用宽松修补猜出收款人、金额等关键参数。

解析成功只证明结构能被解释。之后仍需检查Schema、工具是否存在、参数业务含义、身份与授权、当前状态和幂等条件。合法JSON中的订单ID可以属于别人，完全符合Schema的金额也可能超出预算。

vLLM当前文档明确区分可解析调用与高质量参数，Schema约束能力依赖所选Parser、工具的`strict`配置和解码方式。支持的组合随版本变化，不能泛称“启用结构化输出后所有参数都满足业务规则”。Parser配置还必须与chat template和模型checkpoint对应。

测试覆盖转义引号、嵌套结构、Unicode、多个调用、混合普通文本、跨分片和截断。训练时使用的解析约定也应与部署保持一致，避免离线奖励一个部署端无法执行的格式。解析器通常是软件适配层，模型学习格式与解析器本身“接受训练”不是同一回事。

<h2 id="q-024">面试问题：如何回答“请设计一个自进化、多平台、可长期运行的 Agent 系统”？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

可以用一个持续生成项目周报的助理来展开设计：用户从CLI和企业IM发起任务，系统按授权读取代码与文档，生成报告；每周定时运行，失败可恢复，用户纠错后提出流程改进。先明确是否只生成草稿、哪些数据可访问，以及是否已授权自动投递。

Gateway验证消息来源、绑定身份并去重，将任务交给Runtime。运行时持久化计划、状态、输入版本和未决调用，通过模型路由选择满足数据与能力要求的服务；工具注册表提供契约，执行器落实权限。会话、任务和工作区分别管理，跨平台观察同一任务不自动共享全部私聊历史。

报告生成后检查引用、时间范围和产物，再更新完成状态；投递是单独步骤。通知超时不重新生成报告，远程提交结果未知时先核对。定时计划有真实调度器、时区、漏触发规则和每次运行ID，暂停计划与取消当前执行分别处理。

经验更新走独立路径：从获授权的任务证据提取候选记忆或Skill，保存来源与适用条件，在隔离任务集上验证，按影响范围发布。Curator维护重复、失效和依赖变化，用户可检查差异、停用和恢复。学习任务不能修改自己的权限、独立评分器或审计记录。

文件与命令在受控环境执行，Worktree只承担代码分支管理，Checkpoint覆盖范围明确。日志关联入口、工具、资产更新和最终回执，敏感字段在采集时处理。插件扩展点有明确权限和版本契约，不能借可插拔绕过核心边界。

验收至少包含：相同消息重复投递、用户撤权后后台继续、报告已完成但通知失败、恢复时工具版本变化、恶意内容被提炼进Skill，以及新Skill在保留任务上退化。对每种情形给出应有状态和证据，而不只看最终回复是否自然。

系统可以先由一个进程、持久数据库与少量工具实现，再随并发与隔离需求拆分服务。跨周期价值在于任务状态、业务效果和经验更新均可解释、可验证；接入平台数量和自动生成Skill数量，不是成熟度的直接度量。

## 高频速记

1. 长期记忆与自进化可以重叠，是否改进需要后续任务证据；写Skill不等于训练模型权重。
2. 事实、流程、评测样本与Policy变更建议分流，经验不能自行升级成权限。
3. 候选资产保留来源、条件与版本，发布前检查并发修改和能力退化。
4. Gateway既处理配置路由，也经过消息数据；身份来自验证链路，不能从正文或同名账号推断。
5. 会话关联不等于访问控制，私聊、群聊、租户与后台任务的权限要在读取、执行和投递处落实。
6. 记忆里的提醒不等于定时任务；调度、执行、取消与通知分别持久化。
7. 工具目录记录执行语义，发现、可用和有权调用分开判断；动态升级不能悄悄改变旧调用含义。
8. Skill和插件会改变行为与数据路径，来源签名、权限声明都需执行控制配合。
9. Curator维护内容和依赖，低使用不证明无价值；pin、lock、停用与归档的具体含义按实现核对。
10. 后台复盘按任务授予工具，受控测试可使用shell；记忆和Skill写入本身也有副作用。
11. `realpath`检查存在竞态，测试和安装可以执行代码，循环检测不能替代单次授权。
12. Worktree不隔离全部环境，Checkpoint说明覆盖范围，回滚不撤销邮件或付款。
13. 训练轨迹使用获授权的可观察数据，区分SFT、RL和评测，防止奖励漏洞与评测污染。
14. Tool Parser解释格式，Schema、业务语义、权限与状态仍需分别检查；流式未确认完整时不执行。
