<h1 id="q-001">1. 企业级 Agent 平台的本质是什么？</h1>

<h2 id="q-101">面试问题：平台复用能力与单个应用目标应如何区分？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

企业级 Agent 平台解决的是**多个应用反复遇到的构建、运行和治理问题**。应用团队负责“客户要完成什么任务”，平台团队负责“这类任务如何有一致的运行条件与约束”。平台的价值要在第二个、第三个应用接入时体现：接入时间更短，权限边界更清楚，故障更容易定位。

以客服退款与采购助手为例，两者需要的业务规则不同，却都需要用户认证、模型访问、工具凭证、任务存储、费用配额与审计。把这些共性能力沉淀为服务，可以减少重复建设；退款条件、采购预算归属、验收标准仍由业务方定义。平台如果把业务规则也包成无法修改的“大一统 Agent”，反而会让新场景只能绕路实现。

可以从三个接口判断边界是否成立：开发者怎样声明能力与依赖，运行时怎样调用并留下证据，治理方怎样收紧权限或停用版本。它们对应构建契约、执行契约和管理契约。例如工具上架时声明参数和数据范围，执行时注入受信任身份，撤销时阻止后续调用；三个环节必须使用能够关联的版本与资源标识。

衡量平台不宜只看创建了多少 Agent。更有意义的指标是应用接入周期、共享能力复用率、升级影响范围、单位成功任务成本，以及跨租户和越权问题能否被阻断。复用率高也未必更好：一个高度通用但频繁故障的模块，会把局部问题扩大到所有应用。

早期只有一个场景时，可以先把边界放在模块和接口里，等真实重复出现再拆为独立服务。平台化应当减少业务团队的负担，不能让一次简单的工具接入先穿过十个空壳系统。

<h2 id="q-002">面试问题：Agent 平台和单个 Agent 应用有什么区别？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

单个 Agent 应用与企业平台的差别，主要是**承担的责任范围和服务对象**。成熟应用也可以有完整的权限、评测和监控；不能把“应用”直接等同于写死配置的 Demo。

两者在同一条退款业务链上的分工可以这样理解：

<div align="center">

| 维度 | 应用需要回答 | 平台需要提供 |
| --- | --- | --- |
| 业务目标 | 哪些订单可退，怎样算处理完成 | 目标、版本和验收规则的登记能力 |
| 工具接入 | 查询订单和退款各用什么接口 | 统一凭证、调用约束、依赖与健康状态 |
| 数据使用 | 哪些材料能支持当前决定 | 主体隔离、数据分级与可追踪访问 |
| 质量控制 | 退款场景的失败样本和判分 | 可复用的评测执行、发布门禁和结果存储 |
| 运行治理 | 如何提示用户、处理例外 | 任务恢复、预算、审计与紧急停用能力 |

</div>

平台负责提供机制，应用负责填入领域含义。例如平台可以保证一个审批记录绑定具体参数版本，但谁有资格批准这笔退款、金额上限是多少，需要来自企业授权规则。模型完成率也由具体场景定义，平台不能统一用“没有报错”替代业务成功。

两者通常是渐进关系。先把一个应用做稳，再发现多个应用重复建设的部分，抽成共享能力；并非一定要先搭完整平台才允许应用上线。反过来，把数个聊天界面放到统一门户，也不代表已经完成平台化：若凭证仍各自散落、版本无法追踪、停用策略无法到达执行器，管理成本仍然存在。

面试中可以用一个责任冲突说明理解深度：共享网关故障由平台团队负责，网关正常但退款政策配置错误由业务团队负责；跨边界事故则需要同一任务标识串起双方证据。责任清楚，架构才有运营价值。

<h2 id="q-003">面试问题：为什么企业 Agent 平台需要控制平面？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

控制平面维护“系统应该如何运行”，执行面负责“当前请求怎样实际运行”。当多个团队共享模型、工具和数据时，控制平面提供统一的配置、身份、版本与策略入口，使权限变更能够传播到所有执行节点。

例如企业决定暂停某个退款工具。控制平面将工具版本标记为禁用，发布带版本的策略；执行节点在调度和提交前检查策略。仅从管理页面删除卡片并不够，旧任务、缓存和排队请求仍可能持有工具信息。真正的停用需要定义生效时点、缓存期限、在途请求处理，以及已经提交的交易怎样核对。

控制面也不必承载每一次业务调用。常见做法是分发经过验证的配置快照，执行面就近使用，减少热路径延迟。但权限撤销、紧急停机等对时效敏感的动作，不能无限依赖旧快照；可采用短租约、推送失效、执行前在线校验等机制，按风险决定失联时暂停还是有限继续。

这里有两个容易混淆的边界。第一，策略管理属于控制面，**策略执行点必须出现在真实的数据访问和动作入口**，不能只靠创建 Agent 时检查一次。第二，任务事件、Trace 和审计记录往往由执行面产生，由管理服务汇总；不能因为最终在控制台查看，就把所有记录写入都归为控制面。

设计时还要评估控制面的故障影响。若配置服务短暂不可用就阻断全部只读查询，可用性会受损；若敏感写操作在失去授权校验后仍继续，又可能扩大风险。把不同操作的降级条件写清楚，比笼统地要求“高可用控制平面”更有用。

<h2 id="q-004">面试问题：AgentOS、Agent Runtime、Agent Builder、AgentOps 如何区分？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这四个名称分别强调构建、执行、系统环境和持续治理，但并没有全行业唯一的产品划分。读一个架构时，应先追问它管理哪些状态、能拦住哪些动作，再看名称。

**Agent Builder**帮助人定义任务、工具和流程，产出可版本化的配置或代码。**Agent Runtime**消费这些定义，组织上下文、调用模型、分派工具、等待结果，并处理预算、异常和恢复。**AgentOS**常被用于描述更大的运行环境，例如文件系统、消息入口、进程、会话和长期任务管理；它通常是产品或系统抽象，不意味着真的实现了操作系统内核。**AgentOps**贯穿开发与生产，负责评测、观测、发布、事故处理和反馈回流。

以“读取订单并生成退款草稿”为例，Builder决定有哪些可用工具；Runtime执行查询并记录结果；运行环境提供隔离的临时文件与凭证通道；AgentOps检查草稿质量、费用和异常率。组件可以合并部署，职责仍需分清。

图 1：Runtime推进任务控制环。模型给出候选行动后，还要经过执行与结果核对；环境反馈可以触发继续、澄清或结束。

Runtime的标识设计尤其影响恢复能力。`conversation_id`关联会话，`run_id`关联一次执行，`step_id`关联逻辑步骤，`attempt_id`区分重试，业务幂等键关联同一意图的外部效果。同一退款请求重试时可以更换attempt，但不能因此创建另一笔退款意图；用户明确发起第二笔业务时，也不能错误复用旧幂等键。

这些标识可以帮助关联证据，不能单独保证一致性。业务服务仍需检查幂等记录、资源状态和事务约束。运行时持久化与恢复的具体机制见[第二章](02_编码Agent与AgentOS工程高频考点.md)。

<h1 id="q-005">2. 企业级 Agent 平台通常包含哪些核心模块？</h1>

<h2 id="q-102">面试问题：企业 Agent 平台怎样组织控制面与执行面？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

企业平台的模块划分应沿着**定义如何变成行动、行动如何留下可验证结果**来组织。先画出一条完整请求，再决定哪些模块需要独立部署，容易避免为名词搭架构。

可以以三个阶段展开：

1. **构建与发布。** Builder引用注册过的模型、工具和知识资产，提交配置包；发布服务验证依赖、权限和评测结果，形成不可随意漂移的版本。
2. **调度与执行。** 入口认证后创建任务，Runtime取得任务允许的能力与版本；模型网关处理推理请求，工具适配器访问业务服务，任务存储保存进度和回执。
3. **观察与治理。** 运行事件进入观测与审计系统，费用计入租户配额，失败样本进入评测。策略收紧和版本停用再传回执行入口。

Knowledge、Memory和Session是执行中可访问的数据能力，Workflow引擎负责显式依赖、等待和恢复。它们可以共享数据库或进程，逻辑职责不应混在一起。例如模型生成的计划不能直接覆盖业务订单状态，日常聊天摘要也不能充当已付款的权威凭证。

以课程预约为例，入口确认用户和租户，应用选定预约流程，Runtime收集信息并调用查询工具，预约服务事务性扣减名额，最后回执更新任务状态。模型网关不负责扣库存，Registry不替业务服务鉴权，Trace存储也不是预约结果的唯一来源。

关键接口需传递任务身份、版本、截止时间和可关联的调用标识，但凭证应通过受控通道注入，不能为了方便追踪把密钥写进消息或日志。所有模块共享同一套业务语义边界，比把框图拆成多少层更重要。

<h2 id="q-006">面试问题：Agent Builder 应该提供哪些能力？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Builder的核心产物应当是**可检查、可测试、可发布的Agent定义**。可视化画布只是编辑方式；如果图能运行却无法说明版本、权限和依赖，上线后仍难维护。

一个定义通常包含任务指令、输入输出约束、模型配置、工具与知识引用、状态转移、预算和失败处理。引用要区分编辑时的“最新版本”与发布时的固定版本。例如财务助手选择了一个工具后，发布包应明确它的Schema及权限范围，避免工具作者更新参数语义后，所有线上任务悄悄改变行为。

Builder还需要把错误尽量提前暴露：缺少必填参数、无终止条件的循环、没有出口的等待节点、当前用户无权绑定的数据源，都可以在运行前检查。模型自动生成流程或从OpenAPI转换工具时，同样要验证；自动生成成功只代表得到一份候选定义。

调试能力应覆盖一条成功路径和有代表性的失败路径。业务专家能查看实际工具输入、经过脱敏的结果、状态转移及业务回执，才能判断“取错数据”与“回答错规则”的差别。评测集可以从历史工单提取，但要清理隐私、按时间或实体隔离，并避免把待测答案重新放进模型上下文。

发布权限与编辑权限应分开。业务人员可以调整话术，不意味着能自行增加生产数据库写权限；平台应在发布和执行两处落实约束。已有授权范围内的普通修改可按制度自动通过，不能把所有改动都变成人工工单。

截至2026年11月25日，OpenAI同名产品Agent Builder已处于弃用过渡，官方计划于11月30日关闭，ChatKit继续可用。这是具体产品的生命周期变化，通用Builder职责仍然成立；新系统不能只因为概念同名，就依赖即将退出的产品入口。

<h2 id="q-007">面试问题：Tool Registry、MCP Registry、Agent Registry 如何分工？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Registry是能力资产的目录与生命周期管理入口。三类目录关注不同粒度，但可以共享一套底层资产模型。

<div align="center">

| 目录 | 主要管理对象 | 需要明确的契约 |
| --- | --- | --- |
| Tool Registry | 函数、业务API、代码或浏览器工具 | 参数、返回、业务副作用、幂等和权限范围 |
| MCP Registry | MCP服务器及可发现的能力 | 部署位置、支持版本、认证、能力快照及维护者 |
| Agent Registry | 可委派任务的Agent服务 | 能力声明、任务输入输出、身份要求、服务版本与质量边界 |

</div>

例如企业有一个订单MCP服务器，暴露查询和退款两个工具。服务器上架不意味着每个用户都获得退款权限；工具级授权与订单资源归属仍需执行时判断。同理，Agent Card描述某服务可做财务分析，也不能证明它有权读取本次任务涉及的报表。

目录需要将“可发现、已审核、可调用”分开。开发者可能看得到一种能力，却必须申请授权才能使用；审核通过的版本也可能因凭证过期、依赖故障或安全事件被停用。记录维护者、依赖、数据类别和版本，有助于找到受影响的应用，并安排替换与退出。

发现机制还需要防止隐性变化。运行时看到新的工具描述或Schema，应按变更规则重新验证；不能让服务器新增一个高权限工具后，旧Agent自动拥有它。动态发现可以保留，但实际暴露给模型和执行器的集合要受任务策略约束。

MCP、A2A提供互操作契约，不提供自动的可信认证结论。协议细节见[第四章](04_MCP与A2A协议高频考点.md)；本题关注企业怎样把协议能力纳入可维护的资产治理。

<h2 id="q-008">面试问题：模型网关在 Agent 平台中有什么价值？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

模型网关把分散的模型访问转成统一的调用入口，集中处理身份、路由、配额、费用与观测。它的长期价值在于**让业务对模型的依赖可管理**，同时保留模型能力差异。

一次请求到达网关后，可先确定租户和数据等级，选择允许的供应商与区域，再根据任务所需的模态、工具调用、结构化输出、上下文容量和延迟目标选择模型。调用后记录实际版本、用量、响应状态和路由原因。费用数据需要与供应商账单校准，不能只按估计token计算后长期不核对。

统一接口并不等于统一行为。不同供应商的流事件、工具调用消息、缓存、推理预算和错误语义可能不同。网关可以暴露公共能力，也应保留必要扩展，并对不支持的能力明确报错；静默丢弃参数会让应用误以为约束仍然有效。

Fallback尤其需要条件。公共模型不可用时，敏感任务不能被自动切到未授权的另一个区域或供应商；某模型不支持业务要求的结构化输出，也不能只换名称继续执行。重试还要识别已经产生的输出和远端状态，避免把部分流重复拼接成完整答案，或在托管工具已行动后再次执行同一意图。

脱敏也有成本。删除客户编号可能减少暴露，却让订单匹配失效；若使用可逆映射，映射表本身需要保护。网关侧过滤只是数据治理的一层，应用仍应尽量少发送无关内容。

因此应通过同口径业务评测验证模型切换，并保留可观测的降级路径。一个返回200状态码的统一入口，无法证明任务质量和业务语义也已统一。

<h2 id="q-009">面试问题：会话、任务、记忆、知识库为什么要分开管理？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这几类数据描述的事实、生命周期与一致性要求不同，适合先在逻辑上分开。**逻辑分离不要求每类数据单独建一个数据库。**

<div align="center">

| 数据 | 回答的问题 | 典型约束 |
| --- | --- | --- |
| 会话 | 用户与系统交流过什么 | 消息顺序、访问范围、保留与删除 |
| 任务状态 | 目前执行到哪里，等待什么 | 状态转移、版本冲突、恢复与取消 |
| 记忆 | 哪些信息适合后续复用 | 来源、主体、适用范围、时效与撤回 |
| 知识库 | 哪些业务材料可作证据 | 文档版本、索引更新、引用和ACL |
| 业务记录 | 预约或交易实际发生了什么 | 事务、唯一约束、幂等与权威回执 |

</div>

用户在聊天里说“上次预约成功了”，可以作为待核查信息；真实预约状态应查询业务记录。工具提交成功后响应丢失，任务状态可能还在“核对中”，不应为了让聊天记录看起来完整，就把业务结果写成失败或重复提交。

存储组合需要由访问模式决定。PostgreSQL可以同时承载业务事务、任务记录、JSON事件与部分检索；MongoDB适合结构变化较多的文档数据；Redis可用于缓存、限流和短期协调。它们都不是某一数据类别的唯一选项，也不能仅靠产品名判断持久性和一致性。

真正增加复杂度的是跨库写入：任务库写成功，索引更新失败，系统如何发现和补齐？常见办法是在主记录事务中写outbox事件，异步消费者幂等更新索引，并保留补偿与对账。缓存和搜索索引是派生视图，不能同时成为同一事实可任意修改的权威来源。

删除同样需要传播到摘要、索引、缓存与恢复流程。先明确每类事实由谁写、谁读、谁负责恢复，再决定是否拆库，通常比预先拼装一组数据库更稳妥。

<h2 id="q-029">面试问题：用户意图识别怎么做？规则匹配、LLM 判断和混合方案怎么选？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

意图识别先要定义业务边界：哪些请求可以处理，哪些信息必须补齐，哪些表达需要拒识或澄清。识别器的输出应是受限业务语义，而非直接可执行的代码或任意服务地址。

规则适合固定命令和高精度入口，例如明确的订单号格式、菜单选择；LLM适合“把上周那节课改到周五”这类有上下文依赖的表达。混合方案可以先处理确定性入口，再让模型识别长尾，最后用Schema和业务规则验证。规则数量膨胀且彼此冲突时，也需要评估维护成本，不能默认越多越可靠。

一个输出可包含`intent、slots、needs_clarification`以及支持判断的原文片段。例如“想了解如何退款”通常是规则咨询，“退掉订单A”才是退款意图；即便识别为退款，仍需核查订单归属、当前状态和授权范围。**分类结果是路由依据，不是业务执行许可。**

多轮场景中，已有任务状态会改变短句含义。“周五吧”只有与明确的待补日期字段关联，才有可用解释；同一会话同时讨论两笔预约时，应先确定对应任务。用户真正的身份来自认证上下文，不能根据文本里的“我是管理员”提升权限。

评测应按意图查看召回率、混淆矩阵、未知请求拒识，以及危险混淆的代价。把查询错分为写操作，比把咨询错分为另一个咨询类别影响更大。模型自报的置信度需用独立样本校准，且阈值通过也不能替代权限和业务规则。

上线后还要跟踪拒识率与人工纠正案例。未知意图不断出现，往往说明业务范围或标签体系需要调整，单纯增加提示词例子未必解决根因。

<h2 id="q-030">面试问题：意图识别完成后，怎么把请求路由到不同的业务处理器？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

路由器把合法的意图和槽位映射到受控业务处理器。关键是建立**服务端白名单、明确输入输出契约和可核对的状态转移**，让模型的语言判断不会直接变成任意执行。

注册表可以为每个意图保存处理器标识、参数Schema、所需权限、截止时间、重试条件和返回类型。`knowledge_query`进入知识检索，`booking_query`进入只读查询，`booking_create`进入预约流程。模型只能选择已暴露的意图枚举，不能传入类名、shell命令或URL让路由器动态执行。

处理器应分别接收业务参数和受信任上下文。用户、租户、任务与授权来自宿主，模型参数不能覆盖它们。随后仍由业务服务验证资源归属和状态，例如“当前用户可以使用预约工具”不等于“可以修改任何人的预约”。

多意图请求需按依赖编排。“先查余量，再预约周五的课程”包含两个阶段；后一步依赖实时余量和必要确认，不能将两个处理器无条件并行。对于缺字段、规则拒绝、可恢复故障和结果未知，应返回不同状态，避免模型把所有非成功都解释成“再调用一次”。

状态所有权也要清楚。路由器决定进入哪个流程，流程引擎维护进度，业务服务确认外部效果。请求从另一入口重进时，应关联现有任务与幂等意图，而非仅凭相同用户文本猜测是否重复。

Trace记录分类版本、所选处理器、参数校验和业务回执，才能分辨识别错误、映射错误和服务执行错误。把这三种问题都归成“模型不稳定”，会让优化方向失焦。

<h2 id="q-031">面试问题：Agent 怎么调用 Spring Cloud 微服务？统一网关和 Nacos 在链路里分别起什么作用？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

Agent通过受控工具适配层访问微服务。模型填写允许的业务参数，适配器补入认证、追踪标识、超时和业务幂等信息；业务服务负责资源授权、事务与权威结果。

一种常见链路是：`Runtime → 工具适配器 → Spring Cloud Gateway → 业务服务`。网关可以提供API路由、认证接入、限流、观测和韧性处理。内部服务间也可通过受控客户端直接调用，不是每条链路都必须经过同一个外部网关；关键是约束和审计仍然成立。

Nacos提供服务发现、配置管理及相关治理能力。业务实例注册后，调用方或网关可以依据服务名发现实例并进行负载均衡。当前Nacos 3.x也提供Agent、MCP、Skill等AI资源的注册与发现。**注册发现仍不等于承载每次业务请求的数据转发。** 不应把“向Nacos查询地址”画成“Nacos代理所有业务调用”，更不能让它替代业务授权或模型规划。

例如预约服务有多个实例，工具层只接受`course_id、slot_id`等字段，不能让模型自行生成内网URL。网关或客户端从已允许的服务中选择实例，业务服务在事务内校验用户、名额和幂等键。某次提交超时，适配器先查询结果；网关重试、客户端重试和Runtime重试需统一预算，避免多层重试叠加。

配置更新也属于变更发布。新地址、超时或重试策略需版本化并灰度，服务发现返回健康实例不保证某个请求必然成功。多租户身份不能只放在可伪造的普通请求头中；网关清理外来同名头并注入可信声明，下游验证其来源，必要时使用面向目标服务的短期凭证。

具体集成方式随Spring Cloud、Gateway与Nacos版本变化。面试应讲清发现、转发、认证和事务各自的位置，避免把产品名称当成已经实现可靠调用的证明。

<h1 id="q-010">3. 企业 Agent 平台如何做多租户和权限治理？</h1>

<h2 id="q-103">面试问题：多租户平台应怎样建立身份与资源边界？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

多租户边界要覆盖任务的整个数据与动作路径。入口认证正确只是起点，检索、记忆、缓存、工具、文件、日志和后台任务都需要保持同一个资源归属约束。

可用“主体—资源—动作—上下文”描述一次访问：哪个用户或服务主体，通过哪个Agent，在什么任务中，对哪个租户的资源执行什么动作。租户标识由认证与服务端路由确定，不能从模型生成的JSON里取一个`tenant_id`就相信它。

例如两个客户都有名为“财务知识库”的资源。检索必须依据不可混淆的资源ID和ACL，而非仅按名称选库；缓存键也要包含有效的身份与权限范围。否则底层向量库虽然隔离，缓存仍可能把A租户的结果返回给B租户。导出文件、对象存储签名URL和Trace搜索同样存在这种旁路。

隔离强度可以分层选择：共享表配合行级约束、独立Schema、独立数据库、独立运行环境，各有运维成本与故障范围。物理隔离并不自动解决凭证误配，共享部署也不意味着必然不安全。需要根据数据等级、客户要求和可验证能力确定方案。

权限在任务开始后还可能变化。长任务不能永远持有启动时的授权快照；敏感步骤应检查有效权限，撤销后阻断后续访问，并处理已生成产物的可见性。已泄露的数据无法通过撤权自动收回。

验收应包含相同资源名、伪造租户字段、共享缓存命中、跨租户文件访问、后台恢复和日志查询等路径。只检查界面上“用户看不到另一个租户”，无法证明执行边界完整。

<h2 id="q-011">面试问题：RBAC、ABAC、租户隔离在 Agent 中如何落地？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

RBAC按角色分配权限，ABAC根据主体、资源、动作和环境属性作细粒度判断，租户隔离约束资源归属。它们可以共同使用，各自解决不同问题。

例如“客服主管”角色可以创建客服Agent，这是RBAC；能否退款还取决于订单所属租户、金额、地区、当前政策、任务委派范围等，这是ABAC；无论角色多高，本租户的普通业务身份都不应越界访问另一租户的订单，这是隔离约束。

实现时通常有策略决策点与策略执行点：前者依据可信属性返回允许、拒绝或附加条件，后者在真实查询和工具提交前落实决定。不能只在页面隐藏按钮，也不能将模型的解释当成最终授权结果。属性需要可信来源，诸如数据等级、资源归属和用户部门不应由请求自由声明。

检索中的过滤要在未经授权内容进入模型上下文之前生效。召回后再做确定性ACL核验可以作为补充，但应注意候选不足和信息侧漏；更不能把未授权文档仅仅降低排序分数。权限变化时，缓存的策略结果和检索结果也要失效或在读取时重新核验。

策略冲突需有明确规则。例如角色允许查询，但资源标记禁止外发，应怎样处理；审批是否可以覆盖某条限制，必须由制度明确。不能假设“有审批”就能跳过所有其他约束。

权限服务失联时也要按动作设计。高影响写操作可能需要暂停，部分已授权只读访问可在短期有效租约内继续。记录所用策略版本、属性摘要和判定原因，有助于复盘；敏感属性本身仍需脱敏与访问控制。

<h2 id="q-012">面试问题：Agent 身份和用户身份为什么要分开？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

用户身份说明任务由谁发起，Agent或工作负载身份说明由哪个自动化主体执行。二者分开，才能同时约束人的权限、应用能力和本次委派范围。

例如财务经理启动客服Agent回答一张工单。经理可能有财务报表访问权，客服Agent却只需要工单与订单权限。将用户的完整凭证交给Agent，会让一个狭窄任务获得不必要的能力。对这种代表用户执行的场景，有效权限通常应受用户权限、Agent允许范围、任务授权和当前策略共同限制。

但“Agent权限永远小于用户权限”也过于绝对。企业可能让一个定时结算服务以独立服务身份运行，没有单个交互用户。此时权限来源是正式配置的服务职责、资源范围与组织授权，不能虚构为某位用户的临时委派。需要明确区分用户代理型任务与服务主体型任务。

具体调用可使用on-behalf-of或面向目标服务的短期凭证，记录发起主体、执行主体、委派链、目标资源和过期条件。短期令牌能缩短暴露窗口，但若范围仍是全库读写，风险并未根本消失；令牌的audience、scope和资源约束仍需验证。

授权还应与用户确认分开理解。用户可能已经明确授权一组操作，只要当前行动仍在有效范围内，就不必机械地重复确认；超出范围、参数发生关键变化或制度要求审批时，再获取相应授权。身份认证证明“你是谁”，不能单独证明“你批准了这次操作”。

审计同时保留人的意图、执行主体与业务回执，才能解释某项动作为什么发生。只记录`agent_id`或只记录用户账号，都会丢失一部分责任链。

<h2 id="q-013">面试问题：企业私有化部署需要考虑哪些问题？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

私有化部署需要确认的是**整个数据和执行链留在哪里、由谁维护、故障后怎样恢复**。把Web服务装进内网，仅完成了其中一部分。

先画数据流：用户消息、检索文档、Embedding请求、模型输入、工具结果、Trace、错误报告和备份分别经过哪些位置。应用在内网而Embedding走外部API，或者监控SDK把原始请求发到外部平台，都不符合严格的数据不出域要求。私有模型也不自动解决越权读取、提示注入或日志泄漏。

接着确认身份与网络。企业SSO、OIDC或目录服务负责身份接入；资源权限由业务系统及平台共同执行。网络侧要限制工具可达目标、出站地址与凭证访问，区分访问业务API、下载依赖和发送遥测等用途。完全离线环境还需要模型、镜像、证书、漏洞修复和许可证检查的交付方案。

运维能力决定系统能否长期运行。模型与工具升级需要兼容测试，索引重建要评估容量，备份恢复要核对任务和业务状态。恢复一个旧任务快照，可能面对已经更新的政策和已发生的交易，不能一键重放全部步骤。

成本也不只有GPU。低利用率、冗余容量、部署适配、客户专属版本、值守与升级人力，都会进入总拥有成本。混合部署可以减少部分压力，但要清楚定义哪些数据和任务可出域，不能在故障降级时临时放宽边界。

验收应包含断网、凭证过期、节点崩溃、备份恢复和跨版本升级。私有化的价值需要在这些运行条件下成立，单次在客户机器上启动成功只能证明安装完成。

<h2 id="q-014">面试问题：如何设计 Agent Marketplace / Skill Marketplace？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

Marketplace把可复用能力交给更多人使用，也放大了供应链和权限扩散风险。设计重点是让使用者知道能力来自谁、会执行什么、依赖什么，以及出了问题怎样停止和替换。

一个可审核的条目至少要绑定不可混淆的版本、维护者、依赖、输入输出、所需权限、网络与文件访问范围、代表性测试和适用边界。Agent条目可能是远程服务或应用模板，Skill可能包含指令、脚本和资源；二者都不能仅凭一段好看的描述获得执行信任。

上架时检查结构和依赖，在隔离环境运行功能与恶意输入样本，再按风险决定人工审核和灰度。签名与摘要能确认工件来源、检测篡改，不能证明代码没有漏洞。高下载量和高评分同样不能替代对当前版本的验证。

安装是一次能力授权过程。用户应能看到将新增的权限，凭证由宿主管理，不随模板打包。升级若扩大网络范围或新增写工具，应触发重新评估；不改变行为的展示文案可走较轻流程，指令正文变化仍需行为回归。运行时继续落实授权，不能认为“安装时同意过”就永远允许所有后续变化。

下架也有不同含义：停止新安装、禁止启动新任务、阻断在途调用、撤销凭证和替换依赖，影响范围不同。紧急停用要找到已安装的应用与版本，但已发送邮件等外部效果不会自动消失。

Marketplace还应保留弃用通知、迁移期和维护责任。目录数量没有直接业务价值，能被放心复用且能平稳退出的能力才有。Skill如何从经验候选进入评测和迭代，见[第九章](09_自进化Agent与多平台运行时高频考点.md)。

<h1 id="q-015">4. 企业 Agent 从 PoC 到生产落地有哪些阶段？</h1>

<h2 id="q-104">面试问题：业务场景从试验到生产需要哪些验收阶段？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

从试验到生产，应当逐步增加真实环境、真实责任与可承受影响范围。阶段名称可以不同，但每次扩大范围都要回答：比上一阶段多承担了什么风险，有什么证据支持。

PoC验证任务在给定数据与工具条件下能否完成。应保留原有人工或程序基线，检查必要接口是否存在，别把人工偷偷补齐的信息算成Agent能力。Pilot让少量真实用户在受限范围内使用，观察任务分布、纠错成本和接管需求；试用满意并不自动等于结果正确。

受控生产需要可执行的权限、状态恢复、监控和事故处置。比如客服先生成回复草稿，再开放指定订单查询，最后在清楚的条件下自动处理部分退款。这里的递进取决于动作风险与验证能力；对于边界明确的低风险任务，也可以从较高自动化程度开始，不必机械地经历所有阶段。

规模化验收要关注新增负载和长尾。十个人试用时很少遇到的并发冲突、租户配额争抢、第三方限流和极端输入，可能成为大规模运行的主要失败源。平台化则进一步验证共享能力是否降低新场景接入成本，是否扩大了公共故障的影响面。

每阶段都应有进入与退出条件。例如允许自动完成的任务类型、业务成功率及样本数、危险动作失败上限、P95延迟、人审时间和单位任务总成本。指标阈值应由业务容忍度确定，不能从另一家公司的案例直接照搬。

还要设置暂停条件：异常承诺、越权访问、重复交易或成本失控出现时，怎样缩小能力范围并核对已发生效果。上线的成熟度体现在问题发生后能否有序处理，而非演示路径有多顺。

<h2 id="q-016">面试问题：客服 Agent、数据分析 Agent、编码 Agent、办公 Agent 如何对比？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

几类Agent的差异，主要来自工作对象、可用证据和错误代价。相同模型在不同业务里，需要完全不同的执行和验收条件。

<div align="center">

| 场景 | 价值来源 | 必须核对的结果 | 典型失败 |
| --- | --- | --- | --- |
| 客服 | 缩短处理时间、提高规则一致性 | 订单状态、政策依据、客户承诺 | 错用政策、越权退款、误导承诺 |
| 数据分析 | 降低取数与解释成本 | 数据口径、查询权限、统计推断 | SQL合法但口径错误、相关当因果 |
| 编码 | 降低实现与维护成本 | 需求、diff、测试及运行行为 | 测试通过却遗漏需求、破坏既有修改 |
| 办公 | 协调邮件、日历和文档流程 | 收件对象、时间、版本与回执 | 发错人、重复邀请、覆盖文件 |

</div>

客服的政策可以相对明确，但例外与对外承诺需要谨慎；数据分析常有可执行查询，却仍可能误解业务定义；编码能通过测试获得反馈，但测试不完备；办公操作看似简单，却容易在同名联系人和时区上产生不可忽略的影响。

因此应按“结果能否核验、动作能否限制、失败能否发现、人审是否有效”选择自动化边界。只读建议通常便于早期试验，但并非零风险：读取敏感数据并写入报告，仍可能造成泄露；一份需要专家花更久纠错的草稿，也未必节省人力。

评测需要对应真实价值。客服不能只看回复速度，还要看问题解决与错误承诺；分析不能只看SQL执行率，还要看结论是否符合口径；编码不能只看生成行数；办公不能只看工具调用成功率。业务回执与用户实际工作量共同决定产品收益。

更可行的落地方式是选窄任务，例如固定口径的周报或特定类型工单，在可验证范围内扩大自动化。按“客服、办公、编码”这样的大类直接判断哪一个更容易，通常过于粗糙。

<h2 id="q-017">面试问题：低代码 Agent 平台适合什么场景，不适合什么场景？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

低代码平台适合将可复用流程交给更多业务人员维护。是否能承担复杂生产任务，需要看其执行语义和扩展能力，不能仅凭“画布式界面”作判断。

如果任务由已有连接器、明确条件分支、知识检索和少量人工审核组成，可视化配置往往能缩短沟通与迭代时间。例如业务专家更新客服政策和转人工条件，不必每次修改服务端代码。平台提供可导出的版本、可测试的流程和受控发布时，这种优势可以延续到生产。

当业务需要特殊运行环境、严格状态恢复、复杂并发、精细权限或非常规协议时，关键问题是平台能否表达这些要求。代码节点、外部服务和自定义插件可以扩展能力，但会重新引入依赖、安全、调试与运维成本。不能因为能嵌入任意代码，就声称平台已经替团队处理了这些问题。

可以用几个具体故障验证选型：任务等待审批后服务重启还能否继续；工具提交成功但响应丢失会不会重复提交；发布新流程时旧任务如何处理；权限撤销能否阻断后续节点。只展示一条顺利执行的流程，不足以回答这些问题。

还要检查版本差异。社区版、云版与企业版可能在SSO、角色权限、审计、部署和支持范围上不同；“支持私有化”也不意味着全部云能力能原样迁入。采购与开发需要核对实际购买和部署的版本。

因此，低代码的选择标准是它能否用更少的维护成本表达并守住业务约束。超出平台能力的部分可以由受控业务服务承担，前提是接口、状态和责任边界清楚。

<h2 id="q-018">面试问题：如何评估一个 Agent 场景是否值得做？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

判断场景是否值得做，要估算**完成同样质量任务后的净收益**。频次高、模型调用便宜只能说明有机会，不能直接证明项目成立。

可先用一个简化关系做核算：

```math
V = N\left[C_{\mathrm{base}}-C_{\mathrm{AI}}-C_{\mathrm{review}}-C_{\mathrm{rework}}\right]-C_{\mathrm{fixed}}
```

其中，$`N`$ 为统计期内同口径任务数量，$`C_{\mathrm{base}}`$ 为原流程单任务成本，$`C_{\mathrm{AI}}`$ 包含模型、工具和运行费用，$`C_{\mathrm{review}}`$ 是审核成本，$`C_{\mathrm{rework}}`$ 是失败后的期望返工或损失，$`C_{\mathrm{fixed}}`$ 是统计期内分摊的建设与维护成本。收入提升可以另列，但要有可归因证据，避免把收入和时间节省重复计算。

例如原流程平均需要20分钟，Agent生成草稿需要1分钟，但人工审核与返工平均花18分钟，实际收益很有限。若报告质量下降，或者用户因为更便宜而生成大量无用报告，简单比较生成速度会高估价值。

成本之外，先判断可行性约束：必要数据和工具是否可用，结果是否可验证，授权是否清楚，错误后是否有合理接管路径。重大但难估计的风险不适合随意折成一个小概率成本项；可能需要直接限制自动化范围。

实验应包含原流程对照、真实任务分布和足够长的观察期，同时记录采用率、审核时间、错误分层和业务结果。只挑最容易成功的样本会扭曲收益，用户试用时的兴奋也不等于长期留存。

优先考虑已有明确SOP、结果可核验且重复劳动多的子任务，但不要把高频低风险当成唯一选择。低频任务若价值很高、证据充分且审核可行，也可能值得做；关键在完整成本和责任是否可控。

<h2 id="q-019">面试问题：Agent 产品如何设计 Human-in-the-loop？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Human-in-the-loop需要明确**人在哪个状态介入、看到什么证据、可以作什么决定**。只在动作前弹出“是否继续”，既可能遗漏关键信息，也可能让用户形成机械点击习惯。

课程预约可以用显式状态机组织：收集课程和日期，规范化时区与字段，查询规则和名额，展示待确认方案，取得有效授权，提交时重新校验，最后返回业务回执。缺信息、方案修改、取消、库存冲突和结果未知都要有明确去向。

确认应绑定课程、场次、时间、地点、费用条件、用户和方案版本，并设定合理有效期。用户改了时间，旧确认不应继续覆盖新方案；“好的”只有在明确且仍有效的待确认上下文中才可解释。若用户已明确授权符合条件的自动预约，系统可在这个范围内执行，不必人为增加同义确认。

![课程预约中的确认提交与结果核对](imgs/agent-engineering-80-20261014/06_课程预约的确认提交与核对.png)

</div>

提交阶段由后端约束并发：同一意图使用稳定幂等键，相同键但不同参数应拒绝；预约写入、名额扣减和幂等结果在同一事务中一致提交，或采用有等价约束的可靠协议。确认后名额可能被抢占，因此必须再次校验。跨服务支付、库存和通知不能假装由一个数据库事务全部覆盖，需要预占、释放、补偿和对账。

人类接管也要有状态交接。界面展示已执行动作、未决结果和下一步建议，避免客服接手后重复操作。测试应覆盖双客户端提交、确认过期、提交成功但响应丢失、取消与提交竞争等情况。用户点击确认代表一项授权事实，业务是否完成仍要看实际结果。

<h1 id="q-020">5. 企业 Agent 平台如何控制成本、延迟和稳定性？</h1>

<h2 id="q-105">面试问题：平台的性能、费用与可靠性如何共同约束？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

性能、费用和可靠性需要围绕完整任务共同优化。一次模型响应更快，可能换来更多工具重试；单次请求更便宜，也可能让失败任务的总成本上升。

首先拆解延迟。串行依赖上的模型推理、工具等待、队列和人工处理构成关键路径；彼此独立的只读查询可以并行，但并行度过高会触发限流并拖慢尾部。用户看到第一个token的时间，与拿到可用业务结果的时间是两个指标，不能混用。

其次约束资源。按任务设置token、工具调用、墙钟时间和费用预算，按租户设置并发与配额。预算应覆盖失败重试和外部工具费用，而不仅是模型token；已经送出的远端任务也要跟踪，否则停止本地循环后仍可能持续计费。

可靠性机制需要防止相互放大。超时、重试、退避、熔断和队列应共享截止时间与重试预算，避免某个下游变慢后全系统同时重试。对于有副作用的动作，超时先进入结果核对，不能按只读查询方式盲目重发。

缓存同样有边界。稳定的公共知识可缓存，库存、余额和授权结果需要更谨慎的有效期与重新校验；缓存键必须包含数据版本和实际访问范围。只看命中率而忽略陈旧和跨主体返回，会把性能优化变成正确性问题。

平台看板应并列展示按任务分层的成功率、P95/P99完成时延、失败与接管成本、单位成功任务费用，以及租户间的资源公平性。用真实负载回放或受控压测验证变化，才能知道瓶颈究竟在模型、工具还是队列。

<h2 id="q-021">面试问题：Agent 平台如何做模型路由和成本治理？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

模型路由根据任务所需能力、数据限制、预算和当前运行状态选择模型。大小模型只是其中一个维度，规则程序、专用模型和人工处理也可以是合法路径。

字段提取、意图分类和格式明确的改写，适合先评估成本较低的模型；多证据冲突、复杂代码修复和长链推理可能需要更强能力。但“短问题用小模型”并不可靠：一句简短的法律判断可能比一篇格式化摘要更难。应依据任务集中的真实错误类型，而非输入长度作决定。

级联方案通常先让低成本路径处理，遇到缺字段、格式不合规、验证失败或证据不足时升级。模型自报“很有信心”若未经校准，不能当作可靠概率。升级判据也会出错，需要单独测漏升级与误升级。

若简单路径每次成本为 $`c_s`$，有比例 $`r`$ 的任务升级，升级阶段额外成本为 $`c_l`$，则粗略期望成本是 $`c_s+r c_l`$。这还未包含路由、验证、重复工具执行和失败返工；若升级发生在昂贵动作之后，省下的模型费可能很小。延迟也要计算两阶段串行等待。

评测时固定任务分布，比较直接使用强模型、单一低成本模型和级联方案的成功率、覆盖率、升级率、总成本与时延。不能只报告被路由器留下的容易样本。对高影响业务，所有路径都遵守相同授权和确定性校验，强模型不获得额外越权资格。

路由策略应版本化并可回退。还要区分整题路由与任务内委派：前者选择处理整件事的路径，后者让不同模型承担子任务，其通信和整合成本见[第三章](03_Agent设计模式与工作流编排高频考点.md)。

<h2 id="q-022">面试问题：Agent 平台如何设计发布、灰度和回滚？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Agent发布需要绑定一组会共同影响行为的工件：指令、模型及参数、工具契约、工作流、知识索引、记忆策略、权限与Guardrail。只记录模型名称，无法解释同一任务为什么在两次运行中表现不同。

平台可以将这些引用形成版本清单，评测通过后发布到指定租户或场景。不可固定的外部依赖至少记录实际使用版本与时间，并设置兼容性探测。灰度流量应保持业务可比，避免新版本只处理简单任务，旧版本承担全部长尾，从而制造虚假的提升。

有状态任务使回滚更复杂。一个任务可能在旧工作流里等待审批，新版本已经改变字段或节点。可让旧任务固定版本继续运行，或在兼容边界执行经过验证的迁移；不能直接用新代码解释旧状态，期待它自动理解。权限紧急收紧则应能覆盖旧任务，不能以版本固定为理由继续使用被撤销能力。

回滚也有多个对象：应用配置、存储Schema、索引和工具服务可能不具备相同回退能力。数据库变更通常需要兼容读写或前向修复，已经写入的长期记忆也需考虑旧版本能否解释。恢复旧配置并不会撤销已发邮件和已完成交易。

发布验收要检查成功率与安全约束，并观察任务费用、延迟、接管率和业务回执。异常时先阻止新增影响，核对在途和结果未知任务，再决定配置回退或业务补偿。将这套能力产品化，能让应用团队重复使用同一种发布纪律。

评测门禁与事故分析的细节见[第六章](06_Agent安全评测与AgentOps高频考点.md)；本题重点是版本包、流量控制和状态兼容怎样落实到平台接口。

<h2 id="q-023">面试问题：Agent 平台如何建设可观测性和审计？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

可观测性帮助判断系统现在运行得怎样、故障从哪里开始；审计帮助核对某个主体基于什么授权做过什么。两者共享部分事件，但采样、完整性、访问权限和保留期可能不同。

平台可以用任务ID关联模型调用、工具步骤、后台事件与业务回执，按租户、场景和版本查询。指标层展示请求量、完成率、尾延迟、费用和接管率，Trace帮助下钻到具体步骤。业务成功必须有对应判据，不能只根据HTTP状态或模型最后一句“完成了”计数。

审计记录还应解释授权链：发起者与执行者是谁，访问什么资源，执行时使用哪个策略版本，是否有有效审批，最终产生什么外部效果。普通性能Trace可以采样，关键写操作的审计是否允许采样，应由明确要求决定；缓冲队列溢出和采集故障也要可检测。

日志本身是敏感数据源。原始提示、工具结果、账号和文件路径可能泄露信息，需要字段级控制、脱敏、访问授权和删除策略。哈希能用于一致性核验，但低熵内容可被猜测匹配，不能因为哈希化就声称完全匿名。也不应为了“看懂推理”要求记录模型不可见的内部思维链。

对外提供审计导出时，需定义时间范围、时区、事件版本、完整性证据与关联规则。仅有一串按时间排序的文本，难以证明并发调用的因果关系。日志缺少某项回执，也不证明外部动作没发生，仍要与权威业务系统核对。

平台最终应让运营、开发和审计人员各自看到完成职责所需的信息。统一入口有价值，但把全部原始数据开放给所有运维人员，会削弱原本建立的边界。

<h2 id="q-024">面试问题：Agent 平台如何支持长任务和后台任务？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

长任务需要独立于一次HTTP连接和一次模型响应存在。核心是持久任务记录、可恢复执行与结果查询，让用户断线、进程重启和等待人工都不会丢失任务语义。

创建任务时保存任务ID、输入摘要、授权范围、运行版本、截止时间和初始状态，再可靠投递到队列。数据库记录与消息投递需协调，例如用同事务outbox避免“任务已建但消息永远没发出”。Worker通过租约或等价机制获取执行权，完成阶段写入状态与可核对结果。

状态应区分排队、运行、等待工具、等待输入或审批、成功、失败、取消等情况。多个Worker竞争或旧Worker暂停后恢复时，可用版本比较或递增的租约代号，由存储端拒绝过期执行者的更新；锁本身不能保证外部接口不重复行动，幂等和业务约束仍需落在效果发生处。

进度流是便于观察的视图，持久状态才是恢复依据。客户端断线后可查询当前任务；若产品提供事件重放，要明确序号、保留范围和缺口处理。不能假定所有SSE或WebSocket连接都自动具备重放能力，也不能把观察连接关闭等同于任务取消。

取消是一个有竞态的请求。它可能阻止下一步，无法确保已经发送的支付或邮件被撤销。系统需要区分取消已接受、执行已停止、外部结果已核对等事实；截止时间到达后的未知业务结果也应继续对账。

结果、附件和通知分别管理。任务已成功而通知发送失败，可以重试通知，不应重跑整个任务。对于短而确定的操作，同步接口仍然适合；是否采用任务系统应由持续时间、恢复与交互需求决定。

<h1 id="q-025">6. 当前主流 Agent 平台和框架如何分类选型？</h1>

<h2 id="q-106">面试问题：企业 Agent 产品与开发框架应如何分类？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

选型先确定希望谁管理哪些责任：应用代码、状态恢复、运行环境、身份集成，还是面向业务人员的构建入口。SDK、编排框架和托管平台可以组合使用，不是互斥选项。

<div align="center">

| 层次 | 解决的问题 | 示例与选型关注 |
| --- | --- | --- |
| 代码开发与Agent循环 | 工具、消息、交接和模型适配 | OpenAI Agents SDK、Google ADK；检查能力差异与状态接口 |
| 状态和工作流编排 | 显式依赖、等待、恢复、人工介入 | LangGraph、Microsoft Agent Framework；检查持久化与副作用边界 |
| 数据与协作抽象 | 检索、数据连接、角色协作 | LlamaIndex、CrewAI；判断抽象是否匹配任务 |
| 可视化构建平台 | 让业务人员配置应用和流程 | Dify、Coze Studio、Copilot Studio；核对具体版本和治理能力 |
| 托管运行与治理 | 部署、身份、隔离、弹性、观测 | Amazon Bedrock AgentCore、Google Gemini Enterprise Agent Platform、Microsoft Foundry相关服务 |

</div>

这些分类表达主要职责，不能推断某框架只支持其中一层。一个SDK可能支持持久会话，一个托管平台也可能允许运行自定义框架。应通过具体任务验证接口与语义，而非按营销分类排除选项。

截至2026年11月25日，AutoGen官方仓库已标记归档，不再由Microsoft维护；Microsoft Agent Framework被官方定位为AutoGen与Semantic Kernel的后继路线。AutoGen仍有学习协作思想和维护已有系统的参考价值，但不宜在新项目清单中不加说明地当作持续维护选项。

真正的比较对象应包括团队维护成本、数据位置、权限能力、任务恢复、版本发布和退出方案。若一个平台能快速完成演示，却无法导出必要状态、无法解释失败动作，接入省下的时间可能在生产维护中重新付出。

<h2 id="q-026">面试问题：OpenAI Agents SDK、LangGraph、Semantic Kernel、Google ADK 如何对比？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这几个框架的差异应放在同一个任务中比较，例如“查询业务证据，等待审批，执行动作，崩溃后恢复”。仅列API名称，很难判断哪一个适合团队。

<div align="center">

| 框架 | 主要抽象 | 应重点验证的条件 |
| --- | --- | --- |
| OpenAI Agents SDK | Agent循环、工具、Handoff、会话、Guardrail与Tracing | 应用自管的部署和存储，审批恢复，具体Guardrail覆盖范围 |
| LangGraph | 共享状态、节点和边，持久化与中断 | Checkpoint配置、节点重放、副作用幂等、状态Schema变更 |
| Semantic Kernel | 将模型与现有代码、插件和连接器集成 | 已有C#、Python、Java资产及所用组件维护路线 |
| Google ADK | Agent与Workflow，模型、工具和执行节点组合 | 所用语言支持、会话服务、部署与远程互操作能力 |
| Microsoft Agent Framework | Agent、Harness、显式Workflow和企业集成 | 现有SK或AutoGen迁移、语言差异、状态和中间件行为 |

</div>

OpenAI Agents SDK的循环由应用运行，不应与托管Agents API的会话和沙箱混为一谈。LangGraph把控制流和状态显式化，但持久化需正确配置，重放也不会替业务接口保证外部效果只发生一次。Google ADK提供多种Agent与工作流组合，不应简化成“只能配Gemini”的库。

Semantic Kernel保留了连接企业代码与模型的集成价值。当前Microsoft文档将Agent Framework明确定位为它与AutoGen的后继；新项目应评估这条路线，已有项目则需根据语言、插件和实际依赖制定迁移计划。后继关系不等于各语言和各组件已完全一一替换。

实测时使用同一模型、工具和任务集，核对恢复点、审批上下文、事件记录与总成本。可以让不同组件各司其职，但增加一层框架就多一层状态与错误映射，组合前需要确认收益。选型结果应该能解释“它替团队承担了哪项责任”，而不只是“示例代码更短”。

<h2 id="q-201">面试问题：接口兼容是否足以避免平台锁定，Agent迁移还要保住哪些资产？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐ (3/5)**

接口兼容可以减少调用代码修改，但平台迁移还涉及**状态、权限、执行语义和运行证据**。这几类资产的可迁移性，往往比HTTP路径是否相同更影响退出成本。

模型API适配通常最容易看到；更隐蔽的是待审批任务能否恢复、工具回执如何对应旧任务、记忆和知识索引能否重建、权限策略怎样表达，以及新平台能否继续查询旧审计记录。只导出聊天消息，会丢失许多实际运行所需的信息。

可以把迁移边界分为四组：任务定义与依赖版本，持久状态与业务效果账本，身份授权与凭证引用，评测样本与观测证据。对每组指定权威来源和导出方式。凭证通常需要在新环境重新配置或交换，不应为了“完整迁移”明文打包密钥。

迁移验证要覆盖语义差异。例如旧平台工具超时后不自动重试，新平台默认重试三次；接口能连通，却可能产生重复动作。旧任务在等待审批时切换，新系统是否仍绑定原方案和授权范围，也需要专门验证。

稳妥做法通常是先迁移只读任务，以固定样本比较结果和成本；再小流量迁移新任务；对在途任务选择旧平台完成或明确迁移状态。双跑有副作用的业务不能双重提交，可用隔离环境或只让一个执行路径拥有写权限。最后核对工件、效果和审计记录，再下线旧系统。

2026年的产品退出与框架承接说明，平台生命周期会变化。通用工具协议有助于迁移，但无法自动搬走业务状态和治理责任。长期可保留的资产，是清楚的业务契约、可重建的数据、独立评测和可核对的效果记录；无需为了规避锁定而预先重造全部托管能力。

<h2 id="q-027">面试问题：Dify、Coze、Copilot Studio、Vertex AI Agent Builder、Bedrock Agents 适合什么场景？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这些平台都能帮助构建Agent，但接入生态、部署方式和运行责任不同。选型应以实际版本和区域能力为准，下面按2026年11月25日已核对的官方资料说明定位。

<div align="center">

| 平台或路线 | 适合优先评估的需求 | 需要核实的条件 |
| --- | --- | --- |
| Dify | 可视化工作流、RAG、模型与工具集成、自托管应用 | 社区与企业版的身份治理差异，插件和沙箱运维 |
| Coze Studio及相关商业服务 | 可视化Agent、应用、知识库与工作流 | 开源部署与商业服务功能差异，连接器、凭证和公网暴露 |
| Copilot Studio | 与Microsoft业务生态结合的Agent和工作流 | 所选Harness、授权、连接器、发布渠道与计费 |
| Google Agent Platform路线 | Google Cloud中的构建、运行、身份、检索与治理 | 当前产品入口、区域、组件组合和数据边界 |
| AWS AgentCore路线 | 在AWS托管自定义Agent及配套运行能力 | Runtime、身份、网关、记忆等服务的组合与成本 |

</div>

几个名称变化需要说清楚。原Vertex AI Agent Builder相关文档目前转向**Gemini Enterprise Agent Platform**，官方将其描述为Vertex AI的演进路线，涵盖ADK、Agent Runtime、身份、注册目录和评测等能力。不能继续把旧名称对应的功能表当作永远不变的合同。

Amazon Bedrock Agents现称**Agents Classic**，官方页面说明自2026年7月30日起不接受新用户，已有用户可以继续使用。新项目应评估AgentCore的托管Harness或自定义框架运行路线；它提供模块化运行与治理能力，与Classic不是同一个服务。迁移指南也明确，部分编排与输入收集行为需要重新实现，不能假定接口与状态直接兼容。

Dify和Coze Studio都提供自托管路线，但自托管不代表所有企业能力免费具备，也不代表部署后已完成隔离。Copilot Studio同样不能只概括成“聊天机器人搭建器”，当前文档包含工作流与不同Harness，能力和计费随选择而变。

最好让候选平台完成同一项真实任务，并测试权限撤销、断线恢复、版本升级、结果导出和费用归属。云生态已有投入会影响收益，但不应让团队忽略具体业务约束。

<h2 id="q-028">面试问题：如何回答“请设计一个企业级 Agent 平台”？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

回答平台设计题，可以从一个足够具体的业务切入，再抽象共享能力。先说明服务谁、允许做什么、怎样算完成，架构才有可评价的目标。

以课程服务平台为例：它回答课程规则、查询实时场次、保存经确认的偏好，并在有效授权内提交预约。成功标准包括规则有依据、名额来自实时服务、预约有业务回执，且不会跨用户访问或重复扣减。面试时应替换成自己实际参与的业务，明确个人职责。

一条请求可以这样展开：入口认证并创建任务；意图路由选择咨询或预约流程；知识与记忆提供有限上下文；Runtime调用模型和工具；工具适配器注入可信身份；预约服务在事务内执行；事件与回执更新任务，前端展示结果。Builder、Registry、模型网关、发布与观测则为多个应用提供共同能力。

接着解释最关键的两个失败场景。第一，预约成功但响应丢失，系统进入结果核对，依据幂等意图查询，避免再次占位。第二，用户修改场次，旧方案的确认失效，重新校验并根据授权范围决定是否再次确认。这能说明模型理解、流程状态与业务事务各自承担什么责任。

最后给出建设顺序与验证方法。先完成窄场景、基线和真实工具集成，再把重复出现的身份、任务、工具和观测能力抽成平台。报告有样本数和口径的成功率、失败类型、完成时延、审核成本与费用；没有线上数据就明确是离线实验，不虚构并发或商业收益。

一个可信的设计还应说明哪些能力暂时没有必要独立建设，以及未来如何扩展。平台的成熟度体现在边界清楚、证据可核对、故障可处理，框图层数本身不能说明这些能力。

## 高频速记

1. 应用定义业务目标与验收，平台沉淀可复用的构建、运行和治理机制；成熟应用也可以具备完整治理。
2. 控制面管理期望配置，执行面落实真实访问与动作；撤权必须到达在途任务和缓存后的执行入口。
3. Builder产出可版本化的定义，Runtime推进任务，AgentOS描述系统环境，AgentOps负责持续质量与运营。
4. 可发现、已审核、可调用是不同状态；协议兼容和目录上架都不能替代授权。
5. 会话、任务、记忆、知识与业务结果先逻辑分离，再按访问模式决定存储，避免多个权威写入点。
6. 用户代理型Agent受委派范围约束，独立服务任务需明确服务主体授权；身份认证不等于动作批准。
7. 低代码能否生产落地，取决于具体版本的状态、权限、扩展与发布能力。
8. 收益要扣除审核、返工、运行和维护成本；生成更快不必然节省完整任务成本。
9. 确认绑定具体方案，业务成功依据回执；已有有效授权不需要机械重复确认。
10. 长任务独立于连接存在，取消、超时与业务效果分别核对；通知失败不应重跑整个任务。
11. 模型路由比较整条路径的质量、成本与延迟，版本回滚还要考虑旧任务和数据Schema。
12. 产品生命周期会变，迁移需保住状态、权限、效果账本与评测证据，接口兼容只是其中一层。
