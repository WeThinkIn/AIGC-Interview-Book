<h1 id="q-001">1. AIGC 时代 AI Agent 的本质是什么？</h1>

<h2 id="q-101">面试问题：Agent 的目标、行动与反馈分别意味着什么？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

**Agent 围绕目标选择行动，并根据环境反馈调整后续行为。** 在本板块讨论的大模型 Agent 中，模型主要承担理解与决策，宿主程序负责执行、保存状态和施加约束。这个定义并不要求每个系统都有独立规划器、长期记忆库或多个角色；没有这些模块，也可能构成有效的行动闭环。[1]

三个概念需要落到可检查的对象上：

- **目标**是希望达到的状态，以及不能违反的条件。例如“找到周三晚的课程并完成预约，费用不超过 200 元”，包含日期、预算和预约成功的判据。
- **行动**是当前可采取的操作。查课表获得新信息，提交预约改变业务状态，向用户询问缺失时间也是推进任务的一种方式。
- **反馈**是操作后得到的观测，例如查询结果、库存冲突、预约编号或用户澄清。它可以推翻之前的判断，而不只是给下一轮提示词增加文字。

可用一个简化决策关系理解它：

```math
a_t\sim\pi_\theta(\cdot\mid g,c_t),\qquad
o_{t+1}=\mathrm{Observe}(\mathrm{Execute}(a_t)),\qquad
s_{t+1}=\mathrm{Update}(s_t,a_t,o_{t+1}).
```

这里 $`g`$ 是目标与约束，$`s_t`$ 是运行时保存的状态，$`c_t`$ 是本轮提供给模型的上下文，$`a_t`$ 是行动提案。模型只能根据当前可见信息决策；上下文不一定等于完整历史，也不一定包含环境的全部真实状态。执行器还要拒绝不合法的提案，式子省略了这一步的内部细节。

例如预约接口超时后，“没看到成功响应”只能证明结果未知，不能直接证明预约失败。合格的 Agent 应查询这次请求的业务结果，再决定继续、等待或停止。判断一个系统是否具备 Agent 能力，关键看它能否利用反馈修正行动，以及最终交付是否满足目标，而不是是否输出了长篇计划。

<h2 id="q-002">面试问题：Agent、Chatbot、Workflow、Copilot 有什么区别？</h2>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

这些概念描述的维度不同：Chatbot 主要描述交互形式，Workflow 描述控制流程，Copilot 描述人与系统的协作关系，Agent 描述根据目标和反馈选择行动的方式。它们可以出现在同一个产品里。[1]

<div align="center">

| 概念 | 主要由谁决定下一步 | 典型使用方式 | 需要检查的边界 |
|---|---|---|---|
| Chatbot | 对话逻辑或模型 | 解释概念、回答问题，也可带查询工具 | 有聊天界面不等于具备持续执行能力 |
| Workflow | 程序定义的分支与状态转换 | 审批、报销、订单处理 | 可以包含模型节点、循环和条件分支，并非只能直线执行 |
| Copilot | 用户持续掌握主要操作节奏 | 代码建议、文稿修改、辅助分析 | 人在场也可能误批，仍需清楚展示变更 |
| Agent | 模型在运行时约束内动态选择部分行动 | 排查故障、调查资料、完成开放任务 | 动态决策不等于拥有无限权限 |

</div>

以退款业务为例：“解释政策”适合问答；“核验订单、检查资格、提交退款”可以是固定工作流；遇到订单缺失、物流异常或多个冲突证据时，可以让 Agent 调查原因，再把提交动作交给确定性业务服务。客服人员也可以作为 Copilot 的使用者审核整个处理过程。

因此，不宜按“Chatbot 最低级、Agent 最高级”选架构。规则稳定且验收清楚的环节，固定流程往往更便宜、更可预测；需要根据未知信息改变路径的环节，才更能体现 Agent 的价值。实际设计可以用工作流规定可到达的状态，让 Agent 在某个状态内选择调查方法。

一次工具调用也不能单独判定自主程度。需要继续追问：工具是用户明确指定、程序固定调用，还是模型根据反馈选择？失败后由谁决定下一步？完成由什么证据确认？这三点比产品名称更能说明系统结构。

<h2 id="q-003">面试问题：AI Agent 的核心技术栈如何拆解？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐⭐ (5/5)**

可以沿着一次任务的数据流拆解技术栈：**先明确目标与证据，再组织决策和执行，最后核对结果。** 模块是否独立部署是实现选择，职责之间的边界则必须清楚。

<div align="center">

| 层次 | 保存或处理什么 | 典型失效 |
|---|---|---|
| 接入与身份 | 用户、租户、任务请求、附件 | 把聊天中自报的身份当成可信身份 |
| 上下文与知识 | 指令、检索证据、相关历史、工具说明 | 过期规则或无关内容挤掉关键约束 |
| 模型与决策 | 解释请求、选择工具、提出计划 | 参数正确但选错资源或目标 |
| 运行时与工具 | 调用、状态转换、等待、取消、重试 | 超时后重复执行写操作 |
| 业务与存储 | 库存、账户、订单、任务记录 | 模型文字与实际业务结果不一致 |
| 评估与观测 | 完成判据、轨迹、成本、失败原因 | 只评价回答流畅，漏掉执行错误 |

</div>

权限、预算和审计贯穿这些层，不能只在最终输出前检查。规划和记忆也不是固定必须外接的服务：短任务可能只需一个状态对象，长任务才需要独立的计划、检查点和持久化记忆。

仍以课程预约为例，知识库提供退改规则，查询工具提供实时名额，经过确认的记忆提供时间偏好，模型提出候选方案，运行时管理确认与提交，预约服务通过事务产生最终回执。每个数据来源都应说明“谁负责维护、何时有效、谁能修改”。偏好不能替代库存事实，任务摘要也不能替代业务回执。

跨模块可以使用 `request_id、tenant_id、session_id、run_id、tool_call_id` 关联事件，但这些 ID 只是定位手段，不能自动提供授权或事务一致性。好的设计能回答：这一笔操作是谁授权的，使用了哪个版本的规则，工具到底有没有生效，以及恢复时会不会重复提交。更完整的平台设计见 [第 07 章](07_企业级Agent平台与产品落地高频考点.md)。

<h2 id="q-004">面试问题：为什么 2025-2026 年 Agent 从 Demo 走向工程系统？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

2025—2026 年，Agent 工程的重要变化，是把模型决策放进可以持续运行、观测和恢复的系统。它不意味着行业已经普遍完成生产部署；更准确的判断依据，是公开接口和框架开始明确承担哪些运行职责。[1,2,3]

**第一，行动接口更清楚。** 工具调用把自然语言意图转为结构化提案，协议进一步规定发现、请求和响应。但结构化参数只能减少格式歧义，业务授权、资源存在性和交易约束仍由服务端处理。

**第二，任务持续时间变长。** 仓库修改、数据调查和多阶段业务流程可能跨越模型上下文、连接甚至进程的生命周期。系统因此需要持久化状态、后台任务、取消和恢复。仅在内存里保存聊天消息，无法可靠支持这类任务。

**第三，评测开始进入真实执行环境。** 编码任务可检查补丁与测试，浏览器任务可检查网页或数据库状态，工具业务可检查规则遵循与最终结果。反馈更具体，但也暴露出环境不稳定、测试覆盖不足和评测数据泄漏等问题。

**第四，运行能力逐渐形成可复用基础设施。** 例如 LangGraph 将状态图、检查点和人工中断作为显式能力；OpenAI 当前文档区分应用内 SDK、直接模型接口和托管运行服务。它们反映的是控制流、状态和执行环境需要有明确归属，不是所有框架都具备同一套能力。

企业最终需要验证的仍是业务结果：完成率能否持续、错误是否可追溯、成本是否合算、故障能否恢复。一个演示成功只能证明某条路径可行；在权限不足、数据冲突、依赖超时和用户中途修改需求时仍能正确处理，才更接近可交付的工程系统。

<h2 id="q-032">面试问题：提示词问答、RAG、工具调用和 Agent，这几种应用方式有什么区别？</h2>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

可以从两个问题区分这些应用方式：**回答需要什么外部证据，任务需要改变什么外部状态？** 提示词、RAG、工具调用和 Agent 是可组合的能力，不是必须按顺序升级的四代产品。

提示词问答把指令、问题和示例直接交给模型，适合一般解释、改写和边界明确的推理。RAG 先检索证据，再让模型回答，适合事实来自持续更新的文档或知识库。工具调用让程序查询、计算或执行业务动作，其中检索工具本身也可以是 RAG 的一部分。Agent 再根据已得到的反馈，决定是否继续查、换一种方法、执行或结束。

例如“什么是课时有效期”可以直接解释；“我们机构的退课规定是什么”需要检索有效制度；“今晚还有几个名额”需要实时接口；“找出符合我的时间、预算和前置课程要求的选项，并在授权后预约”需要把多种证据与执行步骤组织起来。最后一个任务也可以由确定性工作流承载，不必把每个判断都交给模型。

选型时应看不确定性出现在哪里：如果只是输入表述不同，用模型提取字段后走固定流程即可；如果调查路径取决于途中发现的事实，动态决策更有价值；如果输出会影响外部业务，就必须有独立于生成文字的验收。

它们也有不同的最低成本基线。没有检索需求时增加向量数据库，不会自动提高答案质量；不需要动态路径时加入多轮 Agent，只会增加失败机会和延迟。先比较同一任务下的准确率、执行成功率和人工处理时间，再决定是否增加系统复杂度。

<h1 id="q-005">2. Agent 的基本运行循环是什么？</h1>

<h2 id="q-102">面试问题：怎样把模型决策组织成可控的执行循环？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

运行时需要把“模型建议做什么”转成明确的状态转换。一个常见循环是：构造当前上下文，获取行动提案，验证并执行，读取结果，更新任务状态，再判断继续还是结束。**模型停止生成、工具返回和任务完成，是三个不同事件。**

<div align="center">

![Agent运行时把决策、执行与结果核对组织为闭环](imgs/agent-engineering-80-20261014/01_Agent运行时的决策执行与验收.png)

</div>

图中“校验并执行”由程序完成，“核对反馈”应包含工具回执或权威业务状态。它是一种职责划分，不要求系统一定由五个独立服务实现。

实现时至少区分三类信息：本轮可见上下文、持久化任务状态、真实环境状态。模型可能只看到搜索摘要，运行时仍要保存完整结果的引用；任务记录写着“提交中”，业务系统可能已经成功，需要进一步对账。

可将一次工具动作分成以下步骤：

1. 解析名称与参数，检查类型、范围和前置条件。
2. 验证当前身份、资源权限、预算和有效授权。
3. 为写操作准备业务请求标识，记录提交尝试，再执行。
4. 将返回值规范化为成功、确定失败或结果未知，保存证据。
5. 根据新状态继续决策；满足完成判据才进入成功终态。

停止条件也要区分语义。成功、取消、不可恢复失败、预算耗尽和等待用户输入不能统一写成 `done`。例如等待确认应保存可恢复状态；预算耗尽应交付已完成部分和剩余事项；取消请求应传播到尚未完成的工具，同时核对已经发生的副作用。

在这个基础上，才适合讨论最大轮数或模型策略。轮数限制能防止无限运行，却不能证明任务完成，也不能修复重复提交。状态机与恢复的实现见 [第 03 章](03_Agent设计模式与工作流编排高频考点.md#q-024)。

<h2 id="q-006">面试问题：ReAct、Plan-and-Execute、Reflection、Tree-of-Thought 如何对比？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这些模式分别处理不同的不确定性：ReAct 帮助边查边做，Plan-and-Execute 管理任务依赖，Reflection 利用反馈修正策略，Tree-of-Thought 比较多个候选推理路径。它们可以组合，也都不能单凭名称保证可靠性。[1]

<div align="center">

| 模式 | 改变了什么 | 适合的任务结构 | 主要代价或失效 |
|---|---|---|---|
| ReAct | 推理与环境行动交替 | 下一步取决于刚获得的事实 | 容易重复调查或忽略全局依赖 |
| Plan-and-Execute | 先形成步骤，再执行和重规划 | 子任务较多且依赖需要协调 | 过早固定计划会把错误假设传到后续 |
| Reflection | 根据反馈形成修订建议 | 失败原因可以被识别并用于下一次尝试 | 没有新证据时可能反复改错或迎合自评 |
| Tree-of-Thought | 生成、评价和搜索多条中间路径 | 候选状态可比较，搜索预算允许 | 评估器错误会把搜索引向错误分支 |

</div>

例如修复软件故障，可以先列出“复现、定位、修改、验证”的依赖；定位阶段用 ReAct 搜索文件并运行诊断；验证失败后根据真实报错反思。只有当存在几种代价相近且可验证的方案时，才值得额外做分支搜索。

反思更适合有编译器、测试或业务规则提供外部反馈的情形。让同一模型重复评价自己的答案，并不会自然产生独立证据。树搜索也要区分“在内存中探索候选方案”和“对真实环境执行动作”：可以回退一个候选文本，不代表可以撤销已发送的邮件。

多 Agent 是任务分工和协调方式，可以在上述模式内使用。它是否有益，要看并行收益、上下文隔离和专业化能否抵消通信与合并成本。各模式的完整机制与边界见 [第 03 章](03_Agent设计模式与工作流编排高频考点.md)。

<h2 id="q-007">面试问题：Function Calling、Tool Use、Structured Output 有什么区别？</h2>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

**Structured Output 约束表达结构，Function Calling 表达动作提案，Tool Use 描述更广的工具交互。** 三者有关联，但不处于同一个抽象层。[4]

Structured Output 可以要求回答包含 `summary、evidence、confidence` 等字段。在支持严格约束的接口中，它能减少缺字段或类型错误，但不保证 `evidence` 对应真实来源，也不保证业务结论正确。还要处理接口支持范围、拒绝和输出不完整等情况。

Function Calling 通常让模型返回工具名称、参数与调用标识。宿主收到提案后，验证参数和权限，执行真正的函数，再将结果与原调用关联交回模型。对应用定义的函数，模型并没有直接连到数据库；托管工具则由服务方实现执行层。需要按具体 API 区分两条路径。

Tool Use 包含这些函数调用，也包括浏览器交互、代码执行、文件操作和搜索等能力。有的工具接受结构化字段，有的通过专门动作协议传递输入。是否采用 JSON Schema，不改变“执行必须有清楚权限和结果”的要求。

例如模型生成 `create_booking(course_id="C12")`，只代表提出预约 C12。服务端还要确定真实用户、验证课程状态、费用、授权版本和幂等键。只有预约服务返回可核实的编号，才可以告诉用户预约成功。

从工具调用扩展到 Agent，还要增加持续状态、根据反馈选择下一步、预算与停止条件、结果验收。一次格式正确的函数调用，只覆盖了闭环中的一段。协议层的完整说明见 [第 04 章](04_MCP与A2A协议高频考点.md)。

<h2 id="q-008">面试问题：工具 Schema 设计有哪些高频坑？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

好的 Schema 应让模型容易提出正确动作，也让执行器能明确拒绝不合法请求。它同时服务于模型理解和程序验证，不能只照搬数据库表字段。[4]

先把动作定义清楚。例如 `query_orders` 与 `submit_refund` 分开，比一个接受任意 SQL 的万能工具更容易限制副作用。描述应说明什么时候使用、需要哪些前置事实、结果有什么含义；但“仅供管理员使用”写在描述里并不会自动产生权限保护。

参数要表达真实业务约束。金额需要币种和单位，时间需要时区，资源需要稳定标识，枚举应有明确含义。字段可省略、允许 `null` 和字符串为空是三种不同状态；某些严格 Schema 接口还有额外约束，应按其支持的 JSON Schema 子集验证。嵌套结构不是越浅越好，关键是复杂度是否对应真实业务对象。

<div align="center">

| 常见设计 | 为什么容易失败 | 改进方向 |
|---|---|---|
| `amount: number` | 无法判断元、分或币种 | 显式金额单位，必要时使用整数最小货币单位 |
| `user_id` 由模型任意填 | 用户身份可能被伪造 | 从可信会话绑定，模型只选择授权范围内资源 |
| `action: string` | 允许凭空编造操作名 | 用明确动作或有限枚举 |
| 只返回 `failed` | 不知道能否修参数、重试或查状态 | 返回错误类别、可恢复信息和请求标识 |
| 一次写操作接受无限列表 | 影响范围不可控 | 限制数量，提供预览和分批策略 |

</div>

返回值同样属于契约。应区分“没有匹配结果”“服务失败”“仍在执行”，保留来源、版本和必要的分页信息。对写操作，还需知道请求已受理还是已完成。模型能生成合法 JSON，只证明语法或类型这一层通过；资源权限、库存约束和授权有效期仍要在执行端检查。

<h2 id="q-009">面试问题：Agent 如何选择工具、调用工具并处理工具失败？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

工具使用可以拆成发现、选择、填参、执行和核对五段。每段需要不同的证据：发现依赖能力目录，选择依赖当前目标，填参依赖上下文事实，执行依赖权限与环境，核对依赖真实结果。

工具较少时可以直接提供完整定义；工具很多时可先检索相关能力，再加载具体 Schema。动态发现能减少无关说明进入上下文，但目录筛选不能替代授权检查。没有被展示的工具不应成为旁路；即使模型知道工具名，执行端也要重新检查当前权限。

失败处理应从**是否已经产生外部效果**开始判断：

<div align="center">

| 反馈 | 合适的下一步 | 不应直接推断什么 |
|---|---|---|
| 参数格式不合法 | 依据错误修正字段 | 不应改写用户意图来凑齐参数 |
| 权限不足 | 核对授权范围，必要时请求合法授权 | 不应换接口绕过同一资源限制 |
| 查询服务暂时不可用 | 有限退避、缓存降级或稍后重试 | 不应把旧缓存当成实时结果 |
| 写请求超时 | 用业务请求标识核对执行状态 | 不应默认未生效并创建第二笔操作 |
| 明确业务冲突 | 更新环境事实并重规划 | 不应靠机械重试消除库存或规则冲突 |
| 返回结果与目标不符 | 检查选择、参数和证据链 | HTTP 200 不等于完成用户任务 |

</div>

重试还需要限制次数、总时长和预算，并区分原动作重试与新动作。某次查询失败后换一个数据源，可能合理；某次付款结果未知后换一个支付接口，可能造成重复扣款。最终输出应准确说明成功、失败、等待或结果未知，保留可继续核查的标识。

<h2 id="q-010">面试问题：Agent 为什么需要 Human-in-the-loop？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Human-in-the-loop 是在确实需要人的判断、责任或授权时，把任务交回给合适的人。人的参与可以发生在目标澄清、方案审核、异常处理和最终验收，不必变成每一步都点击确认。[1,3]

首先区分两种交互。**补充信息**解决“系统不知道应该做什么”，例如两个日期都符合用户描述；**授权**解决“系统知道动作，但需要有权主体允许执行”。权限缺失不能靠让用户随口说一句“继续”解决，审批者必须本身有相应权限。

好的确认界面应展示具体结果或变更，例如待发送邮件的收件人和正文、文件 diff、预约日期与费用，而不只是询问“是否允许 Agent 工作”。批准应绑定动作、资源范围和版本；若执行前价格、收件人或操作内容发生实质变化，就需要重新判断原授权是否仍然覆盖。

对于已经明确授权的低风险动作，可以继续执行，不应反复要求用户确认。对于长任务，则应把等待状态持久化，允许用户稍后回复、拒绝或修改，并保证旧审批不会误用于新方案。

人审也有成本和局限：过多弹窗会让用户机械同意，含糊的总结会掩盖真实影响，审批之后环境还可能变化。因此人工确认应与服务端检查协同。审批表示允许尝试某个方案，不能替代提交时的库存、权限、版本和事务约束。

判断是否需要人工介入，可以综合错误影响、可逆性、信息不确定性和已有授权。目标是把有限的人类注意力放在最能改变结果的地方，而不是用“有人点过确认”替代系统设计。

<h1 id="q-011">3. MCP 为什么成为 Agent 工具生态的重要协议？</h1>

<h2 id="q-103">面试问题：标准协议对 Agent 工具生态有什么价值？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

协议标准化的主要价值，是减少应用与外部能力之间重复实现的接口工作，并让双方能明确协商支持什么。MCP 面向工具、资源和提示模板的接入，A2A 面向独立 Agent 服务之间的消息、任务和产物交换。[5,6]

假设有 $`m`$ 个应用、$`n`$ 个数据或工具系统，每一对都单独适配，最坏情况下需要维护 $`m\times n`$ 条集成关系。若双方都遵守公共协议，可将不少重复工作集中到应用侧客户端和服务侧适配器。这只是接口复用的示意，真实成本还包括认证、数据语义、版本、测试和业务差异，并不会严格变成某个固定线性公式。

以企业文档系统为例，标准服务器可以统一暴露资源与检索工具，不必为每个 Agent 产品重复编写请求格式。宿主仍要决定哪些能力可以展示给用户、哪些结果可以进入上下文，以及如何处理敏感数据。协议通常不会替企业决定这些规则。

标准化也提供了可检查的失败边界：能力是否协商成功，工具 Schema 是否兼容，响应是否匹配请求，权限是否属于当前调用方。相比直接把各种接口细节塞进提示词，问题更容易定位。

但“接得上”与“用得对”仍是两层能力。两个系统都支持 MCP，不代表它们支持相同扩展；同一个工具在两个企业中也可能有完全不同的授权和业务语义。选择协议应以复用收益与互操作需求为依据；只有一个简单内部接口时，直接函数调用通常已经足够。架构细节见 [第 04 章](04_MCP与A2A协议高频考点.md)。

<h2 id="q-012">面试问题：MCP 和 Function Calling 的区别是什么？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

**Function Calling 连接模型的决策输出与应用执行器，MCP 连接宿主应用与外部能力服务。** 一次实际工具操作可以同时经过这两层。[4,5]

典型过程是：宿主通过 MCP 获取工具描述，将适合当前任务的定义映射到模型接口；模型返回函数调用提案；宿主校验后向 MCP Server 发起工具调用；服务器访问实际业务系统；宿主把结果交回模型。模型通常不负责维护 MCP 连接，也不是直接把 JSON-RPC 消息发到业务服务器。

<div align="center">

| 维度 | Function Calling | MCP |
|---|---|---|
| 主要问题 | 模型怎样表达想调用哪个函数及其参数 | 应用怎样发现和使用标准化外部能力 |
| 主要参与方 | 模型 API、宿主和执行器 | Host 中的 Client 与 Server |
| 工具来源 | 可以是本地实现、远程 API 或其他适配器 | 由 MCP Server 暴露 |
| 除执行外的能力 | 取决于模型接口和应用实现 | 还包含资源、提示模板以及经协商的其他能力 |
| 不自动保证的内容 | 参数语义、授权、真实执行成功 | 工具可信性、业务正确性、跨服务事务 |

</div>

因此，MCP 并不替代模型的工具选择能力；Function Calling 也不负责标准化所有外部连接。对于一个查天气接口，应用自行包装函数就很直接；当多个客户端要共享同一批企业能力时，MCP 的接入复用价值更明显。

还要留意数据转换。MCP 返回内容可能包含文本、结构化结果或资源引用，模型接口不一定原样支持，宿主需要保留关键状态与证据。适配时若把“异步受理”压成“成功”，即使两层协议都合法，Agent 仍会错误宣布任务完成。

<h2 id="q-013">面试问题：MCP 的 stdio、Streamable HTTP、SSE 传输如何选择？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

选择传输方式时，先判断服务器是由客户端启动的本地进程，还是独立运行、被多个客户端访问的服务。**SSE 是一种服务器向客户端传送事件的机制，不能把它与 Streamable HTTP 当成完全互斥的能力。**[5]

<div align="center">

| 方式 | 通信与生命周期 | 典型使用位置 |
|---|---|---|
| stdio | 客户端通常启动服务器子进程，经标准输入输出交换消息 | 本机 CLI、开发工具、随客户端管理的服务 |
| Streamable HTTP | 独立服务通过 MCP HTTP 端点处理请求，按需返回 JSON 或 SSE 事件流 | 远程、多客户端和服务化部署 |
| 旧 HTTP+SSE 传输 | 旧规范的独立 SSE 与消息提交端点组合 | 兼容仍未迁移的旧客户端或服务器 |

</div>

Streamable HTTP 已取代旧 HTTP+SSE 作为推荐 HTTP 路线，但它本身仍可以使用 SSE。是否支持会话、事件恢复、流式结果或特定能力，要依据协商版本与服务实现，不能仅看连接使用了 HTTP。

stdio 的部署简单，但服务器是本地可执行程序：依赖包、启动参数、工作目录和继承的环境变量都影响权限。协议输出应走 stdout，调试日志通常走 stderr，避免日志混进消息流。它也不因“本地”就天然安全。

HTTP 服务则需要处理认证授权、Origin 校验、连接中断、代理和负载均衡。本机专用服务通常绑定回环地址；真正需要远程访问时，应按部署拓扑配置身份与网络边界。仅验证请求来自 localhost，不能防止所有浏览器或 DNS rebinding 风险。

传输恢复与业务恢复还要分开：重新收到某段事件，不代表应该重新提交对应动作；连接恢复成功，也不证明之前的写操作没有生效。协议与幂等的进一步设计见 [第 04 章](04_MCP与A2A协议高频考点.md#q-014)。

<h2 id="q-014">面试问题：A2A 和 MCP 分别解决什么问题？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

MCP 和 A2A 都帮助系统互操作，但关注的服务契约不同。MCP 让宿主发现和调用工具、读取资源；A2A 让调用方把任务交给一个独立 Agent 服务，并交换消息、状态和产物。[5,6]

例如一个采购助手可以通过 MCP 查询内部库存，再把“调查几家供应商的交付风险”委托给远程调查 Agent。后者可以在自己的系统里选择模型和工具，返回阶段状态及报告。调用方不必掌握它的内部推理流程，但必须能判断返回的产物是否满足约定。

<div align="center">

| 关注点 | MCP | A2A |
|---|---|---|
| 主要抽象 | 工具、资源、提示模板和协商能力 | Agent 能力、消息、任务、状态、产物 |
| 通常由谁掌握业务执行细节 | 工具服务器提供受定义的能力 | 远程 Agent 自己组织内部工作 |
| 常见交互 | 查询数据、读取上下文、执行动作 | 任务委托、澄清、进度更新、结果交付 |
| 共同需要 | 身份、授权、版本、错误处理、成本边界 | 身份、授权、版本、错误处理、成本边界 |

</div>

这个区别不能简化为“短任务用 MCP，长任务用 A2A”。MCP 的扩展也可能支持长运行任务，A2A 也可以立即返回消息；应该看外部暴露的是工具能力契约，还是一个独立任务承担者。

同一应用中的子 Agent 可以通过函数、消息队列或图状态通信，并不一定要经过 A2A，也不一定运行在同一个进程。只有需要跨实现、跨服务的互操作时，引入标准协议才更有收益。远程委托也不转移最终责任：调用方仍需跟踪授权范围、超时、取消和交付验收。

<h2 id="q-015">面试问题：AGENTS.md、Skills、Memory 文件为什么重要？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这类文件帮助 Agent 获取项目约定、复用任务流程和保持历史连续性，但三者的内容来源与有效范围不同。[7]

`AGENTS.md` 常用于说明仓库的构建、测试、目录约定和协作要求。它随项目演化，适合保存“这个仓库通常怎么工作”。不同产品对查找路径、作用域、覆盖关系和文件名的支持并不完全一致，应按实际客户端解释，不能把某个客户端的规则当成通用标准。

Skill 通常将一类任务的说明、脚本和参考材料组织在一起。渐进式加载先让 Agent 看名称与用途，匹配到任务后再读取正文或所需附件。这样既能复用专业流程，也能减少无关内容进入上下文。Skill 的脚本需要由宿主执行，安装文件本身不等于获得执行权限。

Memory 则用于保存已经确认、以后仍可能有用的信息，例如用户偏好、项目决策与工具经验。它需要来源、范围、时效和更新机制；一次失败尝试不宜直接沉淀成“永远不能这样做”的全局规则。

例如项目说明要求使用某个测试环境，文档导出 Skill 说明 Word 公式如何处理，用户记忆保存偏好的中文术语。三者可以在同一任务中协同，但应分别维护。若项目已更换测试命令，应更新项目约定；不应靠新增一段相互冲突的个人记忆覆盖问题。

文件形式也不构成信任保证。下载的仓库、外部技能包和历史摘要都可能过期或包含恶意指令。系统应区分可信配置与任务资料，按实际授权边界读取和执行，并保留修改与撤销路径。

<h1 id="q-016">4. 当前主流 Agent 框架如何分类？</h1>

<h2 id="q-104">面试问题：如何按运行、编排和接入职责选择 Agent 框架？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

选择框架前，先回答三个问题：**谁运行决策循环，谁保存任务状态，谁负责连接和执行外部能力？** 同一个框架可以跨越多个职责，不宜把项目强行分成互斥类别。[2,3,8]

应用内 SDK 通常提供 Agent、工具、运行器、交接等抽象，适合把 Agent 嵌入已有服务。图式运行时强调状态、节点、控制流、持久化和中断，适合依赖复杂或需要恢复的流程。知识框架更关注文档、索引、检索与证据组织。完整产品或托管服务还可能提供执行环境、会话管理和界面。

以“扫描合同并发起审批”为例，核心难点可能是文档证据和审批状态，而不是多个模型角色。可以使用检索组件处理证据，用状态图组织提取、核对和审批，让模型只处理需要理解的节点。换一个更擅长角色对话的框架，不一定解决审批恢复问题。

评估时可选择一条正常路径和三条故障路径：工具超时、用户修改方案、进程重启。观察框架是否允许清楚表达这些状态，是否能接现有身份与存储，以及是否容易定位失败。如果所有关键逻辑都需要绕过框架，抽象可能没有带来净收益。

还需区分开源库与商业服务。库支持检查点接口，不代表已经部署了高可用存储；能导出 trace，不代表自动满足企业审计要求；支持多模型接口，也不代表模型切换后行为一致。框架定位会演化，生产选型应绑定实际版本、维护状态和部署责任。

<h2 id="q-017">面试问题：OpenAI Agents SDK 的核心能力有哪些？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

OpenAI Agents SDK 的核心作用，是在应用内组织 Agent 循环、工具执行和 Agent 间交接。它提供可复用抽象，部署、业务授权和外部状态仍需由应用负责。当前 OpenAI 文档还区分托管 Agents API 与 Responses API，不能把这些服务的能力全部算作 SDK 自带能力。[2]

一个 Agent 通常定义指令、模型配置、可用工具、交接对象和输出类型。Runner 推动模型调用与工具结果反馈；发生 handoff 时切换到接收方继续循环，得到最终输出、需要等待批准、触及限制或出现异常时再按对应状态返回或暂停。应用仍要为自己的函数工具提供具体实现，指定身份上下文和执行约束。

两个常见协作方式要分清：**把其他 Agent 作为工具调用**时，主 Agent 仍掌握控制权并整合返回值；**handoff** 则把后续处理交给另一个 Agent。比如总客服 Agent 调用税务专家 Agent 获取建议，和把会话后续处理转交售后 Agent，是不同的业务语义。交接也不能自动赋予接收方更多权限。

SDK 的 guardrails 和 tracing 便于在声明的位置检查输入输出、记录调用与交接；覆盖范围取决于具体机制、工具类型和配置，不能假设任何 Shell 或远程副作用都会自动受到同样的拦截。业务侧的对象级授权、幂等与事务约束仍应独立存在。

Session 能帮助保存多轮上下文，但保存历史不等于已经建立了具备事实校验、时效与删除传播的长期记忆系统。输出类型约束同样只处理结构，不替代最终结果核对。

适合的场景是：应用希望保留对运行环境、存储和业务流程的控制，同时复用常见 Agent 循环。如果主要诉求是把运行基础设施交给服务方管理，应另外评估托管运行服务的隔离、状态和计费边界，而不是仅比较 SDK 的函数数量。

<h2 id="q-018">面试问题：LangGraph 为什么适合复杂 Agent 工作流？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

LangGraph 将流程表示为有状态图：节点读取状态并返回更新，边决定控制流，检查点保存执行进度。确定性代码和模型驱动节点可以放在同一张图中；图并不要求全部路径预先固定，也不要求每个节点都是 Agent。[3]

例如处理保险理赔，可以先提取材料，再并行检查保单和票据，汇合后决定是否需要补充信息，最后进入审核。共享状态记录申请编号、证据引用和阶段结果。对于并行更新，还要定义合并规则，避免两个节点覆盖同一字段。

Checkpointer 的意义在于保存线程内的图状态，使中断后能够继续。它与保存跨线程长期信息的 Store 不是同一个东西；内存实现也不会因为叫检查点，就在进程重启后自动保留数据。生产部署需要选择符合持久性与隔离要求的后端。

更容易被忽略的是**恢复粒度**。人工中断恢复时，相关节点可能从头执行，而非从源码中断的那一行继续。因此，节点内中断前的副作用可能重做；即便把写操作放到批准之后，写入成功而检查点尚未保存时发生故障，也可能造成重试。外部系统仍需幂等或去重，长时间等待后还应重新核对价格、库存和权限。

LangGraph 的价值是让这些状态与控制流显式化，方便恢复、观测和人工介入。它不会自动让任意数据库操作具有 exactly-once 语义，也不替应用定义完成标准。若任务只有一次检索和一次生成，普通函数组合可能更清楚；当流程确实具有分支、循环、暂停和恢复需求时，状态图才更能体现优势。

<h2 id="q-019">面试问题：CrewAI、AutoGen、Google ADK、LlamaIndex Agent 如何对比？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

比较框架应看其主要抽象、运行边界和维护状态，而不是给每个项目贴一个永久标签。截至 **2026-11-25**，这些项目的公开文档已经体现出明显的职责重叠。[3,8]

<div align="center">

| 项目 | 值得理解的抽象 | 选型时重点核对 |
|---|---|---|
| CrewAI | Flows 管理事件与状态，Crews 组织角色协作 | 哪些流程交给固定控制流，哪些交给团队式执行 |
| AutoGen | 历史上的事件驱动与多 Agent 对话、AgentChat 等设计 | 官方仓库已标记归档；新项目需核对后继方案及迁移成本 |
| Google ADK | Agent、工作流、工具及会话/产物等服务接口 | 模型与部署支持、状态服务和生态集成边界 |
| LlamaIndex | 数据接入、检索及由工作流组织的 Agent | 证据质量、数据连接和复杂流程的维护成本 |
| LangGraph | 显式状态图、检查点、中断与恢复 | 状态结构、并发更新、持久化与副作用去重 |
| OpenAI Agents SDK | 应用内运行器、工具、handoff、检查与追踪 | 应用需要承担哪些执行、存储和授权职责 |

</div>

AutoGen 的历史机制仍值得学习，但当前仓库已说明不再积极维护，并指向 Microsoft Agent Framework。应保留其研究贡献，同时把维护状态纳入新项目决策；不能继续把旧教程中的定位直接当作今天的推荐。

另一个常见误区是把 ADK 只理解成多 Agent 框架、把 CrewAI 只理解成自由角色聊天。它们也提供工作流或确定性控制结构。反过来，检索框架也能编排动作，状态图也能承载知识型任务。

实际比较最好使用同一组业务任务和故障条件，衡量实现复杂度、恢复正确性、可观测性及迁移成本。支持的功能越多不一定越适合；团队能否用其抽象清楚表达自己的任务，往往更重要。

<h2 id="q-020">面试问题：Claude Code、Codex、Cursor、Devin、Jules 代表什么趋势？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这些产品体现了软件开发工具从局部生成向任务执行扩展的趋势：读取仓库，形成修改方案，编辑代码，运行验证，再交付可审查的变更。不同产品在 IDE、终端、云端任务和协作界面上的侧重点不同，功能也会随版本变化，不能把某一个产品的能力集合复制给所有产品。

这一场景容易形成反馈闭环，因为代码仓库提供了具体对象：文件、依赖、测试、构建结果和版本差异。Agent 可以根据失败测试重新定位，再用 diff 和验证结果说明做了什么。相比只要求写一段看起来正确的代码，任务完成有了更多外部证据。

但可验证不等于已经被充分验证。测试可能覆盖不足，环境可能与生产不同，Agent 也可能修改测试来掩盖错误。仓库级任务还涉及配置、迁移、权限和用户已有改动，不能只检查新函数是否能运行。

可以从四个方面理解产品差异：一是用户在每一步参与多少；二是代码在哪里执行、凭证如何隔离；三是任务能否跨断线和会话持续；四是交付包含补丁、测试、解释还是进一步的发布操作。云端运行不自动更安全，本地运行也不自动更可控，关键是具体的权限与执行边界。

因此，学习编码 Agent 最值得掌握的是仓库检索、最小必要上下文、受控编辑、可恢复执行和验收证据。具体产品可以作为观察这些机制的入口，比较时则应注明版本与公开能力，不推断闭源系统内部架构。完整工程问题见 [第 02 章](02_编码Agent与AgentOS工程高频考点.md)。

<h2 id="q-031">面试问题：预训练、微调和提示词工程有什么区别？</h2>

**难度评分：⭐⭐ (2/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

三者的主要区别，是改变知识与行为的方式，以及改变能持续多久。预训练和微调都会更新模型参数；提示词工程通过当前输入影响输出，通常不更新参数。

预训练在较大规模数据上学习通用表示、语言规律和生成能力，成本与影响范围都较大。微调从已有模型继续训练，可改善特定任务、格式、工具使用或偏好；训练数据的覆盖与质量决定了它能学到什么，也需要检查通用能力是否退化。提示词则组织目标、约束和示例，试验快，但受模型已有能力与上下文容量限制。

以订单助手为例，今天的退款政策改变，优先更新权威文档和检索；某个 API 改了字段，优先更新工具契约；模型长期混淆两种动作且有足够标注数据，才可能值得做行为微调。让训练承担高频业务事实更新，容易产生更新慢、无法追溯和旧知识残留的问题。

上下文内学习是模型利用输入示例调整本次表现，不意味着权重永久改变。把一次经验写进 Memory 或 Skill，也属于外部状态更新。只有之后再次读取并使用它，才可能影响任务；它与参数学习的失效方式、回滚方式不同。

三者可以共同使用，但选用前应先建立可复现的任务集。若错误来自缺证据、错误授权或工具实现，再多训练也不直接解决；若错误稳定来自模型能力，提示词无限变长同样没有保证。先定位误差来源，再选择改输入、改系统还是改参数，能避免把应用工程问题一概变成训练问题。

<h1 id="q-021">5. Agent 为什么需要上下文工程？</h1>

<h2 id="q-105">面试问题：上下文信息如何支撑多步任务？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

上下文工程负责决定当前这次决策能看到什么。它包括获取、筛选、组织和压缩信息，还要保留来源与权限边界。上下文不只是历史消息，也可以包含当前目标、有效约束、工具定义、检索证据、计划和环境观测。[9]

多步任务会不断产生新信息，但这些信息的价值不同。用户的预算上限应持续有效，一次失败搜索的全部网页内容可能不值得保留；刚刚得到的库存信息可能很重要，却很快会过期。简单地把全部历史按时间拼接，既浪费预算，也可能让早期错误假设反复影响后续决策。

以修复登录故障为例，模型本轮可能需要相关调用链、错误日志、复现方式和已经排除的原因，不需要整个仓库所有文件。检索结果应保留路径与版本，日志可先截取错误附近的段落，完整内容留在可再次读取的位置。这样减少输入并没有删除证据，而是改变证据的获取方式。

还需要区分指令与资料。仓库文档可以描述如何构建，网页可以提供某个库的用法，但外部资料中出现的“忽略用户要求”不能因此成为新的控制指令。来源、可信度和使用范围应随内容一起保留。

有效上下文的目标是让下一步决策更准确，而非填满窗口。评估时可比较：移除某段信息后成功率是否下降，加入检索是否减少错误，压缩是否丢掉关键约束，以及同样任务的延迟和费用是否改善。进一步的生命周期与压缩设计见 [第 05 章](05_Agent记忆与上下文工程高频考点.md)。

<h2 id="q-022">面试问题：短期记忆、长期记忆、任务记忆、工具记忆如何区分？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

“短期、长期”描述保留时间，“任务、工具、个人、团队”描述用途或归属，它们不是互斥分类。某条工具经验既可以属于长期记忆，也可以只在一个项目的范围内有效。

<div align="center">

| 视角 | 典型内容 | 应保留的约束 |
|---|---|---|
| 当前工作上下文 | 最近消息、正在看的文件、工具结果 | 受窗口限制，未必是完整记录 |
| 长期记忆 | 已确认偏好、项目约定、稳定知识 | 来源、有效期、用户可修改和删除 |
| 任务状态 | 目标、阶段、请求标识、已完成与未知动作 | 与实际执行一致，支持恢复与核对 |
| 工具经验 | 参数用法、限制、故障处理方法 | 绑定工具版本和环境，防止经验过度泛化 |
| 团队共享知识 | 规范、决策记录、公共操作经验 | 可见范围与维护责任明确 |

</div>

例如用户说“这次不要晚上上课”，它是本次任务约束，不宜自动升级为永久偏好；用户明确要求“以后都优先工作日上午”，才有理由写入相应长期记录。一次工具在旧版本上失败，也不能证明新版永远不能使用。

尤其要把任务事实与叙述性记忆分开。预约请求是否已提交、后台作业是否仍在运行，应保存为可核对的结构化状态；摘要可以帮助模型理解，但不应成为这些事实的唯一记录。

记忆系统因此需要的不只是向量检索，还包括写入判断、冲突处理、范围过滤、版本和删除传播。越是长期保存的信息，越需要防止一次误解在后续任务中持续放大。分类的价值在于指导这些策略，而不是要求每一类都建立一套独立数据库。

<h2 id="q-023">面试问题：Memory 和 RAG 的区别如何快速回答？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

可以快速概括为：**Memory 关注信息为何被保留以及跨任务怎样使用，RAG 关注怎样检索证据来增强当前生成。** 二者存在交集，不能用“一个更新快、一个更新慢”来划界。

长期记忆可以通过 RAG 读取，例如从过去的项目决策中检索与当前修改有关的约束。RAG 也可以查询频繁更新的业务知识；记忆中的某些偏好反而可能长期不变。更新频率由数据本身决定，不由名称决定。

<div align="center">

| 对象或机制 | 主要关心的问题 | 示例 |
|---|---|---|
| 记忆生命周期 | 哪些事实值得保留，谁确认，何时失效 | 用户偏好、团队决策、成功或失败经验 |
| 检索增强生成 | 当前问题需要哪些证据，怎样召回并引用 | 检索制度条款、项目文档或历史记录 |
| 任务状态存储 | 哪些动作已发生，下一步允许做什么 | 预约请求编号、审批版本、后台作业状态 |
| 权威业务数据 | 当前世界中的事实是什么 | 实时库存、账户余额、订单状态 |

</div>

例如用户偏好小班课程，可以作为候选筛选条件；课程制度通过检索得到；是否还有名额则通过实时业务接口判断。偏好不能证明有库存，检索命中的旧订单截图也不能覆盖当前数据库状态。

因此，Memory 与 RAG 的组合应保留信息身份：从哪里来、针对谁、何时有效、能否用于当前任务。若同一个事实同时存在于聊天摘要、记忆表和文档索引中，必须明确哪个版本具有权威性，以及更新和删除怎样传播。具体实现分别见 [第 05 章](05_Agent记忆与上下文工程高频考点.md#q-008) 与 [第 10 章](10_Agent_RAG与混合检索工程高频考点.md)。

<h2 id="q-024">面试问题：上下文窗口溢出时如何处理？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

先控制上下文增长，再考虑压缩已经装入的大量内容。只有窗口快满时才做一次大摘要，容易丢掉此前没有被显式记录的重要状态。[9]

第一层是减少无关输入：文件按范围读取，日志按错误位置截取，搜索结果先返回摘要和定位信息，大工具目录按需发现。第二层是把完整工件保存在文件或对象存储中，模型只保留用途、版本和获取路径。第三层才是历史压缩、检索召回或独立子任务上下文。

上下文预算可以用一个简单约束表达：

```math
B_{\mathrm{instructions}}+B_{\mathrm{state}}+B_{\mathrm{evidence}}
+B_{\mathrm{tools}}+B_{\mathrm{history}}+B_{\mathrm{reserve}}
\le B_{\mathrm{window}}.
```

各项表示指令、状态、证据、工具定义、历史和预留空间的 token 预算。实际可用窗口、输出预留及内部 token 的计费或限制随接口而异，这个式子用于分配思路，不是所有 API 的统一计数公式。

压缩时应优先保留用户目标、仍有效约束、关键决策依据、已完成动作、结果未知的请求和证据引用。长 stdout 可以折叠，但调用与结果之间的关联不能丢；某些 API 要求工具调用消息与对应结果成对，直接截断消息列表可能破坏协议结构。

例如摘要只写“预约没有成功”，就丢掉了“提交超时，尚未核对”的关键语义。恢复后可能重复提交，因此应保留请求标识和结果未知状态。压缩本身也需要评估：用压缩前后相同的后续任务检查约束遵循、事实一致性与恢复行为，而不只看 token 减少了多少。

<h2 id="q-025">面试问题：Agent 如何做自我总结、状态恢复和跨会话连续性？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

可靠恢复需要两类材料：帮助模型重新理解任务的摘要，以及能与真实环境核对的持久化记录。摘要负责解释，状态与回执负责证明，两者应相互对应。

一份可用的恢复记录通常包含：目标与剩余要求、当前阶段、有效约束、关键文件或工件版本、已确认结果、仍在运行的任务标识、结果未知的外部操作、下一步可执行动作。没有必要复制所有对话，但影响下一步决策的证据应可以找回。

恢复过程不能只是把摘要注入模型后继续生成。应先重新检查运行环境：工作树是否被用户修改，引用文件是否仍存在，后台任务是否已结束，权限或业务状态是否变化。对长时间等待的审批，还要核对它是否绑定当前方案。

例如上次执行完测试后用户又修改了文件，旧的“测试通过”只能描述旧版本。系统应比较代码版本或文件哈希，再决定是否需要重新验证。相反，已经提交且有业务回执的写操作，应尽量恢复其结果，避免重新调用。

长期偏好也应按范围重新加载，而非把所有历史内容全部加入新会话。任务特有约束在任务结束后可以失效；稳定项目约定应有明确维护位置；外部来源的不可信文本不能通过摘要变成更高优先级指令。

好的跨会话连续性体现在：能够解释过去发生了什么，知道哪些事实需要重新确认，并从合适的状态继续。它并不要求模型“记住一切”，也不能靠保存一段自然语言总结保证业务恢复正确。

<h1 id="q-026">6. Agent 系统为什么必须重视权限和安全？</h1>

<h2 id="q-106">面试问题：行动能力扩大后，系统需要管理哪些权限风险？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

行动能力使风险从生成内容扩展到外部状态。Agent 可能读到敏感数据，也可能修改文件、提交业务请求或向外发送消息。需要分别管理**访问权、执行权和信息流向**，不能只检查最后一句回答。[5]

以被提示注入的网页为例，网页中的文字可能诱导模型读取本地配置，再把内容作为参数发给外部服务。风险链包含不可信输入、模型决策、文件读取和网络发送几个环节。只过滤最终回答，无法阻止已经发生的数据外传；只关闭某一个工具，也可能留下其他路径。

首先，工具以可信身份执行，用户、租户和资源范围不能由模型自行声明。其次，把可读路径、可写目录、网络目的地和敏感业务动作限制在任务需要的范围内。再次，对重要动作保留授权、参数版本、执行回执和撤销或补偿方式。

权限还要随任务变化。用户撤销授权、任务取消或凭证到期后，排队中的动作不应继续沿用旧权限。子 Agent 或远程服务也不应因为参与同一个任务，就自动继承所有凭证。

沙箱、工具策略、人工审核和审计承担不同职责：沙箱限制进程能访问什么，工具策略约束调用是否被允许，人工审核提供具体授权或判断，审计帮助追溯已经发生的事情。它们可以互补，但没有任何一个能单独保证业务操作正确。

这里的核心是明确每次行动的边界与责任。具体威胁模型、注入防护和上线治理见 [第 06 章](06_Agent安全评测与AgentOps高频考点.md)。

<h2 id="q-027">面试问题：Agent Guardrails 的边界如何快速概括？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Guardrails 是围绕决策和执行布置的检查机制，既可以是确定性规则，也可以是分类器、模型评价、策略引擎或人工审核。不同机制的误报、漏报和执行时机不同，不能把一个“安全模型”当成全部边界。

<div align="center">

| 位置 | 应检查什么 | 检查失败后的动作 |
|---|---|---|
| 输入与上下文 | 来源、敏感内容、指令与资料边界 | 隔离、脱敏、拒绝使用或补充核验 |
| 行动提案 | 参数、身份、对象权限、授权范围 | 拒绝执行或要求修正 |
| 执行过程 | 超时、资源占用、网络与文件访问 | 取消、限流、终止或隔离 |
| 状态写入 | 记忆来源、租户范围、版本冲突 | 阻止污染，保留待核实记录 |
| 输出与交付 | 证据支持、敏感信息、完成声明 | 修正输出或转入人工验收 |

</div>

检查的时序尤其重要。若工具已经把邮件发出，随后输出检查才发现收件人不对，风险已经发生。关键的资源授权和用户确认应在副作用之前同步完成；异步检测更适合告警与复盘，不能冒充事前拦截。

同时要避免把所有工具错误都当成安全事件。库存不足通常是业务冲突，权限不足需要核对授权，格式错误可以修参。准确分类能减少无意义的拒绝，也能防止模型把真正的安全限制误当成需要绕过的技术故障。

效果应同时测量阻止了多少危险行为、误拦了多少正常任务，以及对延迟和成本的影响。不存在只增加一道提示词便完成治理的做法；真正的约束要落实在模型无法通过改写参数绕开的执行边界上。

<h2 id="q-028">面试问题：Agent 可观测性和 tracing 应该记录什么？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Tracing 的目标是重建“这个结果经过哪些可观察步骤产生”，而不是尽可能多地保存原文。一次任务应能关联用户请求、模型调用、工具执行、权限判断、状态变化和最终工件，同时限制敏感数据的暴露。

最低限度可记录任务与调用标识、父子关系、开始结束时间、模型及提示版本、工具名、经过脱敏的参数摘要、错误类别、返回结果引用、费用与 token、审批及取消事件。对业务写操作，应关联业务请求标识和最终回执，便于核对是否真正生效。

例如用户收到“预约成功”，但后台没有订单。通过 trace 可以定位：是模型没有调用提交工具，工具只返回“已受理”，响应映射丢掉了失败状态，还是订单后来被撤销。只保存最终答案无法区分这些原因。

观测边界也要诚实。系统通常能够记录可见输出、工具调用和公开状态，不应声称获得模型隐藏的完整推理过程。即使记录了全部可见消息，也未必能精确复现原行为：远程模型版本、随机性和外部网页都可能改变。可回放的环境与版本快照需要另外准备。

日志本身会成为敏感数据副本，应设置字段级脱敏、访问控制、保留期和删除策略。错误栈、工具 stdout 和检索片段尤其容易夹带密钥或个人信息。必要时保存受控工件引用和哈希，而不把所有原文复制进每个观测系统。

有用的 trace 最终能支持三个动作：定位故障发生在哪一层，构造可重复的回归用例，以及量化改动对成功率、成本和延迟的影响。详细 AgentOps 设计见 [第 06 章](06_Agent安全评测与AgentOps高频考点.md#q-016)。

<h2 id="q-029">面试问题：Agent 常用评测基准有哪些？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Agent 基准的差别主要在环境、可执行动作和成功判据。比较分数之前，要先确认它测的任务是否接近你的业务。[10]

<div align="center">

| 基准 | 主要考察内容 | 外推时的限制 |
|---|---|---|
| SWE-bench 系列 | 针对真实软件问题生成补丁并接受测试 | 数据划分、环境和测试覆盖不同，不能混用分数 |
| WebArena | 网页环境中的多步任务 | 固定网站与真实开放网络有差异 |
| OSWorld | 桌面/操作系统环境中的任务执行 | 环境版本、交互方式和计算预算影响结果 |
| GAIA | 多步推理、检索和工具协作 | 不等于验证生产业务的写操作可靠性 |
| AgentBench | 多种交互环境下的 Agent 行为 | 子环境能力不能由总分完全代表 |
| τ-bench / 后续系列 | 工具、用户交互和领域规则遵循 | 用户模拟、业务规则和环境版本需要固定 |
| HumanEval / MBPP | 相对独立的代码生成与测试 | 只能覆盖编码 Agent 能力的一部分 |

</div>

还要区分两种多次运行指标。`pass@k` 关注多个候选中至少一次成功的机会，适用于允许多次尝试并能挑选正确结果的设置；它并不等于每次都稳定成功。要求同一任务连续多次均成功的可靠性指标更严格，文献中常写作 `pass^k`，其具体估计方法应遵循对应基准。

例如单次成功概率为 $`p`$ 且各次独立同分布时，至少一次成功为 $`1-(1-p)^k`$，全部成功为 $`p^k`$。这个独立性假设只是解释差异，真实运行可能共享错误原因，不能直接当作实测公式套用。

生产评测还需固定预算、工具、权限、重试规则和人工帮助范围，并同时报告完成率、成本、延迟、危险误操作与接管率。公开基准适合比较受控任务；企业仍应有自己的业务任务集，覆盖最常见和影响最大的失败。

<h2 id="q-030">面试问题：如何设计一个企业级 AI Agent 系统？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

设计企业 Agent 时，应先选一条真实业务链路，明确输入、授权范围、完成判据和失败处置，再决定需要哪些组件。以“帮助员工查找合适课程并预约”为例，最终结果应是可核实的预约状态，而不是一段看起来像成功的回复。

**先划分确定性步骤与开放调查。** 身份校验、库存检查、金额计算和提交约束由程序负责；理解自然语言、解释规则、在多个方案间调查可以由模型承担。若只是字段提取加固定流程，没有必要额外增加自由规划。

**再建立证据与动作的接口。** 知识检索提供带来源的规则，实时接口提供当前名额，模型提出候选方案，运行时检查身份、参数与授权，业务服务执行事务并返回回执。MCP 或 A2A 只在确有复用或跨服务互操作需求时引入。

**状态要独立于聊天内容。** 保存当前阶段、确认的方案版本、幂等请求标识和结果未知的动作；用户修改需求时使旧方案失效；连接断开后可查询已有任务，而不是重新开始提交。长期偏好、文档知识和业务数据库分别维护。

**最后定义运行与验收预算。** 设置单任务调用次数、总时长、资源上限和并发策略，记录 trace，建立正常路径和故障路径用例。至少覆盖库存冲突、权限撤销、工具超时、重复消息、用户中途取消及模型错误完成声明。

上线可以从只读查询和建议开始，依据真实失败数据逐步开放写操作。发布的是模型、提示、工具契约、策略与数据版本的组合；回滚模型版本不能撤销已完成的业务交易。系统应同时准备技术回滚和业务补偿路径。

一个设计是否完整，可以用三问检查：正常时怎样完成，失败时怎样知道发生了什么，恢复时怎样避免把错误扩大。平台模块、多租户和具体产品选型见 [第 07 章](07_企业级Agent平台与产品落地高频考点.md)。

## 高频速记

1. Agent 的关键是目标、行动与反馈形成闭环；规划器、长期记忆和多 Agent 都是按需选择的实现。
2. Workflow、Copilot、Chatbot 与 Agent 描述不同维度，可以组合使用。
3. 模型提案、工具执行和任务验收分别负责；格式正确不等于有权限，也不等于业务成功。
4. Function Calling、MCP 和 A2A 处于不同接口层；传输恢复不能替代副作用核对。
5. 上下文服务当前决策，记忆管理信息生命周期，业务事实由权威系统维护。
6. 框架、检查点和沙箱提供机制，授权、幂等、完成判据与运行责任仍需明确设计。
