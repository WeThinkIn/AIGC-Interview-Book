<h1 id="q-001">1. 为什么 AI Agent 需要设计模式？</h1>

<h2 id="q-101">面试问题：模式选择如何服务于任务约束？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

模式选择先看任务的不确定性出在哪里：缺少事实、步骤有依赖、候选方案需要比较，还是多个执行者需要协调。**设计模式的价值，是让一种重复出现的困难有清楚的处理结构。** 模式名称本身既不保证正确，也不证明需要更复杂的系统。[1]

例如查一个订单状态，固定查询和结果核对就足够；排查未知故障，需要根据日志改变下一步调查，可以采用 ReAct；修改多个相互依赖的模块，需要计划管理全局顺序；存在几种可验证的优化方案时，才可能值得搜索多个分支。

选型还要看四个约束：结果能否验收，动作是否可逆，允许多少延迟和费用，故障后能否恢复。同样的搜索机制，在本地候选补丁上可以试错，在真实付款或发信流程中就不能自由展开。任务结构与执行边界共同决定模式，而不是只看问题“难不难”。

不同模式可以分层组合。工作流规定合法状态与关键提交条件，计划维护依赖，局部执行用反馈决定下一步，验证器在有证据时判断结果。若任务只有一次检索和一次回答，不必为了凑齐这些概念分别增加模型调用。

实践中应保留一个简单基线，再观察新增机制解决了什么失败、增加了什么成本。只有在相同任务与预算下改善合格交付，复杂度才有理由留下。跨周期值得学习的是控制流、证据、状态与恢复，具体模式是表达这些机制的工具。

<h2 id="q-002">面试问题：Agent Pattern、Prompt Pattern、Workflow Pattern 有什么区别？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

三类模式分别侧重模型输入、决策与环境交互、程序控制流，边界可以重叠。不要把论文的一个提示方法、一个完整 Agent 架构和一个工作流引擎放在同一层比较大小。

<div align="center">

| 层次 | 主要改变什么 | 典型做法 | 需要额外保证什么 |
|---|---|---|---|
| Prompt Pattern | 单次或若干次调用的指令与示例组织 | 先分解再回答、约束输出、给出示例 | 模型是否理解，内容是否真实 |
| Agent Pattern | 决策、行动、观察与修订的组织 | ReAct、反馈反思、动态任务委派 | 工具权限、执行结果、预算和停止 |
| Workflow Pattern | 步骤依赖、分支与状态转换 | 路由、并行汇合、审批、恢复 | 状态一致性、故障处理和副作用 |

</div>

Self-Consistency 常与提示方法一起讨论，但它还涉及多次采样和答案聚合，不能理解成只加一句“多想几次”。Router 也可以由固定规则、分类模型或 Agent 决定，因此不专属于某一层。

例如修复代码，可以用提示明确修改范围，以 ReAct 调查和验证，再由工作流要求交付前具备补丁与测试证据。是否需要人工审查或创建 PR，由任务授权和团队流程决定，不是所有代码任务的固定结尾。

分层的好处是便于定位故障。输出缺字段，先查格式契约；行动选择错误，查可见证据与策略；重启后重复提交，查运行时与业务幂等。靠修改提示词修所有问题，通常会让提示越来越长而边界仍然模糊。

<h2 id="q-003">面试问题：Agent 和 Workflow 应该如何取舍？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Agent 与 Workflow 的取舍，核心是**哪些决策可以提前写进程序，哪些必须等新证据出现后才能决定**。Workflow 可以有循环、条件分支和模型节点；Agent 也可以在明确的状态范围内行动，两者能够嵌套。[1]

对步骤稳定、规则明确的部分，程序控制流便于测试和审计，例如身份检查、金额计算、订单状态转换。对调查路径依赖未知信息的部分，模型动态选择工具更有价值，例如根据不同报错定位故障，或围绕互相矛盾的文档补充证据。

以退款为例，是否满足退款政策和怎样提交，可以由明确规则与业务接口约束；订单异常的原因可能需要跨物流、客服记录和支付状态调查。可以让 Agent 调查并形成证据，再由工作流推进合规的提交状态。不能因为调查需要灵活性，就把交易约束也交给自由生成。

风险高并不意味着整个任务只能用固定流程，而是关键动作需要更强的验证与授权。风险低也不意味着自由循环更划算：一次可完成的查询，加入多轮规划可能只增加延迟。

实际选择可从简单实现开始，观察哪类例外导致频繁改流程。如果例外仍能稳定分类，增加确定性分支可能更合适；如果每次都需要根据新证据决定路径，可以开放局部动态决策。两层结合时必须明确状态、重试和完成判据的归属，避免各自认为对方已处理失败。

<h2 id="q-004">面试问题：为什么很多 Agent 项目失败在“过度自主”？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

“过度自主”通常指系统开放的决策和行动范围超过了现有验证、恢复与权限能力。它是一类常见失效原因，但没有统一统计足以把所有 Agent 项目失败归因于它。

长任务会放大早期误解。例如用户只要求比较候选供应商，Agent 却自行联系对方、创建采购单，再继续寻找付款方式。后面每一步看似连贯，却已经偏离授权目标。另一种情况是目标没有扩张，但系统反复搜索、重规划，始终缺少可检查的完成条件。

问题不在于模型能否主动推进，而在于系统能否约束“可以决定什么”。先固定目标和不可违反条件，明确工具的资源范围，让每个阶段产生可核查产物；在关键业务动作之前检查前提，在动作之后核对结果。人类介入应放在确实缺信息或缺授权的位置，不必每步确认。

预算也要对应整项任务，包含模型、工具、子任务、重试和等待。达到上限应转入明确终态或可恢复等待，交付已有结果与剩余事项，不能继续创建子任务绕开限制，也不能把预算耗尽写成成功。

最后用故障任务验证边界：目标中途变化、工具返回冲突、写请求超时或权限撤销时，系统是否仍按有效约束工作。限制自主范围可以降低错误扩散，但规则过严也会增加无谓接管，因此应同时观察成功率、危险动作、误拦与人工负担。

<h1 id="q-005">2. ReAct 的核心思想是什么？</h1>

<h2 id="q-102">面试问题：推理与行动交替能解决哪些信息缺口？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

ReAct 将推理与行动交替组织，使下一步决策能够利用刚刚获得的外部反馈。它主要处理两类信息缺口：模型当前不知道的事实，以及只有采取动作后才能观察到的环境状态。[2]

例如查询“某位作者获奖时所在机构”，模型可能先搜索获奖记录，再根据确切年份寻找当时的任职信息。第一次搜索不是为了凑一条引用，而是改变第二次查询的条件。编码排障也类似：运行复现得到错误位置，才能决定读哪条调用链。

论文常用 Thought、Action、Observation 表达过程。工程上可以理解为“基于当前证据选择行动 → 执行器执行 → 读取观察 → 更新状态并再次决策”。它不要求生产接口公开模型的私有思维链；可见动作、参数、反馈和简短决策说明已能构成可审计轨迹。

工具结果也不是天然真相。搜索可能返回过期页面，命令可能只打印部分日志，远程写操作可能结果未知。运行时要保存来源、版本和结果类别，让后续判断能够区分事实、推测与待核实信息。

ReAct 的收益来自反馈改变行动。如果流程和输入已经确定，每一步仍重新询问模型选择相同工具，未必增加价值。它适合有真实信息增量的调查和交互；计算规则明确时，应让代码直接计算，避免用自由文本替代可验证执行。

<h2 id="q-006">面试问题：ReAct 的完整运行循环是什么？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

一个完整 ReAct 循环可以拆成目标与状态准备、行动选择、执行、观察处理和结束判断五步。模型负责提出下一步，宿主负责让提案变成有边界、可追踪的动作。[2]

首先加载当前目标、有效限制、已有证据和允许工具。模型选择行动后，运行时校验名称、参数、身份、资源与授权，再记录调用标识并执行。返回结果需规范化：成功、确定失败、仍在运行或结果未知。将必要观察与原调用关联后，更新上下文及任务状态，决定继续、等待或结束。

例如排查接口超时，读取日志发现数据库连接耗尽，下一步可能检查连接池配置或复现泄漏；若日志工具本身超时，则应核对工具状态，不能把它当成被调查接口的故障证据。观察属于哪一层，直接影响后续判断。

停止条件不能只写“模型输出 Final Answer”。回答型任务要检查证据是否支持结论，编码任务要核对补丁与验证，业务动作要核对权威回执。预算耗尽、用户取消和等待信息分别记录，不能统一包装成完成。

循环还需限制总步数、费用、时间与重复无进展动作。保留可取回的完整工具结果，但只把相关部分放进下一轮上下文。对于写操作，连接中断后先查询原请求结果再决定重试，避免反馈闭环变成重复副作用的放大器。

<h2 id="q-007">面试问题：ReAct 相比 CoT 的优势和局限是什么？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

CoT 主要组织问题的中间推理步骤，ReAct 进一步把行动和外部观察纳入求解。二者并不互斥，也不能简单断言 CoT 总是便宜或 ReAct 总是更准确。

<div align="center">

| 比较角度 | 仅在给定上下文中推理 | 通过行动获得新观察 |
|---|---|---|
| 可用信息 | 输入证据与模型已学知识 | 还可增加检索、计算及环境反馈 |
| 典型优势 | 环境简单，减少外部依赖 | 能更新事实、检查假设、完成操作 |
| 典型失效 | 缺事实时仍可能编造合理解释 | 工具错误、过期证据、循环或越权 |
| 成本来源 | 推理长度与采样次数 | 另有工具、网络、等待和多轮上下文 |
| 可观察证据 | 最终结果和公开解释 | 还包括真实调用、结果及状态变化 |

</div>

例如给定完整合同条款后判断日期冲突，模型可以在这些证据上推理；若缺少最新补充协议，就需要检索或查询。CoT 并非只能依赖模型内部知识，它也可以使用用户提供的资料；关键在于求解过程中能否主动取得新信息。[2]

ReAct 的外部反馈可以纠正错误假设，但错误搜索词也可能把它引向同一批低质量页面。工具带来的事实性收益依赖来源质量和核对方式，不能由工具数量保证。额外观察还会增加上下文压力与注入风险。

选择时先判断是否存在必须查询或执行的信息缺口，再比较额外调用的收益。固定算法计算交给代码，已有充分证据时直接推理，需要环境反馈时使用交互循环。评测应固定预算，避免把多次采样的 CoT 与单次 ReAct 直接比较。

<h2 id="q-008">面试问题：ReAct 与 CoT-SC 混合策略为什么有效？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Self-Consistency 通过多次采样得到候选推理与答案，再按任务定义聚合答案；ReAct 通过行动补充外部证据。前者增加候选多样性，后者增加可用信息，因此在部分任务上可以互补。[2,3]

原始 ReAct 工作研究了两种启发式切换：在限定步数内无法得到答案时回到 CoT-SC，以及 CoT-SC 的多数答案不足阈值时改用 ReAct。它们是在特定问答基准上的实验策略，不是所有生产任务的默认恢复规则。

更通用的组合是先检查信息缺口：若几个候选使用了不同日期或实体，应先查清事实；若事实已经固定、主要难点是组合推理，可以比较多个候选，再用规则或计算验证。例如多条推理都引用同一错误财报，投票再一致也不会修复源头错误。

一致性还不能直接当作经过校准的置信度。同一模型、提示和证据会产生相关错误；候选表述不同，也可能只是同一错误假设的改写。应检查答案规范化、采样多样性、证据独立性及聚合规则，而不只数相同字符串。

尤其不能在实时库存、账户余额或操作结果查询失败时，退回模型内部知识“多数决定”现实状态。事实不可获得时可以说明不确定、等待或请求补充信息。混合策略的价值需要在相同总预算下衡量，新增采样和工具调用都应计入成本。

<h2 id="q-009">面试问题：如何避免 ReAct 陷入无效搜索和循环调用？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

防止循环需要同时限制预算并识别进展。预算给出最坏成本边界，进展判断决定是否还值得继续；只设最大轮数，会让系统在无效路径上耗尽所有额度。

可以记录规范化的工具名、参数、输入版本、结果摘要和任务状态，识别反复查询同一事实、相同错误重复出现或计划长期不变。对搜索还要检查来源和内容是否只是同一材料的重复转载，不能把 URL 不同当成获得新证据。

重复动作不必然无效。轮询一个真正运行中的作业需要重复查询，应保留作业标识，使用合理间隔、截止时间与状态变化判断。某个函数第二次调用时输入文件已更新，也可能是必要验证，不能机械禁止重复工具名。

例如三轮搜索仍得到同一过期公告，下一步应调整证据需求、换已授权来源或说明缺口；继续换几个同义词未必有信息增量。参数错误可以据反馈修参，权限拒绝应核对授权，写请求超时则先查状态，三类情况不能都用“再试一次”解决。

达到无进展阈值后，系统可缩小目标、请求必要信息、转用已定义替代路径，或交付部分结果并结束。子任务与反思也纳入总预算，取消信号传播到活动执行器。停止时应说明实际完成程度和未决动作，避免为了退出循环而生成虚假的成功结论。

<h1 id="q-010">3. Plan-and-Solve / Plan-and-Execute 解决什么问题？</h1>

<h2 id="q-103">面试问题：任务分解、计划维护和执行反馈如何协作？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

任务分解把目标变成子目标，计划维护这些子目标的依赖与状态，执行反馈则检验计划中的假设。三者构成可修订结构，不能把最初生成的一串步骤当成执行事实。

一个可用的计划项至少说明要得到什么、依赖什么输入、完成证据是什么。以升级接口为例，“修改类型定义”完成后才适合更新客户端；前后端可以在契约稳定后并行实现，集成测试必须在双方产物可用后运行。计划管理的是依赖，不只是编号顺序。

执行时把产物和检查结果写回步骤，例如文件版本、测试报告和失败原因。若测试工具不可用，步骤处于待验证；若契约本身被证明不满足需求，则需要修改计划并使相关下游结果失效。不能把任何失败都当成局部修参，也不必每次小错误都重建全计划。

计划还应保留未证实假设。例如“接口支持批量更新”需要先查文档或做允许的验证；若不支持，后续批处理方案就需要调整。把假设写成确定事实，会让后面的行动在错误前提上越走越远。

完成判断最后回到总目标。子任务都标记完成，也可能遗漏跨模块一致性、性能或交付格式，因此还需要总体验收。计划细到不能适应反馈会僵化，粗到无法验收又失去作用，粒度应以可验证产物和依赖边界为准。

<h2 id="q-011">面试问题：Plan-and-Solve 与 Plan-and-Execute 有什么区别？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Plan-and-Solve 最初是一种提示方法：引导模型先分析并制定求解计划，再按计划回答，重点是减少推理中的步骤遗漏。它本身不要求调用外部工具、独立执行器或持久化任务服务。[4]

Plan-and-Execute 更常指架构上的分工：规划器生成子目标与依赖，执行器完成步骤，检查结果后继续或重规划。规划器与执行器可以使用同一模型，也可以是代码、模型和工具的组合，不必都实现成独立 Agent。

例如多阶段数据分析，计划可以先明确字段、过滤条件、统计口径和图表目标，执行器再运行查询与计算，遇到缺列或口径冲突时回到相应假设。若只是对给定数字完成一道题，直接在一次调用中先分解再求解可能已经够用。

与 ReAct 相比，Plan-and-Execute 更突出全局依赖，ReAct 更突出依据当前观察决定下一步。二者可以组合：计划规定“复现、定位、修复、验证”，定位阶段用局部交互循环。计划不必包含尚不知道的每条命令，否则只是把猜测提前写得更长。

代价也不同。规划会增加前期调用和状态维护，短任务未必获益；固定计划可能被新事实推翻，纯局部行动又可能忽略全局约束。是否先规划，应看任务长度、依赖与重规划价值，而不是把“有计划”当成质量保证。

<h2 id="q-012">面试问题：ReWOO 为什么要把推理规划和工具观察解耦？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

ReWOO 将规划、工具执行和最终综合拆开，减少每得到一条观察就让规划模型重新读取整段历史的成本。它利用的是“虽然还不知道工具结果，但已经知道后续需要对这个结果做什么”的可预见依赖。[5]

Planner 先生成计划和证据变量；Worker 调用工具，把真实结果填入变量；Solver 结合问题、计划和证据形成回答。例如比较两家公司同一财年的收入：

```text
E1 = 查询 A 公司指定财年收入及来源
E2 = 查询 B 公司指定财年收入及来源
E3 = 按同一币种、会计口径与期间计算差异，输入 E1、E2
结果 = 综合 E1、E2、E3，说明差异和不可比条件
```

这里 E1 和 E2 没有依赖，可以在权限和资源允许时并行；E3 必须等前两项完成。**提前规划不等于所有工具都可并行。** 若下一步工具的选择依赖结果中的未知分支，仅用变量替换并不能处理全部交互不确定性。

与逐轮 ReAct 相比，主要节省来自减少重复规划输入与模型调用，实际延迟还取决于依赖链和工具耗时。Worker 也可能调用模型工具，因此不能假定只有 Planner 和 Solver 才消耗推理成本。

失败边界在于计划假设。查询结果可能没有指定财年，收入单位可能不同，Solver 不能根据“应该存在的证据”补出数字。工程实现应显式标记缺失或失败，必要时修订计划，而不是把错误变量继续向下传递。ReWOO 适合较可预见的工具链，反馈会改变任务结构时需要额外的动态控制。

<h2 id="q-013">面试问题：Reflection / Reflexion 如何提升 Agent 可靠性？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

一般的 Reflection 是根据输出或反馈做一次检查与修订；Reflexion 更强调把尝试中的反馈转成文字经验，在后续尝试中使用。它通过外部记忆影响行动，通常不更新模型参数，不能把“文字强化学习”误解为已经执行梯度训练。[6]

有效反思应建立“失败证据 → 原因假设 → 可检查的改动 → 下一次验证”的关系。例如日期参数被接口拒绝，反思可以指出接口要求带时区的时间，并在下一次请求前做格式校验；“下次更仔细”既不能改变行为，也无法验收。

原方法把行动者、评价反馈和反思记录组织起来。反馈可来自测试、环境奖励、规则或模型评价，可靠程度不同。编译错误只说明代码未通过编译，不一定证明根因；模型评价若没有新证据，也可能把错误解释写得更自信。

工程上可在阶段验收失败、重复工具错误或高影响动作的复核处使用反思。保存经验时附带任务、工具版本、证据和适用条件；下一次使用前检查是否仍成立。一次偶发网络错误不应被升级成“这个工具永远不可用”。

还应有次数和预算边界，对比不使用反思的基线，观察它究竟减少重复错误还是只增加文字。关键不是是否输出了反思段落，而是后续动作是否发生有证据支持的改进，并通过独立验收。

<h2 id="q-014">面试问题：什么时候反思会带来负收益？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

反思的收益取决于反馈是否提供新信息，以及修订是否能被检验。缺少这两点时，多加一轮模型自评可能把正确答案改错，也可能让同一错误变得更难识别。

例如代码通过了相关测试，反思器仅因“看起来太简单”要求增加抽象，可能引入回归；工具只是暂时超时，却被总结成架构缺陷，会诱发不必要重构。反思必须区分已观察事实与原因假设，不应把解释流畅当成解释正确。

持续自评还可能产生奖励投机：系统反复修改输出，直到评审模型满意，却逐渐偏离用户要求。生成器与评审器使用相同错误证据时，角色分开也不会自动形成独立监督。应保留原需求和外部判据，防止评审标准随输出漂移。

是否触发反思可以依据预期收益，而不只看模型自报置信度。失败诊断、关键阶段核对、已知高风险模式通常更值得投入；简单且规则可检查的步骤直接运行验证即可。必要时对成功轨迹也可总结可复用条件，但要避免把偶然成功泛化。

实践中应限制轮数，保存修改前版本，允许拒绝或撤回错误经验，并把反思后的真实结果反馈回来。评价指标包括净成功率、回归、成本和额外延迟；“反思次数更多”本身不能证明系统在学习。

<h2 id="q-025">面试问题：一个复杂任务里，怎么结合规划、执行和反思这几种机制？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

复杂任务可以用全局计划维持目标和依赖，在局部执行中根据观察调整动作，再用验证结果决定是否修订计划。反思承担解释失败、提出可检验改动的工作，不必成为每一步都要运行的独立角色。

以“分析课程规则并完成预约”为例，首先明确课程、时间、人数和用户授权范围；查询规则与余量后形成候选方案；方案满足约束且获得所需授权，才能提交预约；最终核对预约编号与状态。规则检索可以采用 ReAct，字段和时间合法性可以由代码检查，提交环节由明确工作流控制。

执行反馈可以分三层处理。日期格式错误属于局部修正，修参后重试即可；目标时段已经满员，需要重新选择方案并确认新方案是否仍在授权范围内；预约请求超时则属于结果未知，应先查原请求，不能立刻换时段再次提交。不同失败进入不同路径，流程才不会一遇到异常就从头重来。

反思应解释哪条假设被推翻。例如“余量查询与提交之间存在并发变化”，对应的改进是提交时校验资源版本、处理库存冲突，而非要求模型以后更认真。若新证据提前揭示后续方案不可行，也可以主动重规划，无须等某个节点正式失败。

状态中保存计划版本、输入依据、产物引用、已发生动作和未决结果。验收分别检查步骤产物、跨步骤约束和用户目标：所有节点返回成功，也可能预约了错误日期。限制重试与重规划预算，保留必要的人类介入入口，最后用合格交付率、错误副作用、时延与总成本判断这套组合是否值得。

<h1 id="q-015">4. Tree-of-Thought、Graph-of-Thought、LATS 分别解决什么问题？</h1>

<h2 id="q-104">面试问题：搜索式推理的状态、分支与评价如何组织？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

搜索式推理把一次求解拆成状态、候选扩展、评价与选择。其价值在于让系统比较不同路径，并在预算允许时重新考虑早期选择；能否奏效，取决于这些对象是否定义得足够清楚。

**状态要保留决定后续行动所需的信息。** 在算术谜题中，可以是已经形成的表达式和剩余数字；在代码修复中，可以是具体代码版本、已观察错误与约束；在交互环境中，还需说明对应哪个环境快照。只有一段“目前进展不错”的总结，无法支持可靠搜索。

扩展器从状态产生候选推理步骤或行动。评价器判断候选是否满足硬约束、取得多少进展、还需要多少成本；搜索器据此保留、展开或剪掉分支。最终验证与中间评分应分开：模型给一段代码高分，不代表它已通过测试。

例如为表达式构造题选择下一步运算，可以先用程序排除非法操作，再让搜索保留几条可行路径。若某条路径已无法满足目标，就回到其他候选；若评分器看错了，把唯一正确路径剪掉，增加搜索轮数也未必补得回来。评价偏差和候选覆盖同样重要。

ToT 主要组织树状候选，GoT 允许中间结果复用和聚合，LATS 将语言模型的行动与环境反馈纳入树搜索。[7–9] 这些名称不保证最优性；有限预算、启发式评分和不完整状态都可能使搜索失败。生产日志保存可见状态、候选、评分依据和结果即可，不要求访问模型隐藏思维链。

<h2 id="q-016">面试问题：Tree-of-Thought 和普通 CoT 的区别是什么？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

普通单链 CoT 沿一条中间推理路径继续生成，Tree of Thoughts（ToT）则在若干关键位置生成多个候选，评价后选择继续探索的状态，必要时回溯。这里的 thought 是任务定义的推理单元，可以是一段短文本、一次运算或一个局部方案，不固定等于一个 Token 或一句话。[7]

以“用四个数构造目标值”为例，单链可能一开始选错运算，后面只能在错误方向上继续。ToT 可以同时考虑几种首步运算，计算剩余状态，再保留仍有希望的候选。原工作讨论了广度优先与深度优先搜索：前者维持一批同层候选，后者沿路径深入、遇到失败后回退，两者的内存和探索顺序不同。

它与 Self-Consistency 的区别也很关键。SC 通常先采样多条完整解答，再聚合最终答案；ToT 会评价中间状态，用评价结果影响后续计算分配。它与 ReAct 则可以组合：树中的一步既可以是文本推理，也可以是一次受控工具调用，后者还需承担环境状态管理。

若每个状态产生 $`b`$ 个后继、最多深入 $`d`$ 层，完全展开的节点数为：

```math
N=1+b+b^2+\cdots+b^d.
```

例如 $`b=3`$、$`d=4`$ 时共有121个节点，尚未计入每个节点的生成、评分和工具成本。剪枝与保留宽度能控制规模，但也会漏掉好路径，因此搜索预算必须和任务价值匹配。

ToT 适合候选可构造、中间状态可评估、回溯成本可控的任务。若缺的是最新事实，增加文本分支不能替代查询；若问题已有可靠算法，直接执行算法通常更合适。对当前模型是否仍有收益，需要在相同总预算下重新测量，不能把早期模型上的提升视为永久结论。

<h2 id="q-017">面试问题：Graph-of-Thought 为什么比树结构更灵活？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐ (3/5)**

树中每个非根节点只有一个父节点，适合描述“沿某个选择继续展开”。Graph of Thoughts（GoT）允许一个结果依赖多个前置结果，因此可以表达分支合并、结果复用和反复改进，适合存在汇合关系的推理过程。[8]

例如把长文分块分析：几个分支分别提取事件、时间和主体，再汇合为统一时间线；另一个节点检查冲突，要求对有争议的事件重新核查。树也能把这些信息重复展开，但图可以明确复用同一证据，减少重复处理，并保留结论的依赖关系。

原工作中的实现区分 **Graph of Operations（操作图）** 与 **Graph Reasoning State（推理状态图）**：前者描述生成、聚合、评分、筛选等操作如何连接，后者保存执行中产生的具体候选及关系。不能仅凭“图推理”这个名字，就认为模型能自动构造任意可靠的工作流。

聚合也不是把两段文本拼接。若两个分支都引用同一篇报道，它们并不构成两份独立证据；若使用不同时间或统计口径，合并前必须对齐条件。一个中间结论改变后，依赖它的下游结果需要重新判断是否仍有效，否则图只会把旧错误复用得更广。

工程代价在于依赖管理、去重、冲突解决、评分和停止条件。循环改进必须有上限与进展判据；共享节点应携带版本和来源。GoT 的灵活性描述的是信息组织能力，不能直接推出比树搜索准确，也不等同于知识图谱、图神经网络或任意采用节点界面的编排框架。

<h2 id="q-018">面试问题：LATS / MCTS-style Agent 的核心思想是什么？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐ (3/5)**

Language Agent Tree Search（LATS）把语言模型生成行动、环境反馈、价值评价和蒙特卡洛树搜索结合起来。它会把计算分配给多个候选轨迹，在“继续利用已表现较好的路径”和“探索证据较少的路径”之间权衡。[9]

一次搜索先沿树选择节点，再生成候选 thought/action 并执行或获取对应观察；评价新状态，选择后续模拟或试行路径；得到终止奖励或评价后，把结果沿祖先路径更新。失败轨迹还可形成文字反思，供后续扩展参考。原方法将 selection、expansion、evaluation、simulation、backpropagation 与 reflection 组织起来，不只是多生成几份答案。

常见 UCT 选择准则可写为：

```math
\mathrm{UCT}(s)=\bar V(s)+c\sqrt{\frac{\ln N(p)}{N(s)}}.
```

其中 $`s`$ 是候选子节点，$`p`$ 是父节点，$`\bar V(s)`$ 表示该节点当前的价值估计，$`N(s)`$ 与 $`N(p)`$ 是访问次数，$`c`$ 控制探索强度。第一项偏向已表现好的节点，第二项鼓励访问较少的节点；未访问节点需按初始化规则优先探索，不能直接除以零。具体价值初始化、归一化和更新方式由实现决定。

这里的 backpropagation 是把搜索结果回传并更新树中的统计量，**不等于对语言模型做梯度反向传播**。价值估计也可能来自模型启发式，不能把中途评分当作真实业务奖励。

最重要的使用条件是环境能否回到所需状态。游戏和隔离测试环境可能支持重置，真实发信、转账或下单通常不能靠恢复聊天记录撤回。LATS 原文也明确指出交互决策需要能回到先前环境状态。实际系统可先在模拟或隔离环境中搜索方案，再对选定方案执行授权检查与真实提交；搜索本身不提供副作用隔离，也不保证找到最优路径。

<h2 id="q-019">面试问题：搜索式 Agent 为什么难以直接用于高并发生产场景？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

搜索会把一次用户请求放大成一组相互依赖的模型、评价和工具请求。高并发环境中，难点是让这组额外计算在有限资源下仍能满足服务时延、费用与正确性要求，而非简单地认为搜索永远不能上线。

例如每个请求保留5个候选、继续4轮，单请求看似可控，但大量请求同时进入会争抢推理额度和工具连接。部分步骤必须等上一轮评分才能展开，增加并发不能消除这条依赖链；过高并发还会造成排队、限流和重试，尾部延迟可能比平均值恶化得更快。

可先按任务价值和困难程度分配计算：常规请求走已验证的短路径，必要时才增加候选。设置整个请求的节点数、费用、时间和工具预算，用有界宽度、早停、候选去重和批量评分减少浪费。小模型可以初筛，但要测它是否误删正确候选；单纯把筛选变便宜，可能降低最终成功率。

缓存只在输入、版本、权限与环境条件仍成立时复用。纯计算结果通常比实时库存更适合缓存；多个文本分支也不必分别重新抓取同一份稳定证据。并行执行应限制在真正独立的读取、计算或隔离试验中，不能让几个候选同时对同一账户提交写操作。

评估至少看固定预算下的合格率、总成本、p95/p99时延、吞吐和错误副作用，并纳入失败请求消耗的资源。有些高价值任务值得多花计算，有些简单任务会因搜索增加更多失败点。是否上线取决于这些约束下的净收益，不由“搜索能提高推理上限”一句话决定。

<h1 id="q-020">5. 多 Agent 系统常见编排模式有哪些？</h1>

<h2 id="q-105">面试问题：多 Agent 协作可以采用哪些控制结构？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

多 Agent 编排首先要回答三个问题：谁分配工作，谁持有共享状态，谁对最终结果负责。角色名称相同的系统，也可能采用完全不同的控制结构。

常见结构可按控制与数据流理解：

<div align="center">

| 结构 | 工作如何流动 | 主要设计问题 |
|---|---|---|
| 路由 | 入口根据条件选择处理者 | 路由错误、拒答与转接如何处理 |
| 主控委派 | 主 Agent 分解任务，子 Agent 返回产物 | 子任务边界与主控验收 |
| 顺序流水线 | 上一步产物成为下一步输入 | 数据契约、失败传播和重试 |
| 并行汇合 | 独立子任务并发完成，再合并 | 依赖、冲突和等待超时 |
| 动态交接 | 当前处理者将控制转给另一处理者 | 交接状态、权限和循环边界 |
| 共享工作区 | 多个参与者围绕共享状态协作 | 写入归属、版本与一致性 |

</div>

辩论、评审和竞标也可以嵌入这些结构。固定规则调度不一定需要另一个模型 Agent；动态任务分解才可能让主控判断体现价值。Team、Crew 或 Swarm 等名字没有统一实现标准，应继续检查实际控制路径。

以研究报告为例，独立市场可并行调查，统一口径与最终判断由主控负责；若一个结论依赖另一组尚未确认的数字，就不能把二者当成完全独立任务。子 Agent 返回来源、适用条件和未解决问题，主控才有条件整合。

所有结构都需给出子任务标识、输入版本、完成条件、预算、取消和失败语义。共享上下文能够帮助协作，也可能传播错误或泄露数据；上下文独立则需要补充交接证据。结构选择要对应真实依赖，而不是先定团队人数再寻找分工。

<h2 id="q-021">面试问题：Supervisor、Router、Swarm、Debate 如何对比？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Supervisor、Router、Swarm 与 Debate 分别突出集中协调、分流、动态交接和观点比较，并不是四种互不相容的产品架构。比较时应看控制权何时转移，以及结果由谁验收。

<div align="center">

| 模式 | 核心控制方式 | 适用条件 | 主要失效点 |
|---|---|---|---|
| Supervisor | 主控委派任务并接收结果 | 工作可拆，仍需统一整合 | 主控上下文拥挤或验收错误 |
| Router | 按规则或模型判断选择路径 | 输入类型有可辨识边界 | 分类错误后缺少纠正路径 |
| Swarm / 动态交接 | 当前处理者把控制交给下一处理者 | 专业边界会随对话变化 | 交接丢状态、循环和责任模糊 |
| Debate | 多方提出理由，再评价或综合 | 有可比较证据和可靠裁决 | 共享偏差、互相迎合、以说服力代替正确性 |

</div>

例如客服入口先按意图路由，复杂工单由主控安排调查；需要另一业务权限时进行受控转接，争议方案再进入独立评审。一个系统可以同时包含这些结构，不必选择一个名称包办全部工作。

委派与交接尤其容易混淆。委派通常由主控继续持有目标，子任务完成后返回结果；交接通常让接收者继续负责后续对话或执行，是否返回由协议决定。若两者语义不清，用户可能收到两份最终答复，或者双方都认为对方会收尾。

Debate 不会自动产生事实。几个 Agent 使用相同材料时，意见一致仍可能一起错；让它们先独立提出可核查证据，再比较分歧，往往比连续互相评价更易诊断。选型应通过任务实验检验成功率、额外成本和接管负担，不宜按“客服必用 Router、研究必用 Supervisor”机械归类。

<h2 id="q-022">面试问题：Crew / Team 型 Agent 适合什么场景？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Crew / Team 通常指围绕共同目标进行角色分工的 Agent 系统。它适合工作可以形成相对稳定的输入输出边界，且不同角色确实需要不同知识、上下文、工具或权限的场景；角色提示词本身并不产生专业能力。

以软件变更为例，调查者返回调用关系与影响范围，实施者产生补丁，验证者依据需求和代码版本执行检查，整合者负责交付。调查和独立测试设计可能并行，但验证最终补丁必须等待对应版本可用。把这些步骤都命名为 Agent，并不会自动缩短关键路径。

每个委派合同应说明目标、允许资源、禁止动作、输入版本、产物格式、验收方法和预算。报告应携带文件位置、测试结果或来源引用，不能只回一句“已处理”。主控需要检查子任务结果是否回答了原问题，并解决跨角色冲突。

上下文可以隔离，执行资源也要按需要隔离。两个 Agent 各有消息历史，却同时修改同一文件，仍会互相覆盖；使用不同工作目录，也可能共享数据库、缓存和凭证。可按文件或资源分配写入责任，独立产出补丁后统一整合，必要时使用真正隔离的试验环境。

当任务高度耦合，每推进一步都需等待另一个角色解释，通信成本可能超过分工收益。短查询、强时延要求或缺少独立验收标准的任务，先保留简单实现更容易判断。团队式结构的价值来自可验证分工和专业资源差异，不能由角色数量证明。

<h2 id="q-023">面试问题：为什么多 Agent 不一定比单 Agent 更好？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

多 Agent 的潜在收益主要来自并行、专业化、上下文分担和相对独立的检查，同时会增加任务分解、信息传递、同步与验收成本。只要新增成本超过这些收益，多个 Agent 就可能比一个更慢、更贵或更容易出错。

例如三个研究 Agent 都检索同一关键词、读取同一篇转载，得到相同结论并不等于三重验证。若分别核对原始数据、方法条件与反例，才可能带来互补信息。独立上下文只是减少直接污染的一种方式，证据和模型偏差仍可能高度相关。

并行加速也受串行部分限制。在忽略通信开销的理想条件下，若可并行部分占比为 $`p`$，使用 $`n`$ 个工作者，速度提升上界可近似写为：

```math
S(n)\leq\frac{1}{(1-p)+p/n}.
```

这是经典 Amdahl 思路在固定工作量下的近似。任务定义、最终整合和验收常在串行部分；新增 Agent 若又增加协调工作，实际收益会更低。它不适合直接预测所有动态 Agent 任务，但能提醒我们先分析依赖，再讨论人数。

公平比较应固定任务、数据、工具权限与总体预算，至少保留单 Agent、单 Agent 多次采样、多个 Agent 分工几种基线。若多 Agent 使用了数倍模型调用，不能把全部提升归因于协作结构；若主控漏验错误产物，还可能只是把问题藏到最后。

优先拆分能独立验收且不会争抢资源的工作，再逐步增加分工。最终看合格交付、端到端时延、总成本、冲突和人工整合负担。具体协作机制解释不了收益时，增加角色通常不是可靠的优化方向。

<h2 id="q-201">面试问题：大模型与小模型如何分工，怎样判断委派是否真正节省成本？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐ (2/5)**

大模型与小模型协作，可以把范围明确、容易核查的子任务交给成本较低的模型，让主模型维护总体目标、处理困难决策并验收结果。判断分工是否值得，要看**合格完成整项任务的总成本**，不能只看主模型少用了多少 Token。

这与整题路由不同。整题路由通常在开始时判断问题难度，选择由哪个模型完成整题；角色委派则在同一任务内，把资料定位、字段提取、局部调查或测试结果整理分出去。例如主模型负责修改鉴权逻辑，小模型只调查相关调用方并返回文件位置、证据与未确认项，主模型据此决定修改范围。

子任务需要窄目标和明确报告契约。原始引用、代码位置和执行结果能降低核查成本，但“引用字符串确实存在”仅证明引用不是凭空编造，仍要检查上下文是否支持结论。小模型无证据、结果冲突或反复失败时，应能够拒绝完成或升级处理，不能为了交付把缺口补成确定事实。

总费用可以按统一货币口径拆为：

```math
C_{\mathrm{total}}=C_{\mathrm{main}}+C_{\mathrm{sub}}+C_{\mathrm{tools}}
+C_{\mathrm{compute}}+C_{\mathrm{review}}+C_{\mathrm{rework}}.
```

这里依次是主模型、子模型、工具、本地计算、审查与返工成本；各项要避免重复计费。完成时间单独统计，尤其关注新增串行委派、排队和失败升级的延迟。即使本地小模型没有 API 账单，也仍占用硬件、内存、能耗与维护资源。

2026年11月的 Delegent 提供了一个角色委派案例：主模型保留控制，子模型在独立上下文完成聚焦任务，只把报告送回；任务约束和双侧缓存共同影响结果。[13] 其主要节省口径是前沿模型 API 费用，部分实验的完成时间反而增加，小模型费用也并非在所有实验中完整计入。因此可以借鉴它的任务边界、证据报告和成本拆分，不能把论文标题外推为任意任务上“性能无损且全面提效”。

验收时固定任务集与成功标准，对比全大模型、整题路由和角色委派，统计失败任务的消耗、升级比例、净合格率与总时延。随着模型能力和价格变化，具体分工会调整；按任务可验证性分配计算、按完整交付核算成本，这两条判断仍然成立。

<h2 id="q-024">面试问题：如何设计可持久化、可恢复的 Agent 工作流？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

可恢复工作流需要保存能够继续执行的状态，并在恢复时核对外部事实。聊天记录解释了曾经讨论什么，却不一定告诉系统哪个请求已经产生业务效果、哪个批准仍有效、哪份产物对应当前版本。

通常要持久化任务目标与约束、计划版本、已完成节点、待处理事件、动作标识、工具回执、产物引用，以及恢复所需的运行配置。checkpoint 保存某个时刻的工作流状态，事件记录说明状态为何变化；两者各有作用，但都不等于远端业务数据库。

最危险的窗口是“外部已成功，本地还没写成功记录”。例如预约服务已经创建订单，调用方在保存回执前崩溃。重启后若仅看到节点未完成就再执行一次，可能重复预约。应使用持久的业务意图标识与幂等键，查询原请求的权威状态后再推进。

<div align="center">

| 恢复时的证据 | 应采取的动作 |
|---|---|
| 能证明尚未提交 | 核对授权与前提后执行 |
| 已提交，仍在处理 | 跟踪同一请求，保留截止时间 |
| 已提交，结果未知 | 查询或对账，不能直接重发 |
| 权威回执确认成功 | 保存结果，检查验收条件后推进 |
| 权威回执确认失败 | 根据失败原因重试、改计划或结束 |

</div>

“查询不到”可能只是读副本延迟，必须结合服务端状态与一致性契约解释。幂等键也要有明确作用域、请求内容校验和保存期限，不能假定任意接口都会永久去重。本地事务与待发送事件一起提交可以减少丢发，但不能自动把远端业务合入同一个事务。

具体框架的恢复边界还需单独核对。LangGraph 的 `interrupt` 恢复可能从所在节点开头重跑，暂停前的副作用要幂等或放到具有适当持久化语义的独立步骤中。[11,12] 最后注入调用前、调用中和提交后断连等故障，验证真实恢复行为；文件回滚、取消与补偿作用范围不同，都不能泛称跨系统 exactly-once。

<h2 id="q-026">面试问题：Workflow 和 Agent Runtime 是什么关系？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

Workflow 描述工作如何流动：节点依赖、分支、汇合、暂停与状态转换。Agent Runtime 提供运行这些工作所需的能力：调用模型和工具、装配上下文、执行权限检查、控制预算、处理事件与终止。它们是职责划分，可以位于同一个进程，也可以由多个组件协作实现。

一种方式是工作流包住 Agent。例如预约流程规定字段核对、方案选择和提交的前置关系，调查异常的节点内部使用动态工具循环。另一种方式是 Agent 调用确定性子流程，例如在完成资料分析后调用已经实现并测试过的报表生成任务。

组合时最重要的是确定权威状态和失败归属。图引擎保存节点状态，业务服务保存实际预约，运行时保存工具调用与预算；三者需要用统一任务和动作标识关联。节点返回正常，不一定表示业务接受；业务拒绝也不一定是进程故障。

例如工具适配器自动重试三次，工作流又在节点失败后重试三次，若没有统一语义，外部写请求可能被重复放大。应明确哪层负责哪类重试，取消如何向下传播，迟到结果怎样记账，已完成的外部动作如何核对。

框架可能已经包含持久化、流式事件和模型循环，不必为了满足一张架构图再造一层。按实际代码画出职责和状态持有者，检查每个关键保证由谁实现。工作流恢复解决控制状态的连续性，业务幂等和外部事务仍需各自的机制。

<h2 id="q-027">面试问题：LangGraph 的 State、Node、Edge 分别是什么？怎么配合完成流程编排？</h2>

**难度评分：⭐⭐⭐ (3/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

LangGraph 的 Graph API 用 State、Node、Edge 表达有状态的执行图。State 是节点之间共享的数据契约，Node 读取状态并完成计算或调用，Edge 决定后续执行路径。节点可以调用模型，也可以只是普通函数，所以图中的每个节点不必是一个 Agent。[10]

以课程预约为例，State 保存意图、课程、时段、方案版本、授权依据和提交结果。识别节点返回意图更新，条件边把请求送入规则问答或预约分支；字段缺失进入补充信息步骤，前提满足后进入提交，再核对业务结果。共享状态应保留必要值与大对象引用，而不是无限追加全部原始日志。

节点通常返回**部分更新**，每个状态字段的 reducer 定义如何把更新合入旧值。默认覆盖与列表追加的含义不同；两个并行节点写同一字段时，不能指望框架猜出业务合并规则。例如收集多份报告可以定义聚合，订单状态则不能简单拼成一个列表当作已解决冲突。消息字段还可使用按消息 ID 更新的专用合并机制。

固定边表达确定的下一步，条件边根据状态决定路径。`Send` 可按运行时产生的条目动态分发工作，`Command` 可同时更新状态并决定转移，也用于暂停后的恢复。给同一节点同时配置固定后继与动态转移时要谨慎：动态跳转不会天然取消固定边，可能使两条路径都执行。

LangGraph 按 super-step 推进消息：同一步可运行多个活跃节点，再进入后续步骤。因此并行状态合并、汇合依赖和循环终止都要明确。需要持久恢复时配置合适的 checkpointer、稳定的 `thread_id`，并按框架契约恢复暂停；线程标识用于定位状态，不是访问凭证。[11,12]

面试时可沿一条真实请求说明“哪个节点读什么、返回什么更新、哪条边决定下一步、哪里持久化”。再用并发写冲突和提交后断连解释边界，比只背三个名词更能证明理解了编排机制。

<h2 id="q-028">面试问题：你实际使用了 LangGraph 框架吗？哪些流程由 LangGraph 编排，哪些由 Agent Runtime 自己处理？</h2>

**难度评分：⭐⭐⭐⭐ (4/5)  |  考察频率：⭐⭐⭐⭐ (4/5)**

这是一道项目真实性与架构边界题，应先如实说明使用程度：生产使用、原型验证、阅读源码或尚未接入。没有实际使用经历，就以方案设计回答，不能把自写状态机包装成 LangGraph 项目经验。

如果实际使用过，可以围绕一项具体任务说明四件事：为什么选图编排，图里保存什么状态，节点和边如何执行，以及发生故障后怎样恢复。例如一个预约助手用图管理意图分流、字段补齐、有效确认和提交后的核对；应用层负责用户认证、业务权限、工具适配与成本限制。这只是可行分工，实际职责要以所用版本和代码为准。

展示证据时，优先准备 State Schema、节点定义、条件边、checkpointer 配置，以及一条从输入到交付的运行记录。说明 `thread_id` 如何与租户和用户绑定，谁能访问恢复状态，大对象存在哪里，版本变更如何影响暂停中的任务。只有图的截图，无法说明这些保证。

再演示一次失败：提交节点已发起外部预约，但调用方断连。指出恢复后哪些代码重跑，系统凭什么判断原预约结果，何时写 checkpoint，如何防止重复创建。如果回答只停留在“框架会自动恢复”，就没有解释外部副作用窗口。

验证可分两层：先用固定输入和模拟工具结果测试路由、并发更新、暂停、重启和取消；再接入模型观察识别与决策错误。前者证明控制逻辑，后者评估模型与流程组合后的任务能力，二者不能相互替代。

最后解释框架带来的收益与维护成本。线性三步且无持久恢复需求的任务，普通函数可能更清晰；长任务、复杂分支和人工介入可能更需要显式状态图。可核查的选择依据、实现边界和故障证据，比声称“完整采用某框架”更有说服力。

## 高频速记

1. 模式选择先看信息缺口、任务依赖、验证能力与副作用边界，复杂度必须有可测收益。
2. CoT 可以使用给定证据；ReAct 在求解过程中通过行动补充新观察，两者可以组合。
3. Self-Consistency 的答案一致性不能直接当作校准置信度，更不能替代实时业务状态查询。
4. 计划管理可验证子目标与依赖，反馈可以修正动作、计划假设或恢复路径。
5. Plan-and-Solve 是提示方法；Plan-and-Execute 强调规划与执行的架构分工。
6. ReWOO 减少重复规划输入，只有无依赖的工具调用才有并行空间。
7. 反思要把失败证据转成可检验改动；文字经验更新不等于模型参数训练。
8. ToT 评价中间候选，GoT 进一步表达复用和汇合；评价器误判会使搜索剪掉正确路径。
9. LATS 的价值回传更新搜索统计，真实外部操作不能靠回退文本历史撤销。
10. 多 Agent 的收益来自可验证分工与互补信息，需要扣除通信、整合和验收成本。
11. 大小模型委派应核算完整任务成本与时延，主模型 API 费用下降不等于总收益已成立。
12. checkpoint 保存控制状态，业务回执证明外部事实；恢复时要处理结果未知窗口。
13. LangGraph 的 State、Node、Edge 管理状态与控制流，权限、业务幂等和资源隔离仍要有明确实现。
